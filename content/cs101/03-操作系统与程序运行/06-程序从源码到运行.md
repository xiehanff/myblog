# 程序从源码到运行

`gcc hello.c -o hello && ./hello` 只花一秒，却掩盖了从源码文本到进程映像的全部中转站。等出错时代价就出现了：`undefined reference to 'add'`、`cannot open shared object file`、`Segmentation fault` 打印在同一个终端里，原因却分别属于链接期、装载期和运行期，用同一种方式排查只会反复重启构建。

把"编译"当成一步，也回答不了几个具体问题：为什么头文件里只有一行 `printf` 声明程序就能跑？为什么本地能跑的文件拷到服务器会报找不到 `.so`？为什么调试器里 `main` 不是最先执行的地方？它们都指向同一条链路：源码文本 → 目标文件 → 可执行文件 → 进程映像 → `_start` → `main` → 退出。

本文用一个最小 C 程序走完这条链路：先拆开 GCC 的四个阶段，再讲链接器的符号解析与重定位、静态库与共享库的差异、ELF 的节与段两种视图、动态链接器的查找顺序，最后落到 `execve`、启动代码与退出路径。示例环境为 Ubuntu 22.04.5 LTS（x86-64）、GCC 11.4.0、GNU binutils 2.38、glibc 2.35；命令输出会随发行版与工具链版本变化，正文只引用稳定字段。

## 一条 gcc 命令背后的完整旅程

```text
构建期（工具链）                     运行期（内核 + 运行库）
hello.c
   │ 预处理：展开 include、宏与条件编译
   ▼
hello.i ──编译──▶ hello.s ──汇编──▶ hello.o ──链接──▶ hello（ELF）
   │ 装载：内核映射段，动态链接器装载共享库
   ▼
进程映像 → _start → 初始化 → main → exit → 退出状态
```

"编译"有大小两种口径：日常说的"编译一个 C 程序"包含预处理、编译、汇编和链接；GCC 手册的四阶段模型则指预处理（preprocessing）、编译（compilation proper）、汇编（assembly）与链接（linking），顺序固定。`gcc` 是驱动程序（driver），负责按顺序调度这些阶段，真正干活的编译器前端、汇编器和链接器是它调用的外部程序。

> **关键认知：** 报错发生在哪一阶段，决定了修复方向；"编译不过"把四个阶段混成一件事，所以它无法
> 指导任何修复动作。

> **面试高频：** 编译分为哪几个阶段？
> **答题脉络：** 四阶段名称与顺序 → `-E`/`-S`/`-c` 各自的停止点 → 产物是 `.i`/`.s`/`.o`/可执行文件
> → 补一句"链接由链接器完成，不属于编译器内部"。
> **追问方向：** 链接器做哪两件事；静态库与共享库差异；`-O2` 会不会改变阶段划分。

## 准备贯穿全文的最小程序

全文只用一个 `hello.c`：一个本文件的局部函数、一次跨库调用、一次返回值，足以覆盖符号、重定位与退出状态。

```c
#include <stdio.h>

static int add(int left, int right) {
    // 1. 本文件内的局部函数，编译后成为当前目标文件的局部符号。
    return left + right;
}

int main(void) {
    // 2. result 属于本次调用的自动存储对象。
    int result = add(20, 22);

    // 3. printf 的实现来自 C 运行库，这里只通过头文件获得声明。
    printf("result=%d\n", result);

    // 4. main 的返回值会成为进程的退出状态。
    return 0;
}
```

<!-- verify: .work/verify/B06/linux/hello.c -->

```bash
mkdir -p build
# 1. -O0 让汇编更容易和源码对应，-g 保留调试信息，-Wall -Wextra 打开常用告警。
gcc -std=c17 -Wall -Wextra -O0 -g hello.c -o build/hello

# 2. 运行并检查退出状态。
./build/hello
printf 'exit=%d\n' "$?"
```

```text
result=42
exit=0
```

> **时效信息（核查日期：2026-09）：** C 语言现行标准是 ISO/IEC 9899:2024（俗称 C23），ISO 记录的
> 发布状态为 2024-10-31（第 5 版）；WG14 项目页面同样把 C23 列为已发布的现行标准，并显示 C2y
> 修订仍在进行、尚未发布。示例用 `-std=c17` 作为兼容基线：它在本文的 GCC 11.4.0
> 与更新的工具链上都可用，而这段代码本身只用到 C89 时代的特性。`-std=c23` 这种拼写需要较新的编译器：本文的 GCC 11.4.0 会
> 提示 `unrecognized command-line option '-std=c23'; did you mean '-std=c2x'?`。

> **关键认知：** `-O0` 与 `-g` 只影响可观察性（汇编是否好读、有没有调试信息），不改变本文关心的
> 链路；换成 `-O2` 机器码会变，但四阶段结构和符号、重定位的存在逻辑不变。

## 预处理：先改变源码文本

预处理器处理的是以 `#` 开头的指令，不是 C 语法：替换 `#include`、展开宏、按条件编译保留或删除代码、删除注释，并插入行标记帮助后续阶段报错定位。

```bash
# 1. 只做预处理，结果写入文件。
gcc -std=c17 -E hello.c -o build/hello.i

# 2. 观察行标记，并查找 printf 的声明与 main 的位置。
grep -n '^# ' build/hello.i | head -4
wc -l build/hello.i
grep -n 'extern int printf' build/hello.i | head -1
grep -n '^int main' build/hello.i
```

```text
1:# 0 "hello.c"
4:# 1 "/usr/include/stdc-predef.h" 1 3 4
  559 build/hello.i
361:extern int printf (const char *__restrict __format, ...);
550:int main(void) {
```

行标记（line marker）是"头文件展开后报错仍能指回原文件"的原因之一；`/usr/include/stdc-predef.h` 是 GCC 自动预包含的头文件，属于实现行为而不是 C 标准要求。加 `-P` 可去掉行标记：同一文件从 559 行降到 219 行。

> **关键认知：** 头文件提供的是声明和宏，不是实现；`hello.i` 里只有 `extern int printf`，`printf`
> 的机器码一行都没有被复制进来。

## 编译：从语言语义到目标架构汇编

`-S` 让驱动在生成汇编后停止。编译器在这一步完成词法、语法、语义检查与优化，再按目标指令集生成汇编。

```bash
# 1. 从预处理结果生成汇编。
gcc -std=c17 -Wall -Wextra -O0 -g -S build/hello.i -o build/hello.s

# 2. 查看局部函数 add 的开头：两个参数先落在寄存器 edi、esi 上。
sed -n '/^add:/,/ret/p' build/hello.s | head -14
```

```text
add:
	endbr64
	pushq	%rbp
	movq	%rsp, %rbp
	movl	%edi, -4(%rbp)
	movl	%esi, -8(%rbp)
```

上面只保留真实指令，略去了 `.file`/`.loc`/`.cfi_*` 等调试伪指令；`endbr64` 来自本环境默认启用的控制流保护选项，与本文主题无关。可以看到 `-O0` 会把寄存器里的参数又存回栈上，这正是"未优化构建便于调试"的具体表现。

为了让优化前后的汇编更容易对照，另准备一个只返回结果的 `bump.c`：

```c
static int bump(int value) {
    return value + 1;
}

int main(void) {
    return bump(2);
}
```

换 `-O2` 再看这个文件：

```bash
gcc -std=c17 -Wall -Wextra -O2 -S bump.c -o build/bump_O2.s
sed -n '/^bump:/,/ret/p' build/bump_O2.s
sed -n '/^main:/,/ret/p' build/bump_O2.s
```

```text
bump:
	leal	1(%rdi), %eax
	ret
main:
	movl	$3, %eax
	ret
```

`main` 里的 `bump(2)` 被内联并折叠成常量 3，`bump` 函数本身则只剩一条 `leal`。这不是编译器"不守规矩"：C 语言只约束可观察行为（输出、退出状态、易失访问等），不约束局部变量是否真的在栈上。

> **关键认知：** "一行 C 代码对应几条汇编"不是 C 语言的保证；用 `-O0` 观察结构只是教学手段，不能
> 据此推断优化后的行为，更不能依赖未定义行为。

想看驱动打算调用哪些程序，用 `-###`（只打印、不执行）：

```bash
gcc -### -std=c17 -Wall -O0 hello.c -o build/hello 2>&1 \
  | tr ' ' '\n' | grep -E 'cc1$|as$|collect2$' | sort -u
```

输出里能看到 `cc1`、`as`、`collect2` 三个名字，它们是实现细节，不在 C 标准里；`collect2` 是 GCC 用来收集初始化信息并最终调用链接器的外壳。启用链接时优化（LTO）后，机器码会推迟到链接阶段才最终生成，传统四阶段的边界被有意模糊。

## 汇编：机器码为什么仍不能直接运行

`-c` 让驱动在汇编后停止，产出可重定位目标文件（relocatable object file）。

```bash
# 1. 只汇编，不链接。
gcc -c -g build/hello.s -o build/hello.o

# 2. 看文件类型、符号与重定位。
file build/hello.o
nm -n build/hello.o
readelf -r build/hello.o | head -6
```

```text
build/hello.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), with debug_info, not stripped
                 U printf
0000000000000000 t add
0000000000000018 T main
```

`nm` 的字母是符号表里的类型：大写通常表示全局符号、小写表示局部符号，`U` 表示未定义（undefined）——本文件引用了它，定义在别处。`add` 是 `static` 函数，所以是小写 `t`；`main` 无 `static`，是大写 `T`；`printf` 只有声明，是 `U`。

重定位表回答另一个问题："哪些已经写进机器码的位置，还要在链接时填入最终地址？"

```text
Relocation section '.rela.text' at offset 0x688 contains 2 entries:
  Offset          Info           Type           Sym. Value    Sym. Name + Addend
00000000003e  000400000002 R_X86_64_PC32     0000000000000000 .rodata - 4
00000000004b  000b00000004 R_X86_64_PLT32    0000000000000000 printf - 4
```

偏移 `0x3e` 处的指令需要一个指向只读数据 `.rodata` 的 PC 相对偏移（`R_X86_64_PC32`），偏移 `0x4b` 处的调用需要一个指向 `printf` 的 PLT 相对地址（`R_X86_64_PLT32`）。汇编器不知道最终可执行文件会把 `.rodata`、`printf` 放在哪里，甚至不知道 `printf` 来自哪个库，只能留下"待填"记录。

目标文件里已有真实机器码，却不能单独运行：给它临时加上执行权限后执行 `chmod +x build/hello.o && ./build/hello.o`，得到的是 `cannot execute binary file: Exec format error`（格式错误），而不是"找不到符号"。

> **关键认知：** 目标文件（`ET_REL`）、可执行文件（`ET_EXEC`）与共享目标（`ET_DYN`）是三种用途
> 不同的 ELF 类型；"有机器码"不等于"可以交给内核执行"。

## 链接器的两项核心工作

链接器以一组可重定位目标文件与库为输入，产出可执行文件或共享对象。它做的两件事可以分开看。

### 符号解析

符号解析（symbol resolution）把每个符号引用与一个符号定义关联起来：谁定义了 `add`、`printf` 来自哪个库、某个符号是全局可见还是仅本文件可见。程序里每个函数名、全局变量名、`static` 变量名都是一个符号。

### 重定位

重定位（relocation）先为每个符号定义确定地址，再按重定位表修改所有引用。链接器把多个目标文件的同类型节合并成输出节，算出地址后回填。

```bash
# 1. 编译"使用者"与两个"提供者"，再把三个目标文件链接起来。
gcc -c -Wall -O2 app.c -o build/app.o
gcc -c -Wall -O2 add.c -o build/add.o
gcc -c -Wall -O2 mul.c -o build/mul.o
gcc build/app.o build/add.o build/mul.o -o build/app_both
./build/app_both
```

```text
42 42
```

### 只有声明和重复定义

```bash
# 1. 只有声明、没有定义。
gcc -std=c17 undefined.c -o build/undefined
```

```text
undefined.c:(.text+0xe): undefined reference to `helper'
collect2: error: ld returned 1 exit status
```

```bash
# 2. 两个目标文件都提供同名全局符号。
gcc build/dup_a.o build/dup_b.o -o build/dup
```

```text
/usr/bin/ld: build/dup_b.o: in function `shared':
dup_b.c:(.text+0x0): multiple definition of `shared'; build/dup_a.o:dup_a.c:(.text+0x0): first defined here
collect2: error: ld returned 1 exit status
```

两处细节值得记住：`undefined reference` 是链接器（`ld`）报的，所以"头文件没包含"和"库没链接"都可能表现为它，修复动作却完全不同；C 没有名字改编（name mangling），链接器只看符号名、不检查参数类型，把 `int add(int, int)` 的定义与 `double add(double, double)` 的声明链接在一起不会报错，只会得到错误的运行行为。符号除了全局和本地，还有弱符号（weak）等绑定级别，以及 `-fvisibility` 之类的可见性控制，它们决定同名冲突谁胜出、共享库哪些符号对外可见；具体规则由 ABI 与工具链文档定义，工程上应回到 `nm`/`readelf -s` 确认，而不是猜。

> **关键认知：** 链接器保证的是"符号能对上、地址能填对"；它不做语义检查，也不验证参数个数与类型
> 是否匹配（C 语言层面）。

> **面试高频：** `undefined reference` 可能是哪些原因？
> **答题脉络：** 只有声明没有定义 → 定义在库里但库没出现在命令行 → 库的顺序不对 → 符号可见性或版本
> 不匹配 → 先用 `nm`/`readelf -s` 确认符号在不在、是 `U` 还是 `T`。
> **追问方向：** 静态库为什么吃顺序；符号版本不匹配的报错形态。

## 静态库如何按需抽取目标文件

静态库（static library，`.a`）本质是一组目标文件的档案（archive）。打包和查看都用 `ar`。

```bash
# 1. 打成档案：r 替换或加入成员，c 创建，s 写入符号索引。
rm -rf build/a && mkdir -p build/a
gcc -c -Wall -O2 add.c -o build/a/add.o
gcc -c -Wall -O2 mul.c -o build/a/mul.o
ar rcs build/a/libmathutil.a build/a/add.o build/a/mul.o
ar t build/a/libmathutil.a

# 2. 只调用 add 的使用方：目标文件在前，库在后。
gcc -c -Wall -O2 app_add_only.c -o build/app_add_only.o
gcc build/app_add_only.o -Lbuild/a -lmathutil -o build/app_add_only
./build/app_add_only

# 3. 同时调用 add 与 mul 的使用方。
gcc build/app.o -Lbuild/a -lmathutil -o build/app_static
./build/app_static
```

```text
add.o
mul.o
42
42 42
```

链接使用方时用 `-L` 增加搜索目录、`-l` 指定库名（去掉 `lib` 前缀与 `.a`/`.so` 后缀）。关键差异是：链接器不把整个档案塞进产物，而是**按未解析符号抽取成员**。上面只调用 `add` 的 `app_add_only` 里就没有 `mul`：

```bash
nm build/app_add_only | grep -E ' (add|mul)$'
size build/app_add_only build/app_static
```

```text
0000000000001190 T add
   text	   data	    bss	    dec	    hex	filename
   1471	    600	      8	   2079	    81f	build/app_add_only
   1548	    600	      8	   2156	    86c	build/app_static
```

对 `app_static` 执行同一条 `nm | grep` 会看到 `add` 与 `mul` 两个符号，`text` 段也随之从 1471 增长到 1548 字节（`data`/`bss` 不变，因为两个成员都不含已初始化数据）。

库在命令行中的位置同样有语义：链接器从左到右处理输入，遇到库时只解决**此刻**仍未解析的符号，所以"目标文件在前、库在后"是稳妥的默认写法。

```bash
# 1. 故意把库放在目标文件之前。
gcc -Lbuild/a -lmathutil build/app_add_only.o -o build/app_order
```

```text
/usr/bin/ld: build/app_add_only.o: in function `main':
app_add_only.c:(.text.startup+0x13): undefined reference to `add'
collect2: error: ld returned 1 exit status
```
库之间有环状依赖时，链接器提供"组"机制让一组库被反复扫描（GNU ld 用 `--start-group`/`--end-group`）；这是工具链能力，需要按当前 `ld` 手册使用。

> **关键认知：** "静态链接"常被混用。链接静态库只是把库代码复制进产物，产物仍可依赖共享的 C 运行
> 库；`-static` 才要求不使用共享库。证据：只链接了 `.a` 的 `app_static` 仍是 `DYN` 且
> `NEEDED libc.so.6`，而 `-static` 产物是 `EXEC`，`ldd` 报 `not a dynamic executable`。

> **面试高频：** 静态库为什么受命令行顺序影响？
> **答题脉络：** 链接器单趟从左到右 → 遇到库时只抽取能解决当前未解析符号的成员 → 未解析符号出现在
> 库之后时没有"回车"机会 → 用组或调整顺序解决。
> **追问方向：** `.a` 与 `.so` 同时存在时 `-l` 选哪个（GCC 手册：默认偏好共享库，除非 `-static`）；
> 动态库为什么受顺序影响更小。

## 共享库把哪些工作留到运行时

共享库（shared library，`.so`；Windows 上叫 DLL）把"把库代码塞进产物"改成"在产物里记一条依赖，运行时再装载"。

```bash
# 1. 库代码编译为位置无关代码（PIC）。
gcc -c -Wall -O2 -fPIC add.c -o build/add.pic.o
gcc -c -Wall -O2 -fPIC mul.c -o build/mul.pic.o

# 2. 链接成共享对象，并写入 SONAME。
gcc -shared -Wl,-soname,libmathutil.so -o build/libmathutil.so build/add.pic.o build/mul.pic.o

# 3. 链接使用方，产物里只留依赖名。
gcc build/app.o -Lbuild -lmathutil -o build/app_shared
readelf -d build/app_shared | grep NEEDED
```

```text
 0x0000000000000001 (NEEDED)             Shared library: [libmathutil.so]
 0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]
```

### PIC、GOT 与 PLT

共享库会被映射到哪个地址，链接时并不知道（PIE 与 ASLR 下每次运行还可能不同），所以库内代码不能依赖"符号地址是编译期常量"。`-fPIC` 的做法是查表寻址：**全局偏移表（Global Offset Table，GOT）** 通常由每个加载对象各自拥有一份，存放该对象在当前进程里的相关地址；**过程链接表（Procedure Linkage Table，PLT）** 为每个被外部调用的函数提供入口桩（stub），调用方跳进桩，桩再经 GOT 跳到真实实现。反例最能说明问题：

```bash
gcc -c -Wall -O2 -fno-pic -fno-pie nopic.c -o build/nopic.o
gcc -shared -o build/libnopic.so build/nopic.o
```

```text
/usr/bin/ld: build/nopic.o: relocation R_X86_64_32 against `.rodata.str1.1' can not be used when making a shared object; recompile with -fPIC
collect2: error: ld returned 1 exit status
```

`R_X86_64_32` 表示"把符号的绝对地址截成 32 位写进指令"，这在位置无关的共享对象里无法满足，于是链接失败；换成 `-fPIC` 后同一份源码就能做成 `.so`。再看可执行文件里的调用点是直接调用还是穿过 PLT：

```bash
objdump -d --disassemble=main build/hello | grep call
readelf -r build/hello | grep -A2 'rela.plt'
```

```text
    1177:	e8 cd ff ff ff       	call   1149 <add>
    1193:	e8 b8 fe ff ff       	call   1050 <printf@plt>
Relocation section '.rela.plt' at offset 0x610 contains 1 entry:
000000003fd0  000300000007 R_X86_64_JUMP_SLO 0000000000000000 printf@GLIBC_2.2.5 + 0
```

`add` 就在本文件内，链接时地址已定，直接调用；`printf` 属于共享库，调用落在 `printf@plt`。`R_X86_64_JUMP_SLOT` 的语义是"把解析出来的 `printf` 地址写进 GOT 的槽位"；谁在什么时候写、写几次，取决于绑定策略。

### 绑定策略与 ABI 兼容

传统默认策略是**惰性绑定**（lazy binding）：函数地址通常在第一次调用时才解析，未执行到的调用点可能一直不解析。现代发行版常改为**立即绑定**（`-z now`），让动态链接器在启动时把符号解析完——代价是启动变慢，收益是地址表在装载后更容易设为只读、攻击面更小。

```bash
readelf -d build/app_shared | grep -E 'BIND_NOW|FLAGS'
gcc build/app.o -Lbuild -lmathutil -Wl,-z,lazy -o build/app_lazy
readelf -d build/app_lazy | grep -E 'FLAGS_1'

# 用 LD_DEBUG 看绑定时机：lazy_probe 里的 add 调用点默认执行不到。
LD_DEBUG=bindings LD_LIBRARY_PATH=build ./build/lazy_probe 2>&1 | grep -c "symbol \`add'"
LD_DEBUG=bindings LD_BIND_NOW=1 LD_LIBRARY_PATH=build ./build/lazy_probe 2>&1 | grep "symbol \`add'"
```

```text
 0x000000000000001e (FLAGS)              BIND_NOW
 0x000000006ffffffb (FLAGS_1)            Flags: NOW PIE
 0x000000006ffffffb (FLAGS_1)            Flags: PIE
0
      1679:	binding file ./build/lazy_probe [0] to build/libmathutil.so [0]: normal symbol `add'
```

这也解释了一个常见现象：老式惰性绑定程序启动很久后的第一次库调用会"卡一下"，正是那次调用触发了绑定。`LD_DEBUG`、`LD_BIND_NOW` 由 glibc 动态链接器提供，属于实现能力而非 ELF 强制要求。

> **时效信息（核查日期：2026-09）：** 本文环境（Ubuntu 22.04.5 LTS + GCC 11.4.0）默认写出
> `BIND_NOW`/`FLAGS_1: NOW PIE`，即默认立即绑定加 PIE；这属于发行版与工具链配置，不是 ELF 或 C
> 标准的规定。默认是否 PIE、默认链接器是谁、是否提供静态 libc，都要按目标平台实测。

共享库的部署优势是"一个库文件被多个程序共享，替换库文件即可升级"，但前提是 **ABI 兼容**：符号名、参数与返回类型、结构体布局、语义都不能破坏。把库换成缺少某个符号的版本，链接期不会报错（程序本来就是动态链接），装载或运行时才失败：

```bash
LD_LIBRARY_PATH=build/abi ./build/app_abi
```

```text
./build/app_abi: symbol lookup error: ./build/app_abi: undefined symbol: mul
```

> **关键认知：** "替换 `.so` 即可升级"只在不破坏 ABI 时成立；删改符号或数据结构后，"不用重新编译"
> 这个结论立刻失效。

> **面试高频：** PIC、GOT、PLT、惰性绑定是什么关系？
> **答题脉络：** PIC 解决"不知道装载到哪" → 数据访问经 GOT 间接寻址 → 函数调用经 PLT 桩 → 桩里地址
> 何时回填由立即绑定还是惰性绑定决定 → 用 `readelf -r`、`objdump -d`、`LD_DEBUG=bindings` 观察。
> **追问方向：** `.rela.plt` 与 `.rela.dyn` 的差别；`-z relro`/`-z now` 的作用；`LD_PRELOAD` 为什么
> 能拦截调用。

## ELF：section 是链接视图，segment 是装载视图

ELF（Executable and Linkable Format）同时服务两组使用者，所以有两套描述结构：**节（section）** 是链接器、调试器与分析工具的组织单位（`.text` 机器指令、`.rodata` 只读常量、`.data` 已初始化的可写全局/静态数据、`.bss` 零初始化数据，符号表与重定位表也是节）；**段（segment，程序头表）** 是装载器使用的单位，内核只关心"哪些区域要映射进地址空间、起始地址与长度、权限是什么"，因此段会把若干节按权限合并。

```bash
readelf -W -S build/bss_demo | grep -E '\.text|\.rodata|\.data|\.bss'
readelf -lW build/bss_demo | grep '^  LOAD'
```

```text
  [16] .text             PROGBITS        0000000000001060 001060 00012a 00  AX  0   0 16
  [18] .rodata           PROGBITS        0000000000002000 002000 000015 00   A  0   0  4
  [25] .data             PROGBITS        0000000000004000 003000 000014 00  WA  0   0  8
  [26] .bss              NOBITS          0000000000004020 003014 001020 00  WA  0   0 32
  LOAD           0x002db8 0x0000000000003db8 0x0000000000003db8 0x00025c 0x001288 RW  0x1000
```

`readelf -l` 还会直接给出节到段的映射，这比记住规则更可靠：

```text
   03     .init .plt .plt.got .plt.sec .text .fini
   04     .rodata .eh_frame_hdr .eh_frame
   05     .init_array .fini_array .dynamic .got .data .bss
```

`.bss` 那一行值得单独看：类型是 `NOBITS`，"有地址、有长度，但文件里不占这么多字节"。上面那条 `LOAD` 的 `FileSiz`（`0x25c`）与 `MemSiz`（`0x1288`）之差约 4 KiB，正好对应示例里 4096 字节的零初始化数组加对齐填充。

```bash
ls -l build/bss_demo
size build/bss_demo
```

```text
-rwxrwxrwx 1 root root 17400 ... build/bss_demo
   text	   data	    bss	    dec	    hex	filename
   1416	    604	   4128	   6148	   1804	build/bss_demo
```

（所有者与时间戳随环境变化，关键是数字。）`bss` 有 4128 字节，文件大小却停在 17400 字节，没有再多出 4 KiB 的零。

各工具回答的问题不同，混用最容易得出错误结论：`file` 告诉你格式、架构与是否动态链接；`readelf -h/-S/-l` 分别给出 ELF 头、节表与程序头表；`nm`/`readelf -s` 列出符号及其绑定与可见性；`readelf -r` 列出待处理的重定位；`readelf -d` 列出声明的动态依赖与动态标签；`objdump -d`/`-S` 反汇编，带调试信息时可与源码交错显示；`size` 汇总 text/data/bss，用来验证零初始化数据不占文件空间的结论。

属于"现代扩展"、不影响主线但值得知道来源的有：GNU 风格的 `.gnu.hash` 动态符号哈希（由 `--hash-style=gnu` 决定）；GNU ld 的 `--pack-relative-relocs` 产生的 `DT_RELR` 系列紧凑相对重定位；glibc 用 `printf@GLIBC_2.2.5` 这样的版本化符号记录 ABI 演进；`.note.gnu.property` 记录控制流保护等体系结构属性。

> **关键认知：** 不要拿节表解释运行时内存。运行时的读写与可执行权限来自段（程序头表），而 `.text`
> 也不会永远落在同一地址——PIE 与 ASLR 会让模块基址每次运行都变。

> **面试高频：** 节（section）与段（segment）有什么区别？
> **答题脉络：** 服务对象不同（链接/调试 vs 装载）→ 节按内容分类，段按权限与映射方式合并 →
> `readelf -S` 与 `readelf -l` 分别观察 → 用映射表把两种视图连起来。
> **追问方向：** `.bss` 为什么是 `NOBITS`；`PT_LOAD`/`PT_INTERP`/`PT_DYNAMIC` 各做什么；PIE 与
> `-no-pie` 的头部差异。

## 动态链接器如何找到并绑定共享库

可执行文件里记录了三类信息：`PT_INTERP` 段说明"用哪个程序解释我"（本文环境是 `/lib64/ld-linux-x86-64.so.2`），`.dynamic` 节里的 `DT_NEEDED` 逐条记录依赖的库名，`PT_DYNAMIC` 告诉动态链接器去哪里读 `.dynamic`。

### 查找顺序

依赖名含斜杠时直接当路径使用；不含斜杠时，按 `ld.so(8)` 规定的顺序查找目录：

1. 可执行文件的 `DT_RPATH`（仅当不存在 `DT_RUNPATH` 时使用，较老的机制）；
2. 环境变量 `LD_LIBRARY_PATH` 列出的目录（安全执行模式下被忽略）；
3. 可执行文件的 `DT_RUNPATH`（较新的机制，只作用于直接依赖）；
4. 缓存文件 `/etc/ld.so.cache`（由 `ldconfig` 根据 `/etc/ld.so.conf` 维护）；
5. 默认目录 `/lib`、`/usr/lib`（部分 64 位架构下先 `/lib64`、`/usr/lib64`）。

```bash
./build/app_shared
```

```text
./build/app_shared: error while loading shared libraries: libmathutil.so: cannot open shared object file: No such file or directory
```

库就在当前目录，但"当前目录"不在上面任何一步里。临时解法是 `LD_LIBRARY_PATH=build ./build/app_shared`；可部署的解法是把相对自身的位置写进产物。

### RPATH 与 RUNPATH

```bash
gcc build/app.o -Lbuild -lmathutil -Wl,-rpath,'$ORIGIN' -o build/app_rpath
readelf -d build/app_rpath | grep -E 'RPATH|RUNPATH'
```

```text
 0x000000000000001d (RUNPATH)            Library runpath: [$ORIGIN]
```

`$ORIGIN` 由动态链接器展开为"这个对象自己所在目录"，所以把程序与库一起拷到别处仍能运行：

```bash
mkdir -p dist
cp build/app_rpath build/libmathutil.so dist/
./dist/app_rpath
mv dist/libmathutil.so dist/renamed.so
./dist/app_rpath
```

```text
42 42
./dist/app_rpath: error while loading shared libraries: libmathutil.so: cannot open shared object file: No such file or directory
```

`DT_RPATH` 与 `DT_RUNPATH` 的关键差别是传递性：`DT_RPATH` 作用于整棵依赖树，`DT_RUNPATH` 只作用于直接依赖。写入哪一个由链接器的 new-dtags 选项决定：本文环境默认得到 `RUNPATH`，加 `--disable-new-dtags` 才得到 `RPATH`。GNU ld 手册说明这两个选项控制是否生成新标签，实际结果取决于驱动传给链接器的参数，所以**永远用 `readelf -d` 确认**。

`ld.so(8)` 还规定了"安全执行模式"（secure-execution mode）：`AT_SECURE` 非零时进入该模式，典型触发条件是可执行文件带 set-user-ID 位、或真实与有效用户/组 ID 不一致；此时 `LD_LIBRARY_PATH`、`LD_PRELOAD`、`LD_DEBUG`、`LD_SHOW_AUXV` 等环境变量会被忽略甚至从环境中剥离，程序自己也读不到。

> **时效信息（核查日期：2026-09）：** 查找顺序、RPATH/RUNPATH 分工、安全执行模式与环境变量清单均
> 引自当前 `ld.so(8)`（Linux man-pages 项目）；动态链接器文件名、默认目录与缓存内容由发行版和架构
> 决定，本文的 `/lib64/ld-linux-x86-64.so.2` 只是 x86-64 Linux 上的常见取值。

> **面试高频：** 程序启动时报 `cannot open shared object file`，怎么查？
> **答题脉络：** 先分清"声明的依赖"（`readelf -d`/`objdump -p`）与"实际解析结果"（`ldd`）→ 按
> `ld.so(8)` 顺序检查 RPATH/RUNPATH、`LD_LIBRARY_PATH`、`ld.so.cache`、默认目录 → 用 `$ORIGIN`
> 做相对部署 → 注意安全执行模式会忽略环境变量。
> **追问方向：** RPATH 与 RUNPATH 的传递性差异；`ldconfig` 什么时候必须执行；hwcaps 子目录为什么
> 会让同一台机器上不同 CPU 选到不同的库。

## ldd 很方便，但不要对不可信文件使用

`ldd` 打印的是"**在当前环境下**，每个依赖名会被解析到哪个文件"，回答的是运行期解析问题。

```bash
ldd build/app_shared | sed -E 's/ \(0x[0-9a-f]+\)$//'
LD_LIBRARY_PATH=build ldd build/app_shared | sed -E 's/ \(0x[0-9a-f]+\)$//'
```

```text
	libmathutil.so => not found
	libmathutil.so => build/libmathutil.so
```

只加了一个环境变量，解析结果就变了，而文件本身没有变化。`ldd(1)` 同时给出了明确的安全警示：某些情况下 `ldd` 会通过直接执行程序来获取依赖信息，因此"绝不要对不可信的可执行文件使用 `ldd`"，而应改用静态检查：

```bash
objdump -p build/app_shared | grep NEEDED
readelf -d build/app_shared | grep NEEDED
```

```text
  NEEDED               libmathutil.so
  NEEDED               libc.so.6
 0x0000000000000001 (NEEDED)             Shared library: [libmathutil.so]
 0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]
```

较新的 glibc 已会拒绝解析非 ELF 文件：

```bash
ldd build/notelf.sh
```

```text
	not a dynamic executable
```

但这不能被当作"可以放心用"的理由，而且 `ldd` 在共享目标上可能输出 `statically linked`——那表示该 `.so` 自身没有动态依赖，不代表它是静态可执行文件。

> **关键认知：** `readelf -d`/`objdump -p` 给出文件里声明的依赖（静态事实），`ldd` 给出当前环境下
> 实际解析到的路径（动态结果）；两者都不能单独回答"换个环境还能不能跑"。静态检查还有个边界：它只
> 显示直接依赖，不含依赖的依赖。

## execve：可执行文件如何变成进程映像

在 shell 里输入 `./build/hello` 后，shell 通常先创建子进程，再由子进程通过 `execve` 请求内核用目标 ELF 替换自己的进程映像。`execve` 成功时不返回，失败才返回 `-1`，所以"运行一个新程序"的准确说法是"用新映像覆盖当前进程"。

```bash
strace -f -e trace=execve ./build/hello
```

```text
1534  execve("./build/hello", ["./build/hello"], 0x7fffed9c99c8 /* 15 vars */) = 0
1534  +++ exited with 0 +++
```

（进程号与指针值每次都不同，这里只保留字段结构。）

内核对 ELF 的处理顺序可以概括为：校验文件格式与目标架构（`ET_REL` 不被接受，这就是直接执行 `.o` 报 `Exec format error` 的原因）→ 按程序头表中的 `PT_LOAD` 段建立虚拟内存映射 → 在初始栈顶布置 `argc`、`argv`、环境变量指针数组与辅助向量（auxiliary vector）→ 如果存在 `PT_INTERP`，先把控制权交给该解释器（本文环境即动态链接器），由它装载共享库并完成重定位，再跳到主程序 ELF 头记录的入口；没有解释器时，内核直接从该入口开始执行。

辅助向量可以直接观察：

```bash
LD_SHOW_AUXV=1 ./build/hello | grep -E 'AT_PHDR|AT_PHNUM|AT_BASE|AT_ENTRY|AT_EXECFN'
```

```text
AT_PHDR:              0x7f4763e51040
AT_PHNUM:             13
AT_BASE:              0x7f4763e10000
AT_ENTRY:             0x7f4763e52060
AT_EXECFN:            ./build/hello
```

`AT_PHNUM` 是程序头数量（和 `readelf -l` 报的 13 个一致），`AT_ENTRY` 是入口的**运行时**地址，`AT_BASE` 是解释器（动态链接器）的基址。这些数不是常量：再运行一次，`AT_BASE`/`AT_ENTRY` 就会变成另一组值。它们与 ELF 头的关系可以直接算：AT_PHDR 减去程序头表偏移 `0x40` 得到本次加载基址 `0x7f4763e51000`，再加上入口偏移 `0x1060` 恰好是 `AT_ENTRY`。对 `-no-pie` 产物，同一台机器上的 `AT_ENTRY` 固定为 `0x401050`，即 `readelf -h` 里写死的入口地址。

动态链接器随后用 `mmap` 把共享库的不同权限区域映射进来：

```bash
strace -y -e trace=mmap ./build/hello 2>&1 | grep -E 'libc\.so' | head -1
```

```text
mmap(NULL, 2264656, PROT_READ, MAP_PRIVATE|MAP_DENYWRITE, 3</usr/lib/x86_64-linux-gnu/libc.so.6>, 0) = 0x7f7ead1c0000
```

同一次装载里，同一个库文件会被拆成"只读""可读可执行""只读""可读写"多段映射（映射地址每次运行都不同），正是共享库多个 `PT_LOAD` 段落到页表上的结果：代码页通常只读且可执行，因此同一文件的代码页能被多个进程共享；可写数据以及发生私有重定位或写入后的页，则按进程分别计入。

顺便澄清一个常见混淆：`fork` 与 `execve` 是两件事——`fork`（或 `posix_spawn` 等机制）产生进程副本，`execve` 替换当前进程映像；shell 只是习惯先 `fork` 出子进程再在子进程里 `execve`，`execve` 本身不要求先有 `fork`。进程生命周期与 wait 语义见[进程、线程与调度](./02-进程、线程与调度.md)。

> **关键认知：** 装载把"一个文件"变成"一组映射 + 初始栈与辅助向量 + 一个入口地址"；它不解析
> `main`，也不执行 C 语言语义。

> **面试高频：** 链接与装载、`fork` 与 `exec` 分别有什么区别？
> **答题脉络：** 链接在构建期把符号与地址确定在文件里；装载在运行期把文件映射进地址空间并交给入口
> → `execve` 替换映像不创建进程，`fork` 创建进程不加载新程序 → 观察手段分别是 `readelf -l` 与
> `strace execve`。
> **追问方向：** `PT_INTERP` 的作用；`AT_SECURE` 与 setuid；虚拟地址空间布局（见下一篇）。

## 从 ELF 入口到 main

ELF 头里的入口地址是内核（或解释器）最终跳转的地方，它不是 `main`：

```bash
readelf -h build/hello | grep Entry
nm -n build/hello | grep -w _start
objdump -d --disassemble=_start build/hello | sed -n '/<_start>:/,/ret/p'
```

```text
  Entry point address:               0x1060
0000000000001060 T _start
0000000000001060 <_start>:
    1078:	48 8d 3d e2 00 00 00 	lea    0xe2(%rip),%rdi        # 1161 <main>
    107f:	ff 15 53 2f 00 00    	call   *0x2f53(%rip)        # 3fd8 <__libc_start_main@GLIBC_2.34>
```

上面略去了栈对齐与 `push`、`xor` 指令，只保留关键两行：`lea ... # 1161 <main>` 是在取 `main` 的地址并作为第一个参数放进 `rdi`，随后调用 `__libc_start_main`。`_start` 不在 `hello.o` 里，它来自链接器自动加入的启动文件：

```bash
gcc -### -std=c17 hello.c -o build/hello 2>&1 | tr ' ' '\n' | grep -i crt | sort -u
```

分工大致是：`crt1.o`（生成 PIE 时用 `Scrt1.o`）提供 `_start`，衔接内核与 C 运行库；`crti.o`/`crtn.o` 提供 `.init`/`.fini` 的函数序言与尾声；`crtbeginS.o`/`crtendS.o` 负责初始化与收尾框架。换成 `-no-pie` 构建，同一台机器上出现的就是 `crt1.o`、`crtbegin.o`、`crtend.o`：名字带 `S` 的变体服务于位置无关产物。这些名字与分工属于**实现细节**，不是 C 标准规定。

### 启动代码做了什么

本文环境（glibc，x86-64）的路径是：内核按 ABI 约定把 `argc`、`argv`、环境变量与辅助向量放在初始栈顶，然后跳到 `_start`；`_start` 取出这些参数、对齐栈，把 `main` 的地址与参数交给 `__libc_start_main`；后者完成 C 运行库一级初始化（必要的自重定位、线程局部存储 TLS 与栈保护值、依次执行 `.preinit_array` 与 `.init_array` 中的初始化函数、登记退出处理；C++ 全局对象构造就在这里），最后才调用 `main`。

可以顺手确认初始化数组确实存在于文件里：

```bash
readelf -d build/hello | grep -E 'INIT_ARRAY|FINI_ARRAY'
```

```text
 0x0000000000000019 (INIT_ARRAY)         0x3db8
 0x000000000000001b (INIT_ARRAYSZ)       8 (bytes)
 0x000000000000001a (FINI_ARRAY)         0x3dc0
```

这些节在 `readelf -l` 的映射表里与 `.data`、`.bss` 同属一个可写段，所以初始化函数地址表在运行时是可读可写的——这也是 RELRO 机制要把 `.got`、`.init_array` 之类的页在重定位完成后设为只读的原因。

> **关键认知：** `_start`、`__libc_start_main`、`crt*.o` 都是 glibc 与 GNU 工具链的实现细节，C 标准
> 只保证"从 `main` 开始执行程序的可观察语义"；换成 musl 或别的平台，这条路径的每一步都可能不同，
> 业务代码不应依赖这些符号。

`_start` 能把 `main` 的地址、`argc`、`argv` 传给 `__libc_start_main`，靠的是体系结构规定的调用约定（calling convention）。x86-64 上两大主流 ABI 的整型参数寄存器不同：`System V AMD64`（Linux、macOS 等）用 `rdi` `rsi` `rdx` `rcx` `r8` `r9` 六个，浮点参数走 `xmm0`–`xmm7`；`Microsoft x64`（Windows）只用 `rcx` `rdx` `r8` `r9` 四个，且调用者必须预留 32 字节影子空间。两者装不下的参数都从右到左压栈，整型返回值都放 `rax`。

约定决定了"第几个参数放在哪个寄存器"，所以跨平台代码不能假设某个参数在栈上的固定偏移；可变参数函数必须使用 `<stdarg.h>` 提供的机制，让编译器按 ABI 算出位置。栈帧如何建立与回收、局部变量为什么"通常"在栈上、栈溢出如何触发 SIGSEGV，属于运行时内存行为，见[虚拟内存、地址空间与函数调用](./04-虚拟内存、地址空间与函数调用.md)。

> **面试高频：** 为什么说 `main` 不是 ELF 的入口？
> **答题脉络：** ELF 头里写的是 `_start` → `_start` 取 `main` 地址交给 `__libc_start_main` → 运行库
> 完成初始化后才调用 `main` → 这条链是 glibc 实现案例，不是 ISO C 规定。
> **追问方向：** `main` 为什么可以有不同签名；初始化数组在哪个段；`_start` 如何拿到 `argc`/`argv`。

## main 返回以后

从初始 `main` 返回，效果等价于用返回值调用 `exit`，因此正常退出是一条有顺序的用户态清理流程：执行 `atexit` 登记的退出处理函数（后登记的先执行）、刷新 C 标准 I/O 缓冲区、把退出状态交给操作系统（随后由内核回收地址空间与文件描述符并通知父进程）。

```bash
./build/exit_two
```

```text
main is leaving
handler registered second
handler registered first
```

缓冲区差异可以用重定向放大：写到文件时 stdio 使用块缓冲，正常退出会刷新，`_Exit` 则直接终止。

```bash
./build/exit_demo > logs/exit_demo.txt
wc -c logs/exit_demo.txt
./build/exit_skip > logs/exit_skip.txt
wc -c logs/exit_skip.txt
```

```text
28 logs/exit_demo.txt
0 logs/exit_skip.txt
```

几种退出方式可以这样记：`return`（从 `main`）与 `exit(status)` 都走正常退出流程；`_Exit(status)` 与 `_exit(status)` 跳过 C 运行库清理，用于特殊的进程控制场景；`abort()` 触发异常终止（默认产生 `SIGABRT`），不保证刷新用户态缓冲区。`EXIT_SUCCESS`/`EXIT_FAILURE` 的具体数值由实现定义。

> **关键认知：** 进程退出时操作系统会回收地址空间和内核资源，但这不等于 C 运行库会替你刷新所有用户态缓冲区；缓冲区刷新、文件关闭、`atexit`
> 顺序都是可观察行为，跳过它们会丢数据。

## 错误发生在哪一个阶段

| 阶段 | 常见问题 | 典型提示 | 首选观察命令 |
|---|---|---|---|
| 预处理 | 头文件找不到、宏展开不符合预期 | `fatal error: ... No such file or directory` | `gcc -E` 后的 `.i` |
| 编译 | 语法、类型、声明错误 | `error: expected ';' before ...` | 直接读第一处报错 |
| 汇编 | 目标架构不支持某条指令 | `Error: no such instruction: ...` | `gcc -c` 的报错 |
| 链接 | 只有声明、重复定义、库顺序或路径不对 | `undefined reference to ...`、`multiple definition of ...` | `nm`、`readelf -r/-s` |
| 链接 | 对象文件体系结构不匹配 | `i386 architecture ... is incompatible with i386:x86-64 output` | `file` 每个输入 |
| 装载/绑定 | 依赖库找不到、版本不匹配 | `cannot open shared object file`、`symbol lookup error` | `readelf -d`、`ldd`、`strace` |
| 运行 | 空指针、越界、逻辑错误 | 崩溃、错误输出、非零退出状态 | Sanitizer、gdb |

同一条命令在不同路径下报的错，正好对应不同阶段：

```text
build/missing_header.c:1:10: fatal error: nosuch_header.h: No such file or directory
build/missing_semicolon.c:1:26: error: expected ';' before '}' token
undefined.c:(.text+0xe): undefined reference to `helper'
./build/app_shared: error while loading shared libraries: libmathutil.so: cannot open shared object file: No such file or directory
```

三条线索很有用：报错前缀是 `ld:`/`collect2:` 属于链接阶段；出现 `error while loading` 属于初始装载阶段，`symbol lookup error` 可能发生在装载时，也可能发生在惰性绑定触发的运行期，此时链接已经成功，问题在运行环境或库版本；程序已经跑起来才崩溃，则属于运行期问题，构建产物未必有错。

> **关键认知：** 把所有失败都叫"编译错误"会掩盖修复方向：链接错误要动的是库与命令顺序，装载错误
> 要动的是运行环境与部署布局，运行期错误才需要看代码逻辑。

## 同一流程在 macOS 与 Windows 如何落地

阶段模型跨平台通用，产物格式与运行时组件不同。下表只做角色对照；本文未在 macOS/Windows 上执行这些命令，具体选项以各平台官方文档为准。

| 角色 | Linux | macOS | Windows |
|---|---|---|---|
| 可执行文件格式 | ELF | Mach-O | PE/COFF |
| 查看格式信息的工具 | `readelf`、`objdump`、`nm` | `otool`、`nm` | `dumpbin`、MinGW 的 `objdump` |
| 编译器驱动 / 链接器 | `gcc`、`clang` / GNU ld、LLD | `clang` / `ld`（Apple） | `cl`、`clang-cl` / `link.exe` |
| 动态链接器 | `ld.so`/`ld-linux*.so` | `dyld` | 系统加载器（解析 PE 导入表） |
| 依赖记录方式 | `DT_NEEDED` + `RPATH`/`RUNPATH` | `LC_LOAD_DYLIB` 等加载命令，含 install name | 导入表（import table）对应的 DLL |
| 相对定位机制 | `$ORIGIN`、`LD_LIBRARY_PATH`、`ld.so.cache` | `@rpath`、install name（`DYLD_*` 环境变量受系统保护机制限制） | DLL 搜索顺序（应用目录、系统目录、`PATH` 等） |

Mach-O 用加载命令（load command）描述"加载哪些 dylib、装到什么地址"，PE 用节加数据目录，动态依赖体现为导入表；因此 macOS 上查看依赖用 `otool -L` 一类命令，Windows 上可以用 `dumpbin /DEPENDENTS`（按 Microsoft 文档，它输出镜像导入的 DLL 名）或 `dumpbin /HEADERS` 看文件头。

> **关键认知：** "四阶段 + 装载 + 启动代码"的抽象跨平台成立，可迁移的是思路；具体格式、工具与搜索
> 规则必须各自查官方文档，不能把 ELF 的结论当作通则。

## 一套可复制的观察清单

遇到"这段代码到底发生了什么"时，按由外向内、由静态到动态的顺序做实验：

```bash
# 1. 格式、架构、是否动态链接。
file build/hello

# 2. 预处理是否按预期展开。
gcc -std=c17 -E hello.c -o build/hello.i

# 3. 汇编与源码对照，并看目标文件的符号与重定位。
objdump -S -d build/hello | sed -n '1,40p'
nm -n build/hello.o
readelf -r build/hello.o | head -6

# 4. 链接后的节、段、入口与声明的依赖。
readelf -h -S -l build/hello | head -40
readelf -d build/hello | grep NEEDED

# 5. 运行期的解析与装载，最后看输出与退出状态。
ldd build/hello
strace -f -e trace=execve ./build/hello
./build/hello
printf 'exit=%d\n' "$?"
```

定位到运行期问题后，再引入 Sanitizer 诊断（它改变内存布局与性能，不是 C 语言的执行阶段，只应在排查时启用）：

```bash
gcc -std=c17 -Wall -Wextra -g -fsanitize=address,undefined oob.c -o build/oob
./build/oob   # runtime error: index 5 out of bounds ... / AddressSanitizer: stack-buffer-overflow
```

> **关键认知：** 观察顺序应当"先静态、后动态"：`readelf`/`nm` 看到的是文件里的事实，`ldd`/`strace`
> 看到的是当前环境下的一次实际行为，两者回答不同的问题。

## 常见误区

- ❌ `main` 是 ELF 文件的入口。
  ✅ 入口是 ELF 头里的 `Entry point address`，本文环境里它落在 `_start`；`main` 的地址只是作为参数传给 `__libc_start_main`。
- ❌ `stdio.h` 里包含 `printf` 的实现。
  ✅ 头文件给声明和宏；`hello.i` 里只有 `extern int printf`，机器码来自共享的 C 运行库。
- ❌ `.bss` 里有多少字节，文件里就存多少零字节。
  ✅ `.bss` 是 `NOBITS`：文件里只记录"运行时需要多大、放在哪里"，装载时按需求零页；`size` 的 `bss` 列与 `ls -l` 的文件大小对比即可验证。
- ❌ 动态链接意味着所有函数都在第一次调用时才解析。
  ✅ 惰性绑定只是一种策略；本文环境默认产物已带 `BIND_NOW`（立即绑定）。两者都能用 `readelf -d` 与 `LD_DEBUG=bindings` 观察。
- ❌ 替换 `.so` 永远不需要重新编译。
  ✅ 只有保持 ABI 兼容时成立；删掉一个符号会让程序在装载或运行时以 `symbol lookup error` 失败。
- ❌ ELF 里的地址在运行时固定不变。
  ✅ 默认 PIE 加 ASLR 下模块基址与 `AT_ENTRY` 每次运行都不同；`-no-pie` 才让入口落在固定地址。不要把 `nm` 显示的链接期地址当作运行期地址。

## 一句话总结

> 一份 C 源码要依次经过预处理、编译、汇编和链接变成 ELF 文件，再由内核与动态链接器装载成进程映像，从 `_start` 初始化到 `main`，最后沿正常退出流程把状态交还操作系统；把每个阶段的产物和工具分清楚，构建与装载错误就不再互相冒充。
