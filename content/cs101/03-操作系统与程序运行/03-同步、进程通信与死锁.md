# 操作系统与程序运行｜03-同步、进程通信与死锁

## 从一次丢失更新看并发正确性

先看一段最朴素的并发缺陷。两个执行流各自把一个共享计数从 0 自增到 1，但自增不是一步完成，它可以拆成「读入」「加一」「写回」三个动作。只要两个执行流的动作发生交错，就可能出现下面这条时间线：

```text
T1: 读 count -> 0
T2: 读 count -> 0
T1: 写 count = 1
T2: 写 count = 1      <- T1 的结果被覆盖，一次自增丢失
```

这种「结果取决于未受约束的执行顺序」的现象称为竞态条件（race condition）；被多个执行流共享、访问时需要排他的数据称为临界资源；访问它的那一段代码称为临界区（critical section）。修复办法是给临界区加上进入与退出协议，使同一时刻至多有一个执行流处于临界区，而不是指望线程「跑得慢一点」。

注意：上面的交错只是「可能」发生，而不是「每次」发生。同样的程序在轻载时可能连续运行几万次都正确，压力或调度一变就出错——这正是竞态 bug 难复现的根源。把「可能出错」写成「必然出错」会误导排查方向。

用 C 描述这段代码时还要额外注意语言层面的规则：C 的内存模型把两个执行流对同一非原子对象的并发冲突访问定义为数据竞争（data race），而有数据竞争的程序行为未定义（undefined behavior，UB）。这意味着不能把「最终得到 1」当作程序保证的错误结果，也不能指望得到任何确定结果——可能得到 1、2，也可能因为编译器优化产生完全意料之外的代码。要获得可推理的行为，就必须用锁或原子操作建立顺序。

下面的 Dart 程序把两个执行流的每一步显式建模，穷举所有交错并统计最终值。下面抽取其中的 `Flow` 类（省略 `Counter`、交错枚举与统计部分）；它不代表真实线程的执行方式（Dart 的 isolate 之间不共享可变内存、只能通过消息通信），只是一个可数的交错模型，用来展示「有时丢失、有时不丢失」：

```dart
class Flow {
  Flow(this.name, {required this.uninterruptible});

  final String name;
  final bool uninterruptible;

  int _register = 0;
  int _phase = 0;

  /// 执行一个步骤； [counter] 是两个执行流共享的状态。
  void step(Counter counter) {
    if (uninterruptible) {
      counter.value = counter.value + 1; // 1. 读-改-写不可分割
      _phase = 1;
      return;
    }
    if (_phase == 0) {
      _register = counter.value; // 2. 读入本地寄存器
      _phase = 1;
      return;
    }
    counter.value = _register + 1; // 3. 用本地值写回
    _phase = 2;
  }
}
```

程序输出：

```text
不加保护：交错数=6，最终值集合=[1, 2]
划分临界区：交错数=2，最终值集合=[2]
```

6 种交错里有 2 种会丢失更新，其余 4 种正常；一旦把读-改-写合并为不可分割的一段，最终值恒为 2。这个最小实验同时回答了三个问题：竞态为什么难查、临界区到底保护什么、原子性在这里意味着什么。

竞态的危险来自程序语义对调度顺序的依赖，「某一步被打断」只是表象；临界区协议的价值是把「依赖交错」变成「与交错无关」。

## 同步、互斥与通信不是同一件事

三个词经常被混用，但各自回答不同的问题：

- 同步（synchronization）：约束多个执行流的先后关系，例如「数据准备好之后消费者才能取」。
- 互斥（mutual exclusion）：约束同一时刻的访问者数量，例如「同一时刻只有一个线程能写这个表」。
- 通信（communication）：在执行流之间传递信息，例如管道里的字节、消息队列里的一条消息。

前两者是「正确性约束」，通信是「信息通路」。真实系统里它们经常同时出现：管道既搬运字节，又通过阻塞唤醒间接表达先后；但**机制可以兼任，概念不能合并**，否则选型时会问错问题。看到「保护共享状态」应想到互斥，看到「等某个条件成立」应想到条件同步，看到「把结果交给另一个执行流」才想到通信。

讨论正确性时还要区分两类属性：

- 安全性（safety）：坏事永远不发生，例如「不会出现两个线程同时进入临界区」。
- 活性（liveness）：好事最终会发生，例如「每个线程最终都能进入临界区」。

互斥只保证前者。一个只保证互斥的协议完全可能让某个线程永远进不去——这就是饥饿（starvation），属于活性问题，需要公平策略或避免永久等待的机制来补齐。

互斥保证「不会同时进入」，不保证「最终有人能进入」；后者是活性，必须单独设计，死锁与饥饿都是活性被破坏的形态。

## 建立正确性的三个层次

### 原子性、可见性与顺序性

「加了锁就安全了」这句话背后的机制，可以拆成三个层次：

- 原子性（atomicity）：一个操作是否可能被观察到中间状态。`count++` 是「读-改-写」复合操作，天然不具备原子性；单条对齐的字长读写在某些硬件上可能不可撕裂，但这不是 C 内存模型对并发访问的保证，编译器优化和跨缓存行也可能改变结论。
- 可见性（visibility）：一个执行流的写入何时对另一个执行流可见。寄存器、写缓冲和缓存都可能导致「我写了，你还没看到」。
- 顺序性（ordering）：编译器可以在不改变单线程语义的前提下重排内存操作，CPU 也会用乱序执行和写缓冲隐藏延迟。「单线程看是对的」不代表「多线程看的顺序也一致」。

为了把三者统一成可推理的模型，语言和硬件共同约定了 happens-before 关系：如果操作 A happens-before 操作 B，那么 A 的结果对 B 可见，且顺序有保证。在具体语言或库明确规定同步语义时，锁的解锁与加锁、消息的发送与接收、原子操作的 release 与 acquire 会建立相应的 happens-before 边。临界区之所以有效，正是因为它把「同时互斥」和「前后可见」一起解决了。

### 谁在重排：三层不能混为一谈

「CPU 会乱序」是一句过于笼统的话。至少要分清三个层面：

1. 编译器重排：寄存器分配、公共子表达式消除等优化可能把访问移出循环、合并或提前。
2. CPU 与内存子系统重排：写缓冲、无效队列、弱内存模型允许没有依赖的访问以不同顺序被其他核观察到。
3. 运行时层：JIT、GC、语言运行时的优化同样可能改变访问时机。

同步原语的作用是给这三层同时加上约束；在 C/C++ 语境中，只针对其中一层（例如只加 `volatile`）无法得到跨线程的正确性保证。C/C++ 的 `volatile` 语义是「不要把这次访问当作普通可省略访问」，不是「建立 happens-before」，因此它不能替代同步原语；其他语言对 `volatile` 的定义可能不同。

锁解决的不只是「同时进入」；它还建立 happens-before，使临界区内的写入对下一个持锁者可见，并阻止编译器与 CPU 把访问重排到锁外。

> **面试高频：** 原子操作能否替代锁？
> **答题脉络：** 单个变量的读-改-写可以用原子操作 → 无锁算法依赖 CAS 与内存序 → 但多变量不变量、等待条件、复合协议无法靠单个原子操作表达 → 选错内存序还会得到「看起来对」的错误代码。
> **追问方向：** `relaxed` / `acquire` / `release` / `seq_cst` 的差异；CAS 循环与 ABA；无锁结构为什么不一定更快。

## 常见同步原语如何选择

选型前先问三个问题：要**保护一段状态**、要**等待一个条件**，还是要**传递数据**？对应到原语，就是下面几类。

### 互斥锁：所有权与互斥

互斥锁（mutex）是最直接的临界区协议：`lock` 成功即持有，`unlock` 释放，持有者有明确身份。它适合「一小段共享状态必须排他访问」的场景。POSIX 还定义了两种常见变体：错误检查型（同线程重复加锁返回 `EDEADLK`）和递归型（同线程可重复加锁，需相同次数解锁）；在 Linux 的默认普通 mutex 上，同线程重复加锁通常会阻塞，不能依赖它自动检测，具体行为仍应以 mutex 类型与平台文档为准。

两点容易被忽略：

- POSIX 不保证互斥锁的唤醒顺序公平。等待者中「谁先拿到锁」由调度策略决定，理论上某个线程可能长期抢不到。
- 持锁时间越短越好。锁竞争会把并行变成串行，持锁执行 I/O 或长计算会放大等待。

延伸机制只给入口，不展开：鲁棒互斥锁（robust mutex）让持有者异常终止后的下一个加锁者收到 `EOWNERDEAD`，并可调用 `pthread_mutex_consistent` 恢复一致性；实时场景常用优先级继承或优先级天花板协议缓解优先级反转，它们是否可用取决于平台对相应 POSIX 选项的支持。

### 条件变量：等待谓词，不是计数器

条件变量（condition variable）用来等待「某个谓词成立」。它必须与一个互斥锁配合：等待前持锁检查谓词，等待时原子地释放锁并睡眠，被唤醒后重新获取锁，再重新检查谓词。POSIX 明确规定虚假唤醒（spurious wakeup）可能发生，因此判断必须放在 `while` 循环里，而不是 `if` 里。

另一个关键区别：条件变量**不保存状态**。在没有等待者时调用 `signal` 不会留下「欠一次唤醒」的记录；真正的状态存放在共享变量里，条件变量只负责挂起与唤醒。`signal` 通常唤醒一个等待者，`broadcast` 唤醒全部——当一次状态变化可能满足多个等待者时用后者。POSIX 允许在未持锁时调用 `signal`/`broadcast`，但若修改谓词时不与等待者使用同一把锁，可能产生丢失唤醒；工程上的标准写法是在持锁时修改谓词并发出通知。

Linux man-pages 给了一个标准写法，可以直接作为模板：

```c
pthread_mutex_lock(&mut);
while (x <= y) {
    pthread_cond_wait(&cond, &mut);
}
/* 此时谓词成立，且持有 mut；操作共享状态 */
pthread_mutex_unlock(&mut);
```

### 信号量：许可计数，不是「更高级的锁」

信号量（semaphore）内部是一个非负计数器，`sem_wait` 把计数减一，计数为 0 时阻塞；`sem_post` 把计数加一，并唤醒等待者。它表达的是「还有几个可用许可」，而不是「谁拥有锁」：**互斥锁记录所有者，信号量不记录所有者**，一个执行流可以 `wait`，另一个执行流可以 `post`。这正是它适合表达「等待某个事件完成」和「限制并发数量」的原因。

历史上教材用 P/V 或 `down`/`up` 描述信号量操作，具体实现不应照抄「关中断」的伪代码；在 POSIX 上对应的是 `sem_wait`、`sem_post` 等函数。把信号量当二值锁使用时，它与互斥锁的差别集中在所有权语义、优先级继承支持和异步信号安全性上（`sem_post` 是 async-signal-safe 的，而 `pthread_mutex_lock` 不是）。

互斥锁记录「谁持有」，信号量记录「剩几个许可」，条件变量什么都不记录——它只在共享状态变化时挂起或唤醒调用者。

### 读写锁、原子操作与自旋锁

- 读写锁（read-write lock，rwlock）：允许多个读者同时持有读锁，写者独占。它的公平策略是实现相关的：POSIX 只在支持线程执行调度选项时规定了写者优先条件，否则「新读者能否越过已等待的写者」由实现决定。因此「读多写少一定更快」不成立，写者饥饿是常见风险。
- 原子操作（atomic）：对单个内存位置的读-改-写提供原子性，并可指定内存序。它适合计数器、标志位、无锁结构的构建块，但无法表达「多个变量组成的不变量」，也不提供等待谓词的能力。
- 自旋锁（spinlock）：拿不到锁时忙等而不是睡眠，适合**极短**临界区且能容忍短暂 CPU 空转的场景。在用户态，如果持锁者被抢占，自旋者会白白消耗整个时间片；重复加锁、未初始化使用都属于未定义行为。是否适合还要看核数与竞争强度。

| 原语 | 是否记录所有者 | 拿不到时的行为 | 典型职责 |
| --- | --- | --- | --- |
| 互斥锁 | 是 | 睡眠等待 | 保护临界区 |
| 信号量 | 否 | 睡眠等待 | 许可计数、事件与并发上限 |
| 条件变量 | 否（依附于锁） | 睡眠并释放锁 | 等待谓词成立 |
| 读写锁 | 区分读/写持有状态，不是单一所有者 | 睡眠等待 | 读多写少的共享访问 |
| 原子操作 | 不适用 | 不等待 | 单变量的无锁读改写 |
| 自旋锁 | 否（通常） | 忙等 | 极短内核式临界区 |

### Linux 的 futex：实现机制，不是接口（拓展）

Linux 上大量锁与等待机制共享同一套底层机制：futex（fast userspace mutex，快速用户态互斥锁）。它的要点是：

1. 无竞争时，加解锁在用户态用一次原子比较交换完成，不进入内核。
2. 只有可能要阻塞时，才通过 `futex` 系统调用进入内核，并带有「原子比较并阻塞」的语义——内核会先核对用户态字是否仍等于期望值，再决定阻塞。
3. futex 字是用户态可访问、按要求对齐的 32 位字；同一进程的线程可使用进程私有 futex，多进程同步则必须把它放在进程间共享的映射中，并使用共享 futex 操作。
4. 内核还提供优先级继承的 PI-futex 变体：futex 字存放持有者线程 ID，争用时置 `FUTEX_WAITERS` 位，内核用 RT-mutex 实现优先级继承。

需要强调：futex 是 Linux 特有的实现机制，POSIX 只规定互斥锁与条件变量的**语义**，不要求任何实现使用 futex；即使在同一台 Linux 上，「互斥锁借助 futex」也只是实现路径，不是可依赖的接口契约。

> **面试高频：** mutex 和信号量有什么区别？
> **答题脉络：** 记录内容不同（所有者 vs 许可计数）→ 使用模式不同（成对加解锁 vs 任意线程 wait/post）→ 能力不同（优先级继承、异步信号安全）→ 结论：二值信号量可以模拟互斥，但语义并不等价。
> **追问方向：** 计数信号量限流；事件通知；信号处理函数里能调用哪些函数；自旋锁与互斥锁的等待代价差异。

## 用有界缓冲区串起互斥与条件同步

生产者和消费者是同步问题里最值得写透的一个，因为它同时包含互斥（保护缓冲区）和条件同步（不满才能放、不空才能取）。先写不变量，再写代码：

1. `0 <= count <= N`：缓冲区元素个数始终在合法范围。
2. 元素只在缓冲区中存放一次：生产者放入的每个元素最终恰好被取出一次。
3. 判断「满」与「空」必须读取同一个受保护的 `count`。

### 正确版本：一个互斥锁，两个条件变量

下面抽取 `pc_cond.c` 中共享结构、不变量检查与读写函数的连续片段（省略 `#define`、线程函数与验证部分）：

```c
typedef struct {
  int slots[SLOTS];
  int head;   /* 下一个取出的位置，仅在持锁时访问 */
  int tail;   /* 下一个写入的位置，仅在持锁时访问 */
  int count;  /* 当前元素个数，仅在持锁时访问 */
  int done;   /* 生产者全部结束后置 1，仅在持锁时访问 */
  pthread_mutex_t mutex;
  pthread_cond_t not_empty; /* count > 0 或 done */
  pthread_cond_t not_full;  /* count < SLOTS */
} buffer_t;

static void die(const char *message) {
  fprintf(stderr, "失败：%s\n", message);
  exit(1);
}

/* 1. 只在持锁状态下调用，检查 0 <= count <= SLOTS。 */
static void check_invariant(const buffer_t *b) {
  if (b->count < 0 || b->count > SLOTS) die("缓冲区计数越过边界");
}

/* 2. 放入：先等“不满”，再写入；唤醒方向由条件变量表达。 */
static void buffer_put(buffer_t *b, int value) {
  pthread_mutex_lock(&b->mutex);
  while (b->count == SLOTS) pthread_cond_wait(&b->not_full, &b->mutex);
  b->slots[b->tail] = value;
  b->tail = (b->tail + 1) % SLOTS;
  b->count++;
  check_invariant(b);
  pthread_cond_signal(&b->not_empty);
  pthread_mutex_unlock(&b->mutex);
}

  /* 3. 取出：当 payload 不使用 -1 时，返回 -1 表示已结束且缓冲区为空。 */
static int buffer_get(buffer_t *b) {
  pthread_mutex_lock(&b->mutex);
  while (b->count == 0 && !b->done) pthread_cond_wait(&b->not_empty, &b->mutex);
  if (b->count == 0 && b->done) {
    pthread_mutex_unlock(&b->mutex);
    return -1;
  }
  const int value = b->slots[b->head];
  b->head = (b->head + 1) % SLOTS;
  b->count--;
  check_invariant(b);
  pthread_cond_signal(&b->not_full);
  pthread_mutex_unlock(&b->mutex);
  return value;
}
```

三个细节决定了正确性：等待前先持锁；`wait` 返回后重新检查 `while` 谓词；状态变化后向**相反方向**发信号（放入后通知「非空」，取出后通知「不满」）。完整文件另有 2 个生产者、2 个消费者搬运 600 个不同编号，并跨消费者验证「每个编号恰好被取出一次」；循环 50 轮的结果是：

```text
完成了 50 轮：生产 30000，消费 30000，编号无重复、无丢失
```

### 失败版本：把「等资源」放到「拿锁」之后

同样的有界缓冲区，换用三个信号量（`mutex` 保护缓冲区、`empty` 计数空位、`full` 计数元素）时，顺序错误会直接死锁：

```text
伪代码，不可直接编译；展示“先拿锁、再等资源”的错误顺序：

生产者: down(mutex); down(empty); ...放入...; up(full); up(mutex)
消费者: down(full);  down(mutex); ...取出...; up(empty); up(mutex)
```

假设缓冲区已满（`empty = 0`）：生产者先拿到 `mutex`，再执行 `down(empty)` 时发现没有空位，于是睡眠——但它没有释放 `mutex`；消费者虽然拿到了 `full` 许可，却在 `down(mutex)` 上永远等不到锁。双方各持一部分资源互相等待，缓冲区永远无法被消费，生产者也就永远等不到空位。

阻塞式等待不能在持锁状态下进行；「先拿锁、再等资源」是死锁的经典模板。等待资源前应先释放保护资源的锁，或者干脆让信号量的检查发生在加锁之前。

把等待顺序调整为「先 `down(empty)`，再 `down(mutex)`」即可避免；这也说明信号量版本的难点不在 API，而在**资源与锁的获取顺序**。

### 为什么必须用 while 重检

用 `if` 替换 `while` 会引入三类错误：

1. 虚假唤醒：等待可能在没有 `signal` 的情况下返回，谓词并未成立。
2. 状态被其他线程先消耗：线程被唤醒并重新拿到锁前，另一个线程可能先取走资源，谓词又变为假。
3. 信号不保证立即运行：多个等待者共享条件变量时，被唤醒的线程还要重新竞争互斥锁，拿到锁后仍必须确认谓词。

POSIX 对条件变量的要求写得很直接：每次等待都必须与一个涉及共享变量的布尔谓词关联，返回后必须重新求值。这也是面试里「条件变量为什么必须配 mutex、为什么必须 `while`」的权威依据。

> **面试高频：** 条件变量为什么必须和互斥锁配合，而且要在 `while` 里重检？
> **答题脉络：** 谓词读写需要和等待动作原子衔接 → `wait` 原子释放锁并挂起，返回时重新持锁 → 虚假唤醒与竞争使谓词可能再次不成立 → 因此只能循环重检。
> **追问方向：** `signal` 与 `broadcast` 的选择；无等待者时信号丢失；条件变量与信号量的语义差异。

## 经典问题真正考什么

### 哲学家进餐：把环拆开

五位哲学家围坐，每人需要同时拿起左右两把叉子才能进餐。如果所有人同时先拿左边，那么每个人都持有一把叉子并等待右手边的叉子，形成环：

```text
T0 持有叉 0，等待叉 1
T1 持有叉 1，等待叉 2
...
T4 持有叉 4，等待叉 0
```

哲学家问题的考点是识别「环形等待」，然后用**偏序**（固定获取顺序）、**同时获取**（要么两把都拿到，要么一把都不拿）或**限制并发**（例如最多只允许 4 人同时尝试）把它拆开，代码本身背下来没有意义。

### 读者—写者：策略与饥饿

读者—写者的约束是「读共享、写独占」，可选策略会决定谁可能被饿死：

- 读优先：只要还有活跃读者，新读者就能进入。持续有读者到达时，写者可能永远排不上队。
- 写优先 / 公平策略：写者排队后阻止新读者插队，用票号或队列保证有界等待。

下面的 Dart 程序把两种策略放在同一到达序列下对比：读者每片到达一名并占用 3 片。下面抽取 `idleTicks` 与 `fifoWriterWaitTicks` 两个函数（省略常量与统计部分）；读优先策略下，写者等不到「没有活跃读者」的时刻，换成 FIFO 票号后，写者的等待有上界。

```dart
/// 读优先策略：只要当前没有活跃读者，写者就能进入。
/// 返回 [window] 片内“活跃读者数为 0”的时间片编号。
List<int> idleTicks({required int window}) {
  final idle = <int>[];
  for (var tick = 0; tick < window; tick++) {
    // 1. 每个时间片都有新读者进入，并一直占用到 tick + readTicks。
    final activeReaders = <int>[
      for (var arrival = 0; arrival <= tick; arrival++)
        if (arrival + readTicks > tick) arrival,
    ];
    if (activeReaders.isEmpty) idle.add(tick);
  }
  return idle;
}

/// 写者在第 [writerArrival] 片到达，并且此后到达的读者必须排在它后面（FIFO 票号）。
/// 返回写者等待的时间片数。
int fifoWriterWaitTicks({required int writerArrival}) {
  // 2. 先到先服务：编号在写者之前的读者先全部结束。
  var lastReaderEnd = 0;
  for (var arrival = 0; arrival <= writerArrival; arrival++) {
    final end = arrival + readTicks;
    if (end > lastReaderEnd) lastReaderEnd = end;
  }
  // 3. 之后的读者排在写者后面，因此写者的等待时间有上界。
  return lastReaderEnd - writerArrival;
}
```

输出：

```text
读优先：200 片内“没有活跃读者”的时间片数=0
FIFO 票号：写者等待 3 片后进入
读者在第 10 片后停止到达：写者最早在第 13 片进入
```

最后一行说明：写者的等待之所以无限延长，是因为读者**持续到达**；一旦到达停止，读优先策略下的等待也是有界的。饥饿是「累计到达」造成的，不是单次等待本身。

> **面试高频：** 读写锁一定比互斥锁快吗？
> **答题脉络：** 收益来自读写并发 → 代价是读写切换、缓存一致性流量与写者饥饿 → 公平策略（写优先）又会削弱读并发 → 结论：要按读写比例与公平性需求评估，不能默认更快。
> **追问方向：** 读锁升级为写锁为什么容易死锁；读者—写者三种策略；rwlock 的实现差异。

## IPC 先按数据语义选型

进程间通信（inter-process communication，IPC）的选型问题，本质是三个问题：要传的是**字节流、结构化消息还是共享字节**？参与方是**同机还是跨机**？**同步责任在谁**？先建立这张对照表，再往下看机制：

| 机制 | 数据语义 | 关系范围 | 同步与唤醒 | 额外同步责任 |
| --- | --- | --- | --- | --- |
| 匿名管道 | 字节流，无消息边界 | 通过描述符继承的相关进程 | 读写阻塞，EOF 通知 | 应用自己定义消息边界 |
| 命名管道（FIFO） | 字节流，无消息边界 | 任意进程（按路径打开） | 读写阻塞 | 同上 |
| 消息队列 | 有边界的消息，可带优先级 | 同机任意进程 | 队列空/满阻塞、可异步通知 | 队列本身串行化，应用协议仍需自定 |
| 共享内存 | 共享字节区域 | 同机任意进程 | 不提供等待 | 必须另配同步机制 |
| 信号 | 事件通知，不承载一般数据 | 同机进程/线程 | 异步投递 | 只能做通知，数据要另走通路 |
| Unix 域套接字 | 字节流或消息，可传描述符/凭据 | 同机任意进程 | 读写阻塞 | 协议与边界由应用定义 |
| 网络套接字 | 字节流/数据报 | 跨主机 | 读写阻塞、超时 | 协议、重传、边界全靠应用 |

「共享内存最快」是一个需要加条件的说法：它省掉了内核对数据的复制，但引入了同步、生命周期管理和缓存一致性成本；小消息场景下，管道或本地套接字的端到端开销可能与之相当，甚至更低。

IPC 机制的差别首先在数据语义与同步责任——内核是否替你保留消息边界、是否提供阻塞唤醒、你是否必须自己建立 happens-before；「哪个最快」这种说法几乎没有信息量。

> **面试高频：** 共享内存已经是同一块物理内存，为什么还需要同步？
> **答题脉络：** 共享的是字节，不是顺序 → 一个进程的写入何时对另一个进程可见、多个写入的先后如何确定，都没有默认保证 → 需要信号量、互斥锁或原子操作建立 happens-before → 否则会读到撕裂的数据。
> **追问方向：** `mmap` 的 `MAP_SHARED` 语义；进程共享互斥锁的属性；管道与消息队列在「消息边界」上的差异。

## 管道、消息与共享内存的机制边界

### 管道与 FIFO

`pipe(2)` 返回两个文件描述符：一个读端、一个写端，数据是**单向字节流**，没有消息边界的概念。管道有几个值得记住的边界：

- 写入不超过 `PIPE_BUF` 长度时保证原子性（不会与其他写者的数据交错）；Linux 上 `PIPE_BUF` 为 4096 字节，POSIX 只要求至少 512 字节，因此跨系统代码不应写死。
- 所有写端关闭后，读端会读到文件结束（返回 0）；所有读端关闭后继续写会收到 `SIGPIPE`（忽略该信号时返回 `EPIPE`）。
- 匿名管道没有名字，只能通过描述符引用；`fork` 后子进程继承描述符，因此常见于有亲缘关系的进程。但「只能父子进程使用」是误解：**拿到描述符的进程都能读写**，描述符可以通过 Unix 域套接字传给无关进程。

FIFO（命名管道）在文件系统中有一个名字，任何进程都可以像打开文件一样打开它，因此不受描述符继承限制。在 Linux 上可以这样观察：

```bash
mkfifo /tmp/demo.fifo
ls -l /tmp/demo.fifo                      # 类型位为 p，表示 FIFO
(printf 'hello fifo\n' > /tmp/demo.fifo) & # 打开写端前，读端会阻塞
cat /tmp/demo.fifo                         # 输出 hello fifo
getconf PIPE_BUF /                         # 4096
```

### 消息队列与信号

POSIX 消息队列（`mq_open` / `mq_send` / `mq_receive`）保留消息边界，每条消息带优先级并按优先级出队，还支持 `mq_notify` 异步通知。它与 System V 消息队列是两套不同的 API。需要区分的是：**队列内部的操作由内核串行化**（不会两进程同时把一条消息放进同一个槽位），但「收到消息后如何更新应用状态」仍然需要自己定义协议——消息只是数据，不是同步语义。

信号（signal）适合做「发生了某件事」的通知，不适合承载一般数据：

- 标准信号不排队：同一信号在被阻塞期间多次到达，只会保留一个实例。
- 实时信号会排队，并且可以用 `sigqueue` 携带一个值。
- 信号处理函数只能调用 async-signal-safe 的函数。`sem_post` 在安全清单里，`printf`、`malloc`、`pthread_mutex_lock` 不在——在信号处理函数里调用它们可能死锁或破坏状态。

### 共享内存：共享的只是字节

POSIX 共享内存的典型流程是 `shm_open` 创建/打开对象、`ftruncate` 设置大小、`mmap` 映射到地址空间；Linux 上这些对象位于 `tmpfs` 文件系统（通常挂载在 `/dev/shm`）。映射本身的机制（地址空间、页表、写时复制）由 [虚拟内存、地址空间与函数调用](./04-虚拟内存、地址空间与函数调用.md) 讲解。手册的措辞值得原样记住：**访问共享内存对象的进程通常必须使用例如 POSIX 信号量之类的机制自行同步**。共享的只是字节，没有锁，也没有顺序。

### Unix 域套接字与网络套接字

Unix 域套接字（`AF_UNIX`）在同机进程间提供 `SOCK_STREAM`、`SOCK_DGRAM`、`SOCK_SEQPACKET` 三类接口，其中 `SOCK_SEQPACKET` 保留消息边界。它有两个网络套接字没有的能力：通过辅助数据传递打开的文件描述符（`SCM_RIGHTS`）和进程凭据（`SCM_CREDENTIALS`）；Linux 还支持与文件系统无关的抽象命名空间（Linux 扩展）。跨主机通信与 `select`/`poll`/`epoll` 的细节属于网络板块的 [Socket与I/O模型](../04-计算机网络/10-Socket与I-O模型.md)，本文只在选型图里出现它。

内核在 IPC 里只负责「搬运与排队」；数据边界、事件通知的真实含义、以及 happens-before 的建立，永远需要应用自己确认。

## 死锁、饥饿与活锁

三个词都在描述「不前进」，但结构完全不同。下面三条最小时间线可以区分它们。

死锁（deadlock）：两个执行流各持一把锁并互相等待，没有外力就永远无法推进。

```text
T0: 持有 L1，请求 L2
T1: 持有 L2，请求 L1
两个线程都阻塞，谁也不会释放
```

饥饿（starvation）：系统整体在前进，但某个执行流长期得不到资源。

```text
写者一直在排队
每次轮到它之前，都有新读者先获得读锁
系统持续处理请求，但写者的等待时间不收敛
```

活锁（livelock）：没有阻塞，执行流也在持续动作，但始终完不成任务。

```text
T0: 发现 T1 也要用，释放锁并重试
T1: 发现 T0 也要用，释放锁并重试
两者同步重试、同步碰撞，CPU 在消耗，任务没有进展
```

死锁要求存在「相互等待」的静态结构；饥饿是公平性问题，系统仍在推进；活锁是重试策略问题，执行流在运行但没有完成——三者的排查入口完全不同。

> **面试高频：** 死锁、饥饿、活锁怎么区分？
> **答题脉络：** 先看是否形成相互等待（死锁）→ 再看是个体长期得不到资源而系统仍在推进（饥饿）还是执行流持续动作却没有进展（活锁）→ 给出各自典型修复方向。
> **追问方向：** 公平锁的代价；重试加随机退避；检测到环是否等于已死锁。

## 死锁的四个必要条件

经典理论把「可能发生死锁」的前提归为四个条件（Coffman 条件）：

1. 互斥：资源要么已经被分配，要么可用，不能同时被多个执行流持有。
2. 占有且等待（hold and wait）：已经持有资源的执行流可以继续申请新资源。
3. 不可抢占（no preemption）：已分配的资源不能被强制收回，只能由持有者显式释放。
4. 循环等待（circular wait）：存在一条等待环，环上每个执行流都在等待下一个执行流持有的资源。

两个互斥锁反序加锁，正好逐一满足四条件：锁本身互斥；T0/T1 各持一把并继续申请；锁不能被强制拿走；等待边 `T0 -> L2 -> T1 -> L1 -> T0` 构成环。下面的 Dart 程序穷举两个线程的所有交错，搜索「没有任何线程能推进」的状态，并对比固定锁顺序的结果。下面抽取搜索核心 `Explorer.run`（省略辅助函数与线程计划）：

```dart
  void run(List<int> pcs) {
    final key =
        '${pcs.join('-')}|${[for (final l in _lockNames) _owners[l]].join(',')}';
    if (!_visited.add(key)) return;

    final runnable = <int>[
      for (var t = 0; t < plans.length; t++)
        if (pcs[t] < plans[t].length && !_blocked(pcs, t)) t,
    ];

    if (runnable.isEmpty) {
      // 1. 没有任何线程能推进：要么全部完成，要么就是死锁状态。
      if (!_allFinished(pcs)) deadlocks.add(_describe(pcs));
      return;
    }

    for (final t in runnable) {
      final action = plans[t][pcs[t]];
      final lock = action.substring(1);
      final previous = _owners[lock];
      _owners[lock] = action.startsWith('+') ? t : null; // 2. 施加这一步
      pcs[t] += 1;
      run(pcs);
      pcs[t] -= 1;
      _owners[lock] = previous; // 3. 回溯，换下一种交错
    }
  }
```

输出表明：反序加锁的状态空间中确实存在死锁状态，而「两个线程都按 L1 → L2 申请」的状态空间中不存在：

```text
反序加锁：搜索状态数=19
  死锁状态：T0 持有[L1] 等待[L2]；T1 持有[L2] 等待[L1]
全局锁序号：搜索状态数=14
通过：全局锁序号下不存在死锁状态
```

固定全局顺序之所以有效，是因为它把等待关系变成全序：所有线程都只能沿同一方向等待，等待图不可能出现环，第四条件被直接破坏。它也是工程上最实用的预防手段。

两个容易答错的细节：

- 四条件同时成立只是「可能死锁」的必要前提，不是「已经死锁」的判定。真正的判定要看资源分配图（或等待图）里有没有环。
- 环是否足够判定死锁，取决于每类资源的实例数：单实例资源时环即死锁；多实例资源时环只是必要条件，还要结合剩余资源能否让环外线程完成来判断。

四条件是「可能性」的必要条件集合；「是否已经死锁」要用等待关系图判断，且多实例场景下必须考虑可用资源。

> **面试高频：** 为什么固定锁顺序能防死锁？
> **答题脉络：** 死锁需要循环等待 → 给锁定义全序，所有线程按同一方向申请 → 等待边只能从低序号指向高序号 → 有向图无环 → 循环等待条件被破坏。
> **追问方向：** 动态获取的锁如何编号；`trylock` 失败后的退避；锁升级（读锁转写锁）为什么不在全序保护下。

## 处理死锁的四条路线

按「何时介入」可以把处理方式分成四类：预防（运行前破坏条件）、避免（运行时检查状态）、检测与恢复（放任发生后处理），以及不做全局处理、把规则交给应用的设计取舍。教材把最后一种称为鸵鸟策略（ostrich algorithm）：不试图消除死锁，而是接受「概率低、代价高」的现实；这只是一个设计取舍，不代表可以忽视锁顺序。

### 预防：破坏条件

逐一对应四个条件：

- 破坏互斥：把资源虚拟化，让多个执行流共享同一份逻辑资源（例如打印机的假脱机队列）。**并非所有资源都能这样改造**——大多数锁和数据结构的价值恰恰在于排他访问，无法「共享化」。
- 破坏占有且等待：要么一次性申请所需的全部资源，要么在申请新资源前释放已持有资源（两阶段锁的思路）。代价是资源利用率下降，而且很多场景无法提前知道需要哪些资源。
- 破坏不可抢占：只有能够保存与恢复状态的资源才行得通（例如 CPU 寄存器、可回滚的事务）。普通锁被强制释放后，持有者留下的中间状态无人能收拾。
- 破坏循环等待：给资源（锁）规定全局顺序，所有代码按同一顺序申请。这是实际工程中最常用、成本最低的一种。

### 避免：需要预知最大需求

避免策略在运行时检查每次分配是否会让系统进入不安全状态：需要对每个执行流声明「最大需求」，维护「已分配」「可用」向量，并在每次请求时判断是否存在安全序列。银行家算法是这一思路的经典代表。它的关键前提是**资源需求可预知、且系统有统一的分配中心**——这两点在应用级互斥锁上通常都不成立。

还要区分两个状态概念：

- 安全状态：存在一种调度顺序，让所有执行流按声明的最大需求依次完成。
- 不安全状态：找不到这样的顺序。它**不等于已经死锁**，只是存在死锁的可能，避免算法会拒绝把系统带入该状态。

### 检测与恢复

检测不阻止死锁，只在运行时寻找环：单实例资源用资源分配图（resource-allocation graph），多实例资源用类似银行家算法的可完成性扫描，找出无法完成的执行流集合。恢复的手段有三类：

- 终止全部或部分卷入死锁的执行流（简单粗暴，代价高，需处理回滚与幂等）。
- 抢占资源：选择牺牲者、保存现场，稍后回滚重试——要警惕同一执行流反复被选为牺牲者而产生饥饿。
- 回滚到检查点（checkpoint）：需要应用或系统提前保存一致状态。

### 工程缓解不能当作证明

预防靠结构约束（运行前破坏条件），避免靠预知需求（运行时判断安全状态），检测与恢复靠运行时开销换取可恢复性；选哪条路线取决于前提是否成立，跟哪种更「高级」无关。

日常开发里更常见的是局部缓解手段：`trylock` 失败后释放已持有资源并退避重试、给等待设置超时、运行期记录锁顺序违例。它们把「永久挂起」变成「可观测的失败」，但都没有证明系统不存在死锁：

- 超时只说明这一次等待太久，不能区分死锁、饥饿与单纯的慢。
- `trylock` 加随机退避能缓解活锁，但不能消除两个执行流每次都碰撞的可能。
- 真正的保证仍来自结构：统一的锁顺序、避免在持锁时调用外部代码、让等待条件可重检。

> **面试高频：** 预防、避免、检测与恢复有什么区别？
> **答题脉络：** 预防是运行前破坏四条件之一 → 避免是运行时用最大需求判断安全状态 → 检测是允许发生再找环 → 恢复是终止、抢占或回滚 → 工程中常用预防（锁顺序），避免受前提限制最大。
> **追问方向：** 银行家算法为什么需要预知需求；检测环的多实例细节；回滚与幂等。

## 银行家算法为何常见却少直接落地

银行家算法（Banker's algorithm）把资源分配问题类比成银行放贷：客户事先声明最大借款额（Max），银行家只有在「即使所有客户都借到上限，仍存在某种还款顺序让每个人都能周转」时才继续放款，这个状态称为安全状态。每次请求时，算法尝试找出一个安全序列，找得到就批准，找不到就拒绝。

一个单资源的最小例子：

```text
进程   已分配   最大需求   还需要
A       3        9         6
B       2        4         2
C       2        7         5
当前空闲 = 3
```

扫描一遍：A 还需要 6，超过空闲 3，暂时不行；B 还需要 2，可以完成 → B 归还 2，空闲变为 5；C 还需要 5，可以完成 → 空闲变为 7；A 还需要 6，可以完成。安全序列为 B、C、A，因此当前状态安全。

下面的 Dart 程序实现了这个「找安全序列」的扫描，并用教材死锁章的几组状态交叉验证。下面抽取 `safeSequence` 函数（省略回放验证与输出部分）：安全状态能找到序列，不安全状态找不到；把某个进程的声明上限调小，原本不安全的状态就会变得安全——因为**算法依赖声明本身**。

```dart
/// 寻找安全序列：每一步挑一个“还需要量不超过当前可用量”的进程，
/// 让它跑完并归还所持资源。返回空列表表示当前状态不安全。
List<String> safeSequence({
  required List<String> names,
  required List<List<int>> maximum,
  required List<List<int>> allocation,
  required List<int> available,
}) {
  final remaining = List<int>.of(available);
  final finished = List<bool>.filled(names.length, false);
  final order = <String>[];

  while (order.length < names.length) {
    var picked = -1;
    for (var i = 0; i < names.length; i++) {
      if (finished[i]) continue;
      final need = <int>[
        for (var r = 0; r < remaining.length; r++)
          maximum[i][r] - allocation[i][r],
      ];
      // 1. 只有“剩余需求”全部不超过当前可用量，这个进程才一定跑得完。
      if (_fits(need, remaining)) {
        picked = i;
        break;
      }
    }
    if (picked == -1) return const [];
    finished[picked] = true;
    for (var r = 0; r < remaining.length; r++) {
      remaining[r] += allocation[picked][r]; // 2. 完成后归还持有的资源
    }
    order.add(names[picked]);
  }
  return order;
}
```

```text

图 6-11(c)：安全序列=[]（空表示不安全）
图 6-11(c) 且把 B 的上限改为 3：安全序列=[B, C, A, D]
```

为什么它常见却少直接落地？问题都出在前提上：

1. 需要每个执行流事先声明最大资源需求。应用通常无法可靠知道「我最多会持有几把锁、多少内存」。
2. 需要一个全局分配中心来串行化所有请求与安全状态检查；用户态锁各自为政，没有这样的权威。
3. 检查有开销，而且安全是「一定不会死锁」的充分条件、不是必要条件：为保证安全，算法会拒绝一些实际上不会死锁的请求，牺牲利用率。
4. 不安全不等于死锁：算法只是拒绝进入不安全状态，不能说明当前系统已经死锁。

因此银行家算法更像一个教学模型和「准入控制」思想的原型：它示范了「用预知的需求换取提前拒绝」这一取舍，而不是通用应用锁的日常方案。

安全状态的含义是「按声明的最大需求一定存在完成顺序」；不安全状态只是失去保证，不等于已死锁——输入声明的准确性就是算法的命门。

## 实战排查卡住的线程

### 先看现象，再选工具

- 进程几乎不消耗 CPU、所有线程不推进：典型是互斥等待或条件变量等待，应查等待环。
- CPU 持续打满但任务不完成：优先怀疑活锁或自旋等待。
- 部分请求正常、个别任务长期不返回：优先怀疑饥饿与公平性。

`ps -L -o pid,tid,psr,stat,comm -p <pid>` 是只读的第一步观察（线程状态与所在 CPU）；更完整的进程排查命令见 [Linux 命令行与进程排查](../07-工程工具与代码质量/01-Linux命令行与进程排查.md)。

### gdb：看线程停在哪里等

```bash
gdb -p <pid> -batch -ex "info threads" -ex "thread apply all bt"
```

`-p` 附加到进程、`-batch` 执行完自动退出；`thread apply all` 对全部线程执行命令，`bt` 打印调用栈；进入交互式 gdb 后也可以执行 `taas bt`（`taas` 是 `thread apply all -s` 的简写，`-s` 表示静默忽略命令产生的报错与空输出）。权限方面需要注意：

- 附加调试器需要同用户或相应权限；若目标机器启用了 Yama，`ptrace_scope=1` 时只能追踪自己的后代进程或被声明的调试者，是否启用与当前值以 `/proc/sys/kernel/yama/ptrace_scope` 为准。
- 生产环境附加会暂停进程，应使用只读命令并尽快退出；容器里还要考虑 `CAP_SYS_PTRACE`。

读栈时关注等待点：`pthread_cond_wait`、`sem_wait`、`read`/`recv`、`__futex_abstimed_wait_*` 一类帧表示线程正在等；但**调用栈不包含「谁持有锁」的信息**，看到两个线程都停在等待点上，仍要结合锁实现与代码路径才能拼出等待环。不同 glibc 版本帧名不同，关键是把等待点与持有点对应到源码，而不是记某个具体符号。

### strace：看系统调用层面的等待

```bash
strace -f -p <pid>                       # -f 跟随线程；输出很大，建议重定向
strace -f -p <pid> -e trace=futex,read   # 只保留关心的系统调用
```

`strace` 通过 ptrace 工作，权限要求与 gdb 类似；它能显示线程在哪个 futex 地址上等待、在哪个 `read` 上阻塞，这些地址与调用点是定位环路的重要线索。它同样不是证明：输出只说明「此刻停在哪」，不能替代对锁顺序规则的分析。

### 工具与锁顺序审计

把检测工具放进构建或测试流程，比事后附加调试器更划算：

- ThreadSanitizer（TSan）：`-fsanitize=thread` 编译后主要用于检测数据竞争；锁顺序反转/死锁检测是否可用、是否默认开启取决于具体运行时与工具版本，不能把一次无报告当成没有死锁。支持该能力的运行时可能报告如下潜在环：

```text
WARNING: ThreadSanitizer: lock-order-inversion (potential deadlock)
  Cycle in lock order graph: M0 => M1 => M0
  Mutex M1 acquired here while holding mutex M0 in thread T1
  Mutex M0 acquired here while holding mutex M1 in thread T2
SUMMARY: ThreadSanitizer: lock-order-inversion (potential deadlock)
```

- Valgrind 的 Helgrind 工具检测不一致的加锁顺序与数据竞争。
- 内核代码使用 lockdep 在运行时校验锁的使用与依赖关系。

工具之外还要做锁顺序审计：列出每段代码路径上「已持有哪些锁、还要申请哪些锁」，把成对出现的顺序与全局规则比对；重点检查回调（持锁时调用外部代码可能重新进入）、锁升级（读转写）、动态锁（按对象地址排序或使用 `trylock`）。复现时尽量构造最小程序（两个线程、两把锁、固定交错），不要依赖重启服务「碰运气」。TSan 报告的是「潜在」，一次 backtrace 也只是快照；只有把等待点、持有点和顺序规则三样拼起来，才能确认并修复环路。

工具报告的是可能性，backtrace 只说明线程停在哪里；定位死锁必须把等待点、锁的持有者关系和代码中的加锁顺序合在一起分析。

## 常见误区与面试答题框架

### 常见误区

- ❌ 信号量就是互斥锁。✅ 二值信号量能提供互斥，但不记录所有者，也没有互斥锁的所有权相关能力（如优先级继承协议）；反过来，信号量能表达许可计数与事件，互斥锁不能。
- ❌ 条件变量有等待者，`signal` 之后它就立刻运行。✅ 唤醒只是把线程移到可运行队列，它还要重新获取互斥锁，何时真正运行由调度器决定。
- ❌ 共享内存不需要同步。✅ 共享的是字节；可见性与顺序仍需别的机制建立 happens-before。
- ❌ 检测到等待环就一定已经死锁。✅ 单实例资源时环即死锁；多实例资源时环只是必要条件，还要看可用资源。
- ❌ 操作系统会替应用消除所有锁死锁。✅ 操作系统提供同步原语与调试手段（例如内核自身的 lockdep），但应用级锁的顺序与使用规则由应用负责。
- ❌ `volatile` 可以当同步原语。✅ 它约束编译器优化该次访问，不建立跨线程顺序。
- ❌ 加超时就能解决死锁。✅ 超时只是把永久等待变成可观测失败，恢复仍需重试协议或消除环路。

### 答题框架

被问到并发问题时，按「共享状态 → 交错窗口 → 协议」三步展开：先指出哪些数据被多个执行流访问、不变量是什么；再指出哪段代码可能被打断；最后说明用什么机制保护、等待条件如何重检。被问到选型时，按「保护状态 / 等待事件 / 传递数据」对应互斥锁、条件变量或信号量、IPC 机制。被问到死锁时，先用四条件定位可能的环，再在预防、避免、检测恢复中选一条与场景匹配的路线，并说明工具的结论只是线索。

## 小结

并发正确性来自明确的协议：用锁与条件变量保护不变量、依据数据语义选择 IPC 并承担相应同步责任，再用统一的锁顺序与检测工具把死锁限制在可排查、可恢复的范围内。
