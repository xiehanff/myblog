# 虚拟内存、地址空间与函数调用

打印一个局部变量的地址，多次运行会发现它每次都不一样；`malloc` 了 256 MiB 再 `free`，进程占用的物理内存却迟迟不降；忘写递归终止条件，程序几秒后以 Segmentation Fault 退出，而机器上还有几十 GB 空闲内存。这三个现象都无法用"内存就是一个很大的数组"来解释。

更常见的问题是知识割裂：多数人知道"局部变量在栈上、`malloc` 在堆上"，也背过分页、页表、TLB，却没法从一个指针出发，讲清它属于哪个映射、有没有页表项、对应的物理页是否驻留。于是栈溢出、野指针、内存泄漏、进程隔离只能靠零散口诀应付。

本文按"一个指针的四层问题 → 地址空间与真实观测 → 栈与调用约定 → 堆与分配器 → 页表、TLB 与缺页 → 置换与大页 → 排查"推进。ELF 如何生成、链接与装载见《[程序从源码到运行](./06-程序从源码到运行.md)》，进程与线程生命周期见《[进程、线程与调度](./02-进程、线程与调度.md)》。

## 从一个指针建立完整问题链

写下 `int count = 10;` 时，程序同时牵扯四层互不相同的问题：

- **对象层**：这个地址上此刻存在有效对象吗？它的类型、长度和生命周期允许访问吗？
- **区域层**：这个地址落在地址空间的哪个映射里？权限是读、写还是可执行，私有还是共享？
- **映射层**：这个虚拟页在页表里有没有对应项？若地址落在合法 VMA 内而页表项尚未建立，访问可能触发缺页并由内核补建；未映射地址则通常直接失败。
- **驻留层**：对应的物理页帧当前在内存中吗？不在就要通过缺页处理换入。

层级之间没有固定的对应关系。同一个函数里的两个局部变量，可能一个只存在于寄存器、一个在栈上；两块相邻的虚拟地址可能对应毫不相干的物理页；一块 `malloc` 得到的内存可能在 `brk` 主堆里，也可能是一段独立的匿名映射。后面的每一节，都在补其中一层。

> **关键认知：** 指针的值只是某个进程地址空间中的虚拟地址，不携带物理位置、长度和生命周期信息；判断一个指针能不能用，依据是对象与所有权规则，而不是地址数值。

## 进程地址空间的全景

### 地址空间是一组映射，不是一根尺子

内核为每个进程维护一张"允许访问的虚拟地址范围"清单，每个范围记录起止位置与权限，称为虚拟内存区域（Virtual Memory Area，VMA）。地址空间的编辑动作只有几个：`mmap` 建立映射、`munmap` 撤销、`mprotect` 改权限、`brk` 推进主堆边界。

下面是从真实进程 `/proc/<pid>/maps` 归纳出的文本图（不含固定地址，按低地址到高地址排列）：

```text
低地址
┌────────────────────────────────────────────┐
│ 可执行文件映射：ELF 头/只读数据 r--p         │
│ 可执行文件映射：机器指令        r-xp         │
│ 可执行文件映射：只读数据        r--p         │
│ 可执行文件映射：已初始化数据    rw-p         │
├────────────────────────────────────────────┤
│ 匿名映射：BSS 续接区、分配器 arena、[heap]   │
├────────────────────────────────────────────┤
│ mmap 区：共享库（libc、ld.so 各拆成多段）、   │
│   大块 malloc、文件映射、其他线程的栈         │
├────────────────────────────────────────────┤
│ [stack]：主线程栈                rw-p        │
│ [vvar] / [vdso]：内核提供的只读页  r--p/r-xp │
├────────────────────────────────────────────┤
│ 内核部分：用户态不可访问（高半区保留）         │
└────────────────────────────────────────────┘
高地址
```

三点必须记住：**它是映射集合而不是一段可以随便读写的连续内存**（映射之间的空洞是未映射区域，访问它同样出错，不会"读到随机数据"）；**权限按页设置**（代码页可执行不可写，数据页可写通常不可执行）；**堆和栈的方向只是实现习惯**（主堆向上、主线程栈向下是常见实现，不是标准保证）。

地址空间里除了可执行文件映射，还有大量匿名页（无对应文件，内容为零或由程序写入）与文件映射（内容来自磁盘文件，可被多个进程共享）。虚拟内存的价值就来自这些映射的组合：独立页表带来的隔离、物理页可以分散却对外呈现连续、先给地址后给物理页的按需分配、以及按页设置的权限与共享。

> **关键认知：** 两个进程打印出相同的虚拟地址，并不意味着它们指向同一块物理内存；虚拟地址只在所属进程的页表里才有意义。

> **面试高频：** 虚拟内存到底解决了什么问题？
> **答题脉络：** 隔离（各自页表，指针不能越进程）→ 连续视图（物理可分散）→ 按需分配（先给地址，写入才给物理页）→ 权限与共享（按页设 rwx，只读页可多进程共享）→ 顺带解释"为什么 `malloc` 大块内存不会立刻占用等量物理内存"。
> **追问方向：** 32 位与 64 位地址空间大小、共享映射、写时复制、匿名页与交换分区的关系。

### ASLR 与 PIE：地址为什么每次都在变

地址既已是虚拟的，内核就有余地把映射基址随机化，这就是地址空间布局随机化（Address Space Layout Randomization，ASLR），它让栈、堆、共享库的位置每次运行都不同。ASLR 只随机化装载位置，不改变程序内部的相对偏移；若可执行文件本体仍固定在同一个基址，攻击面依旧存在。位置无关可执行文件（Position-Independent Executable，PIE）让程序本体也像共享库一样装载到随机基址，代价是要靠相对寻址访问自身代码与数据。

> **时效信息（核查日期：2026-09）：** 在 Ubuntu 22.04.5 + gcc 11.4.0 上，默认编译产物类型为 `DYN`（PIE），加 `-no-pie` 后变为 `EXEC`，可用 `readelf -h` 查看；本机 `/proc/sys/kernel/randomize_va_space` 为 `2`。这是示例环境的默认值，不是所有发行版与工具链的通则。

## 用一个 C 进程观察真实映射

概念再多，不如直接看内核公布的事实。下面的程序让局部变量、已初始化/零初始化全局变量、小块与大块分配同时存在，打印地址后挂起进程：

```c
/* 进程地址空间观察：打印各类对象的地址后挂起，便于用 pmap 与 /proc/<pid>/maps 观察。
 * 编译：gcc -std=c17 -O0 -g address_space.c -o address_space
 * 运行：./address_space（需要 Linux 的 /proc 与 procps 工具）
 */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int initialized_value = 42; /* 已初始化全局变量：通常落在可写数据区 */
int zero_initialized;       /* 零初始化全局变量：通常落在 BSS */

int main(void) {
    int local = 7;                       /* 自动存储期：位于本线程栈 */
    char *small = malloc(4096);          /* 1. 小分配：通常从主堆切分 */
    char *big = malloc(8 * 1024 * 1024); /* 2. 大分配：可能落在一段独立匿名映射 */
    if (small == NULL || big == NULL) return 1;

    printf("pid=%d local=%p small=%p big=%p\n", (int)getpid(), (void *)&local, (void *)small,
           (void *)big);
    printf("initialized_value=%p zero_initialized=%p\n", (void *)&initialized_value,
           (void *)&zero_initialized);

    for (;;) sleep(1); /* 3. 挂住进程，便于在另一个终端观察映射 */
}
```

三件事比背布局图有用：**同一个文件被拆成多条映射**（`libc.so.6` 在本段输出中被截取为 `r--p`、`r-xp`、`---p` 三条，完整输出还包括可写的 `rw-p` 数据段与不可访问的填充页）；**伪路径由内核标注**（`[heap]` 是主堆，`[stack]` 是主线程栈，`[vdso]` 是内核提供的虚拟动态共享对象，而其他线程的栈只是普通匿名映射）；**`nm` 的符号地址与运行时地址对不上是正常的**（`nm` 给链接时地址，PIE 程序还要加随机装载基址）。

> **关键认知：** `/proc/<pid>/maps` 列出的是“已建立的映射”，RSS 反映的是“已驻留的页”，两者不能互相推断：映射了几百 MiB 而一个物理页都没驻留，是完全正常的状态。

> **时效信息（核查日期：2026-09）：** 上述输出取自 Ubuntu 22.04.5（WSL1，内核 4.4.0-Microsoft）+ gcc 11.4.0 的一次运行。该内核实现在本次核查时未提供 `/proc/<pid>/smaps_rollup`，`pmap -x` 因此只能列出映射而没有 RSS 列；字段定义本身来自内核文档与 man-pages，不代表所有内核都提供同样的文件。

## 栈与函数调用：生命周期先于布局

栈是"自动存储期"的实现方式：对象随函数进入而创建、随返回而失效，存放位置由编译器和调用约定共同决定。先把调用链写全：

```c
/* 调用链示例：main → calculate → add，用于观察栈帧的嵌套。
 * 编译：gcc -std=c17 -Wall -Wextra -O0 -fno-omit-frame-pointer call_chain.c -o call_chain
 * 运行：./call_chain，预期退出码 0。
 */
#include <stdio.h>

int add(int left, int right) {
    int result = left + right; /* 1. add 的局部数据属于本次调用的栈帧 */
    return result;             /* 2. 返回后，result 的生命周期结束 */
}

int calculate(int base) {
    int value = add(base, 3); /* 3. calculate 暂停在调用点，等待 add 返回 */
    return value * 10;        /* 4. calculate 继续执行 */
}

int main(void) {
    int answer = calculate(2); /* 5. main 调用 calculate */
    printf("answer=%d\n", answer);
    return answer == 50 ? 0 : 1;
}
```

<!-- verify: .work/verify/B04/c/call_chain.c -->

执行到 `add` 内部时，线程的调用栈自上而下依次是 `main`、`calculate`、`add` 的栈帧，栈指针指向最上面那一帧。一次普通调用可以拆成四步：调用者把参数放到约定位置，执行 `call`；`call` 把返回地址压栈并跳转；被调用者建立栈帧、腾出局部变量空间、必要时保存调用者寄存器；返回时结果放进约定寄存器，`ret` 弹出返回地址，调用者继续执行。

`-O0 -fno-omit-frame-pointer` 下 `add` 的序言与尾声最能说明问题（`objdump -d` 截取）：

```text
114d: push   %rbp             ; 保存调用者的帧指针
114e: mov    %rsp,%rbp        ; rbp 指向本帧底部，作为定位局部变量的参照
1151: mov    %edi,-0x14(%rbp) ; 第 1 个参数从寄存器写入本帧
1154: mov    %esi,-0x18(%rbp) ; 第 2 个参数也留在本帧内
115f: mov    %eax,-0x4(%rbp)  ; result 存进局部变量槽位
1162: mov    -0x4(%rbp),%eax  ; 返回值放进 eax
1165: pop    %rbp             ; 恢复调用者的帧指针
1166: ret                    ; 弹出返回地址，回到调用者
```

这段汇编里没有一条指令显式保存"结束后回到哪里"：返回地址是 `call` 由硬件自动压栈、`ret` 自动弹出的，程序员从未写它。这正是缓冲区溢出能劫持控制流的原因——把超长输入写进栈上数组时，越界部分可能覆盖保存的返回地址，函数返回时就跳到被改写的位置。

> **关键认知：** 返回地址不是程序员保存的数据，而是 `call` 与 `ret` 隐含使用的栈内容；任何越过数组边界的写都可能改写函数返回后的执行路径。

### 为什么不能返回局部变量的地址

```c
/* 反例：返回局部变量的地址。
 * 编译：gcc -std=c17 -Wall -Wextra -O0 local_address.c -o local_address
 * 预期：编译器给出返回局部变量地址的警告；
 *       运行时该地址指向的存储已失效，读取结果是未定义行为。
 */
#include <stdio.h>

int *wrong_number(void) {
    int value = 42; /* 1. value 位于本次调用的栈帧中 */
    return &value;  /* 2. 函数返回后，该地址不再指向有效对象 */
}

int main(void) {
    int *pointer = wrong_number();
    printf("pointer=%p（内容读取为未定义行为）\n", (void *)pointer);
    return 0;
}
```

<!-- verify: .work/verify/B04/c/local_address.c -->

编译器能发现问题：`warning: function returns address of local variable [-Wreturn-local-addr]`。运行期则是未定义行为：本次核查中它恰好打印 `(nil)`，但这不是可依赖的结果，优化等级与调用者的后续栈使用都会改变实际内容。正确做法通常是让调用者提供输出空间、把对象放到生命周期由调用者管理的堆上，或使用静态存储期对象（但要注意共享状态与线程安全）。

> **面试高频：** 为什么不能返回局部变量的地址？
> **答题脉络：** 局部量属于自动存储期 → 函数返回时其存储随之失效 → 返回的是悬垂地址 → 解引用属未定义行为 → 给出两种替代（调用者传入缓冲区、堆上分配并明确谁释放）。
> **追问方向：** 按值返回结构体为什么安全、返回字符串字面量地址为什么可以、`free` 后置 `NULL` 能否解决别名指针。

## x86-64 ABI 下参数到底放在哪里

"参数都压在栈上"是 32 位 x86 时代的印象。x86-64 通用寄存器增加到 16 个，两大主流约定都改成寄存器优先、栈兜底。System V AMD64 应用二进制接口（Application Binary Interface，ABI）规定：整数（INTEGER 类）参数按从左到右使用 `%rdi`、`%rsi`、`%rdx`、`%rcx`、`%r8`、`%r9`，浮点（SSE 类）参数使用 `%xmm0`–`%xmm7`，放不下的按从右到左压栈；整数返回值放在 `%rax`（必要时 `%rax:%rdx`），浮点返回值放在 `%xmm0`；`call` 执行前栈指针必须 16 字节对齐。

```c
/* 参数传递观察：整数参数超过 6 个后，多余参数改走栈。
 * 编译：gcc -std=c17 -O0 -fno-omit-frame-pointer -S many_args.c
 * 运行：gcc -std=c17 -O0 many_args.c -o many_args && ./many_args
 */
#include <stdio.h>

int sum7(int a1, int a2, int a3, int a4, int a5, int a6, int a7) {
    return a1 + a2 + a3 + a4 + a5 + a6 + a7; /* 第 7 个参数来自栈 */
}

int uneven(int left, int right) {
    return left - right; /* 两个 int 只占 8 字节，展示调用前的对齐填充 */
}

int main(void) {
    printf("sum7=%d uneven=%d\n", sum7(1, 2, 3, 4, 5, 6, 7), uneven(10, 4));
    return 0;
}
```

```text
11be: mov  $0x6,%r9d        ; 第 6 个参数 → r9
11c4: mov  $0x5,%r8d        ; 第 5 个参数 → r8
11ca: mov  $0x4,%ecx        ; 第 4 个参数 → rcx
11cf: mov  $0x3,%edx        ; 第 3 个参数 → rdx

11d9: mov  $0x1,%edi        ; 第 1 个参数 → rdi
11de: call 1149 <sum7>
```

这段反汇编顺带解释三件常被追问的事：**整数与浮点是两条独立计数线**（`f(int a, double b, int c)` 中 `a`、`c` 用 `%rdi`、`%rsi`，`b` 用 `%xmm0`，互不挤占）；**栈对齐会产生"看似多余"的指令**（`main` 序言里的 `sub $0x8,%rsp` 是为满足调用前 16 字节对齐，`push %rbx` 是在保存被调用者必须保持不变的寄存器，即 `%rbx`、`%rbp`、`%r12`–`%r15`）；**可变参数的位置只有编译器能算**（System V 下浮点可变参数只入向量寄存器，实际用到的向量寄存器数由 `%al` 携带（0–8）；Microsoft x64 则要求浮点参数镜像到整数寄存器。两种 ABI 都必须走 `<stdarg.h>`，不能按偏移手工取参）。

Windows 的 Microsoft x64 是另一套约定：整数参数用 `rcx`、`rdx`、`r8`、`r9` 四个寄存器，浮点用 `xmm0`–`xmm3`，第 5 个起入栈；无论参数多少，调用者必须在栈上预留 32 字节影子空间供被调用者按需把寄存器参数写回内存。

| 对比点 | System V AMD64 | Microsoft x64 |
|---|---|---|
| 使用平台 | Linux、macOS 等 | Windows |
| 整型/指针参数寄存器 | rdi、rsi、rdx、rcx、r8、r9（6 个） | rcx、rdx、r8、r9（4 个） |
| 浮点参数寄存器 | xmm0–xmm7 | xmm0–xmm3 |
| 装不下的参数 | 从右到左压栈 | 从右到左压栈 |
| 额外栈开销 | 无强制要求 | 32 字节影子空间 |

同样 7 个整型参数，在 Linux 上只有第 7 个上栈，在 Windows 上第 5–7 个都要上栈。跨平台代码不要假设"第 N 个参数在栈上的某个偏移处"，函数指针类型不匹配、手工声明外部函数都会在这些差异上出错。

> **关键认知：** 调用约定是同一平台上编译器、运行库与内核共同遵守的接口合同，规定参数位置、返回位置、栈对齐与哪些寄存器必须保持不变；它由 ABI 规定，不是 CPU 强制执行。

> **面试高频：** 为什么 x86-64 把参数放进寄存器？可变参数为什么不能手工取参？
> **答题脉络：** 寄存器变多（6 个整型 + 8 个浮点）→ 普通调用几乎不访问内存 → 超出部分仍走栈 → 整数与浮点独立计数 → 可变参数与未原型函数的位置只有编译器按 ABI 算得准，故必须用 `<stdarg.h>`。
> **追问方向：** 结构体按值传参退化为隐藏指针、影子空间、16 字节对齐、被调用者保存寄存器。

> **时效信息（核查日期：2026-09）：** 参数寄存器顺序、16 字节对齐与返回值位置来自 x86-64 psABI 项目的约定章节；Microsoft x64 的 4 寄存器 + 32 字节影子空间来自 Microsoft Learn 当前页面；反汇编输出取自 Ubuntu 22.04.5 + gcc 11.4.0。

## 优化为何会让栈帧消失

同一个 `call_chain.c` 用 `-O2` 编译后，栈帧模型立刻崩塌（`gcc -O2 -S` 截取）：

```text
add:                              ; 参数直接算，没有 push rbp，也没有局部变量
        leal	(%rdi,%rsi), %eax
        ret
calculate:
        leal	15(%rdi,%rdi,4), %eax ; 加 3 再乘 10 被合并成一条 lea
        addl	%eax, %eax
        ret
main:
        subq	$8, %rsp              ; 仅用于保持调用前 16 字节对齐
        call	__printf_chk@PLT
```

改变栈帧形状的原因有四类：**内联**（小函数被展开到调用点，调用、返回与栈帧一起消失）、**寄存器分配**（不需要取地址的局部变量可以只活在寄存器里）、**帧指针省略**（`-fomit-frame-pointer` 在多数平台已是默认，`%rbp` 被释放出来当通用寄存器，栈帧不再串成链）、**尾调用与栈重用**（尾部调用可复用返回地址，不再增长栈）。

调试器能画出调用栈并不只靠 `%rbp` 链：编译器会生成 `.eh_frame`、`.cfi_*` 之类的展开信息，`-O2` 汇编里每条函数后的 `.cfi_def_cfa_offset` 就是它的一部分。反过来说，`-O0 -fno-omit-frame-pointer` 既保住调试视图，也是性能剖析时保留完整调用链的常用构建方式。

> **关键认知：** "局部变量在栈上""每次调用都有固定形状的栈帧"只是未优化构建下的常见实现模型，不是语言或 ABI 的保证；依赖某个局部量"恰好"挨着另一个局部量（例如靠越界访问改到它）的结果会随优化等级变化。

## 栈溢出、保护页与栈保护不是一回事

线程栈是虚拟地址空间里一段有限区域，上限来自资源限制而非硬件：

- **`RLIMIT_STACK` 决定主线程栈上限**：`getrlimit(2)` 说明"这是进程栈的最大长度，达到上限时产生 SIGSEGV"，要处理该信号必须先准备备用信号栈。
- **子线程默认栈大小取自 `RLIMIT_STACK`**：`pthread_create(3)` 说明软限制不是 `unlimited` 时由它决定，为 `unlimited` 时按架构固定（多数架构 2 MiB，POWER 与 Sparc-64 为 4 MiB）。
- **栈保护区域默认一页**：`pthread_attr_setguardsize(3)` 说明默认保护大小为系统页大小，溢出到保护区域时"在多数硬件架构上收到 SIGSEGV"。
- **只有主线程的栈能动态增长**：`pthread_attr_setstacksize(3)` 明确写出这一点。

```c
/* 栈耗尽：无限递归加一个较大的局部数组，很快越过线程栈的合法边界。
 * 编译：gcc -std=c17 -O0 stack_overflow.c -o stack_overflow
 * 运行：./stack_overflow；在 Linux 上以 SIGSEGV 结束（退出码 139），属预期现象。
 */
#include <stdio.h>

static int depth;

static void dive(void) {
    int pad[4096];  /* 1. 每层递归约占用 16 KiB 栈空间 */
    pad[0] = depth; /* 2. 首次写入触发物理页按需分配 */
    depth = pad[0] + 1;
    dive(); /* 3. 没有终止条件，栈帧不断向低地址推进 */
}

int main(void) {
    dive();
    printf("depth=%d\n", depth); /* 正常情况下不会执行到这里 */
    return 0;
}
```

本次核查环境（Ubuntu 22.04.5，`ulimit -s` = 8192 KiB）运行该程序，退出码为 139（128 + SIGSEGV）：它撞上的不是整机内存不足，而是自己那条线程的栈边界。其他运行时的报告方式不同：同样的无限递归在 Dart 里会抛出可捕获的 `StackOverflowError`，本次核查中约三万余层后抛出。

本次运行输出 `捕获到 StackOverflowError，失败前的递归深度为 34207`。深度值不稳定，可依赖的结论只有一条：栈被耗尽。

> **关键认知：** "栈有上限"是所有运行时的共同事实，区别在于超限如何报告——Dart 运行时把它变成可捕获的 `StackOverflowError`，C 进程通常直接收到 SIGSEGV；而栈溢出可以在机器有大量空闲内存时发生，它和"内存不足"是两个问题。

保护页只在"越过边界的第一步仍落在它上面"时才生效。如果一次巨大的栈分配直接跳过保护页、落到相邻映射上，就不会触发任何保护——这正是 2017 年公开的 Stack Clash 类问题。GCC 的 `-fstack-clash-protection` 会在一次超过一页的栈分配中插入逐页探测，让"跳过保护页"变成"立刻在保护页上失败"：

```text
;; 默认（本机 gcc 已开启该选项）：sub $0x1000,%rsp 后立刻触写该页，循环推进
11c0: orq $0x0,(%rsp)        ; 触碰该页，使越过保护页的访问变成受控的 SIGSEGV
;; -fno-stack-clash-protection：一次性把 64 KiB 栈帧推完，中间页没有被触碰
11b1: sub $0x10020,%rsp
```

栈相关的名词职责不同，混在一起会得到错误结论：

| 名称 | 应对的问题 | 失效条件 |
|---|---|---|
| 栈上限（`RLIMIT_STACK`） | 单线程栈用超配额 | 与整机内存无关，超限即 SIGSEGV |
| 保护页（guard page） | 贴着边界一路越界 | 一步跳过保护页时不触发 |
| 栈保护（`-fstack-protector`） | 返回地址或保存寄存器被覆写 | 只插桩部分函数，只负责发现并终止 |
| 逐页探测（`-fstack-clash-protection`） | 大栈分配跳过保护页 | 编译器插桩范围有限，不是运行时隔离 |

> **时效信息（核查日期：2026-09）：** 常见默认值 `ulimit -s` = 8192 KiB（8 MiB）只是特定发行版与容器配置下的常见取值，取决于 `RLIMIT_STACK`；把它当成标准会误判容器、嵌入式与自定义线程栈环境。本机 gcc 11.4.0 默认开启 `-fstack-clash-protection`，可用 `gcc -Q --help=common` 查看默认状态。

> **面试高频：** 一个线程的栈有多大？递归太深为什么会崩？
> **答题脉络：** 主线程栈上限由 `RLIMIT_STACK` 决定（常见 8 MiB，非标准）→ 新线程默认栈取自该限制，`unlimited` 时按架构取值 → 每线程另有默认一页保护区域 → 递归层数 × 每层帧大小超过配额即 SIGSEGV → 与整机剩余内存无关。
> **追问方向：** 保护页为什么挡不住大数组越界、`-fstack-protector` 与它的区别、深递归改迭代或显式栈、容器里的 `ulimit -s`。

## 堆与动态分配解决生命周期问题

栈只能处理"生命周期与调用结构一致"的对象。长度或生命周期要到运行时才能确定时——读完文件才知道大小的缓冲区、要跨函数留存并传递的容器——就需要动态分配。

```c
/* 堆分配示例：申请、使用、释放的最小闭环。
 * 编译：gcc -std=c17 -Wall -Wextra -O0 malloc_demo.c -o malloc_demo
 * 运行：./malloc_demo，预期退出码 0。
 */
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    const size_t count = 3;
    int *numbers = malloc(count * sizeof *numbers); /* 1. 按元素类型计算字节数 */
    if (numbers == NULL) {                          /* 2. 申请失败时不能继续解引用 */
        return 1;
    }

    for (size_t index = 0; index < count; index++) {
        numbers[index] = (int)(index + 1) * 10; /* 3. 下标范围 0 ~ count-1 */
    }
    printf("numbers[2]=%d\n", numbers[2]);

    free(numbers);  /* 4. 只释放一次，交还堆空间 */
    numbers = NULL; /* 5. 减少同一指针再次误用的机会 */
    return numbers == NULL ? 0 : 1;
}
```

<!-- verify: .work/verify/B04/c/malloc_demo.c -->

动态分配把三件事交给程序员：**大小正确**（`malloc` 只按字节数分配，不知道里面放几个元素）、**边界正确**（越界访问属未定义行为）、**生命周期正确**（谁申请谁释放，释放后不得再访问）。四类高频错误由此而来：泄漏、重复释放（double free）、释放后使用（use-after-free）、越界读写。把指针置空只能降低同一指针再次误用的概率，其他别名指针仍然指向已释放的对象。

这类错误属于未定义行为，编译器不一定报错，工具能把它们变成明确报告：

```text
$ gcc -std=c17 -g -fsanitize=address,undefined oob.c -o oob && ./oob
==4574==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x502000000014 ...
SUMMARY: AddressSanitizer: heap-buffer-overflow /.../oob.c:2 in main
```

另外，调用者只拿到指针时无法从指针推知数组长度：`sizeof(numbers)` 在函数参数上得到的是指针大小，长度必须与指针一起传递。

还有一点必须在"堆"这个词上澄清：C 标准只规定 `malloc`/`free` 这类分配接口，"堆"不是标准里一个连续命名的区域。glibc 手册明确写道，其分配器维护多个大块区域（arena）以优化多线程使用，其中还可能包含通过 `mmap` 直接建立的独立区域。"堆在数据段之上、连续向上增长"只是教科书里的最简模型。

| 对比点 | 栈 | 堆 |
|---|---|---|
| 生命周期 | 随函数进入与返回（自动存储期） | 由程序显式申请与释放（动态存储期） |
| 大小确定时间 | 编译期可静态确定（VLA 例外） | 运行时确定 |
| 管理方式 | 编译器与调用约定协作 | 分配器库（glibc、jemalloc、tcmalloc 等） |
| 典型失败 | 栈溢出、返回局部对象地址 | 泄漏、重复释放、释放后使用、越界 |

> **关键认知：** `malloc` 解决的是"长度与生命周期在编译期无法确定"，而不是"内存更大"；栈上的对象同样可能很大（只要不超栈配额），堆上的对象也可能是 16 字节的小块。

> **面试高频：** 栈和堆有什么区别？
> **答题脉络：** 先按"生命周期由谁决定"区分（自动 vs 显式）→ 再讲大小确定时间与管理方（编译期/编译器 vs 运行时/分配器）→ 然后讲典型错误与代价（泄漏、碎片、缓存局部性）→ 最后纠正"栈一定快"这类口诀。
> **追问方向：** 线程栈的大小与共享性、堆分配与系统调用的边界、泄漏与悬垂指针的定位工具。

堆与栈共享的边界问题（同一对象被多个引用持有、谁负责释放）属于所有权与复制语义，见《[对象复制、所有权与深浅拷贝](../05-程序设计与软件设计/02-对象复制、所有权与深浅拷贝.md)》。

## malloc 背后的分配器

### chunk、arena 与每线程缓存

`malloc`/`free` 是库函数，不是系统调用：它们向内核"批发"大块地址空间（`brk` 或 `mmap`），再切成小块"零售"，因此绝大多数调用只发生在用户态。

以明确标注的实现为例（glibc，后端源自 ptmalloc）：每次分配的内存前面藏着管理头部，连同数据构成一个 chunk；`free` 时相邻空闲 chunk 会尝试合并，以满足后续更大的请求。多线程下，glibc 维护一个主 arena 与若干额外 arena（各有锁），让不同线程尽量在互不竞争的 arena 上分配；较新版本还在线程内加了一层小尺寸空闲块缓存（tcache），缩短小分配的加锁路径。

> **时效信息（核查日期：2026-09）：** 分配器常量随版本变化，不要背成规则。`mallopt(3)` 与 glibc 手册给出的是默认值与调整机制；当前 glibc 源码中 tcache 的每类缓存块数常量已从早期的 7 调整为 `TCACHE_FILL_COUNT = 16`，大块缓存范围也扩展到 MiB 级块。请按目标 glibc 版本与运行参数核查。

### brk 主堆与 mmap 匿名映射

glibc 走哪条"进货"路径由阈值参数决定：**主堆**通过 `brk`/`sbrk` 推进数据段末端，扩出的一段由用户态切分与回收；**匿名 `mmap`** 为一块需求单独建立映射，`free` 时可整块归还。

| 对比点 | `brk` 扩展主堆 | 匿名 `mmap` 映射 |
|---|---|---|
| 典型用途 | 中小块分配、碎片可控时复用 | 超出当前阈值的大块、线程 arena |
| `free` 之后 | 回到空闲链复用；仅堆顶空闲足够大时才收缩归还 | 整块立即归还内核 |
| 地址位置 | 与数据段相邻、向上连续扩展 | 独立映射，位于 mmap 区域 |
| 碎片风险 | 中间碎片可能长期留在堆里 | 整块进、整块出，几乎没有 |

`M_MMAP_THRESHOLD` 默认 128 KiB，但 `mallopt(3)` 说明 **glibc 现在默认使用动态阈值**：初始值为 128 KiB，当更大的块（64 位平台上不超过 `DEFAULT_MMAP_THRESHOLD_MAX` = 4 MiB × `sizeof(long)`，即 32 MiB）被释放时，阈值上调到该块大小；一旦通过 `mallopt` 或环境变量显式设置 `M_MMAP_THRESHOLD`、`M_TRIM_THRESHOLD`、`M_TOP_PAD`、`M_MMAP_MAX` 中任意一个，动态调整就会关闭。`M_TRIM_THRESHOLD` 默认同样是 128 KiB，控制"堆顶连续空闲多大时收缩堆"。

第一个实验把大块分配的路径与归还结果直接测出来：

```c
/* 大块分配走独立匿名映射：free 之后整块归还内核。
 * 编译：gcc -std=c17 -O0 malloc_mmap.c -o malloc_mmap
 * 前置条件：Linux；可读 /proc/self/statm。
 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define BIG_BYTES (64L * 1024 * 1024)

static long resident_kib(void) {
    FILE *f = fopen("/proc/self/statm", "r");
    long total = 0;
    long resident = 0;
    if (f == NULL || fscanf(f, "%ld %ld", &total, &resident) != 2) return -1;
    fclose(f);
    return resident * 4; /* 每页 4 KiB */
}

int main(void) {
    const long start_rss = resident_kib();
    char *big = malloc(BIG_BYTES);
    if (big == NULL) return 1;

    memset(big, 1, BIG_BYTES); /* 1. 写入后物理页才真正驻留 */
    const long touched_rss = resident_kib();
    free(big); /* 2. 独立映射整块归还 */
    const long freed_rss = resident_kib();

    printf("malloc 后 RSS = %ld KiB\n", start_rss);
    printf("写入后   RSS = %ld KiB\n", touched_rss);
    printf("free 后  RSS = %ld KiB\n", freed_rss);

    /* 3. 断言：驻留上升接近 64 MiB，free 后回到起点附近。 */
    if (touched_rss - start_rss < 60 * 1024) return 1;
    return freed_rss - start_rss > 4 * 1024 ? 1 : 0;
}
```

换个访问顺序，结论相反：先分配大量中小块并释放，堆顶又被一小块占住时，`free` 不会把内存交还内核。

```c
/* 堆顶被占住时 free 不归还内核，malloc_trim 才有机会归还空闲堆页。
 * 编译：gcc -std=c17 -O0 malloc_trim.c -o malloc_trim
 * 前置条件：Linux + glibc；mallopt(3)/malloc_trim(3) 属 glibc 扩展。
 */
#include <malloc.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define CHUNK_BYTES (64 * 1024)
#define CHUNK_COUNT 4096

static long resident_kib(void) {
    FILE *statm = fopen("/proc/self/statm", "r");
    long total = 0;
    long resident = 0;
    if (statm == NULL || fscanf(statm, "%ld %ld", &total, &resident) != 2) return -1;
    fclose(statm);
    return resident * 4;
}

int main(void) {
    char **blocks = malloc(CHUNK_COUNT * sizeof *blocks);
    if (blocks == NULL) return 1;
    const long start = resident_kib();

    for (int i = 0; i < CHUNK_COUNT; i++) {
        blocks[i] = malloc(CHUNK_BYTES);
        if (blocks[i] == NULL) return 1;
        memset(blocks[i], i & 0xff, CHUNK_BYTES); /* 1. 写入后占用物理页 */
    }
    char *blocker = malloc(4096); /* 2. 堆顶留一块占位的小分配 */
    if (blocker == NULL) return 1;
    const long allocated = resident_kib();

    for (int i = 0; i < CHUNK_COUNT; i++) free(blocks[i]); /* 3. 空闲块留在堆中 */
    const long freed = resident_kib();
    free(blocker); /* 4. 堆顶空出来 */
    const long unblocked = resident_kib();
    const int trimmed = malloc_trim(0); /* 5. 主动请求归还空闲堆页 */
    const long after_trim = resident_kib();

    printf("起点=%ld 写入后=%ld free后=%ld 去占位后=%ld trim(%d)后=%ld (KiB)\n", start,
           allocated, freed, unblocked, trimmed, after_trim);

    if (allocated - start < 200 * 1024) return 1; /* 写入 256 MiB 后驻留应明显上升 */
    if (freed - start < 200 * 1024) return 1;     /* free 未把内存还给内核 */
    return after_trim > freed / 8 ? 1 : 0;        /* trim 之后应大幅下降 */
}
```

两个实验合起来回答了最常见的疑问：**"`free` 之后内存降不下来"通常不是泄漏，而是分配器按策略保留着已获得的页**（尤其堆顶被占住时收缩条件不成立），它宁可留给下次分配复用，也不愿每次 `free` 都做系统调用。`malloc_trim(0)` 是 glibc 的显式请求，手册说明它通过 `sbrk(2)` 或 `madvise(2)` 归还空闲堆内存，`pad` 参数决定堆顶保留多少空闲。不同分配器的取舍不同：jemalloc 强调分级与 per-thread arena，tcmalloc 强调 per-CPU 缓存与低延迟，具体行为以各自官方设计文档为准，不建议凭经验排名。

> **关键认知：** `free` 的效果是"把块还给分配器"，不是"立刻还给内核"；只有整块由匿名映射承载的内存（如超过动态阈值的大块）才会立即归还，而 128 KiB 只是 glibc 的初始默认阈值，会被分配模式动态调整。

> **面试高频：** `malloc` 是系统调用吗？为什么 `free` 之后物理内存不降？
> **答题脉络：** `malloc`/`free` 是库函数，只在需要扩展时才进入内核（`brk` 或匿名 `mmap`）→ 小块来自堆的空闲链，`free` 只把块还回分配器 → 堆顶被占住或有碎片时不满足收缩条件 → 只有超过阈值走独立映射的大块会整块归还 → 需要主动归还可用 `malloc_trim` 一类扩展接口。
> **追问方向：** `M_MMAP_THRESHOLD` 的动态调整与关闭条件、arena 与线程数、RSS 与 VIRT 的区别、如何区分越界与泄漏。

## 虚拟地址如何翻译成物理页帧

先统一术语：**虚拟页**是虚拟地址空间中被切出的固定长度单位（常见 4 KiB）；**物理页帧**是物理内存中被切出的同长度单位；**页表项**（Page Table Entry，PTE）记录"这个虚拟页对应哪个页帧、以及有什么权限"。

翻译分两步：把虚拟地址拆成"页号 + 页内偏移"，用页号查表得到页帧号，再拼上原来的偏移。偏移不参与翻译，不跨页的相邻地址因此落在同一页帧内。下面这份算术给出三个关键数字：

```text
虚拟地址 0x7ffd2a3f4b28 → 四级索引（十六进制）0ff 1f4 151 1f4 + 页内偏移 0xb28
玩具地址 0x3A4F（32 位、4 KiB 页）→ 页号 3 = 0x3A4F >> 12，页内偏移 0xA4F
单级页表规模：2^(48-12) 个页表项 × 8 字节 = 512 GiB
```

48 位用户地址被拆成 4 级索引，每级表 512 项（x86-64 的常见形态，9 + 9 + 9 + 9 + 12）：

```text
 47        39 38        30 29        21 20        12 11             0
┌──────────────┬──────────────┬──────────────┬──────────────┬────────────────┐
│ 第 4 级索引 9 位│ 第 3 级索引 9 位│ 第 2 级索引 9 位│ 第 1 级索引 9 位│  页内偏移 12 位  │
└──────────────┴──────────────┴──────────────┴──────────────┴────────────────┘
第 4 级开始逐级指向下一级页表，末级页表项给出物理页帧号
```

多级结构换来的正是空间：程序几乎不会用到整个 48 位地址空间，中间层页表可以按需建立，未使用的区域根本不需要内存；单级页表则要为整个地址空间各准备一项，本次实验算出的 512 GiB 说明它不可行。代价是每次翻译要多访问若干次内存，于是需要 TLB。

TLB（Translation Lookaside Buffer，快表）是 MMU 内部的小容量缓存，保存最近用过的"虚拟页 → 页帧 + 权限"映射：命中时翻译在极短时间内完成，未命中时由硬件或内核遍历页表补齐。因为条目少，一条大页映射可以覆盖更多内存，这是大页的主要动机之一。

页表项除页帧号外还保存若干概念位：是否存在（present）、是否可写、是否允许用户态访问、是否被访问过（accessed/young）、是否被写过（dirty）、是否禁止执行（NX）。具体位名与布局由架构决定，但语义必须分清：**"存在与否"决定是否触发缺页，"可写/用户"决定访问是否合法，"访问过/写过"决定内核能否回收或换出这一页**。

> **关键认知：** 多级页表不是"更快的页表"，而是"更省空间的页表"：它让页表本身也变成可按需建立、甚至可被换出的普通页，代价是翻译路径更长，必须由 TLB 兜住热点。

> **面试高频：** 多级页表为什么能省空间？
> **答题脉络：** 单级页表要覆盖整个虚拟地址空间（48 位 + 4 KiB 页对应的页表本身就远超可接受规模）→ 多级把索引拆开，未使用的中间层根本不分配 → 只有真正用到的区域逐级建立 → 代价是 TLB 未命中时多次访存。
> **追问方向：** TLB 覆盖范围与大页、页表项权限位与 COW、页表本身缺页怎么办、x86-64 的 4 级与 5 级页表。

位宽与地址计算属数据表示的前置知识，见《[二进制表示与位运算](../01-数据表示/01-二进制表示与位运算.md)》。

## 缺页不是错误的同义词

把上面的机制串成一条访问路径：

1. CPU 发出一个虚拟地址的访问请求。
2. MMU 先查 TLB：命中就用缓存中的页帧号拼出物理地址。
3. 未命中则遍历页表（采用四级页表且不是大页映射时，x86-64 最多 4 次表项读取；启用 LA57 的五级页表时层数会增加，逐级依赖）。
4. 某级页表项标记为"不存在"或权限不允许这次操作时，硬件产生缺页异常并把控制权交给内核。
5. 内核判断类型：合法的按需分配、文件映射、写时复制就补建映射并重新执行访问；权限违规则升级为信号（Linux 上通常是 SIGSEGV）。

同样一次缺页，代价差别很大。`getrusage(2)` 用两个计数把它们分开：`ru_minflt` 是不需要 I/O 的缺页（零页按需分配、COW 复制、页表补齐），`ru_majflt` 是需要从存储设备读入的缺页（例如被换出的匿名页要换回）。

```c
/* 缺页计数观察：首次写入新分配的内存只产生 minor fault，不会读存储设备。
 * 编译：gcc -std=c17 -O0 fault_types.c -o fault_types
 * 前置条件：Linux；getrusage(2) 可用。
 */
#include <stdio.h>
#include <stdlib.h>
#include <sys/resource.h>

static void show(const char *label, long *minor, long *major) {
    struct rusage usage = {0};
    if (getrusage(RUSAGE_SELF, &usage) != 0) return;
    printf("%-22s minor=%ld major=%ld\n", label, usage.ru_minflt - *minor,
           usage.ru_majflt - *major);
    *minor = usage.ru_minflt;
    *major = usage.ru_majflt;
}

int main(void) {
    const size_t bytes = 64 * 1024 * 1024;
    const long pages = (long)(bytes / 4096);
    long minor = 0;
    long major = 0;

    show("启动时", &minor, &major);
    char *region = malloc(bytes);
    if (region == NULL) return 1;
    show("malloc 之后（未写入）", &minor, &major);

    for (size_t offset = 0; offset < bytes; offset += 4096) {
        region[offset] = 1; /* 1. 每页写一次，按需建立映射 */
    }
    show("逐页写入之后", &minor, &major);

    /* 2. 按需分页只增加 minor fault；正常环境下不应出现 major fault。 */
    const int failed = minor < pages || major != 0;
    free(region);
    return failed;
}
```

```text
malloc 之后（未写入） minor=32 major=0      ; 只拿到虚拟范围，几乎不缺页
```

两个结论立刻可读：`malloc` 本身几乎不产生缺页，写入才产生；本环境中 64 MiB 顺序写入带来约 1.6 万次 minor fault，没有一次 major fault——按需分配不需要访问存储设备。

同类装置在不同场景复用：**按需分页**（访问全新匿名页，内核给一个已清零页帧）、**文件映射**（访问未读入的部分由页缓存提供，可能触发读盘，属 major fault；多个进程以只读或共享方式映射同一文件时，物理页通常可以共享，私有写入则会触发 COW）、**写时复制**（`fork(2)` 后父子共享可复制的物理页并只复制页表，任何一方写入时才复制相应页面——手册原文是 Linux 下 `fork()` 用写时复制页实现，代价主要是复制页表并建立任务结构）、**权限违规**（页存在但这次操作不允许，内核不会修好它，而是发送信号）。

> **关键认知：** 缺页是内核实现按需分配、文件映射与写时复制的基本手段，属于正常事件；只有访问违反权限、超出映射范围或无法满足资源约束时，它才升级为 SIGSEGV/SIGBUS 或 OOM 处理。

> **面试高频：** TLB 未命中与缺页有什么区别？minor fault 与 major fault 有什么区别？
> **答题脉络：** TLB 未命中只是缓存没命中，页表里有有效映射，补齐条目后继续执行 → 缺页是页表项无效或权限不符，必须进入内核 → 内核再区分 minor（不需要 I/O，如零页给出、COW、页表补齐）与 major（需要读存储设备）→ 权限违规不修复，直接给信号。
> **追问方向：** `fork` 的 COW 代价、页缓存与文件映射的共享页、交换与 refault、内存超卖与 OOM killer。

## 分页、分段与段页式的历史位置

教材把"分段"讲成虚拟内存的另一条主线，但今天用户态程序依赖的主要是分页：

| 对比点 | 分页 | 分段 |
|---|---|---|
| 划分依据 | 固定长度的页，地址一维 | 逻辑单元（代码、数据、栈等），地址二维（段号 + 段内偏移） |
| 大小是否可变 | 页大小固定 | 段长可变、可动态增长 |
| 程序员可见性 | 透明，程序只看线性地址 | 需要显式划分或由编译器分配段 |
| 主要目的 | 实现按需分页与虚拟内存、统一管理物理内存 | 提供逻辑独立的地址空间、便于共享与保护 |
| 碎片形态 | 内部碎片（最后一页用不满） | 外部碎片（空闲总量够但切不开） |

段页式把两者叠起来：地址空间先按逻辑段划分，每段内部再分页，既保留分段在共享与保护上的表达力，又得到分页在物理内存管理上的灵活性。

> **关键认知：** "段"在不同语境下是三个不同的东西：硬件分段（CPU 段寄存器与段表）、可执行文件的 segment（装载时按权限合并的连续区间）、日常口语里"地址空间的一段"。讨论前先说清是哪一种，否则会得到互相矛盾的结论。

> **历史机制（不推荐）：** x86 的保护模式分段机制仍存在于 CPU 中，但 64 位模式下用户态地址空间基本是平铺的：段基址不再用于进程隔离，`fs`/`gs` 仍保留给线程本地存储等用途。教材里"用段实现保护"的模型不再对应现代 Linux 的用户态实现。[核查日期：2026-09]

ELF 的 section 与 segment、PIE 的生成与装载见《[程序从源码到运行](./06-程序从源码到运行.md)》。

## 内存紧张时该换出谁

物理内存无法容纳所有进程的完整工作集，内核必须在缺页时"腾位置"。教材把问题抽象成：给定固定引用串与有限页框，换出谁才能让缺页最少。时间与空间局部性是前提——访问完全随机时任何策略都无从优化；正因为热点会重复出现，"最近用过的页更可能再次被用到"才有意义。工作集超过可用页框时程序陷入抖动（thrashing）：刚换出的页马上又要用，缺页率飙升，CPU 大量时间花在换页而不是计算上。

- **最优置换（OPT）**：换出"未来最久才会被访问"的页，缺页率理论下界，需要预知未来，只能当基准。
- **先进先出（FIFO）**：换出最早装入的页，实现简单，但可能换出频繁使用的页，甚至出现 Belady 异常——页框变多、缺页反而变多。
- **最近最久未使用（LRU）**：换出最久未被访问的页，更贴近局部性，但每次访问都要更新顺序，精确实现代价高。
- **近似结构**：NRU 用"访问位 + 修改位"把页分四类，优先淘汰未被访问且未被修改的页；第二次机会与时钟算法（Clock）用环形链表加引用位，把判断摊到每次扫描里。

下面的模拟先在长度 20 的经典引用串上对比三种策略的缺页次数，再用经典 Belady 引用串 1,2,3,4,1,2,5,1,2,3,4,5 复现“页框变多、缺页反而变多”：

```dart
// 前置条件：Dart 3.x；纯 Dart；无第三方依赖。
// 在两组固定引用串上模拟 FIFO、LRU、OPT 三种页面置换算法，并复现 Belady 异常。
// 运行：dart run B04/page_replacement.dart

enum ReplacementPolicy { optimal, fifo, lru }

/// 返回在 [frameCount] 个页框上按 [policy] 处理 [references] 时的缺页次数。
int countFaults(
  List<int> references,
  int frameCount,
  ReplacementPolicy policy,
) {
  final frames = List<int>.filled(frameCount, -1); // -1 表示空闲页框
  final loadedAt = List<int>.filled(frameCount, -1); // FIFO：装入时刻
  final usedAt = List<int>.filled(frameCount, -1); // LRU：最近使用时刻
  var faults = 0;

  for (var time = 0; time < references.length; time++) {
    final page = references[time];

    // 1. 命中时只需更新“最近使用”时刻。
    final hitFrame = frames.indexOf(page);
    if (hitFrame >= 0) {
      usedAt[hitFrame] = time;
      continue;
    }

    // 2. 缺页：优先使用空闲页框。
    faults++;
    var victim = frames.indexOf(-1);

    // 3. 没有空闲页框时按策略选择牺牲页。
    if (victim < 0) {
      victim = switch (policy) {
        ReplacementPolicy.fifo => _leastRecent(loadedAt),
        ReplacementPolicy.lru => _leastRecent(usedAt),
        ReplacementPolicy.optimal => _farthestNextUse(frames, references, time),
      };
    }
    frames[victim] = page;
    loadedAt[victim] = time;
    usedAt[victim] = time;
  }
  return faults;
}

// 装入/使用时刻越小越“老”，对应 FIFO 或 LRU 的牺牲页。
int _leastRecent(List<int> times) {
  var victim = 0;
  for (var i = 1; i < times.length; i++) {
    if (times[i] < times[victim]) victim = i;
  }
  return victim;
}
```

```text
OPT , 3 个页框：9 次缺页
LRU , 3 个页框：12 次缺页
FIFO, 3 个页框：15 次缺页
FIFO, 4 个页框：10 次缺页
FIFO, 3 个页框（Belady 串）：9 次缺页
FIFO, 4 个页框（Belady 串）：10 次缺页
Belady 异常成立：页框 3→4，缺页 9→10
全部检查通过
```

FIFO 不满足“栈性质”（页框增加时保留集合不构成包含关系）：在经典 Belady 引用串上，多出来的页框改变了淘汰顺序，把之后仍会被访问的页提前换出，缺页反而从 9 增到 10；而在上面长度 20 的引用串上它的缺页从 15 降到 10，说明 FIFO 这次变好只是引用串的巧合，没有结构性保证。LRU 与 OPT 属于栈算法，页框增加时缺页数不会上升。

真实内核比这段模拟复杂：它同时管理匿名页与文件页（回收代价不同）、干净页与脏页（脏页需先回写）、活跃与不活跃队列，并用 refault 距离等指标评估"刚被换出的页又回来了"的程度。正因精确 LRU 要在每次访问时维护顺序，现实实现只能是近似结构；较新的 Linux 还提供了多代 LRU（Multi-Gen LRU，MGLRU）这一替代实现。

> **时效信息（核查日期：2026-09）：** 内核文档把 MGLRU 描述为 "an alternative LRU implementation"，用于在内存压力下优化页回收。它是否启用取决于内核版本与配置（如 `CONFIG_LRU_GEN`）以及发行版选择，不能写成"所有 Linux 都默认使用多代 LRU"，请以目标内核文档与配置为准。

> **关键认知：** 页面置换算法教的是"如何利用局部性降低缺页率"，真实内核做的是"用近似结构、多队列与回写策略在代价可控的前提下逼近它"；把 Clock、LRU 的参数直接当成内核实现会得到错误结论。

## 大页与现代 Linux 回收机制

页表层级越深、TLB 条目越少，翻译开销越贵。更大的页有两个直接好处：一条 TLB 条目覆盖更多内存（减少未命中），一次缺页补齐更多内存（减少缺页次数）。代价同样明确：内部碎片更严重，分配与回收需要更长的清零、复制与整理时间，访问分散的负载可能因此变慢。

Linux 提供两条路线：**显式大页（hugetlb）**由管理员在系统里预留固定数量的大页（`/sys/kernel/mm/hugepages`），程序通过 `hugetlbfs` 或 `mmap` 标志使用，可控可预测但需要预留；**透明大页（Transparent Huge Page，THP）**由内核对合适的场景自动合并，无需预留，内核文档强调它相比 hugetlbfs 的预留方式"最大化空闲内存的可用性"，并允许分页等高级内存特性继续可用；**多尺寸透明大页（multi-size THP，mTHP）**提供比传统 PMD 尺寸小、比基础页大的粒度（以 2 的幂递增，例如 16K、32K、64K），用于支撑匿名内存，这些页仍是 PTE 映射的：缺页次数显著减少，同时单次缺页要清理的内存更少，延迟尖峰更不明显。

> **时效信息（核查日期：2026-09）：** 内核文档说明 THP 开关既可全局设置也可按尺寸设置，当前默认为 PMD 尺寸 `inherit`（继承顶层 `enabled`）、其他尺寸 `never`，`defrag` 默认是 `madvise` 风格。把所有尺寸都设为 `never` **并不等于**全局禁用透明大页，因为 `madvise(MADV_COLLAPSE)` 会忽略这些开关，而 `MADV_COLLAPSE` 自 Linux 6.1 起提供（man-pages 标注）。启用状态请以目标内核的 `/sys/kernel/mm/transparent_hugepage/` 与文档为准。

> **关键认知：** 大页是"用内存占用与回收灵活性换 TLB 命中率和缺页次数"的权衡，不是无条件加速；对内存敏感或访问分散的负载，开启大页反而可能让 RSS 上涨、回收变慢。

## 从 VIRT、RSS 到一次内存排查

排查内存问题的第一步是分清指标，否则会把"虚拟地址范围大"误判成"内存快用满"：

| 指标 | 含义 | 常见误判 |
|---|---|---|
| VIRT / `VmSize` | 虚拟地址空间总量 | 大不等于占用物理内存（映射而未驻留） |
| RSS / `VmRSS` | 实际驻留的物理内存 | 不降不等于泄漏（分配器保留、页缓存） |
| PSS | 共享页按持有者数量分摊后的 RSS | 只在 smaps 汇总中出现，不是 `statm` 字段 |
| 匿名页 / 文件页 | 无后备文件 / 有后备文件 | 文件页回升可能是页缓存，不是泄漏 |
| swap | 被换出的匿名页 | 有 swap 不等于发生严重抖动；频繁换入换出才是性能信号 |

两个已验证的例子正好说明这两种误判：`malloc` 之后 RSS 只有几百 KiB，写入 64 MiB 后才涨到 66 MiB（虚拟 ≠ 驻留）；`free` 掉 256 MiB 后 RSS 仍是 265 MiB，只有主动 `malloc_trim` 才回落（不降 ≠ 泄漏）。排查可以按下面的顺序做，每一步只回答一个问题：

```bash
# 1. 虚拟大小与驻留页数（第二列是驻留页数，乘页大小得到 RSS）
cat /proc/<pid>/statm
# 2. 更可读的汇总：VmSize / VmRSS / VmSwap
grep -E "VmSize|VmRSS|VmSwap|VmData|VmStk" /proc/<pid>/status
# 3. 驻留与共享的分摊情况（内核提供该文件时），先看总量再看单条映射
grep -E "Rss|Pss|Shared_|Private_|Anonymous|AnonHugePages|Swap" /proc/<pid>/smaps_rollup
# 4. 逐条列出映射，找异常增长的区域：堆、匿名映射还是文件映射
cat /proc/<pid>/maps
# 5. 系统层面是否真有内存压力，以及进程缺页速率（procps / sysstat 提供）
vmstat 1 5
pidstat -r -p <pid> 1 5
```

判断顺序建议是：先确认"真的驻留"（RSS/PSS）还是"只是地址范围大"（VIRT）；再确认增长来自堆、匿名映射还是文件映射；然后判断是分配器保留、页缓存还是泄漏；最后才决定改代码（配对释放、减少复制、流式处理）、调分配器参数，还是调整系统策略（交换、cgroup 限制、大页策略）。

代码侧另有一套工具：`-fsanitize=address` 能发现越界与释放后使用（本次核查中直接给出了 `heap-buffer-overflow` 与定位行号），`-fsanitize=undefined` 覆盖若干未定义行为，Valgrind 能在不重新编译的情况下发现部分问题。它们都有明确边界：只覆盖被插桩或被执行到的路径，**没有报告不等于没有问题**；而 RSS 高位不动也可能完全正常。工具安装与参数差异较大，具体用法见《[Linux 命令行与进程排查](../07-工程工具与代码质量/01-Linux命令行与进程排查.md)》。

> **关键认知：** 内存排查先分层再动手：泄漏（对象无法再被访问却仍被引用）、分配器保留（空闲块留在堆里）、页缓存（文件页可回收）、映射与工作集（虚拟范围与共享页）是四个不同问题，处理方式完全不同。

## 常见误区与面试答题链

- ❌ 虚拟内存就是"把磁盘当内存用"。✅ 它的核心是"每个进程一套虚拟地址到物理页帧的映射"，磁盘交换只是物理内存不足时的一种后备手段。
- ❌ 页表放在 MMU 里。✅ 页表在内存中（页表项本身也是普通页），MMU 只负责按页表翻译；TLB 才是 MMU 附近的小容量缓存。
- ❌ 缺页一定意味着读磁盘。✅ 零页按需给出、COW 复制、页表补齐都会产生缺页但不需 I/O；只有需要从存储读入的才是 major fault。
- ❌ 栈一定向下增长、堆一定向上增长。✅ 这是常见实现而非标准保证，更不能据此推断两个局部量的相对位置。
- ❌ 函数参数都在栈上。✅ x86-64 的主流 ABI 都优先用寄存器，装不下的才入栈，对齐与影子空间还会带来额外调整。
- ❌ 局部变量一定在栈上。✅ 优化后它可能只存在于寄存器、被内联消除或与别的变量合并；`-O0` 的映射只是教学视图。
- ❌ 大块 `malloc` 一定走 `mmap`。✅ 是否走映射由分配器的动态阈值决定；由独立匿名映射承载且可解除映射的块，通常能在 `free` 时整块归还。
- ❌ `free` 之后 RSS 一定下降。✅ 小块回到分配器的空闲结构里，堆顶被占住或有碎片时不会归还内核，需要显式 `malloc_trim` 一类请求。
- ❌ 分段就是 ELF 的段。✅ 硬件分段、ELF segment、口语中的"地址空间一段"是三个概念，现代 x86-64 用户态主要靠分页与权限位隔离。

面试回答可以按两条固定线索组织：

- **"给你一个指针，怎么判断能不能用"**：先问对象（类型、有效长度）→ 再问生命周期（是否有效、谁负责释放）→ 再问区域与权限（落在哪个映射、可读写可执行吗）→ 最后才问缺页代价（是否已驻留、访问是否连续）。
- **"进程内存一直涨，怎么排查"**：先看 RSS/PSS 与 VIRT 是否同步增长 → 再看增长来自堆、匿名映射还是文件映射 → 区分泄漏、分配器保留、页缓存与工作集 → 用工具定位到代码（ASan、Valgrind、分配统计）→ 最后选择改代码或调分配器与系统参数。

## 一句话总结

> 进程看到的不是物理内存，而是内核用页表维护的一组映射：栈与堆只是其中生命周期和权限不同的区域，而每次访问最终是否落到物理内存，要等 MMU、TLB 与缺页处理走完才知道。
