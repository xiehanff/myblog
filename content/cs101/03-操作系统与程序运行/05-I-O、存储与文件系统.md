# 操作系统与程序运行｜05-I/O、存储与文件系统

`write()` 明明返回了成功，进程随后崩溃或断电，日志里的最后一行却不见了；同一个 `read()`，一次只要几微秒，另一次却要几毫秒。这两件怪事来自同一个原因：应用看到的“读写”和存储设备上真正发生的读写之间，隔着应用缓冲、页缓存、文件系统、块层、驱动和设备控制器。

把存储当成“更慢的内存”，就无法解释为什么返回值和持久化是两回事；只背 FCFS/SSTF，也解释不了最短寻道算法为什么在现代闪存上不再是主角。本文沿一次 `read`/`write` 的路径逐层展开：先分清“返回”与“落盘”的边界，再看操作系统如何控制设备，然后是 HDD 与 SSD/NVMe 的假设差异、块层与文件系统的分工、页缓存与崩溃一致性；最后统一几组容易混用的 I/O 术语，并给出一套可复现的观察实验。

## 为什么 write 返回不等于数据已经落盘

先给出一条完整路径。一次普通的 `write` 大致要穿过下面这些层，每一层都可能“接受”数据，但接受不等于持久化：

```text
应用缓冲（stdio / StringBuffer / 语言运行时）
  → 系统调用接口：read / write / fsync / fdatasync（陷入与切换细节见 01-操作系统概述）
  → VFS：按文件名找到 inode，决定走哪个文件系统
  → 文件系统：更新元数据、分配块、写日志（journal）
  → 页缓存：数据先落在内存页，带脏标记（dirty）
  → 块层：bio → request，合并相邻请求，交给调度器排序
  → 设备驱动：把请求翻译成设备能理解的命令
  → 设备控制器队列：设备自己决定何时执行
  → 介质：磁盘盘片 / 闪存页 + 设备内部缓存与映射表
```

路径的第一站是系统调用：应用通过 `syscall` 之类的指令陷入内核，由内核分发到 VFS 与文件系统（陷入与内核态切换的过程见 [操作系统概述](./01-操作系统概述.md)）。这条路径上要区分三个不同的事件：

1. **进入内核。** `write()` 返回时，数据通常只写进了页缓存。内核已经接受这批字节，其他进程随后读同一文件就能看到它们。
2. **进入设备队列。** 后台回写或显式同步最终会把脏页变成块层请求，再下发到设备控制器。此时数据仍可能停在设备的写缓存里。
3. **持久化。** `fsync()` 会要求文件系统和设备完成必要的写回与缓存刷写；在设备正确实现协议并具备相应断电保护的前提下，数据才可认为跨过持久化边界。普通 `write()` 本身不提供这个保证。

> **关键认知：** 对普通文件而言，`write()` 成功只表示数据已被内核接受，后续按普通文件语义读取通常能看到它；它不保证数据已经提交到存储设备。man-pages 的原话是：成功返回的 `write()` 不保证数据已提交到磁盘，通常需要在写完后调用 `fsync()`；即使如此，设备是否真正具备断电保护仍是系统边界。Linux 上的普通文件默认走页缓存路径，[write(2)](https://man7.org/linux/man-pages/man2/write.2.html) 的 NOTES 与 [fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html) 分别写明了这两点。

`fsync()` 的边界同样需要写清楚，否则很容易把它当成“万能的落盘开关”：

- `fsync(fd)` 会把该文件已修改的内存数据与元数据刷到设备，并等待设备报告完成；它会请求设备刷写相关写缓存，但最终可靠性仍依赖设备正确实现协议与断电保护（[fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html)）。
- `fsync()` **不保证目录项也已落盘**：新建文件后如果只对文件 `fsync`，断电后可能找不到这个名字，需要对目录本身也 `fsync`（同上）。
- `fdatasync()` 只保证随后的数据读取仍正确，因此可能省掉不影响读回数据的元数据（如访问时间）；文件大小这类元数据仍然会刷。
- 关闭句柄（`close`）本身不提供持久化保证，`close` 只释放“打开文件描述”。

> **面试高频：** `write` 返回后数据到底在哪里？断电会丢吗？
> **答题脉络：** 应用缓冲 → 页缓存（`write` 在此返回）→ 回写进块层 → 设备队列与设备缓存 → 介质；然后指出 `fsync`/`fdatasync`、目录 `fsync`、`O_SYNC` 各自覆盖哪一段。
> **追问方向：** `fsync` 与 `fdatasync` 的差别、为什么还要 `fsync` 目录、`O_DIRECT` 的边界、日志型文件系统能否替代 `fsync`。

## 操作系统如何控制设备

设备对操作系统而言是“一块可编程硬件”：厂商规定的寄存器（状态、命令、数据）加上一套交互协议。操作系统用**设备驱动**把这些差异封装起来，向上只暴露块设备、字符设备或网络设备这样的少数接口。一次典型交互是：操作系统等待设备不忙 → 写入数据与命令 → 等待完成（[OSTEP 第 36 章](https://pages.cs.wisc.edu/~remzi/OSTEP/file-devices.pdf) 用一个“标准设备”描述了这套协议）。

访问寄存器有两种方式：

- **内存映射 I/O（Memory-Mapped I/O，MMIO）**：把设备寄存器映射进 CPU 的物理地址空间，CPU 用普通访存指令读写。内核文档把 MMIO 称为“最广泛支持的形式”：一段地址空间被解释为对设备的访问而不是对内存的访问（[Bus-Independent Device Accesses](https://docs.kernel.org/driver-api/device-io.html)）。
- **端口 I/O（Port I/O）**：x86 保留了独立的 I/O 端口空间，用专门的 `in`/`out` 类指令访问；ARM 等架构没有这一空间，只有 MMIO。这一层属于体系结构与驱动开发，本文只需知道“寄存器操作由驱动翻译成块层或网络层的请求”。

接下来是三种让 CPU 与设备协同的机制，它们解决的是不同问题：

| 机制 | CPU 参与方式 | 主要代价 | 何时合适 |
|---|---|---|---|
| 轮询（polling） | 反复读状态寄存器直到完成 | 空转浪费 CPU，且随设备变慢而恶化 | 设备通常立即完成、或对延迟极度敏感 |
| 中断（interrupt） | 下发命令后去干别的，完成后被打断 | 每次中断的执行与缓存扰动；高频完成时形成中断风暴 | 大多数慢速与中速设备 |
| DMA | CPU 只设置描述符，数据由控制器直接读写主存 | 需要地址映射与一致性处理（IOMMU 等） | 成块传输，尤其是磁盘与网卡 |

> **关键认知：** 中断与轮询不是非此即彼的选择：高吞吐场景下常见“先用中断唤醒、随后切换成批量轮询”的混合模式。Linux 网络栈的 NAPI 就是例子——设备先用中断通知，之后可以不经中断直接被轮询（[NAPI 文档](https://docs.kernel.org/networking/napi.html)）；块设备与 `io_uring` 也提供轮询模式。

DMA 的价值在于去掉“数据必须经过 CPU”的瓶颈：控制器在主存与设备之间直接搬运，CPU 只负责准备描述符并处理完成中断。它的代价是需要处理映射与缓存一致性，因此在有 IOMMU 的平台上，地址转换与隔离由硬件配合完成。

> **面试高频：** 中断、轮询、DMA 各解决什么问题？
> **答题脉络：** 轮询 = 简单但浪费 CPU；中断 = 让 CPU 在等待期间做别的事，代价是中断开销；DMA = 去掉逐字节搬运；再补一句“现代实现常把中断与轮询混合”。
> **追问方向：** 中断上半部与下半部、中断合并、NAPI 的批量收割、DMA 与缓存一致性。

## 缓冲、缓存与假脱机

这三个词在中文技术讨论里经常混用，但它们的目标完全不同：

- **缓冲（buffering）**解决“生产者和消费者的速率或单位不匹配”。终端按行缓冲、网络栈重组分片、`dd` 的 `bs=` 都属此类；缓冲区的内容是“正在路上”的临时数据。
- **缓存（caching）**解决“同一份数据被重复访问”。它保存的是已有数据的副本，按位置索引，目标是命中率；页缓存、设备内部控制器的缓存、CPU 缓存都属于这一类。
- **假脱机（spooling）**解决“独占设备如何被多个进程共享”。最典型的例子是打印：进程把内容写成磁盘上的排队文件，由打印调度器（如 CUPS 的 `cupsd`，[cupsd(8)](https://man7.org/linux/man-pages/man8/cupsd.8.html)）依次送交打印机，于是多个进程看起来可以“同时”使用一台独占设备。经典教材把假脱机与设备预留放在内核 I/O 子系统中讨论（[Silberschatz 等，第 12 章](https://os-book.com/OS10/)）。

> **关键认知：** 缓冲改的是速率与粒度匹配，缓存改的是重复访问代价，假脱机改的是独占设备的并发性；三者目标不同，不能互相替换，也不能用其中一个的名字解释另一个的行为。

一个容易观察的后果是“双重缓冲”：应用层的 stdio 缓冲与内核页缓存同时存在。不 `flush` 应用缓冲，数据甚至还没进内核；`flush` 之后数据进了页缓存，但依然可能没落盘。这就是“写入成功却读不到”和“读得到却断电丢失”两种现象的来源。

## HDD 的机械结构与经典调度

机械硬盘（Hard Disk Drive，HDD）把数据存在旋转的盘片上：盘面（platter）分成同心磁道（track），磁道再分成扇区（sector），磁头（head）由机械臂（actuator arm）在磁道间移动，主轴（spindle）带动盘片旋转。

一次读写的时间由三部分组成：**寻道时间**（磁头移动到目标磁道）、**旋转延迟**（等待目标扇区转到磁头下）、**传输时间**（把数据读出的时间）。直觉上就知道为什么教材总说寻道最贵：以 7200 rpm 为例，转一圈约 8.3 ms，平均旋转延迟约 4.2 ms，而寻道动辄几毫秒，传输一小块数据却只要几十微秒。

术语上要修正一句老话：**512 字节并不是“最小的物理存储单位”**。设备对上暴露的是**逻辑块大小**（`logical_block_size`，通常 512 字节），而**物理块大小**（`physical_block_size`）描述设备内部处理物理扇区的粒度，通常是 4096 字节；它不自动等于软件层的事务性或断电原子写保证。SATA 盘常见“4KB 物理扇区 + 512B 逻辑扇区”的组合，即所谓 512e（[sysfs block ABI](https://www.kernel.org/doc/Documentation/ABI/stable/sysfs-block)）。两者都由设备与固件决定，应该查设备和内核暴露的值，而不是背结论。

经典调度算法的目标是减少总寻道距离，用一个请求序列就能看出它们的差别（“柱面号”即请求所在磁道）：

- **先来先服务（First Come First Served，FCFS）**：按到达顺序服务。公平、简单，但平均寻道距离可能很长。
- **最短寻道时间优先（Shortest Seek Time First，SSTF）**：每步挑离当前磁头最近的请求。总移动距离通常更短，但两端的请求可能永远等不到——这就是饥饿。它只保证每一步局部最优，不保证全局最优。
- **扫描算法（SCAN，电梯算法）**：沿一个方向服务到没有更远的请求（教科书版本会扫到盘边）再掉头。在请求集合有限且调度持续运行时，它能避免请求无限期被越过，代价是可能做无效的远端移动；只走到最远请求就掉头的变体叫 **LOOK**。

下面这段代码用同一组请求比较三者的磁头移动总量（完整实现见本节末尾的验证映射）：

```dart
void main() {
  // 4. 磁头从第 12 号柱面出发，按到达顺序给出 6 个请求。
  const head = 12;
  final requests = [16, 34, 9, 2, 28, 36];

  final fcfsDistance = fcfs(head, requests);
  final sstfDistance = sstf(head, requests);
  final lookDistance = look(head, requests, movingUp: true);
  print('FCFS 磁头移动总量：$fcfsDistance');
  print('SSTF 磁头移动总量：$sstfDistance');
  print('LOOK 磁头移动总量：$lookDistance');

  expect(fcfsDistance == 88, '本序列的 FCFS 结果应为 88');
  expect(sstfDistance == 64, '本序列的 SSTF 结果应为 64');
  expect(lookDistance == 58, '本序列的 LOOK 结果应为 58');
  expect(
    lookDistance < sstfDistance && sstfDistance < fcfsDistance,
    '本序列上按方向服务的 LOOK 总距离更小，但单次测试不能推广为普遍结论',
  );
}
```

运行输出：

```text
FCFS 磁头移动总量：88
SSTF 磁头移动总量：64
LOOK 磁头移动总量：58
```

这组数字说明了两件事：SSTF 的“每步最近”并不等于总距离最短，带方向的 LOOK 在同一序列上更省；同时也提醒不要把一个序列的结论推广成定理——具体代价取决于请求分布和初始方向。

> **关键认知：** 经典磁盘调度算法优化的前提是“随机访问昂贵，且代价随移动距离增长”。这个前提在 HDD 上成立，在闪存设备上不成立，所以它们在现代存储栈里的角色从“减少寻道”变成“公平性与延迟控制”。

> **面试高频：** FCFS、SSTF、SCAN 的区别与适用边界？
> **答题脉络：** 先说代价模型（寻道 + 旋转 + 传输，寻道最贵）→ 三种策略分别优化什么 → SSTF 的饥饿与 SCAN 的公平性 → 指出这些算法面向机械介质。
> **追问方向：** LOOK 与 C-SCAN、饥饿的判定条件、为什么 SSD 上“最短寻道”不再是核心。

## SSD 与 NVMe 改变了哪些假设

闪存（NAND flash）的组织单位与磁盘不同：芯片分成**块**（block，有时叫擦除块，典型 128 KB 或 256 KB），块内再分成**页**（page，几 KB，例如 4 KB）。三种操作的量级差异很大：读一页仅需几十微秒，编程（写）一页约几百微秒，而擦除一整个块要几毫秒（[OSTEP 第 44 章](https://pages.cs.wisc.edu/~remzi/OSTEP/file-ssd.pdf)）。

最关键的约束是：**写之前必须先擦除整块，而已写入的页不能原地重写**。SSD 因此需要一层闪存转换层（Flash Translation Layer，FTL）：

1. 主机看到的逻辑块地址（LBA）与闪存物理页之间是一张映射表，更新数据时写到一个新的空闲页，再改映射，而不是原地覆盖。
2. 空闲页耗尽后需要**垃圾回收**（garbage collection）：把仍有效的页搬到新位置，然后擦除整块。搬移会带来**写放大**（write amplification）——主机写 1 份数据，设备内部可能写了多于 1 份。
3. 为了让各块的擦写次数大致均衡，需要**磨损均衡**（wear leveling）；预留一部分空间（over-provisioning）让垃圾回收有腾挪余地。

**TRIM/discard** 是主机向设备补充的信息：告诉设备哪些逻辑块已经不再使用，垃圾回收时就不必搬运这些“死数据”。Linux 上对应 `blkdiscard`、`fstrim`，或挂载时的 `discard` 选项。它不是免费的：频繁 trim 可能增加设备处理开销，具体频率应按设备、文件系统和工作负载决定；并非所有设备都支持高效排队 trim（[fstrim(8)](https://man7.org/linux/man-pages/man8/fstrim.8.html)）。

**NVMe** 是面向非易失性存储的协议与设备接口，常通过 PCIe 连接 SSD。它和 AHCI 时代的关键差别不是简单的“更快”，而是**并行**：主机准备多组提交队列/完成队列（SQ/CQ），可以每个 CPU 一组，队列深度可配置，设备同时服务多个队列。规范持续演进，具体版本与能力应以 [NVM Express 官方规范页](https://nvmexpress.org/specifications/) 为准。

| 维度 | HDD（机械模型） | SSD/NVMe（闪存模型） |
|---|---|---|
| 最小可寻址单位 | 逻辑块 512B/4KiB（设备暴露值） | 同样由设备暴露逻辑块大小 |
| 随机访问代价 | 寻道 + 旋转，毫秒级 | 裸闪存读十几到几十微秒，写几百微秒，擦除几毫秒 |
| 主要性能风险 | 寻道距离过长 | 写放大、垃圾回收造成的尾延迟 |
| 调度优化目标 | 减少磁头移动、避免饥饿 | 维持队列并行、限制尾延迟、少触发垃圾回收 |

> **关键认知：** NVMe 的并行来自多队列与闪存通道，而不是“延迟为零”。闪存没有寻道，但仍有擦除块、写放大和垃圾回收，所以随机写依然比顺序写更麻烦；调度也依然存在，只是目标从“最短寻道”变成“并行度、公平性与尾延迟”。

> **面试高频：** 为什么 SSD/NVMe 上 SSTF、SCAN 不再是主角？
> **答题脉络：** 先说明这些算法优化的寻道代价在闪存上不存在 → 闪存真正的代价在 FTL 映射、垃圾回收与写放大 → 因此块层目标转为并行与延迟控制 → 补一句 TRIM 的作用。
> **追问方向：** 写放大怎么算、TRIM 与 `discard` 挂载选项、磨损均衡、队列深度与并行度。

## 现代 Linux 块 I/O 层

块层位于文件系统与设备驱动之间，负责把“页缓存里的脏页”变成设备能执行的请求。当前 Linux 用的是**多队列块层（blk-mq）**，它把队列分成两级（[blk-mq 文档](https://docs.kernel.org/block/blk-mq.html)）：

- **软件暂存队列**（software staging queues）按 CPU 或 NUMA 节点划分，各自加锁，避免多核争抢同一个队列锁。请求在这里可以合并：相邻扇区的请求 3–6、6–7、7–9 可以并成 3–9，这种合并称为 plugging。
- **硬件派发队列**（hardware dispatch queues）对应设备真正支持的提交队列，是交给驱动前最后一站。

请求进入这两级队列后，可以有选择地经过一个**调度器**：`none`、`mq-deadline`、`kyber`、`bfq` 四个名字是目前内核文档列出的可运行时可切换项（[Switching Scheduler](https://docs.kernel.org/block/switching-sched.html)）。它们的定位是排序与限流（截止时间、低延迟节流、按进程或 cgroup 的公平带宽），都只在同一个队列内部生效，无法跨队列重新排序。

观察实际值只能用 sysfs，不要背“某个内核的默认值”：

```bash
# 1. 观察设备与它暴露的逻辑/物理块大小；列名随 util-linux 版本略有差异
lsblk -o NAME,TYPE,SIZE,LOG-SEC,PHY-SEC

# 2. 当前调度器被方括号括起，其余是可切换候选；名字集合随内核与设备变化
cat /sys/block/<设备名>/queue/scheduler

# 3. 排队与合并相关的两个可调项
cat /sys/block/<设备名>/queue/nomerges          # 0 允许全部合并；1 只做简单合并；2 不做合并
cat /sys/block/<设备名>/queue/discard_max_bytes # 0 表示设备不支持 discard
```

> **时效信息（核查日期：2026-09）：** `logical_block_size`、`physical_block_size`、`nomerges`、`discard_max_bytes`、`scheduler` 的含义见内核稳定 ABI 文档 [sysfs block](https://www.kernel.org/doc/Documentation/ABI/stable/sysfs-block)；可用调度器名字与默认选择取决于内核版本、设备类型与发行版配置，请读取上述文件而不是记住固定值。

> **历史机制（已移除）：** 早期的单队列调度器 `cfq`、`deadline`、`noop` 已在 Linux 5.0 的开发周期中被删除（commit `f382fb0`，2018-11），取代它们的是基于 blk-mq 的 `mq-deadline`、`kyber` 与 `bfq`（[内核提交记录](https://github.com/torvalds/linux/commit/f382fb0bcef4c37dc049e9f6963e3baf204d815c)）[核查日期：2026-09]。

> **关键认知：** 块层不改变数据内容，它决定的是“哪些请求合并成一次、以什么顺序、什么时候交给设备”；页缓存一致性、文件系统元数据与持久化语义都不由块层负责。

## 文件系统给字节块增加了什么

块设备只提供“编号的定长块数组”，而用户需要的是名字、层次目录、权限、随机访问与文件增长。文件系统补上的正是这些：

- **命名与挂载**：目录树是多个文件系统拼起来的挂载点集合；`mount` 把某个文件系统接到某个目录上。
- **目录项与 inode**：目录是“名字 → inode 编号”的映射（目录项 dentry），inode 保存类型、权限、大小、时间戳和“哪些块属于这个文件”的映射，数据本身在数据块里。
- **虚拟文件系统（Virtual File System，VFS）**：`open`/`read`/`write` 这些系统调用先进入 VFS，由它转发给具体文件系统实现；这也是同一个 `read()` 能同时读 ext4、XFS、tmpfs 和网络文件系统的原因。

这里存在三层身份，最容易在面试里被混淆：

- **文件描述符（fd）**是进程内表的索引；
- **打开文件描述（open file description）**记录文件偏移、状态标志，以及指向 inode 的引用；
- **inode** 是文件本身在文件系统里的身份。

> **关键认知：** fd 不是 inode 的别名。一次 `open` 产生一个打开文件描述；`dup` 或 `fork` 会让多个 fd 指向同一个描述（因此共享文件偏移），而两次独立 `open` 会得到两个描述（偏移互不影响），它们指向同一个 inode。

硬链接（hard link）是“多个目录项指向同一个 inode”。因此删除名字并不等于删除数据：`unlink` 只删除目录项，只有当链接计数为 0 且没有任何进程仍打开该文件时，空间才会被回收；如果最后一个名字被删除时仍有打开的描述符，文件会一直存在到最后一个 fd 关闭（[unlink(2)](https://man7.org/linux/man-pages/man2/unlink.2.html)）。下面这个玩具文件系统把这条规则显式化成引用计数（按文件顺序摘录三段；`expect` 等定义与文件头省略）：

```dart
class Inode {
  Inode(this.id);

  final int id;
  final List<int> blocks = []; // 数据块编号，按文件内偏移排列
  int linkCount = 1; // 指向该 inode 的目录项数量
  int openCount = 0; // 引用该 inode 的打开句柄数量
}

/// 只实现正常路径：名字不存在或块耗尽时直接抛错，真实内核返回 ENOENT/ENOSPC。
class TinyFileSystem {
  TinyFileSystem({this.blockCount = 8});

  final int blockCount;
  final Map<String, int> directory = {}; // 目录项：文件名 -> inode 编号
  final Map<int, Inode> inodes = {};
  final Map<int, String> blockData = {}; // 数据块编号 -> 1 字节内容
  int nextInodeId = 1;

  int get freeBlocks => blockCount - blockData.length;

  // 1. 创建：为内容分配数据块，并登记目录项。示例只用 ASCII，按字符切分等于按字节切分。
  void create(String name, String content) {
    final inode = Inode(nextInodeId++);
    for (final byte in content.split('')) {
      final block = _allocateBlock();
      blockData[block] = byte;
      inode.blocks.add(block);
    }
    inodes[inode.id] = inode;
    directory[name] = inode.id;
  }

  int _allocateBlock() {
    for (var block = 0; block < blockCount; block++) {
      if (!blockData.containsKey(block)) return block;
    }
    throw StateError('没有空闲数据块');
  }

  // 2. 读取：目录项 -> inode -> 数据块。块编号一定存在，因此取值时才用 ! 断言。
  String read(String name) => _readInode(inodes[directory[name]!]!);

  String readByHandle(int inodeId) => _readInode(inodes[inodeId]!);

  // 3. 硬链接：只新增一个目录项，两个名字共享同一个 inode。
  void hardLink(String existingName, String newName) {
    final inodeId = directory[existingName]!;
    inodes[inodeId]!.linkCount++;
    directory[newName] = inodeId;
  }
```

```dart
  // 4. 打开、删除与关闭：linkCount 与 openCount 都归零才回收数据块。
  int open(String name) {
    final inodeId = directory[name]!;
    inodes[inodeId]!.openCount++;
    return inodeId;
  }

  void unlink(String name) {
    final inode = inodes[directory.remove(name)!]!;
    inode.linkCount--;
    _releaseIfUnused(inode);
  }

  void close(int inodeId) {
    final inode = inodes[inodeId]!;
    inode.openCount--;
    _releaseIfUnused(inode);
  }

  String _readInode(Inode inode) =>
      inode.blocks.map((block) => blockData[block]!).join();

  void _releaseIfUnused(Inode inode) {
    if (inode.linkCount > 0 || inode.openCount > 0) return;
    for (final block in inode.blocks) {
      blockData.remove(block);
    }
    inodes.remove(inode.id);
  }
}
```

## 页缓存、一致性与持久化

Linux 对普通文件的默认读写走**页缓存（page cache）**：读时先查缓存，未命中才向设备发起 I/O；写时只修改缓存中的页并标记为脏（dirty）。脏页由后台回写（writeback）机制送交块层，内核提供若干可调阈值（[sysctl vm 文档](https://docs.kernel.org/admin-guide/sysctl/vm.html)）：

- `vm.dirty_expire_centisecs`：脏页“变老”多久之后有资格被回写；`vm.dirty_writeback_centisecs`：回写线程的周期。
- `vm.dirty_background_ratio` / `vm.dirty_background_bytes`：超过该量启动后台回写。
- `vm.dirty_ratio` / `vm.dirty_bytes`：超过该量时，产生脏页的进程自己被迫参与回写，表现为写入变慢。

这些状态可以直接观察：`/proc/meminfo` 里的 `Cached` 是文件页缓存，`Dirty` 是等待回写的内存，`Writeback` 是正在回写的内存（[proc_meminfo(5)](https://man7.org/linux/man-pages/man5/proc_meminfo.5.html)）。

页缓存带来三个直接后果：

1. 同一文件的重复读取可能在内存中完成，第二次读不会产生设备 I/O；`read` 的耗时因此不能用来判断介质快慢。
2. 进程 A 的写入完成后，进程 B 随后读取普通文件通常能看到同一份缓存页；可见性由内核维护，但并发时序、业务一致性仍需要应用层协调。
3. `MAP_SHARED` 的 `mmap` 映射与 `read`/`write` 访问的是同一份缓存页，两边的修改互相可见；`MAP_PRIVATE` 不提供这种写入共享语义（细节见 [虚拟内存、地址空间与函数调用](./04-虚拟内存、地址空间与函数调用.md)）。

> **关键认知：** 页缓存保证的是“同一台机器上后续的读能看到先前的写”，这是内存层面的可见性；它不提供崩溃后的可见性。持久化边界由显式同步调用、文件系统策略与设备行为共同决定，`close()` 不在其中。

要跨越持久化边界，工具只有几个：

- `fsync(fd)`：提交数据与元数据并等待设备完成；`fdatasync(fd)` 只提交保证后续读回正确的部分；`sync()` 针对所有文件系统（代价最大）。
- 新建或重命名文件后，除了文件的 `fsync`，还要对**目录**做 `fsync`，否则名字可能没落盘。
- `open` 时的 `O_SYNC`/`O_DSYNC` 让每次写入都同步，代价是失去页缓存的批量优势；`O_DIRECT` 绕过页缓存直接对设备发 I/O，但对缓冲地址、长度和偏移有对齐要求，语义也因文件系统而异，不能简单当作“更快”（[open(2)](https://man7.org/linux/man-pages/man2/open.2.html)）。
- 崩溃一致性由文件系统的策略提供：日志型（journaling）把选定的元数据（某些模式也包括数据）写入日志，再更新正式位置，崩溃后重放日志；ext4 的日志子系统是 jbd2（[ext4 文档](https://docs.kernel.org/filesystems/ext4/index.html)）。写时复制型（copy-on-write，COW）先写新块、最后原子切换指针，Btrfs 官方文档就直接把自己定义为 COW 文件系统。两者都只是把崩溃后的状态收敛到某个一致点，不承诺“没调用 `fsync` 也不丢数据”。

> **面试高频：** 页缓存、`write` 返回、`fsync` 与设备缓存之间是什么关系？
> **答题脉络：** 读路径命中页缓存 → 写路径只标脏 → 回写阈值与后台线程 → `fsync` 等待设备完成并刷设备缓存 → 指出目录项与设备谎报等边界。
> **追问方向：** 脏页阈值、`Dirty`/`Writeback` 的区别、`O_DIRECT` 的取舍、日志与 COW 的差别。

## 四组常被混淆的 I/O 词

这四组词描述的是两个正交的维度：**调用在条件不满足时的行为**（阻塞/非阻塞），以及**完成是如何被通知的**（同步/异步）。把它们放在一张表里更清楚：

| | 同步：调用返回时结果已确定 | 异步：调用只是提交，完成后另行通知 |
|---|---|---|
| 阻塞：条件不满足就睡眠等待 | 最常见的组合，普通文件的 `read`/`write` | 少见但存在：提交阶段可能阻塞，完成仍由事件通知（例如提交队列已满的异步接口） |
| 非阻塞：条件不满足立即返回错误 | 组合常见：轮询式 `read`，条件不满足返回 `EAGAIN` | 现代异步接口的典型形态：提交后继续跑，等完成事件 |

需要额外区分的是**接口组织方式**：

- **就绪模型**：先问“哪些 fd 现在可以读写”，再自己去执行 I/O。`select`/`poll`/`epoll` 属于这一类，它们只报告状态，完成结果仍由随后的 `read`/`write` 给出。
- **完成模型**：把请求提交给内核，等它把结果放到完成队列里。完成式接口能同时表达“操作完成”与“操作结果”，这是它与就绪通知的关键差别。

还要注意对象差异：对普通文件来说，数据要么已在页缓存里，要么要等设备，`O_NONBLOCK` 基本没有意义；真正会“暂时不可读/不可写”的是管道、终端和 Socket，Socket 的阻塞与非阻塞语义、事件循环与 `epoll` 细节由 [Socket 与 I/O 模型](../04-计算机网络/10-Socket与I-O模型.md) 主讲。

> **关键认知：** 阻塞/非阻塞描述“条件不满足时调用怎么办”，同步/异步描述“完成由谁通知”，两者可以组合；异步不是多线程的同义词，就绪通知也不等于完成通知。

> **面试高频：** 阻塞/非阻塞、同步/异步、就绪/完成怎么区分？
> **答题脉络：** 先给两个维度的定义 → 用 `EAGAIN` 说明非阻塞 → 用 `epoll` 与 `io_uring` 对比就绪与完成 → 最后落到具体对象（Socket 才有意义）。
> **追问方向：** `epoll` 水平/边缘触发、用户态缓冲与内核缓冲、异步 I/O 与线程池的关系。

## I/O 多路复用的边界

一个线程要同时等多个 fd，最朴素的做法是“一个 fd 一个线程”或反复轮询：前者在连接数上升时被线程栈与上下文切换拖垮，后者浪费 CPU。多路复用解决的就是这一个问题——**用一个线程等待多个 fd 的就绪状态**：

- `select`/`poll` 把待观察的集合交给内核，返回哪些 fd 已就绪；监视集合需要每次从用户态重新传入。
- `epoll` 把监视集合保存在内核的事件表里，只返回发生变化的部分，因此适合长期监视大量 fd 的场景。
- 水平触发（level-triggered）会在条件持续满足时反复通知，边缘触发（edge-triggered）只在状态变化时通知一次；后者要求一次读/写到 `EAGAIN` 为止，否则会漏事件。

这些 API 的签名、复杂度、触发模式与 Socket 事件循环写法全部由 [Socket 与 I/O 模型](../04-计算机网络/10-Socket与I-O模型.md) 负责，本文只强调它的边界：

> **关键认知：** 多路复用只解决“等谁就绪”，既不减少一次 I/O 的拷贝开销，也不改变“调用方要自己发起 I/O”的就绪语义；减少拷贝要靠零拷贝技术，改变完成通知方式要靠完成式接口。

Linux 还有一个完成式接口 `io_uring`：用户态与内核态通过共享的提交/完成环形缓冲区通信，可以批量提交异步请求，从而在合适的配置下减少“一次 I/O 一次系统调用”的开销（[io_uring(7)](https://man7.org/linux/man-pages/man7/io_uring.7.html)）。它是一个能力很强的接口，但不是“epoll 的替代品”：多路复用的使用场景仍然存在，选型要按实际事件模型判断。

## 用一次文件读取串起全链路

把前面所有层缩成一次可观察的实验：写一个最小的 C 程序，只做 `open`、`write`、可选的 `fsync`、`close`，再用 `strace` 看它真正调用了哪些系统调用。

```c
/* io_probe.c：观察 write 返回与 fsync 返回的差异。 */
#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>

int main(int argc, char **argv) {
  if (argc < 2) return 64; /* 需要目标文件路径 */
  int fd = open(argv[1], O_WRONLY | O_CREAT | O_TRUNC, 0644); /* 1. 打开普通文件 */
  if (fd < 0) return 1;
  if (write(fd, "hello", 5) != 5) return 2; /* 2. 写入页缓存后返回 */
  if (argc > 2 && fsync(fd) != 0) { /* 3. 要求把数据与元数据提交到设备 */
    close(fd);
    return 3;
  }
  close(fd); /* 4. 关闭句柄 */
  return 0;
}
```

<!-- verify: .work/verify/B05/c/io_probe.c -->

```bash
# 1. 编译：C99 以上均可，示例在 gcc 11.4（x86-64 Linux）验证
gcc -O0 -o io_probe io_probe.c

# 2. 只跟踪文件相关的系统调用，减少动态链接器噪声
strace -e trace=openat,write,fsync,close -o plain.trace ./io_probe plain.bin
strace -e trace=openat,write,fsync,close -o synced.trace ./io_probe synced.bin fsync

# 3. 过滤掉 ld.so 与 libc 的加载调用，只看这个文件
grep -E 'plain\.bin|write\(3|fsync\(3' plain.trace
grep -E 'synced\.bin|write\(3|fsync\(3' synced.trace

# 4. 同一个文件再读一次：观察 openat/read/write 与文件末尾
strace -e trace=openat,read,write,close -o read.trace cat plain.bin
grep -E 'plain\.bin|read\(3|write\(1' read.trace | grep -v ELF

# 5. 观察文件大小与已分配块；blocks 的单位是 512 字节
stat -c 'name=%n size=%s blocks=%b' plain.bin

# 6. 观察这台机器上的文件系统与块设备栈（只读操作）
findmnt -T . -o TARGET,SOURCE,FSTYPE,OPTIONS
lsblk -o NAME,TYPE,SIZE,LOG-SEC,PHY-SEC
```

两次运行的差别如下。第一次只看到打开、写入与关闭：

```text
openat(AT_FDCWD, "plain.bin", O_WRONLY|O_CREAT|O_TRUNC, 0644) = 3
write(3, "hello", 5)                    = 5
```

第二次多了一次同步调用，它才是“要求落盘”的那一步：

```text
openat(AT_FDCWD, "synced.bin", O_WRONLY|O_CREAT|O_TRUNC, 0644) = 3
write(3, "hello", 5)                    = 5
fsync(3)                                = 0
```

两个片段都按上面的 `grep` 过滤掉了动态链接器对 `ld.so.cache`、`libc.so.6` 的 `openat`。

同样的 5 个字节，第一次只看到 `write` 返回；第二次多了 `fsync`。这就是“`write` 返回”与“要求落盘”在系统调用层面的全部差别，剩下的语义在前面几节里已经解释过。

同一个文件用 `cat` 读一次，追踪到的序列是：

```text
openat(AT_FDCWD, "plain.bin", O_RDONLY) = 3
read(3, "hello", 131072)                = 5
write(1, "hello", 5)                    = 5
read(3, "", 131072)                     = 0
```

`read` 返回 5，把字节交给 `write(1, ...)` 输出到标准输出；随后是一次返回 0 的 `read`，表示已到文件末尾。如果数据此刻仍在页缓存里，这次 `read` 不会产生设备 I/O；但要注意 `strace` 本身**不能**证明缓存命中与否，它只告诉你调用发生了、返回值是多少（过滤命令里的 `grep -v ELF` 只是去掉动态链接器读取库文件的那一行）。

该实验在 Ubuntu 22.04（WSL1，内核标识 `4.4.0-22621-Microsoft`、`strace 5.16`、`gcc 11.4.0`）上验证通过[核查日期：2026-09]。

同样的谨慎也适用于本节的其他命令，哪些结论能由它们证明、哪些不能：

- **能证明**：系统调用序列、每次调用的返回字节数、文件长度与已分配块数、挂载点与文件系统类型。
- **不能证明**：是否命中页缓存（syscall 层看不到缓存命中，需要比较耗时或读内核统计）；块层是否合并了请求、是否被调度器重排（需要 ftrace/blktrace 之类的跟踪点）；设备内部 FTL 的映射与垃圾回收；设备缓存是否真的刷写。
- **环境相关**：`lsblk` 与 `cat /sys/block/<设备>/queue/scheduler` 需要真实的块设备与 sysfs；在容器或 WSL1 这类环境里可能没有 `/sys/block`，此时命令会直接报错，不能据此推断内核不支持某功能。此外 `stat` 的 `size` 与 `blocks` 只有在支持稀疏分配的文件系统上才能体现“空洞不占块”，本次实验所在的 `wslfs` 就不支持，读出为 0 并不代表没有分配。如果要从“哪个进程在读写哪个文件”入手排查，常规命令见 [Linux 命令行与进程排查](../07-工程工具与代码质量/01-Linux命令行与进程排查.md)。

## 常见误区

- ❌ `read` 一定会读盘。
  ✅ 普通文件的 `read` 先查页缓存，命中时完全不产生设备 I/O；未命中才向设备发起请求，且可能顺带预读。所以“读得很快”不能证明介质快。

- ❌ `write` 返回成功就说明数据已持久化。
  ✅ 返回只说明内核已接受数据（页缓存）。要跨越持久化边界需要 `fsync`/`fdatasync`，并注意目录项、设备缓存与文件系统策略各自的边界。

- ❌ SSD 没有寻道，所以不需要调度，也不需要考虑随机写。
  ✅ 闪存没有磁头移动，但有擦除块、写放大与垃圾回收，随机写比顺序写更容易触发设备内部搬运；块层仍在做合并、限流与延迟控制。

- ❌ 文件描述符就是 inode。
  ✅ fd 是进程内表的索引；打开文件描述记录偏移与标志；inode 是文件在文件系统中的身份。三者层次不同，因此才有“删除后仍可读”“`fork` 后共享偏移”这些现象。

- ❌ 异步 I/O 就是多开线程。
  ✅ 异步描述的是完成通知契约（提交后由事件/完成队列通知），线程只是实现异步的一种手段；完成式接口（如 `io_uring`）不需要为每次 I/O 增加线程。

- ❌ `epoll` 比所有 I/O 方案都快。
  ✅ 它优化的是“等待大量 fd 就绪”的场景；连接数少、或需要降低单次 I/O 的拷贝与系统调用开销时，其他方案可能更合适。就绪通知还要配合正确的触发模式与读写循环。

### 面试答题框架

被问到 I/O 与存储时，按“层 → 边界 → 机制 → 设备差异 → 术语 → 失败条件”的顺序组织，通常比先背算法更稳：

1. **层**：应用缓冲 → 系统调用 → VFS/文件系统 → 页缓存 → 块层 → 驱动与控制器 → 介质。
2. **边界**：`write` 返回 ≠ 落盘；持久化要 `fsync`/`fdatasync`（含目录与设备缓存）；一致性可以靠日志或 COW。
3. **机制**：轮询/中断/DMA 解决 CPU 参与方式；缓冲/缓存/假脱机解决不同瓶颈；多路复用解决“等多个 fd”。
4. **设备差异**：HDD 的代价与距离相关，SSD/NVMe 的代价与并行度、垃圾回收相关。
5. **术语**：阻塞/非阻塞与同步/异步是两个维度，就绪模型与完成模型是接口组织方式。
6. **失败条件**：什么时候这套说法不成立——例如容器里没有 sysfs、文件系统不支持稀疏文件、平台不允许删除打开的文件。

## 一句话总结

> 一次 `read`/`write` 的返回值只描述内核与设备之间的分层协作到哪一步完成，真正决定“读到什么、丢了什么、等多久”的，是页缓存、文件系统策略、块层队列与设备介质各自承担的边界。
