# 计算机网络｜06-一次网络请求的完整旅程

移动端或命令行客户端调用一次 `GET /v1/articles?id=3`，结果很慢、抛了一个 `SocketException`，或者干脆收到 502。此时“网络有问题”没有任何信息量：名称解析、本机路由、传输连接、安全握手、HTTP 语义、中间节点，任何一步都可能失败，而每一步该收集的证据完全不同。

不少人背下过一条线性流程：“先 DNS 解析，再三次握手，再 TLS 握手，然后发 HTTP 请求”。这条流程能应付复述，却解释不了真实观测：第二次打开同一个接口为什么快很多；为什么有时抓包里根本没有这次请求；为什么 `curl` 一切正常，App 里却报错。原因在于真实客户端会先查缓存、复用连接、按代理配置转发、在 IPv4 与 IPv6 之间赛跑，甚至换用 QUIC——这些行为会让“标准流程”里的整段阶段直接消失。本文固定一个 URL 作为这次旅程的坐标，按阶段走一遍，每段只解释到能继续故事为止，协议设计动机和字段细节留给各专题主文。读完应该能做到两件事：把一次请求拆成可观察的阶段；根据错误现象判断它停在了哪一步。

## 先给这次旅程划一条可复现的主线

考察这个请求：

```text
https://api.example.com:443/v1/articles?id=3#comments
```

本文描述的是这样一次请求：客户端第一次访问这个服务，本地没有可直接使用的缓存响应，也没有可以复用的空闲连接；它是普通的 HTTPS 请求，不因为它运行在浏览器、移动端还是命令行而改变主线。真实客户端会并行发起名称解析与预连接、命中缓存、经由代理或 CDN 转发、按协商结果使用不同版本的 HTTP，所以这条主线的边界是：阶段可能重叠、可能被跳过，“服务端”可能是一条链路，线上编码也可能与 URL 看不出直接关联。

把这次请求画成一张依赖关系图：

```text
输入 URL
  │
  ├─ 0. 本地检查：应用缓存 / HTTP 缓存 / 代理 / HSTS / 可复用连接
  │      命中即短路，后面的阶段不会发生
  │
  ├─ 1. 解析 URL：scheme、host、port、path、query → 请求目标
  │
  ├─ 2. 名称解析：host → 候选地址列表（A / AAAA / CNAME / HTTPS 记录）
  │
  ├─ 3. 交给下一跳：是否同子网 → 默认网关 → ARP 或 NDP → 链路层帧
  │      之后每个路由器按目的 IP 逐跳转发，TTL 递减，可能经过 NAT
  │
  ├─ 4. 建立传输与安全通道（二选一）
  │      4a. TCP 握手 → TLS 握手（ALPN 协商 HTTP 版本）
  │      4b. QUIC 握手（TLS 1.3 集成在其中）
  │
  ├─ 5. HTTP 请求：客户端 → 代理 / CDN → 负载均衡 → 应用 →（数据库等黑盒）
  │      响应沿原路返回
  │
  └─ 6. 响应交给调用方：原生客户端解码并更新状态；浏览器对 HTML 继续解析
```

> **关键认知：** 这张图的箭头表示“必须先满足的前提”，不是每次都会执行的步骤。一次请求真正走过哪些阶段，由客户端本地状态、中间节点策略和协议版本共同决定。

> **面试高频：** 输入一个 URL 之后发生了什么？
> **答题脉络：** 先声明假设（冷启动还是热路径、是否 HTTPS）→ 本地短路检查 → 解析名称 → 建立传输与安全通道 → 发 HTTP 请求 → 响应交给调用方；每一步都说明“什么时候会被跳过”。
> **追问方向：** 命中缓存时哪些阶段不存在；HTTP/3 走哪条分支；出错时如何判断停在哪一步。

## 第 0 步：客户端可能根本不发网络请求

排查“请求慢”时最容易忽略的一点是：这一步之前，很多客户端已经拿到了答案。按成本从低到高，客户端会依次尝试：

1. **应用自己的缓存**：内存字典、本地数据库、上一次结果的序列化副本。它连 HTTP 缓存都不是，但只要命中，后面的一切都不存在。
2. **HTTP 缓存**：本地副本还在新鲜期内就直接复用；过期后带验证条件去问服务端“变了没有”，未变则只回一个 304。新鲜度、验证器、共享缓存与私有缓存的规则属于 [HTTP 语义与缓存](./07-HTTP语义、缓存与版本演进.md)，这里只需要知道它可能让第 2 到第 5 步全部消失。
3. **浏览器专属：Service Worker**。页面发起的请求可能被脚本拦截，直接由缓存或自定义策略响应，网络层不会出现这次请求。原生客户端没有这一层，不要把它当成通用机制。
4. **代理配置**：浏览器一般跟随系统或 PAC 策略；Dart 的 `HttpClient` 需要显式设置 `findProxy`，例如调用 `findProxyFromEnvironment`，才会按环境变量选择代理，不能把它当作默认行为。代理意味着实际连接的地址、甚至协议版本都可能与 URL 上看到的不一致。
5. **HSTS 与可复用的连接、安全会话**：如果这个域名此前发过 `Strict-Transport-Security` 响应头，客户端会把后续的 `http://` 请求在本地改写成 `https://`，不发出任何明文请求（RFC 6797）；上次请求留下的空闲连接、TLS 会话票据也可能被直接使用，于是第 3、4 步只剩“复用”两个字。

> **关键认知：** 这些检查都是短路开关，命中的结果和失败在观测上非常像：抓包窗口里什么都没有。区分它们要看客户端是否拿到了可用结果，而不是看有没有网络流量。

## 第 1 步：解析 URL，得到请求目标

URL 是客户端的输入格式，它由 scheme、authority（host + port）、path、query、fragment 组成：

```text
https://api.example.com:443/v1/articles?id=3#comments
└─┬──┘  └──────┬───────┘└┬┘└────┬─────┘└──┬─┘└───┬───┘
scheme       host      port   path    query   fragment
```

其中有两个容易被忽略的细节：

- **fragment 不会进入请求**。RFC 9110 明确规定：请求的目标 URI 不包含 fragment 组件，fragment 只保留给客户端自己处理（例如定位到页面内的某个锚点）。所以 `#comments` 在服务端日志里永远看不到。
- **端口可以省略**。省略时按 scheme 的默认值补全，`https` 的默认端口是 443（RFC 9110 §4.2.2）。写不写 `:443` 对最终连接目标没有区别。

客户端真正发出的“请求目标”还有形式差异：直接连源站时使用 origin-form，只保留路径与查询串；请求交给代理时使用 absolute-form，把完整 URI 放进请求行（RFC 9112 §3.2）。这也是“抓包看到的请求行不一样”的常见原因。组件解析方面要注意实现差异：浏览器依据 WHATWG URL 标准，而多数通用语言的 URL 库（包括 Dart 的 `Uri`）按 RFC 3986 实现，边角用例上并不完全一致，RFC 9110 只负责限定哪些组件进入请求。

```dart
// 前置条件：Dart 3.x；纯 Dart；无第三方依赖。
// 示例职责：把 URL 拆成组件，并说明哪些组件会出现在请求行里。
// 运行：dart run .work/verify/B12/lib/url_endpoint.dart
import 'dart:io';

void check(bool condition, String message) {
  if (!condition) throw StateError('检查失败：$message');
}

void main() {
  // 1. 解析一个显式写全端口、查询串和片段标识的 URL。
  final uri = Uri.parse('https://example.com:8443/articles?id=3#comments');
  print('scheme=${uri.scheme}');
  print('host=${uri.host} hasPort=${uri.hasPort} port=${uri.port}');
  print('path=${uri.path} query=${uri.query} fragment=${uri.fragment}');

  // 2. 请求行里的 origin-form 只保留路径与查询串，不含片段标识。
  final originForm = uri.path + (uri.hasQuery ? '?${uri.query}' : '');
  print('request-target=$originForm');
  check(originForm == '/articles?id=3', 'origin-form 不应包含片段标识');

  // 3. URL 不写端口时，端口由 scheme 的默认值补全。
  final defaulted = Uri.parse('https://example.com/articles');
  print('hasPort=${defaulted.hasPort} port=${defaulted.port}');
  check(!defaulted.hasPort && defaulted.port == 443, 'https 默认端口应为 443');
  check(uri.port == 8443, '显式端口应保留');

  // 4. 片段标识只属于客户端一侧的定位信息。
  check(uri.fragment == 'comments', '片段标识应被解析出来');
  check(!originForm.contains('#'), '片段标识不得进入请求目标');
  stdout.writeln('url_endpoint: all checks passed');
}
```

```text
scheme=https
host=example.com hasPort=true port=8443
path=/articles query=id=3 fragment=comments
request-target=/articles?id=3
hasPort=false port=443
url_endpoint: all checks passed
```

> **关键认知：** 服务端看到的不是 URL，而是请求目标加上 `Host` 之类的字段。URL 中用于本地定位的片段、以及 scheme 与默认端口的组合规则，都只存在于客户端这一侧。

> **面试高频：** URL 里的 fragment 会发给服务端吗？
> **答题脉络：** fragment 属于客户端定位信息 → 目标 URI 明确排除 fragment → 请求目标里只有路径与查询串 → 需要传递的信息要放进 query 或请求体。
> **追问方向：** 默认端口与显式端口；代理场景下的 absolute-form；重定向时 fragment 如何延续。

## 第 2 步：DNS 给出候选地址

主机名不能用来建连接，必须换成地址。解析通常按“越近越先查”的顺序进行：客户端自己的缓存 → 操作系统缓存与 hosts 文件 → 系统存根解析器 → 配置的递归解析器。递归解析器代为完成向根、顶级域、权威服务器的迭代查询，并按照记录的 TTL 缓存结果。递归与迭代的差别、记录类型和加密 DNS（DoT/DoH）的细节都在 [DNS 与基础协议](./05-应用层：DNS与基础协议.md)，这里只取旅程需要的结果：客户端实际使用的解析器可能走明文，也可能走加密通道，这只影响可观测性，不影响阶段顺序。

需要强调的是**结果不是唯一地址，而是一张候选表**：一个域名可能同时有 A（IPv4）和 AAAA（IPv6）记录，可能先经过 CNAME 指向另一个名字，还可能有 HTTPS 记录（RFC 9460）在连接之前就告知端点、端口与其他服务参数。表里的每一项都有有效期，解析结果会随时间和网络位置变化。

拿到候选表之后，客户端还要决定先连哪个：优先尝试哪个地址族、要不要交错排列，属于地址选择策略；一个地址可能因为网络屏蔽、路由黑洞或地址族不可用而失败，于是有了 Happy Eyeballs——不等前一个地址彻底超时，而是按一定间隔并发尝试下一个地址，谁先成功就取消其余尝试。尝试间隔是**实现可配置的参数**：RFC 8305 建议的默认值是 250 ms、建议下限 100 ms、建议上限 2 s，实际取值因客户端而异（RFC 8305）。

> **时效信息（核查日期：2026-09）：** Happy Eyeballs 的参数以 RFC 8305 第 8 节“Summary of Configurable Values”为准，它给出的是推荐值而非固定值；实际网络里的观测数字只能作为某次测量的结果，不能升级为“所有浏览器都如此”。在代码里也能看到同一件事：`InternetAddress.lookup` 的返回类型是列表而不是单个地址，文档还特别提示列表顺序“可能、而且很可能会随时间变化”，所以下一阶段必须假设自己手里是一张候选表。

> **关键认知：** 名称解析只完成“名字到候选地址”的映射，它既不选出最终连接目标，也不保证任何一个地址可达或被允许访问。

> **面试高频：** DNS 解析成功，为什么连接仍然失败？
> **答题脉络：** 解析成功只证明名字有记录 → 地址可能过期、被墙、仅 IPv6 而本机无 IPv6 → 端口可能没有监听、被防火墙拦截 → 需要连接阶段的证据（超时还是被拒绝）才能继续。
> **追问方向：** 缓存 TTL 与陈旧记录；Happy Eyeballs 的赛跑与取消；CNAME 与 HTTPS 记录；加密 DNS 保护的是哪一段。

## 第 3 步：把分组交给下一跳

有了目标地址，数据不会“直接飞到服务器”，而是先交给本机的路由决策：

1. 用子网掩码（或前缀长度）判断目标是否与自己在同一网段：同网段就直接找该地址，不同网段则查路由表交给默认网关；
2. 无论哪种情况，都要知道下一跳的链路层地址：IPv4 用 ARP，IPv6 用邻居发现（NDP）；
3. 组装成链路层帧发出去，同一个二层网络内由交换机转发。

出了本机之后，接力棒交给路由器：每一跳都按目的 IP 查表转发，把 TTL（IPv6 中叫 Hop Limit）减一，减到 0 就丢弃并回一个“超时”消息；沿途还可能经过 NAT，把私有源地址和端口改写成公网可见的形式。

这里要纠正一个常见于旧教材的说法：**DHCP 不是每次访问网站都会发生**。主机只有在还没有地址信息（例如刚接入网络、租约过期）时才需要 DHCP 之类的配置过程；一旦拿到地址、掩码、网关和 DNS 服务器，后续访问不会再重复这一流程。

> **关键认知：** 在没有 NAT、代理或隧道改写时，目的 IP 端到端保持稳定，而链路层地址逐跳重写。所以“抓包看到的目的 MAC 是网关”完全正常，它只说明本地下一跳是谁，不说明最终服务器的位置。

细节分别属于 [物理层与数据链路层](./02-物理层与数据链路层.md) 和 [网络层：IP、路由与地址解析](./03-网络层：IP、路由与地址解析.md)：交换机如何学习、ARP 缓存如何老化、NAT 如何维护映射表、路由协议如何选路，都不在这里展开。

## 第 4 步：建立传输与安全通道

这一步开始分叉：客户端可能在 TCP 上建立 TLS，也可能直接使用 QUIC。

```text
分支 A（HTTP/1.1 或 HTTP/2）
  TCP 三次握手（1 个往返，结果：可靠有序的字节流）
    └ TLS 握手（冷启动的完整握手：TLS 1.3 为 1 个往返；TLS 1.2 通常为 2 个往返）
        └ ALPN 协商出 http/1.1 或 h2

分支 B（HTTP/3）
  QUIC 握手（把 TLS 1.3 集成在握手流程里，完整握手 1 个往返）
    └ 协商出 h3；曾访问过该服务器时，可能使用 0-RTT 提前数据
```

无论哪条分支，这一步要产出的东西是一样的：一条可以承载请求的通道，以及通道上的两个共识——**加密与身份**（由 TLS 提供），**接下来用什么 HTTP 版本说话**（由 ALPN 协商，RFC 7301）。握手在最坏情况下会失败：证书链不受信任、主机名不匹配、系统时间偏差、被中间人替换，都会让请求停在 TLS 阶段，连 HTTP 状态码都不会产生。证书链与握手的完整过程见 [HTTPS 与 TLS](./08-HTTPS与TLS.md)，TCP 三次握手与 QUIC 的传输机制见 [传输层：UDP、TCP 与 QUIC](./04-传输层：UDP、TCP与QUIC.md)。

HTTP/3 的发现通常通过 `Alt-Svc` 响应头（RFC 7838）或 HTTPS 记录（RFC 9460）完成，也可以由客户端配置或先验知识直接尝试；随后用 `h3` 这个 ALPN 标识去协商（RFC 9114）。这也解释了同一个站点为什么会出现“不同客户端跑不同 HTTP 版本”。

### 同一台服务器也能协商出不同的 HTTP 版本

下面三组输出来自同一台服务器（`example.com:443`）的实测，区别只在客户端提供的 ALPN 列表：

```text
# 客户端只提供 http/1.1
Protocol: TLSv1.3
ALPN protocol: http/1.1

# 客户端提供 h2,http/1.1
Protocol: TLSv1.3
ALPN protocol: h2

# 客户端不提供 ALPN
Protocol: TLSv1.3
No ALPN negotiated
```

> **时效信息（核查日期：2026-09-22）：** 上述输出由本机 Windows 环境中的 OpenSSL 3.5.4 实际运行得到，命令为 `openssl s_client -connect example.com:443 -servername example.com -alpn <列表>`；版本协商结果依赖客户端提供的能力列表，不能推广为“该站点固定使用某个版本”。

> **关键认知：** HTTP/2 仍然运行在 TCP 上，只是在应用层实现了多路复用；HTTP/3 也不是绕开 TLS，而是把 TLS 1.3 集成进 QUIC 握手。版本协商由客户端能力与服务端支持共同决定。

> **面试高频：** HTTP/2 是否还使用 TCP？HTTP/3 是否完全绕过了 TLS？
> **答题脉络：** 三个版本共享同一套语义，差别在编码与传输 → HTTP/2 用 TCP 加二进制分帧 → HTTP/3 用 QUIC（UDP 之上），TLS 1.3 集成在握手内 → 版本由 ALPN 决定。
> **追问方向：** 队头阻塞发生在哪一层；0-RTT 的重放风险；QUIC 建连需要几个往返。

## 第 5 步：HTTP 请求经过中间节点到达服务

通道准备好之后，客户端才发出真正的应用层消息。一个可读的 HTTP/1.1 请求长这样：

```http
GET /v1/articles?id=3 HTTP/1.1
Host: api.example.com
Accept: application/json
```

响应类似：

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 67
Cache-Control: max-age=60
ETag: "article-list-v7"

{"articles":[{"id":3,"title":"一次网络请求的完整旅程"}]}
```

要注意两点：这只是 HTTP/1.1 的文本形式，HTTP/2 和 HTTP/3 线上使用二进制帧与头部压缩，但方法、状态码、字段名和语义完全相同；`Host` 字段在 HTTP/2 里由 `:authority` 伪首部承担。方法与状态码的含义、字段体系、压缩与分块、条件请求都在 [HTTP 语义、缓存与版本演进](./07-HTTP语义、缓存与版本演进.md) 里，本篇只把它们当作旅程中的坐标。

“服务端”在真实链路上通常是一串节点：

```text
客户端 →（正向代理）→ CDN / 边缘节点 → 反向代理或负载均衡 → 应用服务 →（缓存、数据库等黑盒）
      ←────────────── 响应沿原路返回 ──────────────
```

这意味着你看到的响应可能根本不是应用代码产生的。实测中这个响应就带着缓存节点的痕迹：

```text
< HTTP/1.1 200 OK
< Server: cloudflare
< cf-cache-status: HIT
< Age: 3
```

`Age` 是标准字段，表示发送方估计的“响应自源站生成或验证以来经过的秒数”（RFC 9111 §5.1）；`cf-cache-status` 则是厂商专有字段。两者合起来提示这次响应很可能由边缘缓存直接给出、没有回到源站——但单个响应头只能作为线索，不能证明链路上每一跳的具体行为。数据库、消息队列、业务编排属于应用内部实现，本文只把它们当作黑盒：HTTP 层面的证据（状态码、字段、耗时）只能证明“这条链路上发生了什么”，不能代替服务端日志。携带凭证的请求还要注意 Cookie 与 `Authorization` 字段的边界，机制与安全取舍见 [身份认证：Cookie、Session 与 JWT](./09-身份认证：Cookie、Session与JWT.md)。

> **关键认知：** HTTP 版本只决定消息如何编码与承载，不改变方法与状态码的含义。请求方拿到的响应可能来自缓存或中间节点，应用代码未必参与。

## 第 6 步：响应回到调用方

响应到达后，客户端要做的事取决于它是哪种调用方：

- **原生客户端（Dart、移动端、命令行）**：读取状态码与字段，把响应体解码成数据结构，然后更新界面或业务状态。Dart 的 `HttpClient` 要求把响应体读完（或者用 `drain` 丢弃），否则会留下资源泄漏。
- **浏览器**：如果响应是 HTML，后续才进入解析与渲染流程；如果是 JSON，通常由脚本读取后再更新页面。

### 浏览器分支：响应如何变成页面

浏览器拿到 HTML 之后会一边解析一边发现子资源（CSS、脚本、图片、字体），并为它们发起新的请求；DOM 与样式表组合成渲染树，再经过布局与绘制才变成可交互的页面。这条路径属于浏览器实现细节，本文不展开（可参考 MDN 的 [Critical rendering path](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Critical_rendering_path)），只保留一个对排查有用的结论：**“收到响应”、“HTML 下载完”、“页面可以交互”、“所有资源加载完”是四个不同时间点**，用其中一个去解释另一个会得到错误结论。

> **关键认知：** HTTP 完成只说明“响应字节到达了调用方”。业务是否正确、界面是否可用、数据是否被展示，都属于应用层问题，需要应用自己的证据（日志、埋点、状态）。

## 冷路径、暖路径与 HTTP/3

同一个请求在不同状态下走过的阶段数量差别很大：

```text
阶段            冷路径（首次，TCP 承载）        暖路径（连接可复用）       HTTP/3（首次，QUIC 承载）
本地检查        无可用响应                      无可用响应                 无可用响应
名称解析        DNS 查询（或缓存未命中）        通常命中缓存               通常命中缓存
传输与安全      TCP 握手 → TLS 握手            复用已建立的连接与密钥     QUIC 握手（含 TLS 1.3）
版本协商        ALPN 协商出 h2 或 http/1.1      沿用上次协商结果           ALPN 协商出 h3
应用数据        TLS 握手完成后才发出            立即发出                   1 个往返后发出；有会话票据时可用 0-RTT
```

数值上不要把各阶段简单相加：DNS 与连接可能并行、连接与 TLS 可以在下一次请求中整段消失、HTTP/2 的多路复用让多个请求共享同一条连接、QUIC 的握手把两个往返合并成一个。0-RTT 也有明确代价：它使用事先得到的会话信息提前发送应用数据，而这些数据**可以被攻击者原样重放**，因此不适合承载“重放一次就会产生副作用”的请求（RFC 9001 §4.6），这与方法的幂等性直接相关，语义边界见 [HTTP 语义、缓存与版本演进](./07-HTTP语义、缓存与版本演进.md)。

### 连接复用让后续请求少走几段

下面这段代码在服务端地址和端口固定、请求按顺序发送的实验条件下，用客户端端口变化来观察复用：前后请求使用相同的四元组，才说明复用了同一条 TCP 连接；不能仅凭端口号在一般网络环境中断言连接相同。

```dart
// 前置条件：Dart 3.x；纯 Dart；无第三方依赖。
// 示例职责：用服务端观察到的客户端端口证明连接复用，并给出关闭连接的反例。
// 运行：dart run .work/verify/B12/lib/connection_reuse.dart
import 'dart:convert';
import 'dart:io';

void check(bool condition, String message) {
  if (!condition) throw StateError('检查失败：$message');
}

Future<void> main() async {
  // 1. 记录每个请求实际使用的 TCP 连接，用客户端远端端口区分，顺序与请求一致。
  final server = await HttpServer.bind(InternetAddress.loopbackIPv4, 0);
  final ports = <int>[];
  server.listen((request) async {
    ports.add(request.connectionInfo?.remotePort ?? -1);
    // 2. /close 让服务端在本次响应后关闭连接，迫使客户端下次重新建连。
    if (request.uri.path == '/close') {
      request.response.persistentConnection = false;
    }
    request.response.write('path=${request.uri.path}');
    await request.response.close();
  });

  final client = HttpClient();
  Future<void> fetch(String path) async {
    final request = await client.getUrl(
      Uri.parse('http://127.0.0.1:${server.port}$path'),
    );
    final response = await request.close();
    await response.transform(utf8.decoder).join();
    check(response.statusCode == 200, '$path 应返回 200');
    // 3. 让出一次事件循环，等客户端把用完的连接放回空闲池。
    await Future<void>.delayed(Duration.zero);
  }

  try {
    await fetch('/first');
    await fetch('/second');
    print('连续两次请求使用的端口=$ports');
    check(ports.length == 2 && ports[0] == ports[1], '默认持久连接应复用同一条连接');

    await fetch('/close');
    await fetch('/third');
    print('三次请求使用的端口=${ports.toSet().toList()}');
    check(ports[2] != ports[3], 'Connection: close 之后应新建连接');
    check(ports.toSet().length == 2, '整个过程只应出现两条 TCP 连接');
  } finally {
    client.close(force: true);
    await server.close(force: true);
  }
}
```
<!-- verify: .work/verify/B12/lib/connection_reuse.dart -->

```text
连续两次请求使用的端口=[9712, 9712]
三次请求使用的端口=[9712, 9713]
```

前两次请求落在同一个客户端端口上，说明连接被复用；第三次请求前服务端主动关闭了连接，客户端下次只能新建，于是出现第二个端口。Dart 文档也说明 `HttpClient` 会缓存连接以便复用，空闲连接由 `idleTimeout` 控制，单主机并发连接数由 `maxConnectionsPerHost` 限制。

> **关键认知：** 暖路径变快不是因为“网络变好了”，而是因为少走了若干阶段。判断一次请求是冷是暖，要看有没有复用连接或命中缓存，而不是看总耗时。

> **面试高频：** 首次请求和复用连接的请求差别在哪里？
> **答题脉络：** 冷路径包含名称解析、连接建立、安全握手 → 暖路径复用连接与密钥，可能只剩请求与响应 → 缓存命中时连响应都可能来自本地 → 因此不能把冷路径耗时当成常态。
> **追问方向：** TLS 会话恢复与 0-RTT；HTTP/2 的多路复用；`Connection: close` 与连接池上限。

## 把“慢”拆成可观测的时间段

“慢”必须落到可测量的阶段上，否则无法采取行动。常用的划分与它们的边界是：

| 阶段 | 观测边界 | 常见误解 |
| --- | --- | --- |
| 名称解析 | 请求开始到拿到候选地址 | 命中缓存时接近 0，不代表 DNS 每次都很快 |
| 连接建立 | 确定地址到传输连接可用 | 连接成功不代表目标服务健康 |
| 安全握手 | 连接可用到密钥就绪、版本协商完成 | 只测 TCP 连接成功会漏掉 TLS 的往返 |
| 首字节等待 | 请求发出到收到第一个响应字节 | 含网络往返与所有中间节点等待，不是服务端执行时间 |
| 内容下载 | 首字节到响应体读完 | 受带宽、压缩方式和报文大小影响 |
| 本地处理 | 读完字节到界面或业务可用 | 与网络无关，却常被算进“网络慢” |

```dart
// 前置条件：Dart 3.x；纯 Dart；无第三方依赖。
// 示例职责：观察一次请求的“建连 → 首字节 → 响应体读完”三个可测量点。
// 运行：dart run .work/verify/B12/lib/journey_timeline.dart
import 'dart:convert';
import 'dart:io';

void check(bool condition, String message) {
  if (!condition) throw StateError('检查失败：$message');
}

Future<void> main() async {
  // 1. 端口写 0 由系统分配空闲端口，只监听回环地址，不依赖外部网络。
  final server = await HttpServer.bind(InternetAddress.loopbackIPv4, 0);
  server.listen((request) async {
    request.response
      ..statusCode = HttpStatus.ok
      ..headers.contentType = ContentType.json
      ..write('{"ok":true}');
    await request.response.close();
  });

  final client = HttpClient();
  final uri = Uri.parse('http://127.0.0.1:${server.port}/health');
  final watch = Stopwatch()..start();

  try {
    // 2. 建立连接：目标是 IP 字面量，所以这里只有握手，没有 DNS。
    final request = await client.getUrl(uri);
    final connected = watch.elapsed;

    // 3. 发出请求并等到响应头，即第一个字节到达的时刻（TTFB）。
    final response = await request.close();
    final firstByte = watch.elapsed;

    // 4. 读完响应体，对应“内容下载”阶段。
    final body = await response.transform(utf8.decoder).join();
    final finished = watch.elapsed;

    print('连接可用: ${connected.inMilliseconds} ms');
    print('首字节 TTFB: ${firstByte.inMilliseconds} ms');
    print('响应体读完: ${finished.inMilliseconds} ms');
    print('status=${response.statusCode} body=$body');
    print('服务端连接数=${server.connectionsInfo().total}');

    check(response.statusCode == HttpStatus.ok, '本地服务应返回 200');
    check(body == '{"ok":true}', '响应体应完整读回');
    check(server.connectionsInfo().total == 1, '一次请求应只用一条连接');
  } finally {
    client.close(force: true);
    await server.close(force: true);
  }
}
```

```text
连接可用: 22 ms
首字节 TTFB: 35 ms
响应体读完: 38 ms
status=200 body={"ok":true}
服务端连接数=1
```

三个时间点分别对应“连接建立完成”、“第一个响应字节到达”和“响应体读完”。示例使用 IP 字面量，所以没有名称解析阶段——这正是前面反复强调的边界：能测到哪几段，取决于这次请求真的走了哪几段。

时间与命令行的对应关系可以直接记两条：`time_namelookup` 对应名称解析完成，`time_starttransfer` 对应第一个字节到达且已包含此前的全部准备工作。因为后一个变量包含前一个，**“首字节等待”应取 `time_starttransfer - time_pretransfer`**。

> **关键认知：** 首字节等待里至少含一个网络往返，还包含所有中间节点的等待。要得到纯服务端耗时，必须依赖服务端自己的计时（例如 `Server-Timing` 响应头或应用埋点），不能从客户端总耗时猜测。

## 按失败阶段排查

不同阶段失败时，“下一条证据”完全不同。下表把常见现象映射到阶段：

| 现象 | 请求停在哪一步 | 已经证明 | 还没有证明 | 下一步工具 |
| --- | --- | --- | --- | --- |
| 域名无法解析 | 名称解析 | 名字到地址的映射失败 | 目标是否可达 | `nslookup` / `Resolve-DnsName` |
| 连接超时 | 路由、防火墙或对端静默丢弃 | 数据包没有等到任何回应 | 目标服务是否在监听 | `traceroute` / 抓包 |
| 连接被拒绝 | 目标主机的端口 | 对端可达但拒绝该端口 | 换端口或换路径是否可行 | `curl` / 端口探测 |
| 证书不受信任或主机名不匹配 | 安全握手 | 传输连接已建立，身份验证未通过 | 业务逻辑是否正确 | `openssl s_client` |
| 404 | HTTP 应用路由 | HTTP 通道已走通，某台服务器给出了响应 | 资源是否真的存在（路径可能写错） | 服务端访问日志 |
| 401 / 403 | HTTP 认证或授权 | 请求到达了负责鉴权的节点 | 凭证是否有权限 | 服务端鉴权日志 |
| 502 / 503 | HTTP 中间节点或源站 | 有响应，但响应不是正常结果 | 具体是哪一跳故障 | 网关日志、上游健康检查 |
| 响应解码失败 | 本地处理 | 字节已经到达客户端 | 字段与类型是否符合约定 | 打印原始响应体与字段 |
| 浏览器报 CORS | 浏览器的读取策略 | 浏览器拒绝把响应交给脚本 | 服务端是否收到并处理了请求 | 浏览器网络面板、`curl` |

```dart
// 前置条件：Dart 3.x；纯 Dart；无第三方依赖。
// 示例职责：区分“传输阶段失败”和“HTTP 阶段返回错误状态”两种结果。
// 运行：dart run .work/verify/B12/lib/stage_errors.dart
import 'dart:convert';
import 'dart:io';

void check(bool condition, String message) {
  if (!condition) throw StateError('检查失败：$message');
}

Future<void> main() async {
  // 1. 本地服务按路径返回不同的状态码。
  final server = await HttpServer.bind(InternetAddress.loopbackIPv4, 0);
  server.listen((request) async {
    final status = switch (request.uri.path) {
      '/missing' => HttpStatus.notFound,
      '/bad-gateway' => HttpStatus.badGateway,
      _ => HttpStatus.ok,
    };
    request.response
      ..statusCode = status
      ..write('status=$status');
    await request.response.close();
  });

  final client = HttpClient();
  try {
    for (final path in ['/ok', '/missing', '/bad-gateway']) {
      final request = await client.getUrl(
        Uri.parse('http://127.0.0.1:${server.port}$path'),
      );
      final response = await request.close();
      final body = await response.transform(utf8.decoder).join();
      print('$path -> ${response.statusCode} ${response.reasonPhrase} $body');
      // 2. 只要拿到状态码，就说明 HTTP 阶段已经完成，而不是传输失败。
      check(response.statusCode >= 100, '$path 应得到完整响应');
    }
  } finally {
    client.close(force: true);
    await server.close(force: true);
  }

  // 3. 连接建立失败在 Dart 里抛 SocketException，不会伪装成状态码。
  final probe = await ServerSocket.bind(InternetAddress.loopbackIPv4, 0);
  final closedPort = probe.port;
  await probe.close();
  final failing = HttpClient();
  try {
    final request = await failing.getUrl(
      Uri.parse('http://127.0.0.1:$closedPort/'),
    );
    await request.close();
    throw StateError('连接本应失败');
  } on SocketException catch (error) {
    print('连接失败: ${error.message} osError=${error.osError?.errorCode}');
    check(error.osError != null, '连接被拒绝时应带系统错误码');
  } finally {
    failing.close(force: true);
  }
}
```
<!-- verify: .work/verify/B12/lib/stage_errors.dart -->

```text
/ok -> 200 OK status=200
/missing -> 404 Not Found status=404
/bad-gateway -> 502 Bad Gateway status=502
连接失败: 远程计算机拒绝网络连接。 osError=1225
```

这段输出给出两种完全不同的失败形态：**拿到状态码意味着 HTTP 阶段已经完成**，404 和 502 都是“服务器有话要说”；而**连接阶段失败会抛出异常**（`SocketException` 并带系统错误码），根本走不到 HTTP。排查时第一步就是分清自己面对的是哪一种。

浏览器特有的 CORS 报错需要单独理解：它是浏览器基于响应字段实施的读取限制，原生客户端与命令行工具都不执行这套策略。所以同一个响应在 `curl` 或 App 里正常、在浏览器里报错，通常说明问题出在浏览器策略，而不是网络或服务端不可达。预检的触发条件、`Access-Control-Allow-*` 字段与本场景的排查方法见[浏览器边界：同源策略与 CORS](./07-HTTP语义、缓存与版本演进.md#浏览器边界同源策略与-cors)。

> **关键认知：** 错误发生在哪个阶段，决定了下一步该看什么证据。单个状态码只能说明“有一台 HTTP 服务器作出了回应”，不能推断具体是哪台机器、哪段代码出了问题。

> **面试高频：** 收到 404 和收到 502 分别说明什么？
> **答题脉络：** 两者都证明 HTTP 通道走通并拿到了响应 → 404 表示目标资源在该服务器上不存在，通常是路径、方法或部署版本问题 → 502 表示某个中间节点无法从上游得到有效响应，问题更可能在链路或上游服务 → 都要用服务端日志继续定位。
> **追问方向：** 503 与 502 的差别；响应里的 `Server` 字段能否定位到具体节点；重定向发生在哪一步。

## 用一组命令复走这次旅程

下面几条命令按本文的顺序执行，用来把主线拆成可以单独观察的片段：

```bash
# 1. 名称解析：这个名字现在能解析出什么地址
nslookup example.com
#   PowerShell 中更规整的写法：Resolve-DnsName example.com -Type A

# 2. 路径探测：数据包离开本机后经过哪些跳
tracert -h 4 example.com

# 3. 连接与请求：-v 打印解析、连接、ALPN 与请求响应行，-L 跟随重定向
curl -v -L https://example.com/ -o /dev/null

# 4. 分段耗时：starttransfer 已经包含此前的全部准备工作
curl -sS -o /dev/null -w 'namelookup=%{time_namelookup} connect=%{time_connect} appconnect=%{time_appconnect} starttransfer=%{time_starttransfer} total=%{time_total} http_version=%{http_version}\n' https://example.com/

# 5. 握手细节：TLS 版本、ALPN 结果与证书链
openssl s_client -connect example.com:443 -servername example.com -alpn h2,http/1.1
```

> **关键认知：** 命令行的输出是“网络与协议”的证据；客户端实际行为还受缓存、代理、安全策略和应用代码影响。两者只有同时成立，才能说这个请求真的通了。

## 常见误区

**误区一：DNS 解析成功就说明服务器可以访问。** 解析只给出候选地址，可达性、端口、权限都是后续阶段的事；IPv6 地址存在而本机网络不支持 IPv6 就是最常见的反例。

**误区二：HTTPS 是一种新的应用协议。** HTTPS 是 HTTP 运行在 TLS 之上，请求方法与状态码仍然属于 HTTP；TLS 只负责身份、机密性与完整性。

**误区三：HTTP/2 已经不用 TCP，HTTP/3 完全绕开 TLS。** HTTP/2 仍基于 TCP；HTTP/3 使用 QUIC（UDP 之上），并把 TLS 1.3 集成进握手，而不是不需要 TLS。

**误区四：每次请求都会完整走一遍流程，而且严格串行。** 缓存命中、连接复用、TLS 会话恢复、HTTP/3 首次建连的差异都会让阶段数量变化；“标准流程”是依赖关系，不是执行顺序表；名称解析、连接建立与资源加载也可能并行。

**误区五：拿到 200 就说明业务正确、页面可用。** 200 只说明这次 HTTP 交互成功，页面可能仍有脚本异常、子资源失败或渲染问题；业务正确性需要应用自己的证据。

**误区六：TTFB 就是服务端处理时间。** 首字节等待包含至少一个网络往返，以及所有中间节点的排队与等待；要拆分服务端耗时，需要用 `Server-Timing` 或应用埋点。

**误区七：浏览器报 CORS 说明请求没有发出去。** 不需要预检的跨域请求已经发出，只是响应被浏览器挡住；只有需要预检的请求才会在预检失败时不发出真实请求（判定与字段见[浏览器边界：同源策略与 CORS](./07-HTTP语义、缓存与版本演进.md#浏览器边界同源策略与-cors)）。

## 一句话总结

> 一次网络请求的起点是客户端本地的短路检查，终点是应用能否使用响应；把两端之间每一段都变成可观测的证据，才能把“网络慢或网络坏了”拆成可定位、可验证的结论。
