# 数据表示｜Base64 编码

把一张图片、一个压缩包或任意一段字节塞进邮件正文、URL 参数、JSON 字段时，通常只有可打印文本才能安全通行：控制字符可能被当成指令，换行可能被截断，引号可能改变结构。Base64 用一组固定、可打印的 ASCII 字符重新表示这些字节，成为最常被顺手使用、也最常被误解的编码之一。

它经常被当成加密、压缩或“能保护数据”的手段，这些说法都站不住脚。本文先建立“二进制如何进入文本通道”的问题模型，再用可运行的 Dart 示例观察编码、padding 与折行行为，最后解释“为什么是 6 位一组”，并亲手实现一个最小的编码器和解码器。

## 为什么需要 Base64

计算机中的图片、压缩包、音频和可执行文件，本质上都是一串任意取值的字节。可是很多传输场景最初只允许比较有限的文本字符，例如电子邮件正文、URL 参数、JSON 字段或只接受文本的配置文件。

如果直接把二进制字节塞进这些场景，可能遇到以下问题：

- 某些字节会被当成控制字符，导致内容被截断或解释错误；
- 不同系统对换行、引号、不可打印字符的处理方式不同；
- 复制、粘贴和日志记录时，原始字节很容易被破坏。

Base64 的思路很直接：把任意二进制转换成一组相对安全、可打印的 ASCII 字符。接收方再按照同一套规则反向转换，就能还原原始字节。

> **关键认知：** Base64 解决的是“二进制如何放进文本通道”的问题，不负责保密，也不改变数据含义。

今天通用的规则由 RFC 4648 统一描述，它同时定义了 Base16、Base32 和 Base64 三种编码；电子邮件场景里的折行要求则来自更早的 RFC 2045（MIME）。本文先聚焦最常用的 Base64，这两份规范里的其他内容在后面几节展开。

## Base64 做了什么

Base64 每次处理 3 个字节：

1. 3 个字节一共是 24 位；
2. 将这 24 位从左到右切成 4 组，每组 6 位；
3. 每组 6 位可以表示 `0` 到 `63` 共 64 个数；
4. 用这个数作为下标，从 Base64 字符表中取出一个字符。

### Base64 字符表

标准 Base64 字符表按下标排列如下：

```text
下标  0        25 26       51 52       61 62 63
字符  A ...    Z  a ...    z  0 ...    9  +  /
```

下标 `0` 对应 `A`，下标 `25` 对应 `Z`；接着是小写字母、数字，最后是 `+` 和 `/`。

### 用 `Man` 走一遍完整过程

字符串 `Man` 在 ASCII/UTF-8 中的三个字节是：

```text
M       a       n
01001101 01100001 01101110
```

把三个字节拼起来并切成四组 6 位：

```text
010011  010110  000101  101110
  19      22       5       46
  T       W        F        u
```

所以：

```text
Man -> TWFu
```

这里没有压缩数据，也没有改变数据的含义，只是改变了表示方式。

> **面试高频：** Base64 与加密有什么区别？
> **答题脉络：** 编码只改变表示 → 不需要密钥，任何人都能还原 → 保密要靠加密，完整性要靠消息认证码或签名 → Base64 只是这些机制外层的文本封装。
> **追问方向：** URL-safe 变体、padding、JWT 为什么使用 Base64URL。

## padding：为什么输出会出现等号

Base64 希望每次输出 4 个字符，但输入不一定刚好有 3 个字节。此时用 `=` 把输出补齐到 4 个字符：

| 输入字节数 | 输出形式 | 示例 |
| --- | --- | --- |
| 3 的倍数 | 4 个有效字符 | `Man` → `TWFu` |
| 余 2 个字节 | 3 个有效字符 + `=` | `Ma` → `TWE=` |
| 余 1 个字节 | 2 个有效字符 + `==` | `M` → `TQ==` |

以 `Ma` 为例：两个字节只有 16 位，切出前 2 组完整的 6 位（共 12 位）后还剩 4 位。编码器把这 4 位放入第三组的高位，低 2 位补零，得到第三个有效字符；第四组没有任何输入位，因此使用 `=` 占位。

`=` 不是用来表示某个 6 位数的字符，它表示“这一组没有对应的输入字节”。RFC 4648 第 3.2 节的默认规则是：实现必须在输出末尾带上足够的 `=`，除非引用它的协议另有明确说明。确实有协议会省略 `=`——在 URI 里 `=` 通常还要被百分号编码，当数据长度可以隐式得知时，RFC 4648 允许直接跳过 padding——但把这种字符串交给严格解码器之前，仍需要按 4 的倍数把它补回来。

还有一个容易忽略的规范性细节：padding 补出的无效位必须全部为 `0`，这样同一组字节才只有一个规范表示。例如 1 个字节只使用第二个字符的高 2 位，低 4 位应为 `0`。宽松解码器可能接受非零的补位，但签名、缓存键或协议校验等需要规范表示的场景应拒绝它。

> **关键认知：** `=` 不是字符表里的第 65 个符号，它只声明“这一组缺几个输入字节”，解码时要丢弃补零产生的多余位。

> **面试高频：** 为什么 Base64 末尾会出现 `=`？
> **答题脉络：** 8 位字节与 6 位字符不对齐 → 不足 3 字节时补零并占位 → padding 只补表示、不补数据 → 省略 padding 的协议必须能自行确定长度。
> **追问方向：** URL 中 `=` 的百分号编码、JWT 的 unpadded Base64URL、解码器对非字母表字符的两种策略。

## 最小可运行示例

### 用 Dart 编码和解码

Dart 标准库 `dart:convert` 自带 Base64 支持：

```dart
// 前置条件：Dart 3.12.2；纯 Dart，仅依赖 dart:convert。
// 运行：dart run .work/verify/DD3/base64_basics.dart
import 'dart:convert';

void main() {
  const text = '你好，Base64';

  // 1. 文本先按 UTF-8 编码成字节，Base64 处理的是字节而不是抽象字符。
  final raw = utf8.encode(text);

  // 2. 把字节编码成标准 Base64，结果是一段可打印的 ASCII 文本。
  final encoded = base64Encode(raw);
  print('编码: $encoded');

  // 3. 先把 Base64 文本解码回字节，再按同一编码还原文本。
  final decoded = utf8.decode(base64Decode(encoded));
  print('解码: $decoded');

  // 4. 断言往返无损，避免只凭“看起来对”判断结果。
  if (decoded != text) {
    throw StateError('往返结果不一致: $decoded');
  }
}
```
<!-- verify: .work/verify/DD3/base64_basics.dart -->

文本在进入 Base64 之前必须先转成字节，解码后再用同一编码解释字节；`utf8.encode` 与 `utf8.decode` 就是这一步的约定。如果把 Base64 当成字符级别的方法，遇到非 ASCII 文本时就会出现“解码正确但显示乱码”的现象，完整规则见[字符编码与乱码](./02-字符编码与乱码.md)。

### 用命令行处理文件

也可以使用系统命令处理文件。下面的例子把 `input.bin` 编码到标准输出，再解码到 `output.bin`：

```bash
# 1. -w 0 避免 GNU coreutils base64 为长文本自动插入换行。
base64 -w 0 input.bin > input.bin.b64

# 2. -d 表示 decode，解码后的字节会原样写入目标文件。
base64 -d input.bin.b64 > output.bin

# 3. 用 sha256sum 验证原文件和解码后的文件是否完全相同。
sha256sum input.bin output.bin
```

不同操作系统的 `base64` 参数可能略有差异。如果 `-w 0` 不被支持，可以用 Dart 示例处理，或者查阅当前系统的 `base64 --help`。为什么一个编码工具会“默认插入换行”？答案在 MIME 换行一节。

### URL-safe Base64

标准字符表中的 `+` 和 `/` 在 URL 或文件名中可能需要额外转义，因此 URL-safe Base64 将它们分别替换成 `-` 和 `_`：

```text
标准 Base64:    +  /
URL-safe:       -  _
```

用 Dart 观察同一组字节在两种字母表下的输出：

```dart
// 前置条件：Dart 3.12.2；纯 Dart，仅依赖 dart:convert。
// 运行：dart run .work/verify/DD3/base64_url_safe.dart
import 'dart:convert';

void main() {
  // 1. 这组字节在标准 Base64 中会同时出现 + 和 /。
  final raw = <int>[0xde, 0xad, 0xbe, 0xef, 0xfb, 0xff];

  // 2. 标准 Base64 的 + 和 / 放进 URL 或文件名时可能需要额外转义。
  final standard = base64Encode(raw);
  print('标准 Base64: $standard');

  // 3. URL-safe 版本把它们替换成 - 和 _；这里再去掉末尾的 padding。
  final token = base64UrlEncode(raw).replaceAll('=', '');
  print('URL-safe: $token');

  // 4. 解码前按 4 的倍数补回 padding，Dart 的解码器要求长度合法。
  final padded = token.padRight(token.length + (4 - token.length % 4) % 4, '=');
  final restored = base64Url.decode(padded);

  // 5. 断言还原出的字节与原文一致。
  if (base64UrlEncode(restored) != base64UrlEncode(raw)) {
    throw StateError('还原失败');
  }
  print('还原成功');
}
```
<!-- verify: .work/verify/DD3/base64_url_safe.dart -->

URL-safe 和标准 Base64 的主要差别是字符表，不是安全等级。看到一段字符串时，应先确认它使用哪种变体以及是否省略了 padding；JWT 的头部和载荷就是典型的 unpadded Base64URL 使用者（见[身份认证与 JWT](../04-计算机网络/09-身份认证：Cookie、Session与JWT.md)）。

## 大小为什么会膨胀

原始数据每 3 个字节输出 4 个 ASCII 字符，而一个 Base64 字符只承载 6 位信息。因此对于较大的数据，纯 Base64 载荷大小大约变成原来的 `4 / 3`，也就是增加约 `33.3%`；如果采用 MIME 换行，还要额外计算换行符的开销。

精确的输出长度可以用下面的公式计算：

```text
Base64 长度 = ceil(原始字节数 / 3) × 4
```

例如：

```text
3 字节  -> 4 个字符
10 字节 -> ceil(10 / 3) × 4 = 16 个字符
```

对于很短的数据，padding 会让比例更夸张：1 个字节会变成 4 个字符，相当于 4 倍。因此上传大文件时，Base64 通常会增加网络流量和内存占用；如果协议允许直接传二进制，通常不必为了“看起来像文本”而编码。

> **关键认知：** 膨胀来自“每个字符只承载 6 位”，与内容本身是否可压缩无关；压缩和编码是两件不同的事。

> **面试高频：** Base64 之后体积会变大多少？
> **答题脉络：** 3 字节 → 4 字符，稳定膨胀 4/3 约 33% → 短数据因 padding 比例更高 → 节省空间要靠 gzip、zstd 等压缩算法，不能指望 Base64。
> **追问方向：** Data URL 的体积、链路中重复编码的代价、JWT 为什么要控制载荷大小。

## 常见误区

### Base64 不是加密

Base64 使用公开规则，而且不需要密钥，任何人都可以解码。它不能防止查看、篡改或伪造：

```bash
printf 'secret' | base64
printf 'c2VjcmV0' | base64 -d
```

需要保密时使用 TLS、加密算法和密钥管理；需要证明内容未被篡改时使用消息认证码或数字签名。Base64 最多只是这些机制外层的文本封装。

### 不要混淆“文本”和“字节”

Base64 的输入是字节。文本在进入 Base64 之前必须先约定编码，例如 UTF-8；解码后也要使用同一编码解释字节。否则 Base64 虽然解码正确，显示出来的文字仍可能不对。

### 标准 Base64、URL-safe Base64 不能随意混用

如果数据中出现 `-`、`_`，它很可能是 URL-safe 变体；如果接口要求省略 `=`，就不能简单地把它当作完整的标准 Base64 交给严格解码器。

### 不要重复编码

第一次编码的结果仍然是普通文本。如果把它再次 Base64 编码，得到的只会是“Base64 字符串的 Base64”，并不会增加安全性，大小还会继续膨胀。排查时要确认数据在链路中被编码了几次。

### Base64 不等于压缩

它通常使数据变大，不会减少数据量。如果目标是节省空间，应先使用 gzip、zstd 等压缩算法，再根据传输协议决定是否需要 Base64。

## MIME 换行：76 个字符的限制从哪里来

### 为什么编码结果会被折行

前面的命令行示例用 `base64 -w 0` 特意关闭了折行。为什么一个编码工具会默认换行？这要回到 Base64 最早的大规模应用场景：电子邮件。

SMTP 是一种逐行传输文本的老协议，对行长有硬性限制：每行不超过 1000 个字节，包括行尾的 CRLF（现行规范 RFC 5321 第 4.5.3.1.6 节）。一封带附件的邮件经过 Base64 编码后可能有几万甚至几百万个字符，如果不折行，一行超长文本就可能让链路上的邮件服务器出问题。

### RFC 2045 与 RFC 4648 的规定

MIME（RFC 2045 第 6.8 节）对邮件中的 Base64 提出了两条要求：

1. 编码输出必须分行表示，**每行不超过 76 个字符**；
2. 换行符不属于编码数据本身，解码软件**必须忽略**字母表之外的所有字符（包括换行和空白）。

RFC 4648 第 3.1 节梳理了历史脉络：MIME 的 Base64 继承自更早的 PEM（Privacy Enhanced Mail），PEM 用的是每行 64 字符，MIME 放宽到 76，两者都是为了迁就 SMTP 的行长限制。同时它给通用实现划了一条清晰的界线：

> 除非引用它的规范明确要求，实现不得（MUST NOT）向 Base64 编码数据中添加换行。

RFC 4648 第 3.3 节进一步补上了解码侧的分歧：默认行为应该是**拒绝**字母表之外的字符，除非引用规范明确要求“忽略”（MIME 恰好属于后者）。这一条解释了为什么不同语言的解码器对换行的态度完全不同。

### 在工具和库里观察这个差异

Dart 的 `base64Encode` 不插入任何换行；要得到 MIME 风格输出需要自己折行，解码前也要自己剥离换行：

```dart
// 前置条件：Dart 3.12.2；纯 Dart，仅依赖 dart:convert。
// 运行：dart run .work/verify/DD3/base64_line_breaks.dart
import 'dart:convert';

/// 按 MIME 风格把编码结果折成每行不超过 [width] 个字符。
String wrapForMime(String base64Text, {int width = 76}) {
  if (width <= 0) {
    throw ArgumentError.value(width, 'width', '必须是正数');
  }
  final buffer = StringBuffer();
  for (var start = 0; start < base64Text.length; start += width) {
    final end = start + width < base64Text.length
        ? start + width
        : base64Text.length;
    buffer.writeln(base64Text.substring(start, end));
  }
  return buffer.toString();
}

void main() {
  // 用固定字节让输出可复现：90 字节编码后是 120 个字符。
  final blob = List<int>.generate(90, (index) => index);

  // 1. base64Encode 不插入任何换行，是 RFC 4648 意义上的“纯”Base64。
  final compact = base64Encode(blob);
  print('紧凑形式长度: ${compact.length}');

  // 2. 模拟 MIME 折行：每 76 个字符插入一次换行。
  final wrapped = wrapForMime(compact);
  final lineLengths = wrapped
      .split('\n')
      .where((line) => line.isNotEmpty)
      .map((line) => line.length)
      .toList();
  print('折行后每行长度: $lineLengths');

  // 3. Dart 的 base64.decode 拒绝空白字符，解码前要显式剥离换行。
  try {
    base64.decode(wrapped);
  } on FormatException {
    print('直接解码折行文本: FormatException');
  }
  final restored = base64.decode(wrapped.replaceAll(RegExp(r'\s'), ''));
  print('剥离换行后解码: ${restored.length} 字节');
}
```
<!-- verify: .work/verify/DD3/base64_line_breaks.dart -->

输出里的两个细节值得注意：

- 90 字节编码后是 120 个字符，Dart 的 `base64Encode` 把它放在一整行里；
- 直接 `base64.decode(wrapped)` 会抛出 `FormatException`，因为 Dart 属于 RFC 4648 第 3.3 节的“拒绝”一侧，必须显式剥离换行。

Python 的 `base64.b64decode` 默认丢弃非字母表字符，所以 `b64decode("TWE=\n")` 可以直接工作——同一段数据，不同实现对“容忍”的默认值并不一致。命令行工具同理：GNU coreutils 的 `base64` 默认按 76 列折行（`-w 0` 关闭），macOS/BSD 的实现行为略有差异。遇到“字符串中间混入了 `\n` 导致校验失败”时，先怀疑是不是 MIME 风格折行，再决定是剥离换行，还是让产生数据的一侧改用不折行的方式（如 `base64 -w 0`）。

> **关键认知：** 76 字符限制是邮件传输的格式约定，不是 Base64 编码规则本身。判断一段 Base64 是否合法时，先把换行剥掉，再看总长度是否为 4 的倍数。

## 为什么恰好是 6 位一组

前文一直在说“切成 6 位”，但没有解释这个 6 是怎么来的。它其实是两个约束共同作用的结果。

### 约束一：只能用“在哪都安全”的字符

Base64 面对的通道（早期邮件系统、各种旧协议）对字符非常挑剔。RFC 2045 第 6.8 节记录了当初的筛选标准：这 64 个字符在 ISO 646 的所有版本（包括各国变体）乃至 EBCDIC 中表示一致，并且刻意排除了对 SMTP 有特殊含义的字符（`.`、CR、LF）和 MIME 分隔符（`-`）。

按这个标准，最保险的子集是 62 个字母数字字符：`A-Z`、`a-z`、`0-9`。但 62 不是 2 的幂，无法直接做位分组，于是再补进两个相对安全的符号 `+` 和 `/`，凑成 64 个。

### 约束二：字符表大小必须是 2 的幂

每个字符要承载固定位数的信息，字符表大小就必须是 2 的幂：64 = 2⁶，所以每个字符恰好表示 6 位。假如选 62 个字符，编码和解码就要处理不均匀的进位，实现复杂且容易出错。

### 6 位和 8 位如何配合

字节是 8 位，字符承载 6 位，两者的最小公倍数是 24——这正是“3 个字节一组、编码成 4 个字符”的由来。任何别的分组方式都会让字节边界和字符边界对不齐，解码时无法确定某个字符属于哪个字节。

### 字符更少或更多会怎样

字符更少时（Base32 每字符 5 位、Base16 每字符 4 位），字母表更安全、兼容性更好，但膨胀率上升；字符更多时（Base85 每字符约 6.4 位）更省空间，但字母表里会出现引号、反斜杠这类在文本通道中有语法含义的字符。RFC 2045 第 6.8 节的 NOTE 明确指出，Base85 一类编码不满足邮件场景的可移植性要求。这个取舍的完整对比见下一节。

> **关键认知：** Base64 的“64”不是随意选的：它是“所有环境都安全的字符数量”（62 个字母数字）向上取到最近的 2 的幂；6 位一组，是安全性与膨胀率之间的平衡点。

## Base16、Base32、Base85：同一问题的不同取舍

RFC 4648 的标题是 “The Base16, Base32, and Base64 Data Encodings”——三种编码是同一个思路在不同约束下的产物：把字节流按 N 位一组切开，映射到一个精心挑选的字符表。Base85 虽然不在 RFC 4648 里，但常被放在一起比较。

| 编码 | 每字符承载 | 分组规则 | 大小膨胀 | 字母表特征 | 典型场景 |
| --- | --- | --- | --- | --- | --- |
| Base16（hex） | 4 位 | 1 字节 → 2 字符 | +100% | `0-9 A-F`，大小写不敏感，无需 padding | 调试输出、哈希摘要 |
| Base32 | 5 位 | 5 字节 → 8 字符 | +60% | `A-Z` 和 `2-7`，为大小写不敏感设计 | 大小写不敏感的系统、DNS NSEC3 |
| Base64 | 6 位 | 3 字节 → 4 字符 | +33% | 大小写敏感，含 `+` `/` | 邮件、Data URL、JWT 载荷 |
| Base85 | 约 6.4 位 | 4 字节 → 5 字符 | +25% | 具体字符集取决于变体，可能含引号、反斜杠等 | PDF（Ascii85）、git 二进制补丁 |

几个值得注意的设计细节：

1. **Base32 为什么只用大写字母和数字 2-7**：RFC 4648 第 3.4 节指出，`0` 与 `O`、`1` 与 `l`/`I` 人眼极易混淆，所以 Base32 字母表干脆不含 0 和 1；第 6 节说明它的设计目标是“需要大小写不敏感、但不必便于人阅读”的环境，因为有些文件系统和协议会把文件名或标识符统一成一种大小写。
2. **Base16 不需要 padding**：每个字节恰好拆成两个 4 位组，任何长度都能整除，`=` 无用武之地（RFC 4648 第 3.2、8 节）。
3. **Base32hex 变体保持排序**：RFC 4648 第 7 节定义的扩展十六进制字母表（`0-9 A-V`）有一个特殊性质——按位比较编码结果时，排序与原始数据的排序一致，适合直接当索引键使用（如 DNSSEC 的 NSEC3）。
4. **Base85 不在 RFC 4648 里**：常见变体每 4 字节编为 5 字符，膨胀只有 25%，但具体字符集取决于变体；Ascii85 可能包含 `"`、`\` 等在文本通道里有语法含义的字符，牺牲了“塞进任何文本都安全”的性质。它每字符承载的信息量也不是整数字位，实际约为 6.4 位。

这些编码在 Python 标准库 base64 模块中都有对应函数：`b16encode`、`b32encode`、`b32hexencode`、`a85encode`、`b85encode`，用法与 `b64encode` 一致。Dart 的 `dart:convert` 只内置标准与 URL-safe 两种 Base64；Base16 可以用 `toRadixString(16)` 得到，Base32 与 Base85 需要第三方包或自行实现。

> 选择哪种 Base 编码，本质上是在问：我的通道能容忍哪些字符？能容忍的越少，可用的字母表越小，膨胀就越大。

## 亲手实现一个最小 Base64 编解码器

理解“3 字节切 4 组 6 位”最快的方式是亲手写一遍。下面的编码器只用最直白的字符串操作，不用位运算技巧，每一步都对应前文讲过的规则（位运算本身见[二进制表示与位运算](./01-二进制表示与位运算.md)）：

```dart
// 前置条件：Dart 3.12.2；纯 Dart，仅依赖 dart:convert 用于对拍。
// 运行：dart run .work/verify/DD3/minimal_base64_encoder.dart
import 'dart:convert';

const alphabet =
    'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/';

String myBase64Encode(List<int> data) {
  final out = StringBuffer();

  // 1. 每次处理 3 个字节，最后一组可能不足 3 个。
  for (var i = 0; i < data.length; i += 3) {
    final end = i + 3 < data.length ? i + 3 : data.length;
    final chunk = data.sublist(i, end);

    // 2. 把这组字节拼成一条二进制位串，每个字节固定 8 位。
    final bits = StringBuffer();
    for (final byte in chunk) {
      bits.write(byte.toRadixString(2).padLeft(8, '0'));
    }

    // 3. 末尾补零，让位串长度成为 6 的倍数（16 位补到 18，8 位补到 12）。
    final bitText = bits.toString();
    final paddedBits = bitText.padRight(
      bitText.length + (6 - bitText.length % 6) % 6,
      '0',
    );

    // 4. 每 6 位换算成 0~63 的下标，查字符表得到输出字符。
    final chars = StringBuffer();
    for (var j = 0; j < paddedBits.length; j += 6) {
      final index = int.parse(paddedBits.substring(j, j + 6), radix: 2);
      chars.write(alphabet[index]);
    }

    // 5. 用 = 把这一组补齐到 4 的倍数个字符。
    final charText = chars.toString();
    out.write(
      charText.padRight(charText.length + (4 - charText.length % 4) % 4, '='),
    );
  }
  return out.toString();
}

void main() {
  // 6. 与标准库对拍，覆盖“长度除以 3”的全部余数情况。
  for (var length = 0; length < 100; length++) {
    final data = List<int>.generate(
      length,
      (index) => (index * 37 + length) & 0xff,
    );
    final actual = myBase64Encode(data);
    final expected = base64Encode(data);
    if (actual != expected) {
      throw StateError('长度 $length 时不一致: $actual != $expected');
    }
  }
  final man = myBase64Encode(utf8.encode('Man'));
  print('与标准库输出完全一致，例如 Man -> $man');
}
```

跑通之后再回头看前面 `Man -> TWFu` 的推演，会发现那只是这段代码的一次循环。解码器就是逆过程：查表把字符换回 6 位、拼成位串、按 8 位切开、丢弃 padding 产生的多余位。下面的实现只为展示逆过程，假定输入是编码器生成的标准 Base64；它没有完整校验 padding 位置、长度和补零位，生产代码应使用标准库：

```dart
// 前置条件：Dart 3.12.2；纯 Dart，仅依赖 dart:convert 用于生成对拍数据。
// 运行：dart run .work/verify/DD3/minimal_base64_decoder.dart
import 'dart:convert';

const alphabet =
    'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/';

List<int> myBase64Decode(String text) {
  final out = <int>[];

  // 1. 先去掉 padding，它只表示“这一组没有对应的输入字节”。
  final body = text.replaceAll('=', '');

  // 2. 查表把每个字符换回 6 位，重新拼成一条位串。
  final bits = StringBuffer();
  for (final unit in body.codeUnits) {
    final character = String.fromCharCode(unit);
    final index = alphabet.indexOf(character);
    if (index < 0) {
      throw FormatException('不是 Base64 字符: $character');
    }
    bits.write(index.toRadixString(2).padLeft(6, '0'));
  }

  // 3. 按 8 位一组切回字节，padding 补出的不足 8 位的低位直接丢弃。
  final bitText = bits.toString();
  for (var i = 0; i + 8 <= bitText.length; i += 8) {
    out.add(int.parse(bitText.substring(i, i + 8), radix: 2));
  }
  return out;
}

void main() {
  // 4. 与标准库对拍：先编码再解码，检查字节是否完全一致。
  for (var length = 0; length < 100; length++) {
    final data = List<int>.generate(
      length,
      (index) => (index * 37 + length) & 0xff,
    );
    final restored = myBase64Decode(base64Encode(data));
    if (!_sameBytes(restored, data)) {
      throw StateError('长度 $length 时还原失败');
    }
  }
  print('解码结果与原始字节完全一致');
}

bool _sameBytes(List<int> a, List<int> b) {
  if (a.length != b.length) return false;
  for (var i = 0; i < a.length; i++) {
    if (a[i] != b[i]) return false;
  }
  return true;
}
```
<!-- verify: .work/verify/DD3/minimal_base64_decoder.dart -->

两段代码都用“与标准库对拍”的方式验证：长度覆盖 0 到 99 字节，包含除以 3 的全部余数情况，只有逐字节一致才算通过。

这里的 `myBase64Decode` 是帮助理解位拼接过程的教学实现，只验证了对拍所生成的规范输入，不应直接替代生产环境的解码器：真实接口还应根据协议决定是否接受 URL-safe 字母表、折行、省略 padding，以及是否拒绝非零补位和其他非规范输入。

## 一句话总结

Base64 是把每 3 个字节拆成 4 组 6 位并映射为可打印字符的可逆编码，适合穿过文本通道，但会膨胀数据且绝不提供加密能力。
