## 为什么同一段文字会变成乱码

我们看到的“字”并不是计算机磁盘里直接存放的对象。计算机真正保存和传输的是字节，例如：

```text
E4 B8 AD
```

这三个字节可以按照 UTF-8 解释为“中”，也可以被某种错误的编码方式解释成其他字符。如果发送方和接收方对“这些字节采用什么编码”没有达成一致，就会出现乱码。

因此，乱码通常不是“字体突然坏了”，而是下面这条链路中的某个环节没有使用同一种约定：

```text
字符 → 编码（得到字节）→ 保存/传输 → 解码（还原字符）→ 显示
```

排查乱码时最重要的问题不是“换哪个软件试试”，而是：乱码发生前后的字节分别是什么，以及每个边界声明的编码是什么。

## ASCII：最早的一套小字符集

ASCII 使用 7 位表示字符，可以表示 `0` 到 `127`：

- 英文字母、数字和常见标点；
- 空格、换行等控制字符；
- 不包含中文、日文、表情等大量字符。

在常见的 8 位字节中，ASCII 字符通常表现为最高位为 `0` 的一个字节：

```text
'A' 的 ASCII 值是 65，十六进制是 0x41，二进制是 01000001
```

ASCII 的好处是简单且兼容性极强，但它无法覆盖世界上的各种文字。不同国家曾经在 128 个 ASCII 字符之外设计自己的扩展编码，这也是早期跨语言文本容易出问题的原因之一。

## Unicode：给字符分配统一编号

为了让不同语言共享一套字符体系，Unicode 为字符分配统一的码点（code point）。码点通常写成 `U+` 加十六进制数字：

```text
'A'  → U+0041
'中' → U+4E2D
'😀' → U+1F600
```

码点是“这个字符在字符集中的编号”，不等于文件里的字节。Unicode 还需要一种具体的编码方式，才能把码点转换为字节，例如 UTF-8、UTF-16 或 UTF-32。

这里有一个必须分清的关系：

| 概念 | 解决的问题 | 示例 |
| --- | --- | --- |
| 字符 | 人们想表达的文字或符号 | `中` |
| Unicode 码点 | 给字符分配的统一编号 | `U+4E2D` |
| 编码 | 把码点变成字节 | UTF-8 中是 `E4 B8 AD` |
| 解码 | 把字节按某种规则还原成字符 | `E4 B8 AD` 按 UTF-8 还原为 `中` |

> Unicode 是字符集合和编号体系；UTF-8 是把这些编号编码成字节的具体规则。Unicode 不等于 UTF-8。

## UTF-8 为什么是变长编码

UTF-8 用 1 到 4 个字节表示一个 Unicode 码点：

| Unicode 码点范围 | 字节数 | 首字节模式 |
| --- | ---: | --- |
| `U+0000` ～ `U+007F` | 1 | `0xxxxxxx` |
| `U+0080` ～ `U+07FF` | 2 | `110xxxxx 10xxxxxx` |
| `U+0800` ～ `U+FFFF` | 3 | `1110xxxx 10xxxxxx 10xxxxxx` |
| `U+10000` ～ `U+10FFFF` | 4 | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` |

续字节都以 `10` 开头，所以 UTF-8 可以判断一个字节属于一个字符的开始还是延续。ASCII 的 1 字节形式在 UTF-8 中保持不变，这让大量旧的英文文本天然兼容。

### 用“中”看一次编码过程

字符“中”的 Unicode 码点是 `U+4E2D`。按照三字节 UTF-8 模式填入码点的二进制位：

```text
U+4E2D 的有效位：0100 111000 101101
UTF-8 模式：    1110 xxxx 10xxxxxx 10xxxxxx
填入后：        11100100 10111000 10101101
十六进制：      E4       B8       AD
```

所以“中”的 UTF-8 字节是 `E4 B8 AD`。如果程序把这三个字节按 UTF-8 解码，会得到“中”；如果误按另一种编码解码，就可能得到错误字符。

## UTF-16 与代理对：另一种编码路线

上一节把 UTF-8 讲清楚了，但只看 UTF-8 解释不了另一类常见现象：为什么 JavaScript 里 `"😀".length` 是 `2`？为什么 Java 文档里反复出现 “code unit” 这个词？答案都藏在另一种编码 UTF-16 里——Java、Windows/.NET 和 JavaScript 的字符串在内部都使用 UTF-16，这是 Unicode 官方 FAQ 给出的描述[核查日期：2026-09]。理解它，才能理解这些平台上大量字符串行为的“怪异”之处。

### 从“16 位定长”的历史说起

Unicode 的第一个版本（1991—1995）曾被设计成 16 位定长编码：65536 个编号在当时看来足以装下现代文字。到了 1996 年，Unicode 2.0 把码空间扩展到 `U+0000`～`U+10FFFF`（21 位），大量历史文字、符号和后来的 emoji 都落在了 `U+10000` 以上的“增补平面”。已经按 16 位实现的系统不可能推倒重来，于是需要一个兼容方案——**代理对（surrogate pair）**。

`U+0000`～`U+FFFF` 这段编号空间叫**基本多文种平面（BMP）**，日常文字几乎都分布在这里；其中 `U+D800`～`U+DFFF` 是代理区，不是可独立编码的 Unicode 标量值。超出 BMP 的部分才是需要代理对的“增补字符”。

### UTF-16 的编码规则

UTF-16 以 16 位为一个**码元（code unit）**，规则只有两条：

1. 码点在 BMP 内（代理区除外）：直接用一个码元存放码点；
2. 码点在增补平面（`U+10000`～`U+10FFFF`）：拆成两个码元组成的代理对。

RFC 2781 给出的代理对算法：

```text
U' = U - 0x10000                    1. 先减去 0x10000，得到 20 位的数
W1 = 0xD800 + U' 的高 10 位          2. 高 10 位装入高代理（U+D800～U+DBFF）
W2 = 0xDC00 + U' 的低 10 位          3. 低 10 位装入低代理（U+DC00～U+DFFF）
```

写成位模式就是：

```text
U'  = yyyyyyyyyyxxxxxxxxxx          20 位
W1  = 110110yyyyyyyyyy              高代理
W2  = 110111xxxxxxxxxx              低代理
```

`U+D800`～`U+DFFF` 这 2048 个码点因此被永久保留为“代理区”：它们不代表任何字符，只能成对出现。

### 用“中”和“😀”各走一遍

```text
'中'  U+4E2D < 0x10000   →  4E2D          （一个码元）
'😀'  U+1F600            →  D83D DE00     （一个代理对）
```

'😀' 的推演过程：`0x1F600 - 0x10000 = 0xF600`，写成 20 位二进制是 `0000111101 1000000000`；高 10 位 `0x3D` 加上 `0xD800` 得 `0xD83D`，低 10 位 `0x200` 加上 `0xDC00` 得 `0xDE00`。所以在 JavaScript 里 `"\uD83D\uDE00" === "😀"` 返回 `true`。

> **码元（code unit）和码点（code point）是两个不同的计数单位。** UTF-8 的码元是 8 位、UTF-16 是 16 位、UTF-32 是 32 位；一个码点可能由多个码元组成。`"😀".length` 在 JavaScript 中是 2，因为 `.length` 数的是 UTF-16 码元，不是码点，更不是用户看到的字符数。

> **UTF-8 中永远不该出现代理码点。** RFC 3629 明确禁止把 `U+D800`～`U+DFFF` 编码为 UTF-8，因为这段范围“保留给 UTF-16 的代理对使用，不代表任何字符”。如果 UTF-8 字节流中出现 `ED A0 80` 一类的序列，说明有人把半个代理直接按字节塞了进去，这是非法数据。

### 三种编码形式放在一起看

Unicode 官方 FAQ 用一张属性表对比了三种编码形式，整理如下：

| | UTF-8 | UTF-16 | UTF-32 |
| --- | --- | --- | --- |
| 码元大小 | 8 位 | 16 位 | 32 位 |
| 每字符最少～最多字节 | 1～4 | 2～4 | 4 |
| 字节序问题 | 无 | 有（BE/LE） | 有（BE/LE） |
| 典型使用场景 | Web、文件、Linux 系统 | Java、Windows/.NET、JS 字符串内部 | 部分系统的内部处理 |

UTF-32 定长、按下标随机访问最快，但最耗空间；UTF-16 对 BMP 内的文字很紧凑，代价是引入了代理对；UTF-8 兼容 ASCII、没有字节序问题，是文本交换的首选——WHATWG Encoding Standard 已经把 UTF-8 定为 Web 平台必须支持的编码[核查日期：2026-09]。

> 和上一节对照着记：UTF-8 和 UTF-16 都是变长编码，只是“变长的单位”不同（UTF-8 按字节变、UTF-16 按码元变）。在任何一个平台上问“字符串长度”，都先要问清楚它数的是字节、码元还是码点。

## 可运行示例：观察字符、码点和字节

下面的 Python 程序同时展示 Unicode 码点、UTF-8 字节和解码结果：

```bash
python3 - <<'PY'
text = "A中😀"

# 1. 遍历 Python 字符串中的 Unicode 字符，并打印每个字符的码点。
for character in text:
    print(character, f"U+{ord(character):04X}")

# 2. 按 UTF-8 编码；这里得到的是 bytes，不再是抽象的字符序列。
encoded = text.encode("utf-8")
print("UTF-8 字节:", encoded.hex(" ").upper())
print("字节数:", len(encoded))

# 3. 用同一套 UTF-8 规则解码，恢复原来的文本。
decoded = encoded.decode("utf-8")
assert decoded == text
print("解码结果:", decoded)

# 4. 故意用错误的编码解码，展示“字节没变、解释规则变了”。
print("错误解码:", encoded.decode("latin-1"))
PY
```

运行结果中的字节数不会等于字符数：`A` 占 1 个 UTF-8 字节，“中”占 3 个，`😀` 占 4 个。具体长度取决于字符，而不是人眼看到的字形数量。

也可以在 Linux/macOS 终端检查一个文件的字节和 MIME 信息：

```bash
# 1. 以十六进制查看文件中的原始字节，避免终端显示影响判断。
xxd -g 1 note.txt | head

# 2. 查看系统对文件类型和字符集的推测。
file --mime note.txt

# 3. 已知源文件是 GB18030 时，转换成 UTF-8；不要把未知编码随便填成 GB18030。
iconv -f GB18030 -t UTF-8 old-note.txt > new-note.txt
```

`file` 的判断是启发式结果，不能替代对数据来源的确认；`iconv` 的 `-f` 必须填写真实的源编码。

## 乱码的几种表现和原因

### 出现 `�`

`�` 是 Unicode replacement character（替换字符）。它常常意味着解码器遇到了无效的字节序列，或者上游已经把无法解码的内容替换掉了。

一旦原始字节已经被替换成 `�`，后续再转换编码通常不能找回原文。应尽早回到乱码发生前的边界，保存原始字节和错误日志。

### 出现“涓枃”一类的奇怪文字

这通常是 UTF-8 字节被当成 GBK/GB18030 等其他编码解码，或者反过来造成的“错译”。例如“中文”的 UTF-8 字节是：

```text
E4 B8 AD E6 96 87
```

如果同一组字节被错误地按另一种中文编码解释，就可能显示为“涓枃”。这类乱码往往说明字节还在，但解码方式错了，仍有机会通过改正解码规则恢复。

### 变成 `?` 或 `??`

问号经常发生在“编码”阶段：目标编码无法表示原字符，程序只能用 `?` 替换。例如把中文强行转换成只支持有限字符的 ASCII 时，原字符信息可能已经丢失。

这和解码阶段产生 `�` 不完全相同：前者可能已经丢数据，后者通常表示输入字节不符合当前解码规则。

### 字符是对的，但显示成方框

如果字节、码点和解码都正确，只是字体不包含该字形，界面可能显示方框或豆腐块。这是字体覆盖问题，不一定是字符编码问题。可以用另一个包含目标文字的字体验证，但不要因此随意修改文件编码。

## 按边界排查乱码

### 确定乱码在哪一段出现

把链路拆成几个边界逐一检查：

```text
源代码/文件 → 程序读取 → 网络请求 → 服务端解析 → 数据库 → 页面/终端显示
```

在每个边界记录三件事：原始字节、声明的编码、解码后的文本。只要找到第一处从正确变成错误的位置，问题范围就缩小了。

### 检查声明是否和实际一致

常见声明位置包括：

- HTTP `Content-Type` 中的 `charset`；
- HTML 的 `<meta charset="UTF-8">`；
- 源代码编辑器和编译器的文件编码设置；
- 数据库连接、客户端和导入导出工具的字符集设置；
- 终端的 locale，例如 `locale` 命令输出的 `LANG` 和 `LC_*`。

声明写成 UTF-8 并不能把 GBK 字节自动变成 UTF-8；声明必须和实际字节匹配。

### 只在已知源编码时转换

如果确认输入是 GB18030，目标是 UTF-8，可以转换：

```bash
# 1. -f 指定输入字节的真实编码，-t 指定输出字节的目标编码。
iconv -f GB18030 -t UTF-8 source.txt -o utf8.txt

# 2. 对转换后的文件再次检查字节和字符集信息。
file --mime utf8.txt
```

如果不确定源编码，不要反复尝试编码并覆盖原文件。先复制样本、查看字节、询问数据来源，确认后再转换；否则一次错误转换就可能把可恢复的字节变成问号。

## 码点不等于字：grapheme cluster

前文一直在讲“一个码点如何变成字节”，但还有一层概念没有澄清：**用户眼里的“一个字”不一定对应一个码点**。产品经理说“用户名限制 10 个字”，用户输入了一个家庭 emoji 👨‍👩‍👧‍👦，程序应该算几个字？答案是：看按哪个口径数——而不同编程语言的默认口径并不相同。

### 同一个“é”，两种码点组合

很多西文字符既能用单独的码点表示，也能用“基础字符 + 组合字符”拼出来。例如“é”有两种合法写法：

```text
预组合形式：U+00E9（é）             1 个码点，UTF-8 字节 C3 A9
分解形式：  U+0065（e）+ U+0301（组合尖音符）   2 个码点，UTF-8 字节 65 CC 81
```

两种写法显示效果一样，Unicode 认为它们**规范等价（canonically equivalent）**。文本在进出不同系统时，可能在两种形式之间被自动转换，导致“看起来一样的字符串，比较结果却不相等”。

### emoji：多个码点拼出一个图形

emoji 让这个问题变得更显眼：

- 旗帜 emoji `🇨🇳` 由两个“地区指示符”码点组成：`U+1F1E8`（C）+ `U+1F1F3`（N）；
- 家庭 emoji `👨‍👩‍👧‍👦` 由 4 个人像码点和 3 个零宽连接符（ZWJ，`U+200D`）组成，共 7 个码点。ZWJ 告诉渲染引擎“把这几个图形合成一个”。

### grapheme cluster：用户感知的“字”

Unicode 在 UAX #29（文本切分标准）中定义了 **grapheme cluster（字素簇）**，直译是“字素簇”，通常可以近似理解为“用户感知的单个字符”（user-perceived characters）。日常开发中真正贴近“用户说了几个字”的，是这一层而不是码点；但具体切分结果仍取决于 Unicode 版本和实现。

同一个字符串 `👨‍👩‍👧‍👦`，按不同口径数会得到完全不同的结果：

| 口径 | 数的是什么 | `👨‍👩‍👧‍👦` | 谁在用这个口径 |
| --- | --- | ---: | --- |
| UTF-8 字节 | 编码后的字节 | 25 | 文件大小、网络传输 |
| UTF-16 码元 | 16 位码元 | 11 | JavaScript `.length`、Java `String.length()` |
| 码点 | Unicode 码点 | 7 | Python `len()`、JavaScript `for...of` |
| grapheme cluster | 用户感知的字 | 1 | `Intl.Segmenter`、Swift 的 `Character` |

四个数字都是“对的”，只是回答的问题不同。

### 实际开发中怎么办

```bash
python3 - <<'PY'
import unicodedata

# 1. 两种“é”的码点数不同：预组合形式是 1，分解形式是 2。
print(len("é"))                 # 1
print(len("\u0065\u0301"))      # 2

# 2. NFC 归一化把分解形式合并成预组合形式，常用于比较前的“统一口径”。
print(unicodedata.normalize("NFC", "\u0065\u0301") == "é")   # True

# 3. ZWJ 序列按码点数是 7，用户感知是 1。
print(len("👨‍👩‍👧‍👦"))           # 7
PY
```

三条经验：需要按规范等价比较时，可按协议要求先做 NFC 归一化（它只处理规范等价，不会解决所有“看起来一样”的兼容字符）；“字数限制”类需求按 grapheme cluster 统计；按用户字数截断同理（按码点截断可能把 ZWJ 序列拦腰截断，按码元截断还可能切碎代理对）。NFC 不是通用的 grapheme 统计或安全规范化替代品。

> 码点是编号，grapheme cluster 才接近用户说的“一个字”。两者没有对错，只是口径不同——写代码前先确认业务要的是哪一种。

## BOM：藏在文件开头的签名

还有一类经典问题：文件开头莫名多了三个看不见的字节，导致 JSON 解析失败、shell 脚本报错、两条“看起来一样”的字符串比较不相等。元凶往往就是 BOM。

### BOM 解决什么问题

UTF-16 和 UTF-32 的码元是多字节的，于是产生了字节序（endianness）问题：码点 `U+4E2D` 的单个 16 位码元，在大端机器上存成 `4E 2D`，在小端机器上存成 `2D 4E`。接收方拿到字节流，必须先知道字节序才能正确解码。

Unicode 官方 FAQ 对 BOM 的定义是：**字节顺序标记（BOM）是位于数据流开头的字符 U+FEFF，可用作声明字节序和编码形式的签名**（Unicode 官方 FAQ，[核查日期：2026-09]）。U+FEFF 编码成字节后，不同编码、不同字节序得到的序列各不相同，正好可以当“指纹”用：

| 编码 | 文件开头的 BOM 字节 |
| --- | --- |
| UTF-8 | `EF BB BF` |
| UTF-16 大端（BE） | `FE FF` |
| UTF-16 小端（LE） | `FF FE` |
| UTF-32 大端（BE） | `00 00 FE FF` |
| UTF-32 小端（LE） | `FF FE 00 00` |

顺带一提：UTF-16LE 的 BOM 前两个字节 `FF FE` 恰好和 UTF-32LE 的前两个字节相同，自动检测编码时需要再看后续字节才能区分。

### UTF-8 的 BOM 是个“另类”

UTF-8 按字节流处理，天然没有字节序问题。Unicode FAQ 说得很直接：UTF-8 场景下的 BOM **与字节序无关，只是“这是 UTF-8”的签名**。也就是说，UTF-8 文件根本不需要 BOM；带 BOM 的 UTF-8（`EF BB BF` 开头）只是给自动检测工具一个提示。

### 常见陷阱

1. **期待 ASCII 开头的格式被破坏**。Unicode FAQ 专门举了例子：一些协议和文件格式要求文件以特定 ASCII 字符开头，例如 Unix shell 脚本的 `#!`（shebang）。BOM 抢在 `#!` 前面，脚本就无法执行。JSON 解析器、老式 CSV 导入工具遇到开头的 `EF BB BF` 也可能报错。
2. **字符串比较不相等**。FAQ 提醒：数据库里给每个字段都塞 BOM，会让两条内容完全相同的记录在字节层面不相等，还浪费空间、干扰字符串拼接。
3. **BOM 本身变成乱码**。UTF-8 的 BOM 字节 `EF BB BF` 如果被按 GBK 解码，会显示成“锘”之类的汉字——“文件开头有个锘”就是这一机制的经典乱码。
4. **声明了字节序就不要再附加 BOM**。对于已经明确声明为 `UTF-16BE/LE`、`UTF-32BE/LE` 的数据流，BOM 没有必要，通常也不应再写入；否则会把它作为数据开头的额外字符或造成歧义。

### Python 的实操建议

```bash
python3 - <<'PY'
# 1. 读取来源不明的文件时用 utf-8-sig：开头有 BOM 就自动剥掉，没有也能正常读。
text = open("note.txt", encoding="utf-8-sig").read()

# 2. 写文件用普通 utf-8，避免把 EF BB BF 带进交换数据。
open("out.txt", "w", encoding="utf-8").write("你好")
print("done")
PY
```

> 互联网交换用“UTF-8 无 BOM”最稳妥。WHATWG Encoding Standard 已把 UTF-8 定为 Web 的必备编码；BOM 的价值主要在“读取来源不明的本地文件”时提供提示。[核查日期：2026-09]

## 各语言“按字符遍历”的正确姿势

到这里，四个层次的概念已经齐全：**字节 → 码元 → 码点 → grapheme cluster**。落到代码里，问题就变成：`for` 循环遍历字符串时，每次拿到的到底是哪一层？不同语言的默认答案并不相同，这正是字符串 bug 的高发地。

| 语言/平台 | 默认/常见遍历单位 | 按码点遍历 | 按 grapheme 遍历 |
| --- | --- | --- | --- |
| Python 3 | 码点 | `for ch in s` | 标准库未内置，常用第三方 `regex` 模块的 `\X` |
| JavaScript | 码元（`charAt`、`split("")`） | `for...of`、`Array.from` | `Intl.Segmenter` |
| Java | 码元（`charAt`、`length()`） | `String.codePoints()` | `java.text.BreakIterator`（能力取决于 JDK/Unicode 版本） |
| Swift | grapheme（`Character` 类型） | 默认即用户感知字符 | 默认 |
| Rust | 字节（`&str` 直接迭代） | `s.chars()` | `unicode-segmentation` crate |
| C/C++ | 字节（`char`、`strlen`） | 手动解码或 ICU 库 | ICU 库 |

注意两个最容易踩的坑：

- JavaScript 里用普通 `for` 加 `charAt`（或 `split("")`）遍历，是按 UTF-16 码元走的，增补字符会被拆成两个孤立代理项，后续显示或编码时可能出现异常；换 `for...of` 就按码点走了，但 ZWJ 序列仍可能被拆开。
- Java 的 `String.length()` 数的是 UTF-16 码元（所以 `"😀".length()` 是 2），要数码点得用 `codePointCount()`，要遍历用 `codePoints()`。

两段代码分别展示 Python 和 JavaScript 的正确姿势：

```bash
python3 - <<'PY'
s = "A中😀"

# 1. 直接迭代 Python 字符串，每次得到一个码点（不是字节）。
for ch in s:
    print(ch, f"U+{ord(ch):04X}")

# 2. len(str) 数码点，len(bytes) 数字节，两个口径都先想清楚再用。
print(len(s))                    # 3：三个码点
print(len(s.encode("utf-8")))    # 8：1 + 3 + 4 个字节

# 3. 标准库没有 grapheme 迭代，但 NFC 归一化能统一组合字符的口径。
import unicodedata
e = "\u0065\u0301"               # e + 组合尖音符，用户看到的是一个 é
print(len(e), len(unicodedata.normalize("NFC", e)))   # 2 1
PY
```

```js
const family = "👨‍👩‍👧‍👦";

// 1. length 数的是 UTF-16 码元：4 个增补字符各占 2 个，加 3 个 ZWJ。
console.log(family.length);        // 11

// 2. for...of / 展开语法按码点迭代，但 ZWJ 序列仍会被拆成 7 段。
console.log([...family].length);   // 7

// 3. Intl.Segmenter 才按用户感知的字符（grapheme）切分。
const seg = new Intl.Segmenter("zh", { granularity: "grapheme" });
const parts = Array.from(seg.segment(family), x => x.segment);
console.log(parts.length, parts[0] === family);   // 1 true
```

> 遇到“长度不对、截断出乱码、正则匹配不到 emoji”这类问题时，第一反应应该是确认当前操作落在哪一层：字节、码元、码点还是 grapheme。层次对了，工具自然就选对了。

## 常见误区

### “一个字符就是一个字节”

这只对一部分 ASCII 字符成立。UTF-8 中中文通常占 3 个字节，许多 emoji 占 4 个字节。C 语言的 `char` 保存一个字节，`strlen` 统计的是字节数，不是 Unicode 字符数。

### “把字符串转成 UTF-8”可以无限次执行

字符串通常应在明确的边界编码一次、解码一次。重复执行“转 UTF-8”可能造成双重编码、转义字符或乱码。应先确认当前对象是字符还是字节，再决定是否需要转换。

### “Unicode 就是一种文件格式”

Unicode 规定码点和字符语义；文件仍然需要采用 UTF-8、UTF-16 等编码保存。看到“Unicode 文件”时，还应继续确认具体编码和是否包含 BOM。

### 只看界面，不看字节

显示结果可能同时受到编码、终端、字体、换行和渲染器影响。遇到乱码时先用十六进制工具或程序打印原始字节，能够避免被表面现象带偏。

### 截断 UTF-8 字节序列

UTF-8 一个字符可能跨越多个字节。如果按字节长度截断字符串，可能把一个字符切成半个序列，随后解码就会失败或出现 `�`。需要按字符边界截取，或者使用明确支持 Unicode 的字符串库。

### “字符串长度是一个客观的数字”

同一个字符串按字节、码元、码点、grapheme cluster 数会得到四个都“正确”的答案（见[码点不等于字](#码点不等于字grapheme-cluster)）。不同语言的 `length` 默认口径不同，跨系统传输“长度”字段前，必须先约定口径。

字符编码就是在字符与字节之间建立可逆约定，乱码的本质通常是字节和解码规则不匹配，排查时应沿着数据边界先找出第一处发生错误的位置。
