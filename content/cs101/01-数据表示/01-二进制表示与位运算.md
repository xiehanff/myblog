# 二进制表示与位运算

很多程序并不只是在“计算一个整数”。权限、网络协议的标志位、颜色通道、压缩格式、硬件寄存器，往往都把一个整数看成一串可以分别控制的 0 和 1。

如果只把 `&`、`|`、`^` 当成几个特殊运算符，遇到掩码、补码和移位时很容易混乱。这篇文章从“整数在机器中如何表示”开始，逐步建立一套可以实际使用的位运算模型，再把它落到 C 代码中。

路线是：先建立“固定宽度位模式”的模型，再看补码如何把负数放进这些位里；接着依次拆开四种位运算、移位和掩码，并用一节集中列出常见误区；最后用两组实战（权限掩码与浮点数边界）收束，并核对 C、Java、JavaScript 与 Dart 各自的移位契约——同一段位运算代码，在不同语言里的确定性程度并不相同。

## 先把整数看成固定宽度的位

### 二进制、十六进制与位宽

二进制只有 `0` 和 `1` 两个数字。一个二进制数字称为一位（bit），8 位组成一个字节（byte）。十六进制的一个数字正好对应 4 位，因此读二进制数据时经常用十六进制缩写：

```text
二进制：1100 1010
十六进制：C    A       -> 0xCA
```

“固定宽度”很重要。同一个数 `5`，如果只看有效数字可以写成 `101`；如果放在 8 位无符号整数中，就必须写成：

```text
00000101
```

位运算不是在一条没有长度的数字上操作，而是在某个类型提供的位宽内逐位操作。下面的示意都以 8 位为例：

```text
位权：128 64 32 16 8 4 2 1
位值：  0  0  0  0 0 1 0 1  = 5
```

在 C 中，如果需要明确位宽，优先使用 `<stdint.h>` 中的 `uint8_t`、`uint16_t`、`uint32_t` 等类型。普通 `int` 的宽度和表示范围与平台有关，不适合直接拿来描述协议字段或硬件寄存器。

按位重新分组、再映射到字符表的编码办法也很常见，例如把 24 位切成 4 组 6 位，见 [Base64 编码](./03-Base64编码.md)。

> **关键认知：** 位运算的输入、中间结果和输出都受当前类型的位宽约束；同一个数字在 8 位与 32 位下是不同的位模式，讨论位运算前必须先确定位宽。

### 最小实验：打印一个数的每一位

下面的函数从最高位检查到最低位。`value >> bit` 也能完成取位，但使用掩码更能体现位运算的思路。

```c
#include <stdint.h>
#include <stdio.h>

static void print_bits8(uint8_t value) {
    // 1. 从最高位 7 检查到最低位 0，保证输出顺序符合阅读习惯。
    for (int bit = 7; bit >= 0; --bit) {
        uint8_t mask = (uint8_t)(UINT8_C(1) << bit);

        // 2. 只保留当前位：结果非 0 说明当前位是 1。
        putchar((value & mask) != 0 ? '1' : '0');
    }
}

int main(void) {
    // 3. 0x2D 的二进制形式是 00101101。
    uint8_t value = UINT8_C(0x2D);

    // 4. 先打印二进制，再打印十六进制，观察两种表示的对应关系。
    print_bits8(value);
    printf(" (0x%02X)\n", (unsigned)value);
    return 0;
}
```

编译运行后会得到：

```text
00101101 (0x2D)
```

这里的 `0x2D` 不是另一种数，而是同一个 8 位模式的另一种写法。

> **关键认知：** 二进制、十六进制、十进制只是同一个位模式的不同写法；程序里真正参与位运算的始终是位模式本身，写出十六进制只是为了让 4 位一组的边界肉眼可见。

## 补码：负数如何放进二进制位

### 为什么需要补码

CPU 最擅长做加法。如果正数和负数使用一套适合加法器的表示，那么减法可以转化为加法，硬件就不需要为“正负号”单独设计一套完全不同的运算路径。

现代计算机普遍使用二进制补码（two's complement）表示有符号整数。从标准的角度看，这里有一段演化历史：C23 之前的 C 标准允许三种有符号整数表示——补码、反码（ones' complement）和原码（sign and magnitude），因此只保证 N 位有符号整数至少覆盖 `-(2^(N-1) - 1)` 到 `2^(N-1) - 1`；C++20 和 C23 起强制使用补码，`-2^(N-1)` 到 `2^(N-1) - 1` 才成为标准保证的范围。好在几乎所有真实平台从一开始就是补码，所以下面的讨论以补码为准：

- 无符号整数范围是 `0` 到 `2^N - 1`。
- N 位补码有符号整数范围是 `-2^(N-1)` 到 `2^(N-1) - 1`。
- 补码的最高位不是“单独存放的负号”，而是正常参与计数、权重为 `-2^(N-1)` 的一位。

> **时效信息（核查日期：2026-09）：** C23（ISO/IEC 9899:2024）与 C++20 起，补码成为有符号整数的强制表示；此前 C 标准允许反码和原码，可移植代码只能假定 `-(2^(N-1) - 1)` 到 `2^(N-1) - 1`。

以 8 位为例，正数 `5` 的表示为：

```text
 5       = 00000101
按位取反 = 11111010
再加 1   = 11111011  -> -5
```

所以在固定宽度下，求一个数的相反数可以理解为“按位取反再加 1”，即 `~x + 1`。补码的好处是 `5 + (-5)` 的低 8 位会自然得到 `0`：

```text
  00000101
+ 11111011
-----------
1 00000000    （最高位进位被丢弃）
```

### 补码带来的两个关键认知

第一，位模式本身没有脱离类型的“正负”。例如 8 位模式 `11111011`：

- 按 `uint8_t` 看，它是 `251`。
- 按 8 位补码的有符号数看，它是 `-5`。

第二，`-128` 在 8 位补码中是 `10000000`，它没有对应的正数 `+128`。因此对最小负数求相反数时，数学结果超出了同样位宽可以表示的范围，不能把它当成普通情况处理；在 C 中 `-INT_MIN` 本身就是未定义行为。

实际工程中，位级算法通常使用无符号类型承载位模式，再在需要展示数值时转换为有符号类型。这样可以避开有符号溢出的未定义行为。

> **关键认知：** 补码解释的是“有符号数如何解释位模式”；同一组位在无符号类型和有符号类型下可能代表不同的数值。

> **面试高频：** 为什么求相反数可以写成 `~x + 1`？
> **答题脉络：** 补码的最高位权重是 `-2^(N-1)` → 按位取反等价于用 `2^N - 1` 减原值 → 再加 1 在模 `2^N` 下就是取负 → 边界是 `-2^(N-1)` 取负仍然是自己。
> **追问方向：** 为什么无符号数的回绕是标准行为、有符号溢出不是；`x & -x` 为什么能取出最低位的 1。

## 四种基本位运算

位运算对每一位独立处理，不关心某一位旁边的位是什么。设：

```text
a = 11001100
b = 10101010
```

它们的结果是：

| 运算 | 逐位规则 | 结果 | 常见用途 |
|------|----------|------|----------|
| `a & b` | 两位都是 1，结果才是 1 | `10001000` | 保留指定的位、测试标志 |
| `a \| b` | 任意一位是 1，结果就是 1 | `11101110` | 设置指定的位 |
| `a ^ b` | 两位不同是 1，相同是 0 | `01100110` | 切换位、比较差异 |
| `~a` | 每一位翻转 | `00110011` | 构造反向掩码 |

`~a` 的结果必须放在明确的 8 位范围内理解；在 C 中它还会受到整数提升的影响，后面会专门说明。

最小的 C 实验如下：

```c
#include <stdint.h>
#include <stdio.h>

int main(void) {
    // 1. 准备两个 8 位位模式：11001100 和 10101010。
    uint8_t left = UINT8_C(0xCC);
    uint8_t right = UINT8_C(0xAA);

    // 2. 进行四种逐位运算，并在赋值时明确截断回 8 位。
    uint8_t and_result = (uint8_t)(left & right);
    uint8_t or_result = (uint8_t)(left | right);
    uint8_t xor_result = (uint8_t)(left ^ right);
    uint8_t not_result = (uint8_t)~left;

    // 3. 使用十六进制输出，四位二进制正好对应一个十六进制数字。
    printf("&  = 0x%02X\n", (unsigned)and_result);
    printf("|  = 0x%02X\n", (unsigned)or_result);
    printf("^  = 0x%02X\n", (unsigned)xor_result);
    printf("~  = 0x%02X\n", (unsigned)not_result);
    return 0;
}
```

输出为：

```text
&  = 0x88
|  = 0xEE
^  = 0x66
~  = 0x33
```

不要把位运算和逻辑运算混为一谈：`&` 与 `&&` 不同，`|` 与 `||` 不同。前者操作每一位，后者把整个表达式当成真假值，并且逻辑运算还具有短路特性。

> **关键认知：** 位运算没有“真假”概念，只有逐位结果；把 `x & y` 当成条件使用时，真正参与判断的是整个整数是否非 0，而不是某一位。

## 移位：让位模式移动位置

### 左移和无符号右移

对无符号数来说：

- `x << n`：向高位方向移动 `n` 位，低位补 `0`，被移出高位的位丢弃。
- `x >> n`：向低位方向移动 `n` 位，高位补 `0`。

因此，左移一位通常类似于乘以 2，右移一位通常类似于整除以 2。但“类似”有边界：位被丢弃时，结果就不再等于数学上的乘除；移位也不会自动扩展存储空间。

```c
#include <stdint.h>
#include <stdio.h>

int main(void) {
    // 1. 0x2D = 00101101，左移和右移都只在 8 位结果中观察。
    uint8_t value = UINT8_C(0x2D);
    uint8_t left = (uint8_t)(value << 1);
    uint8_t right = (uint8_t)(value >> 2);

    // 2. 左移后得到 01011010，右移后得到 00001011。
    printf("value = 0x%02X\n", (unsigned)value);
    printf("left  = 0x%02X\n", (unsigned)left);
    printf("right = 0x%02X\n", (unsigned)right);
    return 0;
}
```

> **关键认知：** “左移等于乘 2”只有在没有位被移出、也没有超出类型宽度时才成立；一旦有高位被丢弃，移位和乘法的结果就会分道扬镳。

### C 语言中移位的边界

移位表达式在 C 中有几个不能忽略的限制：

1. 移位量不能是负数，也不能大于等于“提升后左操作数”的位宽；例如 32 位平台上 32 位值不能移 `32` 位，这是未定义行为，不是“得到全 0”。
2. 负数的右移在 C 标准中是**实现定义行为**（implementation-defined）：每个实现必须选定并文档化一种做法，常见平台进行算术右移（高位补符号位），也有平台补 `0`。可移植代码不要依赖这个细节。
3. 有符号数左移尤其危险，有两种触发未定义行为的方式：对负值左移本身就是未定义行为；对非负值左移但结果超出类型可表示范围，同样是未定义行为。需要构造位模式时使用无符号类型。
4. `1 << 31` 先把 `1` 当成 `int`（32 位平台上结果是 2^31，超出 `int` 可表示范围，属于上面的未定义行为）；构造 32 位最高位应写成 `UINT32_C(1) << 31`。

> **关键认知：** “左移溢出”和“移位量越界”在 C 中是**未定义行为**（编译器可以假设它永不发生），而“负数右移”是**实现定义行为**（编译器必须给出一种确定的、写进文档的行为）。两者都不可移植，但性质不同。

例如，安全构造一个 32 位标志位可以写成：

```c
#include <stdint.h>

static uint32_t make_bit_mask(unsigned bit) {
    // 1. 先检查移位量，避免移位 32 位或更多位。
    if (bit >= 32) {
        return UINT32_C(0);
    }

    // 2. 使用无符号的 32 位常量构造目标位。
    return UINT32_C(1) << bit;
}
```

> **面试高频：** 为什么 `1 << 31` 在 C 里是隐患？
> **答题脉络：** `1` 的类型是 `int` → 结果可能超出 `int` 可表示范围 → 有符号溢出是未定义行为 → 改用 `UINT32_C(1) << 31`，并显式检查移位量 → 对比 Java、JavaScript 和 Dart 的取模或截断行为。
> **追问方向：** `int` 宽度与平台；无符号整数的回绕为什么是标准行为；移位量来自变量时如何做边界检查。

## 掩码：只让自己关心的位留下来

掩码（mask）本质上也是一个位模式。`&` 会把掩码中为 `0` 的位置清零，把掩码中为 `1` 的位置保留下来。

### 读取、设置、清除和切换标志位

假设一个 `flags` 的每一位代表一个独立开关：

```text
bit 0：是否可读
bit 1：是否可写
bit 2：是否可执行
```

常用操作可以归纳为：

```c
#include <stdint.h>
#include <stdio.h>

#define FLAG_READ  (UINT8_C(1) << 0)
#define FLAG_WRITE (UINT8_C(1) << 1)
#define FLAG_EXEC  (UINT8_C(1) << 2)

int main(void) {
    // 1. 初始时没有任何标志位被设置。
    uint8_t flags = UINT8_C(0);

    // 2. 使用 | 设置位：不会影响其他已经存在的标志。
    flags |= FLAG_READ;
    flags |= FLAG_WRITE;

    // 3. 使用 & 测试位：要和 0 比较，不要把结果误认为布尔值以外的含义。
    if ((flags & FLAG_READ) != 0) {
        puts("read is enabled");
    }

    // 4. 使用 & 和反向掩码清除位：其他位保持不变。
    flags &= (uint8_t)~FLAG_WRITE;

    // 5. 使用 ^ 切换位：原来是 0 就变成 1，原来是 1 就变成 0。
    flags ^= FLAG_EXEC;
    printf("flags = 0x%02X\n", (unsigned)flags);
    return 0;
}
```

这里有一个很值得记住的四句口诀：

```text
设置：flags |=  MASK;
清除：flags &= ~MASK;
切换：flags ^=  MASK;
测试：(flags & MASK) != 0
```

> **关键认知：** 清位必须使用反向掩码 `flags &= ~MASK`；写成 `flags &= MASK` 会把 `MASK` 之外的所有位全部清零，这是标志位代码里最常见的一类事故。

### 读取和写入多位字段

并非每一位都是独立开关。有时连续的几位共同表示一个小整数，例如用 bit 2 和 bit 3 表示模式 `0` 到 `3`。此时要先清除旧字段，再把新值移到正确位置：

```c
#include <stdint.h>
#include <stdio.h>

#define MODE_SHIFT 2u
#define MODE_MASK  UINT8_C(0x0C)  /* 00001100：bit 2 和 bit 3 */

int main(void) {
    // 1. 先保留其他位，只清除 mode 所占的两位。
    uint8_t config = UINT8_C(0xF0);
    config = (uint8_t)(config & (uint8_t)~MODE_MASK);

    // 2. mode 只能使用低两位，否则会污染字段之外的位。
    uint8_t mode = UINT8_C(2);
    config = (uint8_t)(config | (uint8_t)((mode << MODE_SHIFT) & MODE_MASK));

    // 3. 读取字段时先 & 掩码，再右移回普通整数位置。
    uint8_t decoded_mode = (uint8_t)((config & MODE_MASK) >> MODE_SHIFT);
    printf("config=0x%02X, mode=%u\n", (unsigned)config, (unsigned)decoded_mode);
    return 0;
}
```

这个过程经常出现在协议头、设备寄存器和配置字中。掩码的文档必须同时写清楚“字段占哪些位”和“字段值的范围”，否则调用者很容易把一个字段写到邻近字段中。

> **关键认知：** 一个字段的三个要素——偏移、位宽、取值范围——必须一起定义；只给掩码常量而不写偏移和范围，读写两侧就一定会有人算错。

## 常见误区：位运算正确，不代表代码就安全

### 整数提升会让按位取反超出预期宽度

在 C 中，`uint8_t`、`uint16_t` 等小整数参与表达式时，通常会先提升为 `int` 或 `unsigned int`。所以：

```c
#include <stdint.h>
#include <stdio.h>

uint8_t value = 0x0F;
printf("%X\n", (unsigned)~value);         // 常见 32 位 int 平台上是 FFFFFFF0
printf("%02X\n", (unsigned)(uint8_t)~value); // 截回 8 位后是 F0
```

这不是 `~` 只翻转了部分位，而是 `~` 实际翻转了“提升后类型”的全部位。需要固定宽度结果时，明确转换回目标类型，并按目标类型输出。

### 有符号溢出不能用截断来赌结果

无符号整数的溢出按模 `2^N` 回绕，这是标准定义的行为；有符号整数溢出则可能是未定义行为：

```c
#include <limits.h>

int x = INT_MAX;
// x + 1;  // 不要这样依赖溢出结果，结果未定义。
```

位级算法应优先使用 `<stdint.h>` 的无符号类型。若业务确实需要有符号算术，应在运算前检查范围，而不是依赖某台机器上的补码回绕。

### 移位量、常量类型和优先级

- `value << width`、`value >> width` 不是“得到全 0”，而是越界移位，C 中是未定义行为。
- `1 << 31` 可能先在有符号 `int` 中计算；使用 `UINT32_C(1)` 或 `UINT64_C(1)` 表达意图。
- `^` 是异或，不是乘方；C 中没有用 `^` 表示幂运算的语法。

按位运算符的优先级普遍比直觉低，这是 C 从早期语言继承的历史包袱。与位运算相关的优先级从高到低依次是：算术（`* / %`、`+ -`）→ 移位（`<< >>`）→ 关系（`< <= > >=`）→ 相等（`== !=`）→ `&` → `^` → `|` → `&&` → `||`。两个最典型的陷阱：

```c
// 1. & 的优先级低于 ==：先计算 MASK == 0（得到 0 或 1），再和 flags 按位与。
if (flags & MASK == 0) { }      // 实际含义：flags & (MASK == 0)
if ((flags & MASK) == 0) { }    // 想表达的含义

// 2. << 的优先级低于 +：先算加法再移位。
uint32_t a = 1 << 2 + 3;        // 实际是 1 << 5 = 32
uint32_t b = (1 << 2) + 3;     // 想表达的 4 + 3 = 7
```

即使 C 的优先级能正确解析某个表达式，也建议写成 `value & (UINT32_C(1) << bit)` 这样带括号的形式，不要让读者猜。

> **关键认知：** 只要一个表达式里同时出现位运算和比较、算术运算，就按“给低优先级的那一侧加括号”处理；编译器的 `-Wparentheses` 一类警告能发现其中一部分，但不会覆盖所有写法。

### 位顺序不是字节序

位运算只处理一个整数值的位模式；网络传输或文件存储还要决定多字节整数的字节序（大端或小端）。例如把 `0x12345678` 写入字节数组时，`12 34 56 78` 和 `78 56 34 12` 是两种不同的序列。不能因为某台机器上的位运算结果正确，就认为跨机器序列化也正确。

文本又多一层约定：字节要按哪种字符编码解释，见[字符编码与乱码](./02-字符编码与乱码.md)。

### 不要依赖 C 位域的布局做跨平台协议

结构体位域的分配方向、对齐、填充和跨字节布局都可能由编译器和 ABI 决定。位域适合本地代码中表达寄存器或状态，但用于网络协议、文件格式时，通常应手动使用整数、掩码和明确的字节序。

## 常用位运算技巧与它们的适用边界

掌握了基本规则之后，有一批“位运算技巧”在算法书、面试题和真实代码里反复出现。它们的本质不是聪明，而是补码位模式的几个代数性质。先把性质看懂，再决定什么时候用。这些技巧在算法题里的组合用法见[位运算技巧](../02-算法与数据结构/01-算法基础/14-位运算技巧.md)，题解归档见 [LeetCode 位运算](../02-算法与数据结构/02-LeetCode题解/16-位运算.md)。

### 三个基础性质

下面三个式子以固定宽度的无符号整数 `x` 为例，其中后两个只在 `x ≠ 0` 时有意义（`x = 0` 时结果为 `0`，不再有“最低位的 1”可取）。它们依据的是位模式本身的代数性质；在补码机器上观察有符号数时，位模式通常也呈现同样的结果，但 C 表达式不能因此直接换成有符号类型：例如对 `INT_MIN` 使用一元负号仍可能触发未定义行为。

- `x & 1`：取出无符号 `x` 的最低位。对无符号数来说，它等于除以 2 的余数，因此可以判断奇偶；如果操作数是有符号数，优先使用 `% 2` 表达算术意图，避免把补码假设带入可移植代码。
- `x & (~x + 1)`：取出最低位的 `1`。常见写法是 `x & -x`；这两种写法都应让 `x` 保持无符号类型，避免把有符号溢出误当成位模式回绕。
- `x & (x - 1)`：清除最低位的 `1`。

后两个性质可以用一个例子看清楚。设 `x = 0110 1000`：

```text
x              = 0110 1000
~x             = 1001 0111
~x + 1         = 1001 1000
x & (~x + 1)   = 0000 1000    <- 最低位的 1 被单独保留

x - 1          = 0110 0111    <- 最低位的 1 借位变 0，更低的 0 全变 1
x & (x - 1)    = 0110 0000    <- 最低位的 1 被清掉
```

这两个式子之所以成立，是因为“减 1”只会影响最低位的 `1` 及其右侧的位，左侧的位原样保留；`&` 恰好把“原样保留的部分”提取出来。

### 由性质导出的常用技巧

```c
#include <stdint.h>

/* 1. 判断 2 的幂：2 的幂的位模式只有一个 1，清掉它就变成全 0；0 要单独排除。 */
int is_power_of_two(uint32_t x) {
    return x != 0 && (x & (x - UINT32_C(1))) == 0;
}

/* 2. Brian Kernighan 算法：统计位模式中 1 的个数。
 *    每轮消去最低位的 1，循环次数正好等于 1 的个数（至多 32 次），
 *    而逐位扫描固定要循环 32 次。1 越稀疏，这个算法越省。 */
static unsigned count_bits(uint32_t x) {
    // 计数器记录消去了多少个 1。
    unsigned count = 0;

    // 每次用 x & (x - 1) 消去最低位的 1。
    while (x != 0) {
        x &= x - UINT32_C(1);
        ++count;
    }
    return count;
}
```

### 这些技巧在现代编译器面前的取舍

一个需要明确的态度是：**位技巧的价值在于表达“位级意图”，而不是性能**。

- 判断奇偶，写 `x % 2 != 0` 就好。现代编译器会把它优化成一次 `and`，和手写 `x & 1` 生成的机器码没有区别，而普通写法人人能读懂。
- 除以 2，写 `x / 2`。对无符号数编译器直接生成移位；对有符号负数，C 的除法向零取整而算术移位向负无穷取整，语义本来就不同，手写 `x >> 1` 反而可能改变程序含义。
- `x & (~x + 1)`、掩码字段的读取与写入（见[掩码](#掩码只让自己关心的位留下来)一节）没有等价的普通运算符写法，这些才是必须掌握的技能。
- C23 在 `<stdbit.h>` 中把常见位工具标准化：`stdc_count_ones`（数 1）、`stdc_has_single_bit`（判断 2 的幂）、`stdc_bit_ceil`（向上取整到 2 的幂）等。能用标准函数就优先用标准函数，它们比手写循环更清晰地表达了意图，编译器也能生成最优指令。

> **关键认知：** 用位运算表达“位级语义”（掩码、集合、字段），用普通运算符表达“算术语义”（乘除、取模）。为了“看起来快”而把算术改写成移位，在现代编译器面前通常一无所获，还可能引入有符号语义的 bug。

> **面试高频：** 为什么 `x & (x - 1)` 能清掉最低位的 1？
> **答题脉络：** 减 1 只让最低位的 1 变 0，并把它右侧的 0 全变 1 → 左侧的位不受影响 → 按位与之后只保留了左侧 → 顺带得到“判断 2 的幂”和“数 1 的个数”两个结论。
> **追问方向：** `x & -x` 与它的对偶关系；`x = 0` 时的退化行为；为什么只能在补码表示下通用。

## 实战：用位掩码实现一组权限

前面解决了“对一个开关的四种操作”。真实系统里的权限往往是一组命名的布尔能力——类 Unix 的 `chmod`、打开文件时的模式标志、各类 capability 系统都是这样。这一节把散落的操作组织成一个可以直接抄走的小模块，重点在于“组合”和“遍历”。

```c
#include <stdint.h>
#include <stdio.h>

/* 1. 用枚举把权限定义为掩码：每个权限占独立的一位。 */
enum {
    PERM_NONE  = 0,
    PERM_READ  = 1 << 0,   /* 0001 */
    PERM_WRITE = 1 << 1,   /* 0010 */
    PERM_EXEC  = 1 << 2,   /* 0100 */
    PERM_ADMIN = 1 << 3,   /* 1000 */
};

/* 2. 预组合常用权限包，调用方不必到处重复 | 运算。 */
enum {
    PERM_RW  = PERM_READ | PERM_WRITE,
    PERM_ALL = PERM_READ | PERM_WRITE | PERM_EXEC | PERM_ADMIN,
};

/* 3. 子集检查：mask 中的每一位都必须在 flags 中已设置。 */
static int has_all(uint32_t flags, uint32_t mask) {
    return (flags & mask) == mask;
}

/* 4. 交集检查：只要命中任意一位即可。注意它与子集检查的比较方式不同。 */
static int has_any(uint32_t flags, uint32_t mask) {
    return (flags & mask) != 0;
}

/* 5. 授权与回收：一次可以操作一组位。 */
static uint32_t grant(uint32_t flags, uint32_t mask)  { return flags | mask; }
static uint32_t revoke(uint32_t flags, uint32_t mask) { return flags & ~mask; }

/* 6. 遍历已设置的权限：每次取出最低位的 1，翻译成名字后消掉它。
 *    names 数组与位编号一一对应，这是它能工作的前提。 */
static void print_permissions(uint32_t flags) {
    static const char *names[] = { "read", "write", "exec", "admin" };

    while (flags != 0) {
        // 6.1 取出最低位的 1。
        uint32_t bit = flags & (~flags + UINT32_C(1));

        // 6.2 把孤立的位换算成编号：不断右移直到只剩 1。
        unsigned index = 0;
        while ((bit >> index) != UINT32_C(1)) {
            ++index;
        }
        printf("%s ", names[index]);

        // 6.3 消去这一位，循环自然终止。
        flags &= flags - UINT32_C(1);
    }
    putchar('\n');
}

int main(void) {
    // 7. 从只读权限开始，逐步授权再回收，观察每一步的输出。
    uint32_t user = PERM_READ;
    user = grant(user, PERM_EXEC);
    print_permissions(user);                            // read exec

    printf("has admin: %d\n", has_all(user, PERM_ADMIN)); // 0
    printf("has any rw: %d\n", has_any(user, PERM_RW));   // 1

    user = revoke(user, PERM_READ);
    print_permissions(user);                            // exec
    return 0;
}
```

输出为：

```text
read exec
has admin: 0
has any rw: 1
exec
```

> **关键认知：** `(flags & mask) == mask` 检查的是“包含全部”，`(flags & mask) != 0` 检查的是“命中任意一个”。两者只差一个比较，含义完全不同——权限系统里大多数误授权事故都出在这一步。

这种设计还有一个工程上的好处：一个 `uint32_t` 就能装下 32 个独立开关，序列化、比较、持久化都只需要处理一个整数。代价是可读性变差，所以 `print_permissions` 这类“翻译函数”不是锦上添花，而是这类系统的标配。

同样的思路在 Dart 里可以用 `int` 表达，但要注意原生和 Web 的差别：Dart 原生 `int` 有 64 位，而编译到 Web 后位运算会被截到 32 位，用 31 号以上的位会得到不同结果（见后面的语言对比）。

## 浮点数为什么不能用位运算比较相等

到目前为止我们都在整数世界。浮点数同样是固定宽度的位模式，于是很容易产生一个念头：“整数能用位模式比较，浮点数是不是也可以？”答案是不行，而且原因有三层，一层比一层深。

### 第一层：C 的位运算符根本不接受浮点操作数

`&`、`|`、`^`、`~`、`<<`、`>>` 在 C 中只对整数类型有定义。`double d = 1.5; d & 1;` 无法通过编译。这不是缺陷，而是语言设计者的明确选择：浮点数的位布局不是“二进制权位”，直接按位操作没有一致的代数含义。

想观察浮点数的位模式，标准做法是用 `memcpy` 复制到同样宽度的无符号整数——这符合严格别名规则，不会引入未定义行为。下面的示例以 IEEE 754 binary64 且 `sizeof(double) == sizeof(uint64_t)` 为前提：

```c
#include <stdint.h>
#include <string.h>

_Static_assert(sizeof(double) == sizeof(uint64_t),
               "this example requires 64-bit double");
static uint64_t bits_of_double(double d) {
    uint64_t bits = 0;

    // 1. 复制对象表示，而不是通过指针重新解释类型。
    memcpy(&bits, &d, sizeof d);
    return bits;
}
```

### 第二层：IEEE 754 的布局是分段编码

下面以最常见的 IEEE 754 binary32/binary64 为例。C 标准并不保证所有实现都采用 IEEE 754，因此实际代码还应确认目标平台的浮点格式：

```text
float（32 位）：
[31] 符号 | [30..23] 指数（8 位）| [22..0] 尾数（23 位）

double（64 位）：
[63] 符号 | [62..52] 指数（11 位）| [51..0] 尾数（52 位）
```

规格化数的数值约为 `(-1)^符号 × 1.尾数 × 2^(指数 - 偏置)`（float 的偏置是 127，double 是 1023）。指数和尾数是两段各自编码的小字段，不是从高到低连续的二进制权位。两个特殊的编码约定直接决定了“按位比较”的下场：

- 指数全 1、尾数非 0 编码 NaN（Not a Number）。
- 符号位独立存在，因此有 `+0.0` 和 `-0.0` 两种零。

### 第三层：位相同不等于数值相等，数值相等也不等于位相同

```c
#include <math.h>
#include <stdint.h>
#include <stdio.h>
#include <string.h>

int main(void) {
    _Static_assert(sizeof(double) == sizeof(uint64_t),
                   "this example requires 64-bit double");

    // 1. +0.0 与 -0.0：符号位不同，位模式不同。
    double pos_zero = 0.0;
    double neg_zero = -0.0;

    // 2. 数值上它们相等：== 返回真。
    printf("pos == neg: %d\n", pos_zero == neg_zero);   // 1

    // 3. 位模式上它们不同：memcpy 后按整数比较返回假。
    uint64_t pos_bits = 0, neg_bits = 0;
    memcpy(&pos_bits, &pos_zero, sizeof pos_bits);
    memcpy(&neg_bits, &neg_zero, sizeof neg_bits);
    printf("same bits: %d\n", pos_bits == neg_bits);    // 0

    // 4. 但两者在数学上确实有区别：倒数分别是正负无穷。
    printf("1/pos = %f\n", 1.0 / pos_zero);             // inf
    printf("1/neg = %f\n", 1.0 / neg_zero);             // -inf

    // 5. NaN 与任何值都不相等，包括它自己。
    double nan_value = NAN;
    printf("nan == nan: %d\n", nan_value == nan_value); // 0
    return 0;
}
```

两类陷阱正好方向相反：

- `+0.0` 与 `-0.0`：数值比较（`==`）说相等，位模式比较说不等。
- NaN：把对象表示复制到整数后，同一位模式当然会得到相等的整数；但把这两个值作为浮点数比较时，`==` 仍然为假，`!=` 为真。

也就是说，**位模式相等和数值相等是两套互不一致的判据**，谁也不能替代谁。

### 那到底该怎么比较浮点数

- 判断数值相等：按业务定义容差，`fabs(a - b) <= eps`。注意不存在万能的 `eps`，它应该和数据的量级挂钩；这不是位运算问题，而是浮点舍入的固有问题。
- 判断 NaN：用 `<math.h>` 的 `isnan(x)`，不要依赖 `x != x` 这种副作用式写法。
- 区分 `+0.0` 与 `-0.0`：用 `<math.h>` 的 `signbit(x)`。
- 确实要比较位模式（例如做哈希或序列化去重）时，先用 `memcpy` 取位，再决定是否把 `-0.0` 规范化为 `+0.0`、是否统一 NaN 的负载，让“位相等”重新对齐你要的语义。

> **关键认知：** 浮点数的位模式是“编码”而不是“数值”。整数的位模式就是数值本身，所以位运算有意义；浮点数必须先解码才能比较，而 `==`、`isnan`、`signbit` 就是标准库提供的解码入口。

## 不同语言的移位语义：C、Java、JavaScript 与 Dart

位运算技巧经常在语言之间被抄来抄去——同一段“移位取最低位”的代码，从 C 抄到 Java、再抄到 JavaScript 或 Dart。但这几种语言对移位的契约差别很大，抄之前必须核对规则。

先看结论对比：

| 问题 | C（C23 前/后） | Java | JavaScript | Dart |
|------|----------------|------|------------|------|
| 右移负数 | 实现定义（常见为算术右移） | `>>` 算术右移；`>>>` 无符号右移 | `>>` 算术右移；`>>>` 无符号右移 | `>>` 算术右移；`>>>` 无符号右移 |
| 移位量达到或超过位宽 | 未定义行为 | 按位宽取模（int 取低 5 位，long 取低 6 位） | 按 32 取模 | 文档只要求非负；验证环境中原生 `1 << 64` 与 `-9 >>> 64` 都得到 0，Web 上 `1 << 32` 也得到 0 |
| 位运算的操作宽度 | 操作数类型的实际宽度（`int` 常见 32 位） | 固定：`int` 32 位、`long` 64 位 | 一律先转成 32 位有符号整数 | 原生是有符号 64 位补码；Web 上截断到 32 位，结果按无符号解释 |

本节的具体数值都做过实测：C 用 clang 21.1.6（`-std=c23`），Java 用 JDK 21.0.8，JavaScript 用 Node.js 24，Dart 用 3.12.2 的原生 VM 与 `dart compile js` 输出。其中 C 的未定义行为和实现定义行为只按标准描述下结论，不用某一台机器的实测结果反推可移植性。

### Java：没有无符号整数，只能靠零填充右移

Java 的例子（依据 Java 语言规范 15.19 节）：

```java
// 1. 移位量按位宽取模：1 << 32 等价于 1 << 0。
int a = 1 << 32;   // 1

// 2. int 最高位：结果进入负数区间。
int b = 1 << 31;   // -2147483648

// 3. >> 补符号位，>>> 补 0。
int c = -9 >> 2;   // -3（算术右移）
int d = -9 >>> 2;  // 1073741821（高位补 0，结果恒为非负）
```

Java 提供 `>>>` 的原因是它**没有无符号整数类型**：想按无符号语义看一个 `int` 的位模式，只能靠零填充右移。

### JavaScript：一律转换到 32 位有符号整数

JavaScript 沿用了 `>>>`，并且规定所有位运算都先把操作数转换成 32 位有符号整数（BigInt 除外，`>>>` 对 BigInt 直接抛错）：

```js
// 1. 位运算工作在 32 位有符号整数上，>>> 的结果按无符号解释。
-9 >> 2;    // -3
-9 >>> 2;   // 1073741821

// 2. 移位量按 32 取模：右移 32 位等于没移。
100 >>> 32; // 100
```

### Dart：原生 64 位，Web 上按 32 位截断

Dart 的 `int` 没有 C 那样“平台相关的宽度”，但它有两个目标平台，官方文档给出的模型是：

- 原生（Dart VM、AOT 编译到移动端和桌面端）：`int` 是有符号 64 位补码，运算溢出时按这个宽度回绕。
- Web（编译成 JavaScript）：`int` 用 JavaScript 的 double 表示，能精确表示的范围是 `-2^53` 到 `2^53`；位运算（`&`、`|`、`^`、`~`、`<<`、`>>`、`>>>`）直接使用 JavaScript 的等价运算，操作数被截断成 32 位整数，并按无符号解释。

先确认原生侧的行为：

```dart
// 前置条件：Dart 3.12.2；纯 Dart，无第三方依赖；在 Dart VM（64 位原生）上运行：
//   dart run .work/verify/DD1b/dart_int_semantics.dart
void main() {
  // 1. 原生 int 是有符号 64 位补码，最大值是 2^63 - 1。
  const maxInt = 0x7FFFFFFFFFFFFFFF;

  // 2. 越界既不报错也不变宽，而是按模 2^64 回绕到最小负数。
  final minInt = maxInt + 1;
  _check(minInt == -maxInt - 1, '溢出应按 2^64 回绕');

  // 3. 左移 63 位会把最低位送进符号位，于是得到最小负数。
  _check(1 << 63 == minInt, '<< 只在 64 位内移动');

  // 4. >> 补符号位，>>> 补 0：同一个 -9 得到两个不同的结果。
  _check(-9 >> 2 == -3, '>> 是算术右移');
  _check(-9 >>> 2 == 4611686018427387901, '>>> 把 64 位模式当无符号数看');
  _check(-1 >>> 1 == maxInt, '>>> 的结果不会是负数');

  // 5. ~ 翻转的是 64 位，不是“某个字段的宽度”。
  _check(~0x0F == -16, '~ 按 64 位翻转');
  _check((~0x0F) & 0xFF == 0xF0, '用掩码截到 8 位才得到 F0');

  // 6. 移位量不能为负：Dart 抛出 ArgumentError，而不是反向移位。
  final negativeShift = -1;
  var threw = false;
  try {
    final bad = 1 << negativeShift;
    print('不应走到这里：$bad');
  } on ArgumentError {
    threw = true;
  }
  _check(threw, '负移位量应抛出 ArgumentError');

  // 7. 固定 32 位子字：无论原生还是 Web，都按同一组低位解释。
  _check((-1).toUnsigned(32) == 0xFFFFFFFF, '取低 32 位并按无符号数解释');
  _check(0xFFFFFFFF.toSigned(32) == -1, '重新按有符号 32 位解释');
  print('原生 int 语义检查通过：取值范围 $minInt ~ $maxInt');
}

void _check(bool condition, String message) {
  if (!condition) {
    throw StateError(message);
  }
}
```

再让同一份代码在两个目标平台各跑一次，差异就一目了然：

```dart
// 前置条件：Dart 3.12.2；纯 Dart，无第三方依赖。
// 原生：dart run .work/verify/DD1b/dart_shift_platform_diff.dart
// Web ：dart compile js -o .work/verify/DD1b/out/dart_shift_platform_diff.js \
//         .work/verify/DD1b/dart_shift_platform_diff.dart && node <生成的 .js>
void main() {
  // 1. 官方文档《Numbers in Dart》列出的位运算差异样例。
  final t = 4294967296;
  print('-1 >> 0         = ${-1 >> 0}');
  print('-1 ^ 2          = ${-1 ^ 2}');
  print('2^32            = $t');
  print('2^32 >> 0       = ${t >> 0}');
  print('2^32 >> 1       = ${t >> 1}');
  print('(2^32 - 1) >> 1 = ${(t - 1) >> 1}');

  // 2. 再补几条边界观察：移位量达到 32 位、算术右移与无符号右移。
  final a = 1;
  final b = -9;
  print('1 << 31         = ${a << 31}');
  print('1 << 32         = ${a << 32}');
  print('-9 >> 2         = ${b >> 2}');
  print('-9 >>> 2        = ${b >>> 2}');
  print('~0x0F           = ${~0x0F}');
  print('0xFFFFFFFF | 0  = ${0xFFFFFFFF | 0}');

  // 3. 显式按 32 位子字读，两个平台给出一致结果。
  print('(-1).toUnsigned(32)     = ${(-1).toUnsigned(32)}');
  print('4294967295.toSigned(32) = ${4294967295.toSigned(32)}');
}
```

同一份代码在两个目标平台的实际输出如下（原生用 `dart run`，Web 用 `dart compile js` 加 `node`）：

| 表达式 | 原生（Dart VM） | Web（dart2js + Node.js） |
|--------|-----------------|--------------------------|
| `-1 >> 0` | `-1` | `4294967295` |
| `-1 ^ 2` | `-3` | `4294967293` |
| `2^32` | `4294967296` | `4294967296` |
| `2^32 >> 0` | `4294967296` | `0` |
| `2^32 >> 1` | `2147483648` | `0` |
| `(2^32 - 1) >> 1` | `2147483647` | `2147483647` |
| `1 << 31` | `2147483648` | `2147483648` |
| `1 << 32` | `4294967296` | `0` |
| `-9 >> 2` | `-3` | `4294967293` |
| `-9 >>> 2` | `4611686018427387901` | `1073741821` |
| `~0x0F` | `-16` | `4294967280` |
| `0xFFFFFFFF \| 0` | `4294967295` | `4294967295` |
| `(-1).toUnsigned(32)` | `4294967295` | `4294967295` |
| `4294967295.toSigned(32)` | `-1` | `-1` |

Web 侧的规律可以概括成三条：

1. 32 位以内、且不涉及负数的位运算，原生和 Web 结果一致（`1 << 31`、`(2^32 - 1) >> 1`）。
2. 一旦结果可能为负，Web 会把结果按无符号解释：`-1 >> 0` 得到 `4294967295` 而不是 `-1`，`~0x0F` 得到 `4294967280` 而不是 `-16`。这正好说明 Web 上的 `>>` 和 `>>>` 都是“32 位无符号”家族——`-9 >> 2` 与 `-9 >>> 2` 的差别只在符号位补 1 还是补 0。
3. 操作数超出 32 位时，高位直接被截掉：`2^32 >> 1` 在 Web 上是 `0`。

> **时效信息（核查日期：2026-09）：** Dart 官方文档明确说明 Web 上的数值行为“属于平台相关细节，未来可能调整”。本文给出的具体数值来自验证环境 Dart 3.12.2（`dart compile js` + Node.js 24），不是语言规范的保证。

想在两个平台上得到同一结果，官方建议是**显式按 32 位子字操作**：读取时用 `toUnsigned(32)` 得到 `0 ~ 2^32-1`，需要按有符号解释时再用 `toSigned(32)`；确实需要更大的整数精度时，改用 `BigInt`（原生和 Web 都能用任意精度），但它会带来更大的代码体积和更低的速度。

> **关键认知：** Dart 的位运算原生按 64 位补码进行，Web 上却按 32 位无符号解释；“Dart 的 int 是 64 位”这句话只在原生成立，跨平台位运算必须显式声明并使用 32 位子字。

> **面试高频：** 同一段移位代码从 C 抄到 Java、JavaScript 或 Dart，要注意什么？
> **答题脉络：** 先看移位量语义（C 未定义、Java/JS 取模、Dart 只要求非负）→ 再看负数右移补什么 → 最后看位宽假设与结果符号（Web 上会截到 32 位并按无符号解释）→ 结论是显式限定宽度并写边界检查。
> **追问方向：** `>>>` 为什么在 Java 和 JavaScript 里必需；C 的未定义行为为什么不能靠“先跑一遍”验证；Dart 跨平台时为什么推荐 `toUnsigned(32)`。

## 从位模式回到问题本身

看到位运算时，可以按下面的顺序检查：

1. 这个值的有效位宽是多少？是 `uint8_t`、`uint32_t`，还是平台相关的 `int`？
2. 每一位或每一段位分别代表什么？先画出位布局。
3. 当前操作的目标是设置、清除、切换、测试，还是读取一个多位字段？
4. 移位前后的类型是什么？移位量是否在合法范围？
5. 如果数据要离开当前进程，是否还定义了字节序和编码格式？
6. 如果操作数可能是浮点数，或者这段逻辑要在其他语言里复用，是否核对了对应世界的规则（浮点数见[浮点数为什么不能用位运算比较相等](#浮点数为什么不能用位运算比较相等)，语言差异见[不同语言的移位语义](#不同语言的移位语义cjavajavascript-与-dart)）？
7. 如果代码还要编译到 Web 或 32 位平台，位宽假设是否仍然成立？

## 一句话总结

位运算就是在固定宽度的位模式上做局部修改，掌握补码、整数提升和掩码规则后，`&`、`|`、`^`、`~` 与移位就会从“魔法符号”变成可推导的工具；而把它们带出整数世界（浮点数、其他语言、Web 平台）之前，先核对那片世界的规则。
