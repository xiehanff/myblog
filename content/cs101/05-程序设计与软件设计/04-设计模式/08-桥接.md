## 意图（Intent）

把抽象部分与它的实现部分分离，使两者可以独立变化。

动机：遥控器要控制电视。如果按继承建模，就会得到 `SonyBasicRemote`、`SonyStereoRemote`、`RcaBasicRemote`……两个维度各有 M、N 种取值，类数量是 M × N。真正的问题是“遥控器做什么”和“电视怎么实现”本来就是两条独立的变化轴，把它们塞进同一棵继承树，等于强迫两条轴同步改动。桥接用组合把两条轴连起来：抽象侧持有实现侧协议，各自扩展互不干扰。

## 结构（Structure）

```text
抽象侧                             实现侧
RemoteControl ──持有──▶ Device ◀──implements── SonyTv / RcaTv / LgTv
      ▲                    ▲
BasicRemote          （品牌细节被协议挡住）
RecordingRemote
```

- **Abstraction**：抽象侧的顶层，定义高层动作，持有 Implementor 引用并转发。
- **RefinedAbstraction**：在抽象侧新增能力，例如“记住上次频道”。
- **Implementor**：实现侧协议，声明设备能力。
- **ConcreteImplementor**：具体品牌，只关心自己怎么实现，不知道谁在调用。

依赖方向：抽象侧单向依赖 `Device` 协议；具体设备不认识遥控器。新增品牌只改实现侧，新增遥控器只改抽象侧。

## 实现（Implementation）

用 `Device` 表示设备这条轴，用 `RemoteControl` 表示遥控器这条轴。3 个设备类加 2 个遥控器类，共 5 个类就能覆盖 6 种组合；换成继承则要为每种组合各写一个子类。

以下代码合起来是完整文件 `bridge.dart`。验证环境：Dart 3.12.2；`dart analyze` 无问题，`dart run --enable-asserts` 通过。

```dart
// 前置条件：Dart 3.x；纯 Dart；无第三方依赖。
// 运行：dart run --enable-asserts bridge.dart

/// 实现侧（Implementor）：设备这条变化轴。
abstract interface class Device {
  String powerOn();

  String setChannel(int channel);
}

final class SonyTv implements Device {
  const SonyTv();

  @override
  String powerOn() => 'Sony 开机';

  @override
  String setChannel(int channel) => 'Sony 切到 $channel 频道';
}

final class RcaTv implements Device {
  const RcaTv();

  @override
  String powerOn() => 'RCA 开机';

  @override
  String setChannel(int channel) => 'RCA 切到 $channel 频道';
}

final class LgTv implements Device {
  const LgTv();

  @override
  String powerOn() => 'LG 开机';

  @override
  String setChannel(int channel) => 'LG 切到 $channel 频道';
}

```

```dart
/// 抽象侧（Abstraction）：遥控器这条变化轴，只依赖 Device 协议。
abstract class RemoteControl {
  RemoteControl(this._device);

  // Dart 没有 protected：`_device` 是库级私有，同一库中的子类可直接访问。
  final Device _device;

  // 1. 遥控器的通用动作都转发给设备，不知道自己插的是哪个品牌。
  String power() => _device.powerOn();

  String tune(int channel) => _device.setChannel(channel);
}

/// 基础遥控器：不新增能力，只暴露通用动作。
final class BasicRemote extends RemoteControl {
  BasicRemote(super.device);
}

/// 扩展抽象（RefinedAbstraction）：只在遥控器这一维度上长本事。
final class RecordingRemote extends RemoteControl {
  RecordingRemote(super.device);

  int? _lastChannel;

  String tuneAndRemember(int channel) {
    _lastChannel = channel;
    return tune(channel);
  }

  String replay() {
    final channel = _lastChannel;
    if (channel == null) return '还没有可回放的频道';
    return tune(channel);
  }
}

```

```dart
void main() {
  // 2. 两个维度在装配时组合：3 个设备类 + 2 个遥控器类 = 5 个类。
  final devices = <Device>[const SonyTv(), const RcaTv(), const LgTv()];
  final remotes = <RemoteControl>[
    for (final device in devices) BasicRemote(device),
    for (final device in devices) RecordingRemote(device),
  ];
  assert(remotes.length == 6); // 覆盖 6 种组合，而不是写 6 个子类

  // 3. 同一段遥控器代码，换一个 Device 就换一套输出。
  assert(remotes[0].tune(3) == 'Sony 切到 3 频道');
  assert(remotes[4].power() == 'RCA 开机');

  // 4. 扩展抽象新增的能力只存在于遥控器这一条轴。
  final recording = RecordingRemote(const LgTv());
  assert(recording.replay() == '还没有可回放的频道');
  recording.tuneAndRemember(9);
  assert(recording.replay() == 'LG 切到 9 频道');
  print(remotes[4].power());
}
```

要点：

- “抽象”在桥接里不是父类的同义词，而是相对实现细节的高层概念。`RemoteControl` 是抽象侧，`Device` 是实现侧；两者的耦合点只有一份协议引用。
- 断言集中证明两侧可独立演化：设备列表增加 LG 时，`RemoteControl` 与两个子类一行都不用改；`RecordingRemote` 增加 `replay` 时，三个品牌也一行都不用改。
- Dart 没有 `protected` 关键字，示例用库级私有 `_device`。如果把抽象侧和实现侧拆到不同文件，要么暴露只读 getter，要么用 `@protected`（package:meta）让分析器在越权访问时给出 `invalid_use_of_protected_member` 提示；它是提示而非编译错误，仍需文档约定配合。
- 桥接不是“只要有两个类就用组合”。判定标准是两条轴是否都会被独立扩展；如果实现侧只有唯一实现，或者两个维度总是一起变化，多一层协议只会增加间接成本。
- mixin 与桥接不是一回事：mixin 在编译期把能力叠加到类型上，桥接在运行期通过组合选择实现，两者解决的问题和可变性都不同。

## 适用条件与代价

- 适用：存在两个以上独立变化维度；希望避免类数量按维度乘积增长；抽象侧需要复用同一套高层流程去驱动不同实现。
- 代价：多一层转发，阅读代码时要跟着引用跳到实现侧；如果维度划分错了（比如把本来会一起变化的属性拆成两条轴），抽象会成为负担；接口设计期投入较大，改协议的波及面比改单个子类大。

## Dart 标准库与生态映射

- Dart 标准库没有与桥接直接对应的类型。桥接的本质是“抽象侧持有实现侧协议”，而这正是 Dart 面向接口编程的常规组合方式，标准库不需要专门的 API。
- `Stream` 与 `StreamSink` 之间也是“生产者—消费者”解耦，但那是异步事件的流向，与“两条继承轴独立扩展”的桥接意图不同，不能类比成同一模式。

## 面试追问

- 桥接和适配器都用了组合，区别在哪？（适配器是事后兼容既有接口，桥接是事前把两个变化维拆开）
- 桥接和策略有什么区别？（策略替换的是单个算法，Context 通常不需要被扩展；桥接的抽象侧自己也是一棵可扩展的层次）
- 怎么判断一个场景真的需要桥接，而不是一个普通接口加两个实现？
- 如果实现侧以后要增加 `Device` 不具备的能力，抽象侧应该怎么响应？
- 桥接的抽象侧要不要直接暴露 `Device` 给调用方？暴露的代价是什么？

## 一句话总结

> 桥接把抽象与实现拆成两条可独立扩展的轴，判定标准是两条轴是否真的会各自变化，而不是“用了组合”。
