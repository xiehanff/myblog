## 意图（Intent）

为其他对象提供一种代理，以控制对这个对象的访问。

动机：大图、远端服务、权限受限的数据源，都不能让客户端直接、无限制地访问。客户端希望用的还是同一套接口，但访问需要被延迟、筛选、缓存或转发。代理在客户端和真实对象之间插入一个同协议的替身：什么时候创建真实对象、要不要真的调用它，由代理决定。原始场景里“图片先把尺寸交给布局，等真正渲染时再加载大图”就是典型的虚拟代理。

## 结构（Structure）

```text
Client ──▶ Image ◀──implements── LazyImageProxy ──第一次调用时创建──▶ RemoteImage
              ▲                                                        ▲
              └────────────────── implements ───────────────────────────┘
```

常见四类代理：

- **虚拟代理（Virtual Proxy）**：延迟创建开销大的对象，先提供廉价的元数据。
- **保护代理（Protection Proxy）**：按调用者权限决定是否放行。
- **缓存代理（Cache Proxy）**：复用已经完成的结果，并处理失效与并发请求合并。
- **远程代理（Remote Proxy）**：把调用编码后发往另一个地址空间，对应到 Dart 就是网络或 isolate 边界。

依赖方向：客户端只依赖 `Image` 协议；代理与真实对象都实现该协议；真实对象不知道代理存在。

## 实现（Implementation）

本篇完整实现虚拟代理，并用假的异步 loader 模拟图片加载，示例不访问网络。代理第一次调用时才创建真实对象，并把重复调用合并到同一个 `Future` 上。

以下代码合起来是完整文件 `proxy.dart`。验证环境：Dart 3.12.2；`dart analyze` 无问题，`dart run --enable-asserts` 通过。

```dart
// 前置条件：Dart 3.x；纯 Dart；无第三方依赖；示例不访问网络。
// 运行：dart run --enable-asserts proxy.dart
/// 主题（Subject）：客户端只依赖这个协议。
abstract interface class Image {
  int get width;

  int get height;

  Future<String> render();
}

/// 真实主题（RealSubject）：渲染代价高，虚拟代理负责推迟它的创建。
final class RemoteImage implements Image {
  RemoteImage(this._path);

  final String _path;

  @override
  int get width => 1920;

  @override
  int get height => 1080;

  @override
  Future<String> render() async {
    await Future<void>.delayed(const Duration(milliseconds: 30));
    return '渲染 $_path（1920x1080）';
  }
}

/// 虚拟代理：先把元数据交出去，真实对象推迟到第一次调用。
final class LazyImageProxy implements Image {
  LazyImageProxy(
    this._path, {
    required this.width,
    required this.height,
    required Future<Image> Function(String path) loader,
  }) : _loader = loader;

  final String _path;

  @override
  final int width;
  @override
  final int height;

  final Future<Image> Function(String path) _loader;
  Future<Image>? _real;

  // 1. 第一次调用创建真实对象，之后复用；并发的重复调用共享同一个 Future。
  @override
  Future<String> render() async {
    final real = await (_real ??= _loader(_path));
    return real.render();
  }
}

```

```dart
void main() async {
  var loadCount = 0;
  Future<Image> fakeLoad(String path) async {
    loadCount++;
    await Future<void>.delayed(const Duration(milliseconds: 10));
    return RemoteImage(path);
  }

  final proxy = LazyImageProxy(
    'cover.jpg',
    width: 1920,
    height: 1080,
    loader: fakeLoad,
  );

  // 2. 元数据立即可用，真实加载还没发生。
  assert(loadCount == 0 && proxy.width == 1920 && proxy.height == 1080);

  // 3. 两个“同时”发起的渲染共享同一个 Future，只加载一次。
  final results = await Future.wait([proxy.render(), proxy.render()]);
  assert(loadCount == 1 && results[0] == results[1]);
  print(results.first);

  // 4. 失败也被缓存：两次调用拿到同一个失败的 Future，加载只尝试一次。
  loadCount = 0;
  final broken = LazyImageProxy(
    'missing.jpg',
    width: 0,
    height: 0,
    loader: (path) async {
      loadCount++;
      throw StateError('无法加载 $path');
    },
  );
  for (var index = 0; index < 2; index++) {
    try {
      await broken.render();
    } on StateError {
      // 期望：错误原样传播，而不是被代理吞掉。
    }
  }
  assert(loadCount == 1);
}
```

要点：

- 代理和真实对象实现同一个 `Image` 协议，客户端代码在有无代理时完全一致。这是代理与“给调用方额外塞一个服务对象”的根本区别。
- `_real ??= _loader(_path)` 同时完成两件事：延迟创建和请求合并。两次“同时”调用会共享同一个 `Future`，真实对象只创建一次；`Future` 完成后继续复用，相当于缓存。
- 这个缓存没有失效时间，也没有取消未完成加载的机制；生产代码要根据资源生命周期补充失效、重试、取消和错误缓存策略，不能把一次性的示例直接当成通用缓存代理。
- 失败也会被缓存，这是策略选择而非 Dart 的默认行为。示例中同一个失败的 `Future` 被重复返回，所以不会反复加载。如果业务需要“失败后允许重试”，要在 `catch` 中清空 `_real` 再重新抛出；如果每次调用都重建 `Future`，就既没有缓存也没有合并。
- 异步会向调用方扩散：`render()` 返回 `Future<String>`，代理无法把远端加载伪装成同步、零成本的本地调用。声称“代理对客户端完全透明”时，必须把异步契约、错误和取消行为一并说明。
- 保护代理和缓存代理的结构与虚拟代理相同，区别只在 `render()`（或其他方法）里做什么：检查权限、查缓存、编码转发。本篇只把虚拟代理写成完整代码，避免示例膨胀。
- Dart 没有通用的运行期动态代理机制。`dart:mirrors` 在 AOT 编译下不可用（Flutter 的 release 构建尤其如此），不能设计依赖反射动态生成代理的方案；需要通用代理时，通常用代码生成在编译期产出代理类。
- `noSuchMethod` 只能作为旁注：它让对象在调用不存在的成员时有个兜底实现，但会绕过静态类型检查，把编译期错误推迟到运行期，不适合作为常规代理手段。

## 适用条件与代价

- 适用：访问真实对象的代价高（延迟、网络、内存），需要在调用前后加入统一的控制逻辑（权限、缓存、日志、限流），并且客户端希望保持同一个协议。
- 代价：多一层间接调用，堆栈变长、调试更绕；异步接口会传染给调用方；缓存代理必须处理失效、并发合并和内存增长，示例只演示了合并；远程代理不会让网络变成零成本，超时、重试、序列化边界都要单独设计。
- 与装饰器的区别在意图而不在结构：装饰器给调用方叠加职责，通常一定会调用内层；代理控制访问，可能延迟、拒绝甚至不调用真实对象。

## Dart 标准库与生态映射

- Dart 标准库没有通用的运行期代理类型，本篇示例即最小实现。
- `Future` 是异步结果，不是代理：它不控制对某个对象的访问，也不能延迟创建被访问的对象。两者经常一起出现，但语义不同。
- 需要跨 isolate 或跨网络访问时，用消息通道（`Isolate`、`SendPort`）或 HTTP 客户端显式编码请求，不要指望用透明代理掩盖通信成本。

## 面试追问

- 代理、装饰器、适配器三者的结构都靠“同一协议 + 持有对象”，怎么区分意图？
- 远程代理为什么不能伪装成本地零成本调用？哪些语义会在跨越边界时丢失？
- 缓存代理如何处理失效？多个并发请求同时未命中时怎么办？
- 保护代理的权限检查应该放在代理里还是真实对象里？
- 代理能否改变真实对象的返回值或错误类型？契约边界在哪里？
- Dart 没有动态代理，需要为大量接口生成代理时怎么办？

## 一句话总结

> 代理与真实对象实现同一协议，用延迟创建、缓存或权限检查控制访问；结构相似之下，意图才是它与装饰器、适配器的分界。
