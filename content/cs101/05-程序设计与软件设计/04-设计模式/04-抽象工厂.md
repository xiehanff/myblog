## 意图（Intent）

提供一个接口，用于创建**相关的对象家族**，而不必指定具体类。

动机：编码器和解码器必须配套——JSON 编码的数据要用 JSON 解析，键值对编码的数据要用对应的键值对解析器。如果客户端自己分别去创建两个产品，就可能把不同族的对象拼在一起，错误往往要到数据往返时才暴露。抽象工厂把“一族产品”打包成一个创建入口，客户端只依赖这个入口，就无法混搭。

## 结构（Structure）

```text
Client ──▶ CodecFactory ──createEncoder()──▶ Encoder ◀── JsonEncoder / KeyValueEncoder
                │
                └────────createDecoder()──▶ Decoder ◀── JsonDecoder / KeyValueDecoder

JsonCodecFactory 一次产出 JSON 族的编码器与解码器；KeyValueCodecFactory 同理。
```

- **AbstractFactory / ConcreteFactory**：声明一族产品的创建方法，具体工厂决定用哪套实现。
- **ProductA / ProductB**：两个相互配合的产品协议，客户端同时使用它们。
- 依赖方向：客户端依赖 CodecFactory 与两个产品协议，不认识任何具体类。

和[工厂方法](03-工厂方法.md)的区别：工厂方法只延迟**一个**产品的创建，用继承完成；抽象工厂创建**一族**产品，客户端通过组合持有一个工厂对象。

## 实现（Implementation）

以下三段代码合起来是完整文件 `abstract_factory.dart`（因较长按职责拆分）。验证环境：Dart 3.12.2；`dart analyze` 无问题，`dart run --enable-asserts` 通过。

产品协议与两个具体工厂（对应文件第 1–41 行）：

```dart
// 前置条件：Dart 3.x；纯 Dart；无第三方依赖。
import 'dart:convert' show jsonDecode, jsonEncode;

abstract interface class Encoder {
  String encode(Map<String, Object?> row);
}

abstract interface class Decoder {
  Map<String, Object?> decode(String text);
}

/// 工厂协议：一次创建一族产品，客户端只依赖它。
abstract interface class CodecFactory {
  String get name;

  Encoder createEncoder();

  Decoder createDecoder();
}

final class JsonCodecFactory implements CodecFactory {
  @override
  String get name => 'json';

  @override
  Encoder createEncoder() => JsonEncoder();

  @override
  Decoder createDecoder() => JsonDecoder();
}

final class KeyValueCodecFactory implements CodecFactory {
  @override
  String get name => 'key-value';

  @override
  Encoder createEncoder() => KeyValueEncoder();

  @override
  Decoder createDecoder() => KeyValueDecoder();
}
```

两族的具体产品（对应文件第 43–77 行）：

```dart
final class JsonEncoder implements Encoder {
  @override
  String encode(Map<String, Object?> row) => jsonEncode(row);
}

final class JsonDecoder implements Decoder {
  @override
  Map<String, Object?> decode(String text) {
    final decoded = jsonDecode(text);
    if (decoded is! Map<String, dynamic>) {
      throw const FormatException('期望 JSON 对象');
    }
    return decoded;
  }
}

final class KeyValueEncoder implements Encoder {
  @override
  String encode(Map<String, Object?> row) => row.entries
      .map((MapEntry<String, Object?> entry) => '${entry.key}=${entry.value}')
      .join(';');
}

final class KeyValueDecoder implements Decoder {
  @override
  Map<String, Object?> decode(String text) {
    final row = <String, Object?>{};
    for (final pair in text.split(';')) {
      final separator = pair.indexOf('=');
      if (separator <= 0) throw FormatException('不是 key=value 形式', text);
      row[pair.substring(0, separator)] = pair.substring(separator + 1);
    }
    return row;
  }
}
```

客户端与断言（对应文件第 79–103 行）：

```dart
/// 客户端只持有 factory：编码器和解码器必然来自同一族。
Map<String, Object?> roundTrip(CodecFactory factory, Map<String, Object?> row) {
  final encoded = factory.createEncoder().encode(row);
  return factory.createDecoder().decode(encoded);
}

void main() {
  final row = <String, Object?>{'title': '抽象工厂', 'level': 'high'};

  // 1. 整体替换 factory 就换掉整个产品族，客户端代码不变。
  for (final factory in <CodecFactory>[
    JsonCodecFactory(),
    KeyValueCodecFactory(),
  ]) {
    final restored = roundTrip(factory, row);
    assert(restored.length == row.length);
    assert(restored['title'] == '抽象工厂' && restored['level'] == 'high');
    print('${factory.name}: $restored');
  }

  // 2. 绕过 factory 混搭两族产品：格式错误会立刻暴露。
  try {
    KeyValueDecoder().decode(JsonEncoder().encode(row));
    assert(false, '混用两族应当解析失败');
  } on FormatException catch (error) {
    print('混用产品族失败：${error.message}');
  }
}
```

要点：

- 族一致性由 factory 保证，不靠类型系统：`Encoder` 和 `Decoder` 是独立协议，直接 `KeyValueDecoder().decode(JsonEncoder()...)` 编译期完全合法，只有运行期数据才暴露不匹配。产品协议越弱，这种风险越高。
- 新增族很便宜：加一个 `XmlCodecFactory` 不动客户端；新增产品种类很贵：给 `CodecFactory` 加 `createPrettyPrinter()`，所有具体工厂都要跟着改。
- 只有一族、或只有一个产品维度时，不必上抽象工厂；那通常是[工厂方法](03-工厂方法.md)或简单函数该解决的问题。产品族规模很小时，用一个 record 装两个创建函数也能表达同一契约：`typedef CodecPair = ({Encoder Function() newEncoder, Decoder Function() newDecoder});`。

## 适用条件与代价

- 适用：多组产品必须成套使用，客户端需要在运行时整体切换实现；产品族相对稳定、产品种类较少。
- 代价：工厂协议一旦被当成扩展点，新增产品种类会波及所有工厂；交互式场景里工厂对象通常是有状态的，生命周期和多族并用都要想清楚。
- 与 DI 容器的关系：容器负责装配“用哪个具体工厂”，模式本身只约束“客户端如何取产品”。两者协作时，客户端依赖工厂协议，具体工厂在 composition root 注入。

## Dart 标准库与生态映射

- Dart 标准库没有抽象工厂的同名实现，本篇示例即最小实现。
- 真正的生态替代是依赖注入：把具体工厂在装配点选择好再注入，往往比让客户端自己持有 `CodecFactory` 更直接。
- 不要把 Flutter 的 `Theme`、`ThemeData` 当作本模式的官方案例：它表达的是主题数据，不是一组产品的创建协议。

## 面试追问

- 产品族与单一产品维度有什么区别？（族内产品需要配套；多一个维度就要多一个创建方法）
- 为什么新增产品族容易、新增产品种类困难？（前者加一个实现，后者要改所有工厂协议）
- 与[工厂方法](03-工厂方法.md)、[简单工厂](02-简单工厂.md)怎么区分？（一个对象 / 一族对象；子类覆写 / 集中选择）
- 族的一致性由谁保证？（由客户端只使用 factory 产出的产品来保证，类型系统不强制）
- 抽象工厂和 DI 容器是什么关系？（容器决定注入哪个具体工厂；抽象工厂是客户端取产品的协议）

> 抽象工厂约束的是“一族产品要配套使用”：整体换工厂就能换产品族，但新增产品种类会波及所有具体工厂。
