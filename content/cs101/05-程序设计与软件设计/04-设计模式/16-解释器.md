## 意图（Intent）

给定一个语言，定义它的文法的一种表示，并定义一个解释器，这个解释器使用该表示来解释语言中的句子。

动机：有些规则天然是一棵表达式树——"D And (A Or B)"、折扣条件、功能开关的布尔组合，都属于这种小语言。用一长串 `if/else` 判断当然能跑，但规则一多就会退化：解析输入、判断条件、组合规则全部混在同一段代码里，想加一个"取反"要改多处；换一种输入格式，所有规则都要重写。解释器模式把"文法"和"求值"分开——文法用一棵对象树表示，解释器只负责在这棵树上递归求值。

## 结构（Structure）

```text
Client ──构造──▶ Expr（抽象表达式）
                   │
        ┌──────────┼───────────────┐
      Term        And / Or          Not
   （终结符）   （非终结符）      （非终结符）
                   │
     interpret(expr, context) ──递归──▶ bool
```

- **AbstractExpression（Expr）**：声明解释操作，所有节点都属于这个封闭家族。
- **TerminalExpression（Term）**：终结符，是树的最小单位，直接对上下文求值。
- **NonterminalExpression（And/Or/Not）**：持有子表达式，先递归解释子节点，再组合结果。
- **Context**：解释器之外的信息。本示例是 `Set<String> facts`（原例是待检验的字符串）。
- **Client**：在装配阶段拼出语法树，然后调用 `interpret`。

依赖方向：每个节点只依赖自己的子节点类型与 Context，不认识具体的输入字符串；Client 只依赖 `Expr` 和 `interpret`，不关心求值细节。

## 实现（Implementation）

下面是一个布尔规则检验器：Context 是"已知事实"的集合，语法树用来判断这些事实能否满足规则。原 Java 版让终结符把输入切成 token 再逐个比较，这里改成集合查找——切分输入是 parser 的职责，不该混进解释器。

以下两段合起来是完整文件 `interpreter.dart`。验证环境：Dart 3.12.2；`dart analyze` 无问题，`dart run --enable-asserts` 通过（Dart 默认不启用断言，运行带 `assert` 的示例时要显式开启）。

```dart
// 前置条件：Dart 3.x；纯 Dart；无第三方依赖。
// 解释器：sealed 节点族表达文法，穷尽 switch 求值。

/// 表达式树节点：sealed 封闭全部子类型，switch 必须穷尽。
sealed class Expr {
  const Expr();
}

/// 终结符：叶子节点，直接对应一条事实。
final class Term extends Expr {
  const Term(this.name);

  final String name;
}

/// 非终结符：对子表达式取反。
final class Not extends Expr {
  const Not(this.operand);

  final Expr operand;
}

final class And extends Expr {
  const And(this.left, this.right);

  final Expr left;
  final Expr right;
}

final class Or extends Expr {
  const Or(this.left, this.right);

  final Expr left;
  final Expr right;
}

```

```dart
/// 求值：解释逻辑独立于节点类，新增一种运算只需再加一个函数。
bool interpret(Expr expr, Set<String> facts) => switch (expr) {
  // 1. 终结符在上下文里查事实。
  Term(:final name) => facts.contains(name),
  // 2. 非终结符递归求值。
  Not(:final operand) => !interpret(operand, facts),
  And(:final left, :final right) =>
    interpret(left, facts) && interpret(right, facts),
  Or(:final left, :final right) =>
    interpret(left, facts) || interpret(right, facts),
};

void main() {
  // 3. 直接构造语法树：D And (A Or (B Or C))。
  const rule = And(Term('D'), Or(Term('A'), Or(Term('B'), Term('C'))));

  // 4. 上下文就是已知事实集合，不需要对字符串做切分。
  assert(interpret(rule, {'D', 'A'}));
  assert(interpret(rule, {'D', 'C'}));
  assert(!interpret(rule, {'A', 'B'}));
  assert(!interpret(const Not(Term('D')), {'D'}));

  print(interpret(rule, {'D', 'A'})); // true
}
```

要点：

- `sealed` 让编译器掌握 `Expr` 的全部子类型，`interpret` 里的 `switch` 因此必须穷尽。新增一种节点后如果忘记处理，代码在分析阶段就报错，而不是在运行时悄悄漏掉一个分支——这是把"文法封闭"写进类型系统的做法。
- 求值逻辑写成顶层函数，节点类只保存数据。这是本篇选定的主方案；另一种写法是让 `Expr` 声明 `bool interpret(Set<String> facts)`，各节点覆写。前者在"节点类型稳定、运算不断增加"时更省事：新增运算加一个函数，不碰节点类；后者在"运算稳定、节点不断增加"时更自然。这是经典的表达式问题（expression problem），选哪种取决于哪条轴变化更快。
- `main` 里直接用构造函数拼树，没有解析步骤。真实语言必须先做词法分析和语法分析，再把语法树交给解释器：parser 把 `"D And (A Or B)"` 变成 `And(Term('D'), Or(Term('A'), Term('B')))`，evaluator 只面对树。不要把 `String.split` 或 `RegExp` 当作通用 parser。

## 适用条件与代价

- 适用：文法小且稳定、规则以组合为主、需要频繁新增"对树的运算"、不值得引入完整 parser 生成器的场景。
- 不适用：语法复杂（运算符优先级、括号、错误恢复）、需要高性能，或需要让用户编辑完整语言。此时应使用成熟的 parser（手写递归下降、parser combinator、生成器）或规则引擎。
- 代价：一条文法规则通常对应一个节点类，类的数量随文法增长；求值靠递归，极深的表达式有栈溢出风险；语法错误的位置和原因不在解释器职责内，要在 parser 侧补齐。

## Dart 标准库与生态映射

- `RegExp` 是标准库提供的模式匹配器：它自带正则文法，但正则只覆盖正则语言，不能替代通用 parser，也不是本篇这种 AST 解释器。
- Dart 标准库无同名实现，本篇示例即最小解释器；文法变复杂时不要靠标准库硬凑，应改用成熟的 parser 包或规则引擎。

## 面试追问

- 解释器和[访问者](./24-访问者.md)（Visitor）是什么关系？两者都把"运算"从数据结构里分出来：解释器让文法节点自己组成可求值的树，访问者用双分派为稳定的节点族扩展外部操作。Dart 的 sealed switch 是编译期可穷尽的分派，可以看作其中一种实现手段。
- 为什么解释器不适合复杂语法？每条文法规则都会变成一个类或节点，解析、优先级和错误恢复都要自己实现；规模和性能都不如成熟 parser。
- parser 和 evaluator 各负责什么？parser 把字符串变成语法树并报告语法错误；evaluator 只遍历语法树求值，不关心原始字符串长什么样。
- 新增一种运算和新增一种节点，哪个更便宜？前者只需要新函数（本示例），后者会破坏所有穷尽 switch，需要逐个更新。

## 一句话总结

> 解释器把小型文法表示成表达式树并递归求值；文法或性能一旦复杂到需要完整解析器，就应停止继续堆解释器节点。
