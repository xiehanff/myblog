## 意图（Intent）

动态地给一个对象添加职责，而不修改它的类，也不用为每种组合创建子类。

动机：饮料加配料时，“要不要牛奶、要不要摩卡、要不要打折”会让子类数量迅速膨胀；而且需求变化时包装顺序也可能变。装饰器把每一层职责做成一个实现同一协议、并持有内层对象的包装器，运行时想套几层就套几层。它对应“对扩展开放、对修改关闭”，但边界要说清楚：只在可预期的变化点开放，而不是宣称任何类都不该被修改。

## 结构（Structure）

```text
Client ──▶ Beverage ◀──implements── Milk / Mocha / Discount ──持有──▶ Beverage
              ▲
        DarkRoast（最内层，方法实现不依赖其它对象）
```

- **Component**：被装饰者与装饰者共同的协议。
- **ConcreteComponent**：最内层的原始对象，不知道装饰者的存在。
- **Decorator**：实现 Component 并持有另一个 Component，把请求转发后附加职责。
- **Client**：决定包装哪几层、以什么顺序包装。

依赖方向：所有装饰者单向依赖 `Beverage` 协议；被装饰对象完全不知道外层存在，所以能层层嵌套。

## 实现（Implementation）

沿用饮料与配料的场景，并加入一个乘法的折扣装饰器。加料是加法、可交换；折扣是乘法，包装顺序会改变最终价格。

以下代码合起来是完整文件 `decorator.dart`。验证环境：Dart 3.12.2；`dart analyze` 无问题，`dart run --enable-asserts` 通过。金额以“分”为单位做整数运算，避免浮点误差。

```dart
// 前置条件：Dart 3.x；纯 Dart；无第三方依赖。
// 运行：dart run --enable-asserts decorator.dart；金额单位：分，用整数运算避免浮点误差。

/// 组件（Component）：饮料与配料的共同协议。
abstract interface class Beverage {
  String get name;

  int get priceInCents;
}

base class DarkRoast implements Beverage {
  const DarkRoast();

  @override
  String get name => '深烘咖啡';

  @override
  int get priceInCents => 1200;
}

/// 装饰者基类：实现同一协议，并持有一个同类型的被装饰对象。
abstract class CondimentDecorator implements Beverage {
  const CondimentDecorator(this.inner);

  final Beverage inner;
}

final class Milk extends CondimentDecorator {
  const Milk(super.inner);

  @override
  String get name => '${inner.name} + 牛奶';

  @override
  int get priceInCents => inner.priceInCents + 250;
}

final class Mocha extends CondimentDecorator {
  const Mocha(super.inner);

  @override
  String get name => '${inner.name} + 摩卡';

  @override
  int get priceInCents => inner.priceInCents + 300;
}

/// 折扣装饰器不是加法，而是对当前总价打折：包装顺序从此有意义。
final class Discount extends CondimentDecorator {
  factory Discount(Beverage inner, int percentOff) {
    if (percentOff < 0 || percentOff > 100) {
      throw ArgumentError.value(percentOff, 'percentOff', '折扣必须在 0% 到 100% 之间');
    }
    return Discount._(inner, percentOff);
  }

  const Discount._(super.inner, this.percentOff);

  final int percentOff;

  @override
  String get name => '${inner.name} + 折扣$percentOff%';

  @override
  int get priceInCents => inner.priceInCents * (100 - percentOff) ~/ 100;
}

```

```dart
/// mixin 版本：能力在编译期叠加到类型上，运行期不能再拆开。
base mixin MilkPricing on DarkRoast {
  @override
  String get name => '${super.name} + 牛奶';

  @override
  int get priceInCents => super.priceInCents + 250;
}

final class DarkRoastWithMilk extends DarkRoast with MilkPricing {}

/// 单方法协议还可以用“函数包函数”装饰，不必建类。
int Function() addMocha(int Function() base) =>
    () => base() + 300;

void main() {
  // 1. 运行期逐层包装：每层都是普通对象，套的顺序由调用方决定。
  final plain = DarkRoast();
  final mochaMilk = Milk(Mocha(plain));
  final milkMocha = Mocha(Milk(plain));

  assert(mochaMilk.priceInCents == 1750);
  assert(milkMocha.priceInCents == 1750); // 加法可交换
  assert(plain.priceInCents == 1200); // 被装饰对象本身不被修改
  print('${mochaMilk.name} = ${mochaMilk.priceInCents / 100} 元');

  // 2. 折扣是乘法：先打折再加料与先加料再打折结果不同。
  final discountFirst = Discount(Mocha(plain), 20);
  final mochaFirst = Mocha(Discount(plain, 20));
  assert(discountFirst.priceInCents == 1200);
  assert(mochaFirst.priceInCents == 1260);

  // 3. 同一份基础对象能派生出不同组合，彼此隔离。
  assert(Milk(plain).priceInCents == 1450 && Mocha(plain).priceInCents == 1500);

  // 4. mixin 把“加牛奶”固化进类型；函数版本把“加摩卡”变成高阶函数。
  assert(DarkRoastWithMilk().priceInCents == 1450);
  final doubleMocha = addMocha(addMocha(() => 1200));
  assert(doubleMocha() == 1800);
}
```

要点：

- 装饰者不修改被装饰对象，而是返回一个持有它的新对象。`plain` 在三种包装方式下始终是 1200 分，证明组合是隔离的。
- **包装顺序只在装饰操作不满足交换律时才重要。** 加料是确定数值的加法，`Milk(Mocha(x))` 与 `Mocha(Milk(x))` 相同；折扣对“当前总价”做乘法，所以先折扣后加料（1200 分）与先加料后折扣（1260 分）不同。面试里问“顺序为什么重要”，要能指出这个前提。
- **包装顺序只在装饰操作不满足交换律时才重要。** 加料是确定数值的加法，`Milk(Mocha(x))` 与 `Mocha(Milk(x))` 相同；折扣对“当前总价”做乘法，所以先折扣后加料（1200 分）与先加料后折扣（1260 分）不同。`Discount` 还在构造时拒绝小于 0% 或大于 100% 的输入，避免装饰器制造负价或反向加价。面试里问“顺序为什么重要”，要能指出这个前提。
- mixin 是编译期叠加：`DarkRoastWithMilk` 的类型在写代码时确定，运行期无法拆掉这层“牛奶”。适合“这个类型本来就应该具备的能力”；需要按场景拼装时用装饰者。
- 单方法行为可以用高阶函数装饰（`addMocha`），这与命令、策略里“函数优先”的判断一致：不必为只有一个方法的职责建类。
- Dart 的 `@annotation` 元数据（如 `@Deprecated`、`@override`）不是 GoF 装饰器：它只是附加信息，不会改变对象行为，也不会包装调用。
- 每个装饰者都要保持 Component 的完整契约，包括错误语义。如果内层对象可能抛出特定异常，外层不应把它变成一个看起来成功的结果。

## 适用条件与代价

- 适用：需要按运行期组合叠加职责；扩展点明确且会持续增加；不想为每种组合生成子类；希望复用同一份基础对象派生出多个变体。
- 代价：会产生大量小对象，包装层数一多，调试和定位真实实现都更费劲；依赖运行期类型判断拆解包装非常脆弱；某些框架序列化、比较身份或克隆对象时，可能不认识被包装后的类型；协议越宽，每个装饰者要维护的转发成员越多。

## Dart 标准库与生态映射

- Dart 标准库没有与装饰器对应的类型。`Stream.transform` / `StreamTransformer` 是“事件流水线包装”的相关机制：装饰器通常改变一次调用的返回值，`StreamTransformer` 处理的是事件流，语义并不等价。
- extension method 与 mixin 都能“看起来给类型加了能力”，但前者只影响静态调用语法，后者写进类型定义；两者都不具备装饰者“运行期可拆卸”的特性。

## 一句话总结

> 装饰器在运行期给对象叠加职责而不修改它；包装顺序只在职责不满足交换律（如折扣这种乘法）时才影响结果。
