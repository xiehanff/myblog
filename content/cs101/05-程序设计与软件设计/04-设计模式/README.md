# 设计模式

模式语言的价值不在“背下来 25 个类图”。它是团队对反复出现的设计约束的命名：说“这里用观察者”，同事能立刻理解通知方向、订阅生命周期与代价；没有这套词汇，同样的讨论要重复画一遍图。真正要判断的是——这个约束是否真的出现、封装的代价是否值得、Dart 是否已经提供了更轻的替代。

本目录共 25 篇：GoF《设计模式》的 23 个模式，加上不属于 GoF 23 但常被一并讨论的[简单工厂](./02-简单工厂.md)与[空对象](./25-空对象.md)。每篇保留“意图 → 结构 → 实现 → 适用条件与代价 → Dart 标准库与生态映射 → 面试追问”的固定骨架；实现全部为可运行的纯 Dart，原 Java 代码已按语义重写，不复述 Java 生态。

## 为什么需要模式语言

模式描述的是**对象之间如何协作以应对某类变化**，而不是可以复制粘贴的代码模板。同一个模式在不同语言、不同规模下的实现长度可以差一个数量级，但“谁持有谁、谁调用谁、变化被关在哪里”不变。

判断是否掌握一个模式，不看能否默写类图，而看能否回答：它封装哪个变化轴；参与者各自承担什么职责；不用它的最简替代是什么；引入间接层、生命周期与并发之后代价是什么；什么时候不该用它。只会背名字，恰恰是过度设计的开始——先问“变化出现了吗”，再决定要不要上模式。

> **关键认知：** 模式是对约束与代价的命名，不是“更专业”的证明；为不存在的未来变化引入抽象，是比重复代码更贵的债务。

## 模式、原则与架构的层级

这三类东西经常被放在一起背，但它们不在同一层：

| 层级 | 回答的问题 | 本载体的入口 |
| --- | --- | --- |
| 设计原则 | 边界与依赖方向该按什么准则划（SOLID、DRY/KISS/YAGNI） | [面向对象与设计原则](../01-面向对象与设计原则.md) |
| 对象协作模式 | 一组对象如何分工以应对某类变化（本目录 25 篇） | 下面三节分类导航 |
| 展示层架构模式 | 一次界面交互中，状态归谁、依赖指向哪边（MVC/MVVM/UDF） | [MVC、MVVM 与单向数据流](../03-MVC、MVVM与单向数据流.md) |

原则是判断准则，模式是可复用的协作结构，架构决定整条依赖方向与分层。它们可以组合使用，但不能互相替代：SOLID 讲的是怎么划边界，观察者讲的是通知如何解耦，MVVM 讲的是展示层的角色与引用方向。

> **关键认知：** 模式解决的是“局部协作如何设计”，架构模式解决的是“整体状态与依赖指向哪边”；把 MVVM 当成“更大的观察者模式”会同时误解两者。

## 创建型模式

创建型模式控制“对象怎么被产生”，分别封住实例数量、具体类型、产品族、构建步骤、复制来源这几类变化。

| 篇目 | 封住的变化 | 一句话导引 |
| --- | --- | --- |
| [01-单例](./01-单例.md) | 实例数量 | 在一个 isolate 内表达唯一实例与访问点，并说明全局可访问点的代价。 |
| [02-简单工厂](./02-简单工厂.md) | 具体类型 | 用一个入口按参数决定创建哪个产品；它不属于 GoF 23。 |
| [03-工厂方法](./03-工厂方法.md) | 具体类型 | 定义创建接口，把实例化推迟到子类或实现类。 |
| [04-抽象工厂](./04-抽象工厂.md) | 产品族 | 创建相互配套的一组对象，而不向调用方暴露具体类。 |
| [05-生成器](./05-生成器.md) | 构建步骤 | 把复杂对象的构造拆成步骤，最后统一校验并冻结。 |
| [06-原型模式](./06-原型模式.md) | 复制来源 | 以原型为样板复制新对象，复制深度与资源语义显式声明。 |

## 结构型模式

结构型模式控制“对象如何被组合成更大的结构”，应对接口不兼容、两个维度独立变化、树形整体与部分、运行时叠加职责、访问控制与共享等问题。

| 篇目 | 封住的变化 | 一句话导引 |
| --- | --- | --- |
| [07-适配器](./07-适配器.md) | 接口不兼容 | 把已有接口转换成调用方期望的协议，不改动原实现。 |
| [08-桥接](./08-桥接.md) | 两维独立变化 | 让抽象与实现沿两个方向各自演化，避免维度相乘的类爆炸。 |
| [09-组合](./09-组合.md) | 整体—部分 | 用树形结构统一处理单个对象与组合对象。 |
| [10-装饰](./10-装饰.md) | 运行时加职责 | 用包装器逐层叠加行为，不修改原类、不为组合建子类。 |
| [11-外观](./11-外观.md) | 子系统入口过多 | 为一组子系统接口提供一致的高层入口。 |
| [12-享元](./12-享元.md) | 共享内部状态 | 拆分可共享状态与外部状态，支撑大量细粒度对象。 |
| [13-代理](./13-代理.md) | 访问控制 | 在调用者与目标之间加一层，控制、延迟或记录访问。 |

## 行为型模式

行为型模式控制“职责与通信如何在对象间分配”，覆盖请求的传递与对象化、遍历、状态驱动、算法替换、快照与空值替代等场景。

| 篇目 | 封住的变化 | 一句话导引 |
| --- | --- | --- |
| [14-责任链](./14-责任链.md) | 请求的处理者 | 把候选处理者连成链，让请求沿链找到处理点。 |
| [15-命令](./15-命令.md) | 一次性动作 | 把请求变成对象，以支持排队、记录与撤销。 |
| [16-解释器](./16-解释器.md) | 小语言的求值 | 用对象表示文法规则，并递归求值表达式。 |
| [17-迭代器](./17-迭代器.md) | 遍历方式 | 顺序访问聚合元素而不暴露内部表示。 |
| [18-中介者](./18-中介者.md) | 多对象交互 | 把网状引用收敛到一个协调者，降低耦合。 |
| [19-备忘录](./19-备忘录.md) | 状态快照 | 在封装边界之外保存与恢复内部状态。 |
| [20-观察者](./20-观察者.md) | 一对多通知 | 状态变化时通知订阅者，并管理订阅生命周期。 |
| [21-状态](./21-状态.md) | 状态驱动的行为 | 把每个状态的行为与合法转移装进独立对象。 |
| [22-策略](./22-策略.md) | 可替换算法 | 把算法变成可注入、可替换的值，客户端只依赖协议。 |
| [23-模板方法](./23-模板方法.md) | 算法骨架 | 固定流程骨架，把可变步骤留给子类实现。 |
| [24-访问者](./24-访问者.md) | 操作与元素分离 | 元素结构稳定时，把新增操作外置为访问者。 |
| [25-空对象](./25-空对象.md) | 空值分支 | 用无操作对象替代 `null`；它同样不属于 GoF 23。 |

## 按问题而非名称选择

记不住名字时从问题入口反查；按变化点定位比按模式名定位更不容易选错。

- **只想控制实例数量或提供访问点** → [单例](./01-单例.md)；只想把创建集中到一个入口 → [简单工厂](./02-简单工厂.md)。
- **创建逻辑会随产品类型扩展** → [工厂方法](./03-工厂方法.md)；产品要成套配套扩展 → [抽象工厂](./04-抽象工厂.md)。
- **构造步骤多、需要校验或不可变成品** → [生成器](./05-生成器.md)；从已有样板复制更便宜 → [原型模式](./06-原型模式.md)。
- **接口对不上但不能改对方代码** → [适配器](./07-适配器.md)；抽象与实现沿两个方向各自变化 → [桥接](./08-桥接.md)。
- **整体与部分要统一处理** → [组合](./09-组合.md)；想在不修改原类的前提下叠加职责 → [装饰](./10-装饰.md)。
- **子系统接口太多、想给调用方一个稳定入口** → [外观](./11-外观.md)；对象数量大且可共享内部状态 → [享元](./12-享元.md)；需要控制、延迟或记录访问 → [代理](./13-代理.md)。
- **请求可能由多个候选处理** → [责任链](./14-责任链.md)；请求要排队、记录或撤销 → [命令](./15-命令.md)；需要解释一个小语言 → [解释器](./16-解释器.md)。
- **想在隐藏内部结构的前提下遍历** → [迭代器](./17-迭代器.md)；多对象交互成网状 → [中介者](./18-中介者.md)；需要保存与恢复快照 → [备忘录](./19-备忘录.md)。
- **一处变化要通知多方** → [观察者](./20-观察者.md)；行为几乎完全由当前状态决定 → [状态](./21-状态.md)；算法需要可替换 → [策略](./22-策略.md)。
- **流程骨架固定、个别步骤可变** → [模板方法](./23-模板方法.md)；元素结构稳定、操作却不断新增 → [访问者](./24-访问者.md)；想消除调用方的 `null` 分支 → [空对象](./25-空对象.md)。

## Dart 会让哪些模式变轻

语言能力能省掉样板，但不能替你判断变化轴。下面这些替代只影响实现的长度，不影响“是否引入模式”的决策；各篇的“Dart 标准库与生态映射”小节给出边界。

| Dart 特性 | 让哪些模式变轻 | 仍然存在的设计问题 |
| --- | --- | --- |
| 顶层与 `static` 变量的惰性初始化、`factory` 构造器 | [单例](./01-单例.md)、[简单工厂](./02-简单工厂.md) | 实例唯一性、初始化时序与全局依赖；不需要再用多种懒汉写法模拟。 |
| 函数类型与闭包 | [策略](./22-策略.md)、[命令](./15-命令.md)、[简单工厂](./02-简单工厂.md) | 需要身份、生命周期、撤销或依赖注入时，“只有一个方法的类”仍比裸函数合适。 |
| `Iterable`、`Iterator`、`sync*` | [迭代器](./17-迭代器.md) | 惰性求值、单次遍历、关闭与错误传播的语义仍要显式说明。 |
| `sealed` 类、模式匹配与穷尽 `switch` | [状态](./21-状态.md)、[访问者](./24-访问者.md)、[解释器](./16-解释器.md) | 状态少且封闭时比状态类更轻；转移复杂、状态多时对象化仍更清晰。 |
| 空安全（`?`、`?.`、`??`） | [空对象](./25-空对象.md) | 字段级可空大多可直接表达；需要“无操作对象”参与多态调用时模式仍有用。 |
| 扩展方法与扩展类型 | [装饰](./10-装饰.md)、[适配器](./07-适配器.md) | 扩展不能持有状态、不能覆盖实例成员，涉及状态或多态分派仍要包装对象。 |

> **关键认知：** 语言特性替代的是样板代码，不是设计判断；“Dart 有 `factory` 构造函数”不等于工厂相关问题消失。

## 阅读每篇的固定问题

每篇正文都按同一骨架组织（意图、结构、实现、适用条件与代价、Dart 标准库与生态映射、面试追问），阅读时用同一组问题检查自己：

1. 它封装的变化轴是什么，变化出现在哪里？
2. 参与者各自的职责与协作方式是什么，依赖指向哪边？
3. 最简替代方案是什么，为什么不够用（或其实够用）？
4. 代价是什么：间接层、生命周期、内存共享、并发与测试成本。
5. Dart 标准库或语言特性是否已有更轻的等价物？
6. 当前需求真的需要它吗，移除抽象会失去什么？

模式之外，命名、注释与函数边界同样决定修改成本，见[代码可读性与风格](../../07-工程工具与代码质量/04-代码可读性与风格.md)。
