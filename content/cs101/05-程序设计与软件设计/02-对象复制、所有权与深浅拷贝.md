# 程序设计与软件设计｜02-对象复制、所有权与深浅拷贝

一个编辑器页面同时需要三份"用户资料"：屏幕上正在编辑的草稿、撤销功能要恢复的原始版本、以及交给后台执行单元做校验的数据。直觉是"多存一份就安全了"，但 Dart 里写下的 `final backup = source;` 并没有多出一份数据——两个变量指向同一个对象，编辑草稿会把"原始版本"一起改掉。这种现象叫别名（aliasing），它的根源不是某个 API 用错了，而是我们还没回答"这份状态是否必须独立"。

本文先建立对象图、别名与所有权的心智模型，再看 Dart 中哪些写法只是浅拷贝；然后给出领域深拷贝、JSON 往返、不可变集合与 isolate 消息传递各自的适用边界，最后用跨语言对照解释为什么 Rust、Swift、Python 对同一件事给出不同的默认值。代码以纯 Dart 为主，不依赖 Flutter；C、Rust、Python、JavaScript、Swift 片段只用于展示语言语义本身。

## 为什么多一个变量不等于多一份数据

回到编辑器场景。`Profile` 持有可变的名字和标签列表，编辑功能拿到草稿后直接改名：

```dart
final source = Profile(name: 'Ada', tags: <String>['math']);
final alias = source;
alias.name = 'Grace';
assert(source.name == 'Grace');
```

赋值语句 `alias = source` 只让两个名字找到同一个对象，没有创建第二份资料。撤销功能如果保存的是 `alias`，它保存的其实还是正在被编辑的那个对象。真正需要复制时，先回答四个问题：

1. 哪些状态必须彼此独立；
2. 哪些状态可以安全共享；
3. 哪些资源应该转移所有权；
4. 为了这份独立性，需要付出多少时间和内存成本。

> **关键认知：** 赋值通常只复制"找到对象的信息"（引用、指针或句柄），不重建对象图；副本是否独立，取决于哪些节点和边被真正重建。

## 对象图、别名、可变性与所有权

### 变量不一定直接保存对象

C 语言把两种模型分得很开：`int count = 10; int b = count;` 复制的是整数本身；而 `int *first = &value; int *second = first;` 复制的是地址，`*second = 20` 会同时改变 `first` 看到的值。Dart 没有指针语法，但模型相近：`int`、`double`、`bool`、`String` 等不可变标量赋值后无法再被另一个变量"隔着引用"改掉，类实例变量保存的则是对象引用，赋值只产生别名。

判断两个变量是不是同一份数据，用 `identical(a, b)` 比 `a == b` 更直接：后者可以被类型重写为内容相等，前者比较的是对象身份。

### 一个对象其实是一张对象图

对象通过字段指向其他对象。把对象看成节点、引用看成边，就得到一张对象图：

```text
source ──user──▶ User
   │
   └──tags────▶ List ──▶ String（元素）
```

如果两个字段指向同一个子对象，图中就出现共享节点：

```text
source ──left───┐
                ├──▶ SharedData
source ──right──┘
```

复制对象时要回答的不是"字段从左边搬到右边"，而是"哪些节点和边要重新构造，哪些可以继续共享"。同一张图里，共享关系本身可能是有意义的（两条边本来就该指向同一个对象），深拷贝有责任保留它——这是后文 memo 算法要解决的问题。

### 所有权与可变性决定共享是否安全

理解复制时可以同时问两个问题：

| 问题 | 关注点 |
| --- | --- |
| 谁拥有这个对象或资源 | 谁负责释放、关闭、销毁；对象能活多久 |
| 这个对象能不能改变 | 共享后一处修改是否会被其他使用者观察到 |

Dart 由垃圾回收管理内存，因此"谁释放"的问题通常不落在业务代码上；但文件、Socket、数据库连接、缓存、锁这类资源仍需要明确的生命周期约定。栈、堆与自动存储期的机制见[虚拟内存、地址空间与函数调用](../03-操作系统与程序运行/04-虚拟内存、地址空间与函数调用.md#堆与动态分配解决生命周期问题)。

一个不可变对象即使被许多变量共享，通常也不会产生修改冲突；一个可变对象一旦被多个模块共享，就必须约定修改权限或增加同步机制。这也解释了"复制"和"所有权转移"为什么不能混为一谈：复制可能产生两个拥有者，转移则只改变唯一的拥有者。

> **关键认知：** 深拷贝不是"把世界复制一遍"，而是按类型规则重建对象图中必须独立的那部分；复制深度是语义问题，不是 API 参数。

> **关键认知：** 共享是否安全由可变性决定——不可变对象可以放心共享，可变对象共享时必须约定谁能改、何时改。

## Dart 的赋值与浅拷贝

**浅拷贝（shallow copy）**会新建最外层对象并复制这一层的字段；如果字段保存的是嵌套对象的引用，那么引用本身被复制，嵌套对象仍然共享。下面这段完整程序把四种常见浅拷贝放在一起验证：

```dart
// 前置条件：Dart 3.12；纯 Dart；无第三方依赖。
// 演示：赋值只复制引用；List.from/List.of/展开语法只换外壳，嵌套对象仍共享。
// 运行：dart run --enable-asserts OBJCOPY/shallow_copy.dart

/// 用户资料：tags 是可变的内层列表。
final class Profile {
  Profile({required this.name, required List<String> tags})
    : tags = List<String>.of(tags);

  Profile._(this.name, this.tags);

  String name;
  final List<String> tags;

  /// 只换外壳的浅拷贝：tags 直接复用同一个列表。
  Profile shallowWithName(String name) => Profile._(name, tags);
}

void main() {
  final source = Profile(name: 'Ada', tags: <String>['math']);

  // 1. 赋值只复制“找到对象”的引用，source 与 alias 是同一个对象。
  final alias = source;
  alias.name = 'Grace';
  assert(source.name == 'Grace');
  assert(identical(source, alias));

  // 2. 显式新建对象，但内部的 tags 仍指向同一个列表。
  final shallow = source.shallowWithName('Grace');
  shallow.tags.add('computing');
  assert(source.tags.length == 2);
  assert(identical(shallow.tags, source.tags));

  // 3. List.from / List.of / 展开语法都只复制当前这一层。
  final plain = <Object>[
    source,
    <String>['math'],
  ];
  final from = List<Object>.from(plain);
  final of = List<Object>.of(plain);
  final spread = <Object>[...plain];
  from.add('from');
  of.add('of');
  spread.add('spread');
  assert(plain.length == 2);
  assert(identical(from[0], source));
  assert(identical(of[0], source));
  assert(identical(spread[0], source));
  assert(identical(from[1], of[1]));

  // 4. Map 的复制同样只新建容器。
  final map = <String, Object>{'profile': source};
  final mapOf = Map<String, Object>.of(map);
  final mapSpread = <String, Object>{...map};
  assert(identical(mapOf['profile'], source));
  assert(identical(mapSpread['profile'], source));
  print('shallow_copy：别名与浅拷贝断言通过');
}
```

<!-- verify: .work/verify/OBJCOPY/shallow_copy.dart -->

要点：

- `List.from`、`List.of`、`[...source]`、`Map.of`、`{...source}` 都会返回新容器，`length` 与源对象互不影响，这是"新对象"的一面；
- 容器里的元素引用被原样复制，`identical(from[0], source)` 为真，这是"仍共享"的一面；
- `List.from` 与 `List.of` 的差别主要在类型处理：`List.from` 允许从 `Iterable` 向下转型（例如把 `List<dynamic>` 过滤成 `List<Map<String, dynamic>>`），`List.of` 要求元素本来就是目标类型；两者都不改变复制深度；
- `List.from` 默认 `growable: true`，需要定长列表时显式传 `growable: false`。

浅拷贝适合的场景：对象只有一层简单字段、嵌套对象不可变；只想覆盖最外层配置；明确希望多个对象共享某个只读缓存；或者浅拷贝后会手动替换需要独立的嵌套字段。它的优点是快、内存开销小，缺点是别名关系依然存在，不能当成"完全独立的副本"。

> **面试高频：** Dart 的 `List.from` 为什么不是深拷贝？
> **答题脉络：** 先明确浅拷贝的定义（新建最外层容器、复制元素引用）→ 用 `identical` 证明元素仍是同一对象 → 修改嵌套对象会互相可见 → 给出判据：看内层可变对象有没有被重建。
> **追问方向：** `List.from` 与 `List.of` 的差别、`growable` 参数、`List.from` 向下转型的用途、`copyWith` 是否深拷贝。

## 为领域对象定义真正的复制语义

Dart 没有 Java 的 `Cloneable`/`Object.clone()`，不存在对所有对象生效的统一克隆入口。复制语义必须由领域类型显式提供，常见命名是拷贝构造器、`copyWith` 或 `clone`——名字本身就是成本提示：`copyWith` 通常意味着"便宜地换几个字段"，`clone`/`deepCopy` 才暗示可能重建整张对象图。由原型对象自己定义复制深度、并把"改一份样板"作为创建手段的做法，就是[原型模式](./04-设计模式/06-原型模式.md)的动机。

先看 `copyWith` 的默认行为，以及领域深复制和它的差别：

```dart
// 前置条件：Dart 3.12；纯 Dart；无第三方依赖。
// 演示：copyWith 默认只换字段；要独立的内层状态必须由领域代码显式重建。
// 运行：dart run --enable-asserts OBJCOPY/copy_with.dart

final class UserSettings {
  const UserSettings({required this.theme, required this.notify});

  final String theme;
  final bool notify;

  // 1. copyWith 返回新对象，但字段按原样复制：不可变标量不会被“改回去”。
  UserSettings copyWith({String? theme, bool? notify}) =>
      UserSettings(theme: theme ?? this.theme, notify: notify ?? this.notify);
}

final class Draft {
  Draft({required this.title, required List<String> paragraphs})
    : paragraphs = List<String>.of(paragraphs);

  Draft._(this.title, this.paragraphs);

  final String title;
  final List<String> paragraphs;

  // 2. 只换外壳：新 Draft 与旧对象共享同一个 paragraphs 列表。
  Draft shallowCopyWith({String? title}) =>
      Draft._(title ?? this.title, paragraphs);

  // 3. 领域深复制：重建内层列表；元素 String 本身不可变，所以一层就够。
  Draft deepCopyWith({String? title}) =>
      Draft(title: title ?? this.title, paragraphs: paragraphs);
}

void main() {
  const settings = UserSettings(theme: 'light', notify: true);
  final changed = settings.copyWith(theme: 'dark');
  assert(changed.theme == 'dark');
  assert(settings.theme == 'light');
  assert(changed.notify == settings.notify);

  final draft = Draft(title: 'v1', paragraphs: <String>['intro']);
  final shallow = draft.shallowCopyWith(title: 'v2');
  shallow.paragraphs.add('note');
  assert(draft.paragraphs.length == 2);
  assert(identical(shallow.paragraphs, draft.paragraphs));

  final deep = draft.deepCopyWith(title: 'v3');
  deep.paragraphs.add('own note');
  assert(draft.paragraphs.length == 2);
  assert(identical(deep.paragraphs, draft.paragraphs) == false);
  print('copy_with：copyWith 的浅深差异断言通过');
}
```

<!-- verify: .work/verify/OBJCOPY/copy_with.dart -->

`UserSettings` 的 `copyWith` 看起来"复制得很安全"，只是因为它全部由不可变标量组成；`Draft.shallowCopyWith` 一旦带上可变集合，浅拷贝就暴露了。设计复制语义时至少写清三件事：

1. **哪些字段直接共享**——不可变标量、只读缓存、共享节点；
2. **哪些字段必须重建**——可变集合、可变子对象；
3. **命名能否表达成本**——`shallowCopyWith` 与 `deepCopyWith` 比两个都叫 `copy` 更不容易误用。

构造器里的防御性复制是另一条边界：`Draft` 在构造时用 `List<String>.of` 重建 `paragraphs`，这样调用方后续修改自己手里的列表不会影响 `Draft` 内部状态。防御性复制与复制方法解决的是不同方向的问题——前者防止外部改内部，后者防止副本改原对象。

> **关键认知：** 复制深度由类型定义，不由方法名承诺；`copyWith`、代码生成的复制方法默认都只复制一层，需要独立的嵌套状态必须显式重建。

> **面试高频：** `copyWith` 为什么常常是浅拷贝？复制语义应该由谁定义？
> **答题脉络：** `copyWith` 的定位是"基于旧值改几个字段"→ 字段按引用/值直接复制 → 嵌套可变对象因此共享 → 深复制要么逐层重建、要么改用不可变模型；复制语义属于领域类型，不属于语言或工具生成的样板。
> **追问方向：** 构造器防御性复制、`identical` 与 `==` 的区别、共享节点与环需要 memo、freezed 等代码生成器是否自动深拷贝。

## JSON 往返：可用的技巧，不是通用深拷贝

在无环、形状受限的数据模型上，序列化往返是能用的复制技巧：`jsonEncode` 写出一段文本，`jsonDecode` 解析出全新的结构，文本天然隔离了源对象。

```dart
// 前置条件：Dart 3.12；纯 Dart；无第三方依赖。
// 演示：JSON 文本往返只适合无环的 JSON-shaped 数据，并展示失败边界。
// 运行：dart run --enable-asserts OBJCOPY/json_roundtrip.dart
import 'dart:convert';

Map<String, Object?> deepCopyViaJson(Map<String, Object?> source) =>
    jsonDecode(jsonEncode(source)) as Map<String, Object?>;

void main() {
  final source = <String, Object?>{
    'title': 'v1',
    'tags': <String>['math', 'computing'],
    'meta': <String, Object?>{'revision': 3},
  };

  // 1. 成功路径：副本与源在每一层都独立。
  final clone = deepCopyViaJson(source);
  (clone['tags']! as List<Object?>).add('draft');
  (clone['meta']! as Map<String, Object?>)['revision'] = 4;
  assert((source['tags']! as List<String>).length == 2);
  assert((source['meta']! as Map<String, Object?>)['revision'] == 3);

  // 2. 失败边界：只有能映射成 JSON 的值才能往返。
  final failures = <String, Object>{
    'DateTime': DateTime(2020, 1, 1),
    'Set': <int>{1, 2},
    '非字符串键的 Map': <int, String>{1: 'a'},
    'NaN': double.nan,
    '普通对象': Object(),
  };
  failures.forEach((String label, Object value) {
    try {
      jsonEncode(<String, Object>{'v': value});
      assert(false, '$label 不应编码成功');
    } on JsonUnsupportedObjectError {
      // 预期：抛 JsonUnsupportedObjectError。
    }
  });

  // 3. 循环引用抛 JsonCyclicError。
  final cyclic = <String, Object?>{'name': 'root'};
  cyclic['self'] = cyclic;
  try {
    jsonEncode(cyclic);
    assert(false, '循环引用不应编码成功');
  } on JsonCyclicError {
    // 预期。
  }
  print('json_roundtrip：往返与失败边界断言通过');
}
```

<!-- verify: .work/verify/OBJCOPY/json_roundtrip.dart -->

它只处理"JSON 能表达的世界"，边界必须逐条确认：

- **循环引用直接失败**：`jsonEncode` 抛 `JsonCyclicError`；
- **非 JSON 值不能编码**：`DateTime`、`Set`、非字符串键的 `Map`、`NaN`/`Infinity`、普通类实例都会抛 `JsonUnsupportedObjectError`；`DateTime` 要自定义 `toJson` 转 ISO-8601 字符串，`Set` 要先转 `List`；
- **类型信息丢失**：`jsonDecode` 返回 `List<dynamic>` 与 `Map<String, dynamic>`，元素运行时类型退化，取值往往需要再校验或转换成领域类型；
- **身份与共享关系丢失**：同一子对象被两个字段引用，往返后会变成两份独立副本；这恰好说明 JSON 往返不承诺对象图语义；
- **数字语义要留边界**：Dart Native 的 `int` 支持任意精度（运行时会对小整数做优化），但 JSON 数字在跨语言消费方常按双精度理解；Web 端与 JavaScript 互操作时，超过 ±(2⁵³−1) 的整数不要依赖往返精度；
- **自定义 `toJson` 只复制它暴露的字段**：私有字段、缓存、不可序列化的状态都不会进入副本。

如果目标是与外部系统交换数据，JSON 往返是格式转换；如果目标是复制任意对象图，就应该使用领域 clone 或语言提供的结构化克隆能力。

> **关键认知：** JSON 往返是"序列化 + 解析"，只适合无环、JSON-shaped 的数据；它既不保留类型身份，也不保留对象图中的共享关系。

> **面试高频：** JSON 往返在什么前提下可以接受，为什么不能当通用深拷贝？
> **答题脉络：** 先给前提（无环、可编码类型、不需要保留原型与资源）→ 再列失败边界（环、`DateTime`、`Set`、非字符串键、普通对象、精度）→ 最后指出它只复制数据、不复制身份与共享结构。
> **追问方向：** `JsonCyclicError` 与 `JsonUnsupportedObjectError` 的区别、解码后 `dynamic` 的安全边界、跨语言数字精度、为什么共享节点会变成两份。

## 不可变对象与只读集合

如果对象创建后不再变化，多个使用者共享同一个对象通常和各自持有一份副本具有相同的观察结果，许多语言会直接复用而不是做昂贵的深拷贝。但要区分几种"看起来不可变"的工具：

- `final` 只禁止变量重新绑定，被引用对象仍可能可变，边界见[面向对象与设计原则](./01-面向对象与设计原则.md#不可变数据与纯函数)；
- `const` 要求编译期常量，`const` 字面量会在编译期规范化，内容相同的 `const` 列表共享同一个对象；
- `List.unmodifiable`/`Map.unmodifiable` 创建不可修改的副本（快照），源对象后续修改不影响它；
- `UnmodifiableListView` 是**视图**：只禁止通过它写入，源列表的修改仍会从视图观察到。

```dart
// 前置条件：Dart 3.12；纯 Dart；无第三方依赖。
// 演示：List.unmodifiable 是复制后的只读快照，UnmodifiableListView 是只读视图。
// 运行：dart run --enable-asserts OBJCOPY/unmodifiable.dart
import 'dart:collection';

void main() {
  final base = <int>[1, 2];
  final snapshot = List<int>.unmodifiable(base);
  final view = UnmodifiableListView<int>(base);

  // 1. 修改源列表：快照不受影响，视图立刻反映变化。
  base[0] = 99;
  base.add(3);
  assert(snapshot.length == 2 && snapshot[0] == 1);
  assert(view.length == 3 && view[0] == 99);

  // 2. 快照和视图本身都不能写。
  try {
    snapshot[0] = 5;
    assert(false, '不可修改列表不应允许写入');
  } on UnsupportedError {
    // 预期。
  }

  // 3. Map.unmodifiable 与 Map.from 一样复制一份不可修改副本。
  final mapBase = <String, int>{'a': 1};
  final mapSnapshot = Map<String, int>.unmodifiable(mapBase);
  mapBase['a'] = 42;
  assert(mapSnapshot['a'] == 1);

  // 4. 冻结的是容器，不是元素；嵌在里面的可变对象仍然被共享。
  final nested = <List<String>>[
    <String>['math'],
  ];
  final frozen = List<List<String>>.unmodifiable(nested);
  nested[0].add('computing');
  assert(frozen[0].contains('computing'));

  // 5. const 列表在编译期规范化：内容相同的字面量共享同一个对象。
  const first = <int>[1, 2];
  const second = <int>[1, 2];
  assert(identical(first, second));
  print('unmodifiable：快照、视图与元素共享断言通过');
}
```

<!-- verify: .work/verify/OBJCOPY/unmodifiable.dart -->

最后一条断言常被忽略：`List.unmodifiable` 只冻结容器本身，元素如果是可变对象，仍然可以通过源列表改掉。要得到"深不可变"，需要让对象图里所有可达状态都不可变；Dart API 文档也提醒，"如果元素本身不可变，那么这个列表才不可变"。只读属性用 `final` 字段表达即可，不必为每个字段写 getter。

> **关键认知：** 不可修改包装保护的是"通过这个引用的写入"，不是对象图的只读性；视图与快照是两种不同的承诺——前者随源变化，后者与源分离。

> **面试高频：** `final`、`const`、`List.unmodifiable` 和"深不可变"有什么差别？
> **答题脉络：** `final` 约束变量绑定 → `const` 约束编译期常量并参与规范化 → `unmodifiable` 冻结容器但共享元素 → 深不可变要求整个对象图不可变；判据是"是否还存在能改变可观察状态的路径"。
> **追问方向：** `UnmodifiableListView` 与快照的差别、防御性复制放在构造器还是 getter、不可变对象缓存与享元模式的联系。

## 循环、共享节点和资源句柄

### 用 memo 处理环与共享节点

对象图可能存在环：对象通过若干条引用又指回自己。如果深拷贝算法每次遇到引用都无条件递归，就会无限递归；如果每次遇到同一节点都重新复制，共享关系（两条边指向同一个对象）就会在副本中被破坏成两份。

通用做法是维护一张"旧节点 → 新节点"的映射表（memo）：第一次遇到节点时先创建并登记副本，再处理它的子节点；之后再次遇到同一个旧节点，直接复用已登记的新节点。Dart 里 `HashMap.identity()` 提供按对象身份比较的映射，避免类型重写 `==` 后把"内容相等的不同节点"错误合并。

```dart
// 前置条件：Dart 3.12；纯 Dart；无第三方依赖。
// 演示：按 identity 记录已复制节点的 memo，让深拷贝同时处理共享节点和环。
// 运行：dart run --enable-asserts OBJCOPY/memo_clone.dart
import 'dart:collection';

final class Node {
  Node(this.label);

  final String label;
  final List<Node> children = <Node>[];

  /// 深拷贝：第一次遇到节点时创建并登记副本，之后复用。
  Node deepClone([Map<Node, Node>? memo]) {
    final copied = memo ?? HashMap<Node, Node>.identity();

    // 1. 已经复制过就复用，共享节点不会被复制成多份。
    final existing = copied[this];
    if (existing != null) return existing;

    // 2. 先登记再递归子节点，环上不会无限递归。
    final clone = Node(label);
    copied[this] = clone;
    for (final child in children) {
      clone.children.add(child.deepClone(copied));
    }
    return clone;
  }
}

void main() {
  final shared = Node('shared');
  final root = Node('root')..children.addAll(<Node>[shared, shared]);
  root.children.add(root); // 3. root 通过 children 指向自己，构成环。

  final clone = root.deepClone();
  assert(identical(clone, root) == false);
  assert(identical(clone.children[0], clone.children[1]));
  assert(identical(clone.children[2], clone));
  assert(identical(root.children[0], root.children[1]));
  print('memo_clone：共享节点与环断言通过');
}
```

Python 的 `copy.deepcopy` 也是同一套思想：官方文档把这张表叫 memo 字典，类可以通过 `__deepcopy__(self, memo)` 自定义复制行为，需要继续深拷贝成员时应把同一个 memo 传下去。

### 资源句柄不是普通字段

内存里的普通字段和操作系统资源不是一回事。文件、Socket、窗口、互斥锁、数据库连接、GPU 纹理等对象，往往只是一个语言对象包裹着外部资源句柄；复制包装对象并不会创建第二个资源。

```c
typedef struct {
    size_t length;
    int *items; /* 约定：这块数组由当前 IntArray 独占并负责释放 */
} IntArray;

bool int_array_clone(const IntArray *source, IntArray *target) {
    target->length = 0;
    target->items = NULL;

    /* 1. 空数组没有需要复制的堆内存。 */
    if (source->length == 0) {
        return true;
    }
    /* 2. 检查乘法溢出，避免申请空间不足后越界写入。 */
    if (source->length > SIZE_MAX / sizeof(*target->items)) {
        return false;
    }
    /* 3. 申请新内存，让 source 和 target 拥有不同的存储。 */
    int *items = malloc(source->length * sizeof(*items));
    if (items == NULL) {
        return false;
    }
    memcpy(items, source->items, source->length * sizeof(*items));
    target->items = items;
    target->length = source->length;
    return true;
}

void int_array_destroy(IntArray *array) {
    free(array->items);
    array->items = NULL; /* 二次销毁不会重复释放 */
    array->length = 0;
}
```

<!-- verify: .work/verify/OBJCOPY/c_resource_clone.c -->

片段取自 `c_resource_clone.c` 第 12–44 行；完整文件另含 `main` 中的断言：clone 后的 `items` 与源地址不同、修改副本不影响源、二次 `destroy` 安全。C 没有通用对象运行时，所以必须为具体类型手写 clone 与 destroy；如果结构体里还有字符串指针、子对象、文件句柄或互斥锁，就必须分别定义这些成员的复制规则——`memcpy` 只搬运字节，不会为指针指向的内存创建副本，更不会处理资源。

文件描述符是更直接的例子：

```c
struct {
    int fd;
} first = {3}, second;
second = first; /* 只复制整数 3，不会创建第二个文件资源 */
```

资源对象常见四种设计选择：

1. **禁止复制**：只有一个对象拥有资源，其他代码只能借用；
2. **共享所有权**：复制包装对象时增加引用计数，最后一个拥有者负责释放；
3. **显式复制资源**：调用平台或库提供的 duplicate/clone，真正获得新句柄；
4. **重新打开或重新创建**：根据路径或配置创建具有独立状态的新资源。

"复制文件描述符"也不一定等于"复制文件的全部状态"：某些系统的句柄复制会共享底层文件偏移或连接状态，所以资源复制必须由资源类型定义语义，不能套用普通对象的深拷贝规则。

> **关键认知：** 深拷贝递归必须带 memo，否则环会无限递归、共享节点会被复制成多份；真正的深度由类型的复制规则决定，而不是"递归到不能再递归"。

> **面试高频：** 为什么深拷贝需要基于身份的 memo？为什么资源句柄不能按普通对象复制？
> **答题脉络：** 环导致递归不终止 → 共享节点导致副本结构变形 → memo 先登记后递归同时解决两者；资源由外部系统管理生命周期 → 复制字节不等于复制资源 → 需要禁止复制、共享所有权、显式复制或重新创建。
> **追问方向：** `HashMap.identity()` 与普通 `Map` 的差别、`__deepcopy__` 的 memo 约定、文件句柄复制与引用计数的语义。

## 复制、移动与 isolate 消息

移动（move）或所有权转移不是复制：它通常不创建第二份资源，而是把原对象的使用权交给新变量，原变量不再能按拥有者身份使用。

| 操作 | 新建独立的可变数据吗 | 原对象还能正常使用吗 | 常见成本 |
| --- | --- | --- | --- |
| 浅拷贝 | 只新建当前层，子对象可能共享 | 可以 | 接近复制引用的成本 |
| 深拷贝 | 复制需要独立的嵌套状态 | 可以 | 与对象图大小相关 |
| 移动/转移 | 通常不复制底层数据 | 通常不能再以原所有者身份使用 | 通常很低，常接近 O(1) |

Dart 对普通对象没有语言层面的 move 语法，但 isolate 之间发送消息时，三种语义同时存在。每个 isolate 有自己的内存、全局字段和事件循环，任何状态都不会被其他 isolate 直接访问；同一代代码的 isolate 之间通过 `SendPort.send` 传递对象时，"被识别为不可变的对象（例如字符串）会被共享，其余对象会被复制"。如果发送方与接收方不共享代码（例如 `Isolate.spawnUri` 创建），可发送对象的种类会收窄到基本类型、字面量容器、`TransferableTypedData`、`SendPort`、`Capability` 等，普通类实例不再允许。资源对象（Socket、文件等）无论哪种情况都不可发送。

`Isolate.run` 的结果通过 `exit` 发回，官方文档说明"发送时不复制"；而闭包捕获的不可发送对象会让整个调用在运行时失败，这正是"哪些状态会被带过去"必须显式确认的原因。

需要把大块字节的所有权真正转移给另一个 isolate 时，用 `TransferableTypedData`：

```dart
// 前置条件：Dart 3.12；纯 Dart；无第三方依赖。
// 演示：isolate 之间不共享可变状态；TransferableTypedData 是一次性的所有权转移。
// 运行：dart run --enable-asserts OBJCOPY/isolate_message.dart
import 'dart:isolate';
import 'dart:typed_data';

Future<void> main() async {
  // 1. 可变对象进入另一个 isolate 时按对象图复制：子 isolate 的修改不回传。
  final source = <String>['math'];
  final received = await Isolate.run(() {
    source.add('computing');
    return source;
  });
  assert(source.length == 1);
  assert(received.length == 2);

  // 2. TransferableTypedData：发送近似常数时间，数据所有权随消息交给接收方。
  final port = ReceivePort();
  await Isolate.spawn((SendPort sender) {
    sender.send(
      TransferableTypedData.fromList(<TypedData>[
        Uint8List.fromList(<int>[1, 2, 3]),
      ]),
    );
  }, port.sendPort);
  final message = await port.first as TransferableTypedData;
  final bytes = message.materialize().asUint8List();
  assert(bytes.length == 3 && bytes[1] == 2);

  // 3. materialize 只能调用一次：转移是单向的。
  try {
    message.materialize();
    assert(false, '重复 materialize 不应成功');
  } on ArgumentError {
    // 预期。
  }
  port.close();
  print('isolate_message：复制与转移断言通过');
}
```

<!-- verify: .work/verify/OBJCOPY/isolate_message.dart -->

`TransferableTypedData` 的边界要写清楚：它由 `fromList` 创建时按字节数耗时（复制进一个可转移的容器），发送本身近似常数时间；转移后发送方不能再 `materialize`，接收方也只能取一次。它是一种受限的所有权转移，不是"所有对象都能零拷贝"的通用机制。并发与调度层面的 isolate/线程差别见[进程、线程与调度](../03-操作系统与程序运行/02-进程、线程与调度.md#进程拥有什么线程共享什么)。

> **关键认知：** isolate 之间不共享可变状态；消息传递里可变对象按图复制、被识别为不可变的对象可共享，`TransferableTypedData` 才是一次性的所有权转移。

> **面试高频：** isolate 发送对象与 `TransferableTypedData` 有什么不同？单例为什么只是 per-isolate？
> **答题脉络：** isolate 有独立内存和全局字段 → 普通消息复制或共享不可变对象 → 资源对象不可发送 → 转移只改变所有权、不产生第二份数据且只能取一次；每个 isolate 的全局字段属于它自己，所以"单例"天然是 per-isolate。
> **追问方向：** `Isolate.spawn` 与 `spawnUri` 的可发送类型差异、`Isolate.run` 闭包捕获的陷阱、为什么并发隔离不能替代资源生命周期管理。

## 写时复制与持久化数据结构

深拷贝的成本随对象图增大而上升，但很多修改只动一两个字段。写时复制（Copy-on-Write，COW）换了一个思路：先共享，写入时再分离。

```text
a = make_buffer("abc")
b = cow_copy(a)   // 1. a 和 b 暂时共享同一份只读存储
b[0] = 'A'        // 2. 写入前分配新存储，再让 b 修改自己的副本
a 仍然是 "abc"    // 3. 从使用者角度看，b 像是早已独立
```

COW 的好处是复制很快、读多写少时节省内存；代价是第一次写入会发生额外分配，引用计数和并发写入也需要正确同步。Swift 标准库把这种策略与值语义组合在一起：`struct` 赋值表现为独立副本，`Array`、`Dictionary` 等容器"在修改某一副本之前共享同一份存储"；但数组元素若是类实例，两份数组仍会观察到同一个对象的变化——值语义只保证容器层面的独立。类（`class`）则是引用类型，共享身份，文件句柄、网络连接这类对象在官方建议里就应当用类建模。

```swift
struct User {
    var name: String
    var tags: [String]
}

var first = User(name: "Ada", tags: ["math"])
var second = first

// 1. 结构体赋值获得独立副本：修改 second 不影响 first。
second.tags.append("computing")
assert(first.tags.count == 1)
assert(second.tags.count == 2)
```

片段取自 `swift_value_semantics.swift` 第 4–15 行；完整文件另含 `class` 引用语义的断言（同一实例改一处、另一处可见）。

Dart 标准库的 `List`、`Map` 是普通可变容器，没有内置的 COW 或持久化集合；需要"每次修改产出新版本、旧版本永远可用"时，可以用结构共享手写，或借助包实现。持久化数据结构的核心是：一次更新只重建从根到修改点的一条路径，其余节点直接复用。用持久化栈可以观察到这一点：

```dart
// 前置条件：Dart 3.12；纯 Dart；无第三方依赖。
// 演示：持久化栈的 push 返回新版本，旧版本仍可用，未改动节点被结构共享。
// 运行：dart run --enable-asserts OBJCOPY/persistent_stack.dart

final class StackNode<T> {
  const StackNode(this.value, this.next);

  final T value;
  final StackNode<T>? next;
}

final class PersistentStack<T> {
  const PersistentStack(this._head);

  const PersistentStack.empty() : _head = null;

  final StackNode<T>? _head;

  bool get isEmpty => _head == null;

  T get top {
    final head = _head;
    if (head == null) throw StateError('空栈没有栈顶');
    return head.value;
  }

  /// push 只新建一个节点，其余节点与旧版本共享。
  PersistentStack<T> push(T value) =>
      PersistentStack<T>(StackNode<T>(value, _head));

  PersistentStack<T> get tail {
    final head = _head;
    if (head == null) throw StateError('空栈没有 tail');
    return PersistentStack<T>(head.next);
  }
}

void main() {
  const empty = PersistentStack<int>.empty();
  final v1 = empty.push(1);
  final v2 = v1.push(2);
  final v3 = v2.push(3);

  // 1. 旧版本保持可用：v1 永远只有 [1]。
  assert(v1.top == 1 && v1.tail.isEmpty);
  assert(v3.top == 3 && v3.tail.top == 2);

  // 2. 结构共享：v2、v3 与更早版本的尾部是同一批节点，没有被复制。
  assert(identical(v2._head, v3.tail._head));
  assert(identical(v1._head, v2.tail._head));
  print('persistent_stack：版本独立与结构共享断言通过');
}
```

什么时候用不可变与持久化结构替代深拷贝？满足以下任一条就值得认真考虑：需要保留历史版本（撤销/重做、时间旅行调试，快照的封装见[备忘录模式](./04-设计模式/19-备忘录.md)）；需要廉价判等（引用相等即可断定内容相等）；多个读者并发共享同一份数据；对象很大而修改很稀疏。在展示层，ViewModel 向外发布的不可变快照正是单向数据流能成立的前提之一（见[MVC、MVVM 与单向数据流](./03-MVC、MVVM与单向数据流.md#mvvm-与单向数据流不是同义词)）。这些场景下，"每次修改产出新版本 + 结构共享"往往比"每次修改前深拷贝"更快也更省。

> **关键认知：** COW 的"逻辑独立"不代表底层从一开始就独立，也不自动意味着线程安全；持久化数据结构用结构共享替换全量复制，但要求所有版本都不可变。

## 跨语言对照为何值得保留

不同语言对复制的默认行为，反映的是它们对值语义、引用语义和所有权的不同选择：

| 语言 | 常见默认行为 | 常见复制/转移方式 | 需要特别注意 |
| --- | --- | --- | --- |
| Dart | 对象变量保存引用；赋值产生别名 | 拷贝构造器、`copyWith`、`clone`；`List.of` 等只复制一层 | 没有统一 `Object.clone`；`List.from`/`Map.of`/展开语法都不深拷贝 |
| C | 结构体赋值按成员复制；指针只复制地址 | 为具体类型手写 clone/destroy | 没有通用深拷贝；指针成员与资源的所有权必须写清楚 |
| C++ | 类可自定义拷贝与移动语义 | 拷贝/移动构造与赋值；`unique_ptr` 通常不可拷贝，`shared_ptr` 共享所有权 | 默认成员拷贝对裸指针通常只是浅拷贝 |
| JavaScript | 对象赋值共享引用；展开语法只浅拷贝 | `structuredClone` 处理支持的结构化数据；类型可提供专用复制方法 | 函数、DOM 节点、原型与资源对象有硬边界 |
| Python | 赋值只是绑定另一个名字 | `copy.copy`、`copy.deepcopy` 与 `__copy__`/`__deepcopy__` | 深拷贝可被类型自定义或拒绝；memo 影响环与共享关系 |
| Java | 对象赋值共享引用 | 拷贝构造器、静态工厂、领域专用复制方法 | `Object.clone()` 默认按字段赋值，是浅拷贝，语义容易含糊 |
| Swift | `struct` 等值类型赋值即独立副本；`class` 赋值复制引用 | 值语义自动获得；类实现 `NSCopying` 的 `copy(with:)` | 值语义常由 COW 实现；不可变对象的 `copy` 常返回自身 |
| Rust | 非 `Copy` 值默认移动；借用由类型系统约束 | `Copy`、显式 `Clone`、所有权移动 | `Arc::clone` 只增加引用计数，不是深拷贝；`Clone` 的深度由类型定义 |

### Rust：把复制语义写进类型系统

Rust 的所有权规则是：每个值有唯一所有者；同一时刻一个值只有一个所有者；所有者离开作用域，值被丢弃（执行 `Drop` 清理代码）。因此"两个变量都以为自己拥有同一块内存、各自释放一次"的 double free 无法构造。Rust 的赋值默认是**移动**，官方教材的原话大意是：只复制栈上的指针、长度、容量而不复制堆数据，"听起来像浅拷贝，但因为 Rust 同时使第一个变量失效，它不叫浅拷贝，而叫移动"。要真正的深拷贝必须显式 `clone`：

```rust
// 前置条件：Rust 1.97；无第三方 crate。
// 演示：赋值默认是 move，clone 才是显式深拷贝，Copy 类型按位复制。
// 编译运行：rustc rust_move_clone.rs -o rust_move_clone && ./rust_move_clone
fn main() {
    // 1. String 的数据在堆上，变量保存指针/长度/容量。
    let s1 = String::from("hello");

    // 2. 赋值复制栈上三元组并使 s1 失效——这一步叫移动（move），不是浅拷贝。
    let s2 = s1;

    // 3. 再使用 s1 是编译错误：error[E0382]: borrow of moved value: `s1`
    // println!("{s1}");

    // 4. 显式 clone 才会深拷贝堆数据，两个变量各自负责释放。
    let s3 = s2.clone();
    println!("s2={s2}, s3={s3}");

    // 5. 简单标量实现了 Copy：赋值按位复制，原变量仍然可用。
    let n1 = 10;
    let n2 = n1;
    println!("n1={n1}, n2={n2}");
}
```

<!-- verify: .work/verify/OBJCOPY/rust_move_clone.rs -->

Rust 对复制语义的贡献不是"更好的深拷贝 API"，而是让三种语义在代码里显式可见：移动（默认，原变量失效）、`clone`（显式，成本在调用点一眼可见）、借用（临时访问，不获得所有权）。其他语言靠注释和 code review 守住的边界，这里由编译器守。最后回收一个伏笔：每个类型的 `clone` 深度由它自己的 `Clone` 实现定义——`String::clone` 深拷贝堆数据，`Arc::clone` 只把引用计数加一、共享同一份数据。名字相同，语义由类型说了算。

### JavaScript：structuredClone 的数据边界

`structuredClone` 把 HTML 规范定义的结构化克隆算法直接暴露给开发者，它支持循环引用，并保留 `Date`、`Map`、`Set` 等内置类型；副本中的环指向副本自身。边界同样明确：函数、DOM 节点无法克隆，尝试克隆抛 `DataCloneError`；原型链不复制，类实例克隆后变成普通对象、方法丢失；属性描述符、getter/setter 与私有字段不复制；`Error` 的 `stack` 等属性规范措辞是"期望保留"，以实际运行环境为准。它还有 transfer 选项：可转移对象（如 `ArrayBuffer`）被"移动"而不是复制，转移后原对象不可再用。

```javascript
// 前置条件：Node.js 24（structuredClone 自 Node 17 起可用）。
// 演示：structuredClone 支持环和内置数据类型，但不复制代码与原型。
// 运行：node js_structured_clone.mjs
const node = { name: 'root' };
node.self = node;

const clone = structuredClone(node);
console.assert(clone !== node);
console.assert(clone.self === clone);

class Cart {
  total() {
    return 1;
  }
}
const cartCopy = structuredClone(new Cart());
console.assert(cartCopy instanceof Cart === false);
console.assert(cartCopy.total === undefined);

try {
  structuredClone({ callback: () => {} });
  console.assert(false, '函数必须被拒绝');
} catch (error) {
  console.assert(error.name === 'DataCloneError', error.name);
}
console.log('js_structured_clone：数据边界断言通过');
```

一句话记忆：`structuredClone` 克隆的是"数据"，不是"代码和资源"。Python 的 `copy.deepcopy` 与它同源——官方文档明确 deepcopy 用 memo 处理环，"递归地把副本插入到新对象中"；这也解释了为什么各语言的深拷贝实现总要额外回答"共享节点怎么办"：

```python
# 前置条件：Python 3.14；只用标准库。
# 演示：deepcopy 用 memo 处理循环引用，并保留共享节点关系。
# 运行：python python_deepcopy.py
import copy

node = {"name": "root"}
node["self"] = node

# 1. 循环引用：副本不是原对象，但副本的 self 指向副本自身。
cloned = copy.deepcopy(node)
assert cloned is not node
assert cloned["self"] is cloned

shared = []
source = {"left": shared, "right": shared}

# 2. 共享节点：deepcopy 整张图，两条边仍指向副本中的同一个对象。
clone = copy.deepcopy(source)
assert clone["left"] is clone["right"]
assert clone["left"] is not shared

print("python_deepcopy：memo 语义断言通过")
```

Java 侧的启示则相反：`Object.clone()` 的文档约定"副本应独立"，但默认实现按字段赋值、明确是"浅拷贝"，约定、默认行为与真正需要的语义三者容易错位，所以社区更推荐拷贝构造器或工厂方法。

> **关键认知：** 成熟的复制 API 通常不提供一个万能 `deepCopy`：便宜、隐式的复制用于简单值，昂贵的复制用显式 `clone` 或拷贝构造器；不能复制的资源由类型系统或运行时直接拒绝。

## 性能、并发与选择流程

设对象图有 V 个需要访问的节点和 E 条引用边，典型实现的大致成本如下：

| 策略 | 时间成本 | 额外内存 | 适合场景 |
| --- | --- | --- | --- |
| 引用共享 | 近似 O(1) | 很少 | 只读数据或明确共享的状态 |
| 浅拷贝 | 近似 O(当前层字段数) | 当前层大小 | 只需要隔离外层配置 |
| 深拷贝 | 通常 O(V + E) | 与副本图大小相关 | 需要完全独立的可变快照 |
| 移动/转移 | 通常 O(1) | 很少 | 独占资源交给下一个使用者 |
| COW | 初始接近 O(1)，写入时增加成本 | 按实际写入量增长 | 大对象、读多写少 |
| 持久化数据结构 | 更新近似 O(log n) | 只增加改动路径上的节点 | 需要历史版本或廉价判等 |

深拷贝还可能带来更高的瞬时内存峰值、缓存失效和垃圾回收压力。对一个包含大缓存的业务对象做深拷贝，通常不如只复制真正需要编辑的字段；对数据库连接做深拷贝，甚至可能根本没有合理语义。

并发方面有一个常见误判："深拷贝后各线程各用一份，就一定安全"。"线程安全"并不成立的原因有两层：复制过程本身必须看到一致的数据，源对象正在被修改时拷贝可能得到前后不一致的快照；副本里如果仍包含共享缓存、全局单例或资源句柄，共享状态依旧存在。更常见的并发设计包括：共享不可变对象，只在创建和发布时同步；使用消息传递，把数据的所有权移动给另一个执行单元；使用线程安全的共享对象、引用计数或锁；使用版本化快照或持久化数据结构。Dart 的 isolate 用"不共享可变状态"回避了大部分数据竞争，但跨 isolate 的资源协调、外部 I/O 的并发写入仍需显式设计。复制可以减少共享可变状态，但不能替代锁、原子操作、消息传递和生命周期管理。

选择复制策略时，先确认"隔离边界"而不是先追求"最深的复制"：

1. 只读且生命周期足够长：优先共享不可变对象；
2. 只改最外层：浅拷贝或结构化更新；
3. 需要修改嵌套状态且不能影响原对象：深拷贝，或为领域对象实现专用 clone；
4. 只需要把使用权交给下一个模块/执行单元：移动或转移；
5. 对象很大而写入很少：考虑 COW 或持久化数据结构；
6. 包含外部资源：先定义资源句柄的复制和释放规则，再决定是否复制包装对象。

> **关键认知：** 深拷贝减少别名，但不提供原子性、内存可见性或安全发布；它只是并发正确性的一块拼图，不是开关。

> **面试高频：** 深拷贝能自动保证线程安全吗？
> **答题脉络：** 先拆两个问题——复制过程是否看到一致快照、副本里是否还有共享状态 → 资源句柄、单例、缓存都不随复制消失 → 给出替代或补充手段（不可变共享、消息传递、锁与引用计数）→ 说明 isolate 只解决共享可变内存的一部分问题。
> **追问方向：** 快照的加锁时机、COW 的并发写入同步、引用计数的原子性、`Isolate` 与线程模型差别。

## 常见误区与设计检查清单

- 把赋值当复制：`b = a` 可能只复制引用；即使复制了结构体，也可能只复制了其中的指针。判据不是变量名，而是嵌套可变节点是否拥有不同身份。
- 把展开语法当深拷贝：`{...source}`、`List.of`、`Python` 的 `copy.copy` 都只隔离一层。看到"新对象"不代表对象图已经分离。
- 用序列化替代复制策略：JSON、二进制序列化适合跨进程、跨网络传输，但会改变类型、身份、原型和资源语义；除非数据模型明确受限，否则不能当万能复制。
- 对含指针的 C 结构体直接 `memcpy`：它只搬运字节，不会为指针指向的内存创建副本，也不会处理字符串、引用计数、文件句柄或失败清理。
- 认为深拷贝能自动解决线程安全：复制过程中可能发生竞争，副本中也可能保留共享资源。
- 把不可变和只读混为一谈：`final`、`const`、`Object.freeze`、不可修改视图的作用范围不同，必须检查整个对象图的可变性。
- 只关心值相等，不关心身份和所有权：深拷贝后的对象可以和原对象内容相同，但身份不同；资源句柄即使数值相同，也不代表可以独立关闭和操作。

设计一个类型的复制能力时，依次回答：

1. 复制后哪些字段必须独立，哪些字段允许共享？
2. 字段里是否包含指针、引用、缓存、锁或外部资源？
3. 原对象和副本由谁负责释放？失败时能否安全清理半成品？
4. 对象图是否可能有循环引用或多个字段共享同一子对象？
5. 复制过程是否需要锁、版本号或不可变快照？
6. 复制成本是否可能超过重新计算或按需加载的成本？
7. API 名称能否让调用者看出它是复制、共享还是转移？命名与注释风格的边界见[代码可读性与风格](../07-工程工具与代码质量/04-代码可读性与风格.md)。

如果这些问题没有答案，先不要实现名为 `deepCopy` 的通用方法；应当先定义类型的所有权和可变性，再为具体场景提供 `clone`、`share`、`move` 或不可变视图等语义明确的操作。

## 一句话总结

> 复制策略的核心不是挑一个最深的 API，而是由类型明确回答"哪些状态必须独立、哪些可以共享、资源由谁释放"，再据此在浅拷贝、领域深拷贝、不可变共享、写时复制与所有权转移之间做出选择。
