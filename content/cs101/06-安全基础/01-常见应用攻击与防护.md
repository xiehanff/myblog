# 安全基础｜01-常见应用攻击与防护

上线前做安全检查时，经常出现两种对立的失败：一种是照着清单加几个响应头，把 `X-Content-Type-Options` 和一条宽泛的 CSP 当成"安全做完了"；另一种是知道 XSS、CSRF、注入、DoS 这些名词，却说不清它们各自的成立条件，于是把"过滤输入"当成所有问题的通解。两类做法的共同问题是把攻击名当成了同一类东西。

实际上，这四个名字描述的是三种不同的越界：数据从"值"越界成"代码"（XSS、注入），凭证在用户不知情时被自动使用（CSRF），以及有限资源被耗尽（DoS）。越界位置不同，防护点就不同：输出编码管不了资源耗尽，限速管不了 SQL 注入，加一个 `HttpOnly` 也消化不掉 CSRF。

本文先建立一个最小的威胁模型，把"资产、信任边界、攻击者能力"这三件事摆清楚；再按三条越界线分别讲清成立条件、机制、失败边界与防护组合；最后回答客户端到底能承担什么，并给出一份可以直接对照的检查清单。

## 先建立威胁模型，不要先背攻击名

在讨论具体攻击之前，先回答一个问题：防护措施是在防谁、防哪一步。没有这一步，"加验证码""加 WAF""转义一下"都只是凭感觉叠加。

> **时效信息（核查日期：2026-09）：** OWASP Top 10 的当前发布版本是 **OWASP Top 10:2025**（第 8 版），其中注入类问题位于 A05:2025 "Injection"；上一版 2021 中它是 A03。类别编号会随版本调整，引用时必须带版本年份，不能只说"OWASP Top 10"。

CWE 的 [2025 Top 25 榜单](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html)把 XSS（CWE-79）、SQL 注入（CWE-89）、CSRF（CWE-352）列在前三位，`Allocation of Resources Without Limits or Throttling`（CWE-770）也在榜内。这说明它们不是历史名词，而是长期在野利用的弱点类别；这也意味着防护要落在弱点的机制上，而不是攻击的工具或名字上。

### 四个问题画出攻击面

一个够用的最小框架只需要四问：

1. **资产是什么**：用户数据、凭证、资金操作、服务可用性。资产价值决定投入多少防护成本。
2. **信任边界在哪里**：浏览器与服务器之间、公网与内网之间、应用与数据库之间、第三方内容与自家页面之间。数据跨过边界时，防御必须在它被解释的那一侧重新成立。
3. **输入从哪些入口进入，最终被什么解释器解释**：URL 参数、表单、请求头、上传文件是输入；HTML 渲染器、SQL 引擎、Shell、模板引擎是解释器。
4. **攻击者能控制什么、不能控制什么**：攻击者能构造任意请求、能控制自己的浏览器或脚本客户端；在没有目标源脚本执行权或服务端放行的情况下，通常不能读取跨源响应，也不能直接读取受害者浏览器保存的 Cookie。若站点把 Cookie 设为父域共享，受控的同站子域仍可能获得额外能力，不能把“同站”当成“同源”。

安全目标通常用机密性（Confidentiality）、完整性（Integrity）、可用性（Availability）三个维度描述，简称 CIA。XSS 可能同时影响机密性和完整性；CSRF 主要影响完整性；DoS 针对的是可用性。威胁建模没有唯一模板，[OWASP 的威胁建模备忘单](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html)、微软的 STRIDE 分类都可以作为起点，本文只保留与后面四类攻击直接相关的部分。

> **关键认知：** 防护点必须落在数据真正被解释的那一侧。客户端校验、界面提示只改变用户操作体验，不改变攻击者能否直接构造请求。

> **面试高频：** 认证和授权有什么区别，为什么"登录过"不等于"有权限"？
> **答题脉络：** 认证回答"你是谁"，授权回答"你能做什么"，两者由不同的检查在请求的不同阶段完成；钓鱼能骗过认证，越权则发生在授权缺失时。
> **追问方向：** 横向越权与纵向越权、CSRF 与越权的区别（前者是请求被伪造，后者是权限判断缺失）、权限校验为什么必须放在服务端资源入口。认证、授权与会话的完整关系见[身份认证一篇](../04-计算机网络/09-身份认证：Cookie、Session与JWT.md#认证授权与会话不是一回事)。

### 三类越界与本文地图

把攻击按"越界的对象"重新归类，防护组合就自然浮现：

- **数据越界成代码**：应用把不可信数据放进了一个有语法的位置，解释器把数据当成了指令。XSS 是 HTML/JavaScript 解释器中的这类问题，SQL 注入是数据库解释器中的这类问题，命令注入、模板注入同理。
- **凭证被自动使用**：浏览器自动携带的凭证让第三方页面可以"以用户名义"发请求，而服务端只看到凭证有效。CSRF 属于这一类；会话劫持、重放与凭证泄漏是它的近亲。
- **资源被耗尽**：攻击者用少量成本消耗连接、内存、CPU、带宽或下游依赖，使正常请求得不到服务。DoS 与 DDoS 属于这一类。

后面按这三条线展开：数据越界一条分成 XSS 与注入两节，其余各一节；每节先说清攻击成立的条件，再给防护组合，最后指出防护的失败边界。

## XSS：数据被当成代码执行

跨站脚本（Cross-Site Scripting，XSS）在常见场景下可概括为两项：不可信数据（也可能来自 URL、浏览器存储或客户端状态）到达了可执行的 HTML/JavaScript 上下文，并且应用没有使用匹配上下文的编码、安全汇点或白名单清洗。若脚本确实在目标源页面中执行，它通常会获得该页面脚本可用的同源能力，但 CSP、沙箱、Cookie 属性和页面本身的数据范围仍会限制实际影响。

最直观的存储型例子：论坛把用户评论原样拼接进页面，攻击者留下这样的评论。

```html
<!-- 服务端直接把用户提交的内容拼进了评论节点 -->
<p class="comment">最新评论：<script>alert('xss')</script></p>
```

浏览器解析这段 HTML 时，`<script>` 不是"文字内容"，而是一个标签：脚本块会执行。此后每个访问这条评论的用户都会执行它。攻击者能借这段脚本读取页面上的数据、以受害者身份发请求、修改页面内容或诱导输入；能读到什么取决于页面里有什么，以及 Cookie 是否加了 `HttpOnly` 等限制。

如果输入是被当次响应直接反射回来的（例如搜索关键词出现在"没有找到 xxx"里），就是反射型；用户访问或提交攻击者构造的内容就可能触发。两条路径都应在输出到最后一步时按上下文处理，但 DOM 型场景还要优先改用安全汇点，富文本场景则要使用专门的白名单清洗。

### 三种 XSS 的区别在哪里

| 类型 | 注入发生的位置 | 触发方式 | 影响范围 |
| --- | --- | --- | --- |
| 存储型（Stored） | 服务端存储后再读取时 | 访问包含恶意内容的页面 | 所有访问该内容的用户 |
| 反射型（Reflected） | 当次请求到响应的回显中 | 点击带参数的链接或提交表单 | 被诱导访问的用户（可能不止一人） |
| DOM 型（DOM-based） | 浏览器端脚本把输入写入危险汇点 | 页面脚本处理 `location` 等来源时 | 取决于脚本作用范围 |

> **关键认知：** 存储型、反射型、DOM 型的分类描述的是"注入发生在哪一段"，不是三种不同的技术；它们最终都可能在浏览器里产生脚本执行。服务端回显通常靠上下文编码，DOM 型应优先使用安全汇点，富文本则要靠经过审计的白名单清洗。分类的价值在于定位漏洞位于链路中的哪一段。

### 输出上下文决定编码方式

"过滤掉 `<` 和 `>`"为什么不够？因为同一个值可以进入完全不同的解析环境：HTML 文本、带引号的属性、URL、内联 JavaScript 字符串。每种环境的越界方式不同，用一种规则覆盖所有环境的尝试必然留下空隙。举例来说，把值放进属性时，攻击者可能不闭合标签，只用引号提前结束属性，再塞入事件属性；把值放进 `href` 时，`javascript:` 协议不需要任何尖括号。

正确做法是按输出位置选择编码方式。下面用纯 Dart 实现三个最小的教学示例；生产代码应优先使用框架的自动转义和成熟的 URL/HTML 清洗库，不应把这个示例当作完整的 HTML 安全库。

```dart
// 前置条件：Dart 3.x；纯 Dart；无第三方依赖。
// 同一个不可信输入进入不同输出上下文时，需要不同形式的编码。

import 'dart:convert';

/// HTML 文本上下文：把会改变标签或属性结构的字符换成实体。
String escapeHtmlText(String value) {
  final buffer = StringBuffer();
  // 1. 逐个码点处理，避免码元遍历拆坏代理对。
  for (final rune in value.runes) {
    switch (rune) {
      case 0x26: // &
        buffer.write('&amp;');
      case 0x3C: // <
        buffer.write('&lt;');
      case 0x3E: // >
        buffer.write('&gt;');
      case 0x22: // "
        buffer.write('&quot;');
      case 0x27: // '
        buffer.write('&#x27;');
      default:
        buffer.writeCharCode(rune);
    }
  }
  return buffer.toString();
}

/// JavaScript 字符串上下文：返回一个可直接写进内联脚本的字符串字面量。
String toJsStringLiteral(String value) {
  // 1. JSON 的字符串语法是 JavaScript 字符串字面量的子集，可直接复用。
  // 2. 转义 <、>、& 与行分隔符，防止值里的 </script> 提前结束脚本块。
  return jsonEncode(value)
      .replaceAll('<', '\\u003c')
      .replaceAll('>', '\\u003e')
      .replaceAll('&', '\\u0026')
      .replaceAll('\u2028', '\\u2028')
      .replaceAll('\u2029', '\\u2029');
}

/// URL 上下文：先做协议白名单校验，再进入 HTML 属性。
String safeHref(String value) {
  // 1. 解析失败直接拒绝，不把原始文本写回页面。
  final uri = Uri.tryParse(value);
  if (uri == null) return '#';
  // 2. 只放行显式允许的协议，挡掉 javascript:、data: 一类可执行方案。
  const allowedSchemes = {'http', 'https', 'mailto'};
  if (!allowedSchemes.contains(uri.scheme)) return '#';
  // 3. http/https 必须有主机名，避免相对路径被当成外部地址。
  if (uri.scheme != 'mailto' && uri.host.isEmpty) return '#';
  // 4. 返回解析后的形式，再进入带引号的属性并做实体编码。
  //    这里的协议白名单不是目标主机白名单；如业务只允许自家链接，还要额外校验 host。
  return escapeHtmlText(uri.toString());
}
```

三类处理放在一起对比，能看清"上下文"三个字的含义：

```text
输入 <b>hi & "you"</b>
  HTML 文本   -> &lt;b&gt;hi &amp; &quot;you&quot;&lt;/b&gt;
  属性值      -> 引号被编码，无法闭合属性
  内联 JS     -> 整个值成为带引号的字面量，</script> 变成 \u003c/script\u003e
输入 "javascript:alert(1)" 作为 href
  URL 校验    -> 协议不在白名单，替换为 "#"
```

三条结论：

1. `escapeHtmlText` 处理 HTML 文本；进入带引号的属性时，它同样能挡住引号闭合，但前提是属性值必须始终加引号，绝不能拼接无引号属性。
2. 内联脚本里的值要先变成字符串字面量，再保证值中的 `</script>` 无法提前结束脚本块。把原始值直接写进 `<script>var x = ...</script>` 是常见事故点。
3. `href`、`src` 这类 URL 属性必须走协议白名单。HTML 实体编码不认识 URL 语法，`javascript:` 里没有需要转义的字符。

> **关键认知：** 输出编码取决于数据最终进入哪个语法位置，而不是取决于数据来自哪里、长什么样；同一个值在文本、属性、URL、脚本四种上下文中需要四种不同的处理。

> **面试高频：** XSS 有哪几种类型，防护为什么强调"上下文编码"？
> **答题脉络：** 先分清注入发生的三段位置 → 三种类型的共同点是在浏览器执行 → 防护回到输出上下文 → 黑名单过滤无法穷举不同解析器的差异。
> **追问方向：** DOM XSS 的 source 与 sink、富文本为什么必须用白名单清洗、框架自动转义覆盖不到哪些场景。

### 过滤输入与 DOM 危险汇点

黑名单过滤的困难在于要枚举所有解释器的所有写法：大小写、编码、浏览器解析差异、以及"过滤之后再拼接"引入的二次解析。富文本是必须保留部分 HTML 的场景，正确路线是**白名单清洗（sanitize）**：只允许列出的标签、属性和 URL 协议，其余全部转义或删除，并让清洗发生在最终插入之前。常见误区是"先过滤一次，之后到处拼接就不再处理"——清洗结果一旦再次进入字符串拼接，白名单保证就被破坏。

浏览器端还有一类"危险汇点（sink）"：把字符串当 HTML 或代码解释的 API。`innerHTML`、`document.write`、`eval` 是典型代表，把不可信数据传给它们，等价于在服务端跳过输出编码。对应做法是用只写文本的 API（`textContent`），或者在必须插入 HTML 时先经过清洗库。

> **时效信息（核查日期：2026-09）：** Trusted Types 可把"必须经过策略处理"变成浏览器强制的规则：开启 `require-trusted-types-for 'script'` 后，在支持该策略的浏览器中，向受保护的危险汇点传入普通字符串可能直接抛错。它不提供清洗算法，策略本身仍需调用经过审计的清洗函数；旧浏览器或不支持该指令的客户端不会因此获得同样的保护（[MDN: Trusted Types API](https://developer.mozilla.org/en-US/docs/Web/API/Trusted_Types_API)）。

### HttpOnly 缩小泄漏面，不消灭 XSS

`HttpOnly` 的作用是让 Cookie 不通过 `document.cookie` 一类脚本接口暴露。它的边界需要说清：

- 脚本读不到这份 Cookie 的值，因此无法把会话凭证复制出去；
- 但脚本仍然运行在页面里，可以代替用户发请求、修改页面、发起转账；
- 存在 `localStorage` 或 JS 变量里的令牌不受 `HttpOnly` 保护，会被直接读走；
- 因此 `HttpOnly` 把"永久盗取会话凭证"降级为"在受害者会话内操作"，属于缩小影响面，而不是 XSS 防护。

> **面试高频：** `HttpOnly` 能防住什么，防不住什么？
> **答题脉络：** 限制的是脚本读取通道 → 请求仍会被浏览器自动发出 → XSS 仍能代替用户操作 → 它是凭证保护措施，不是 XSS 修复手段。
> **追问方向：** `SameSite` 与 CSRF 的关系、令牌放在 Web Storage 的风险、XSS 之后是否必须轮换会话。Cookie 属性的完整语义见[身份认证一篇](../04-计算机网络/09-身份认证：Cookie、Session与JWT.md#决定行为的属性)。

### CSP：让注入的脚本无法执行

内容安全策略（Content Security Policy，CSP）是浏览器执行的第二道防线：即使页面里混进了脚本，浏览器也可以拒绝执行它。关键区别在于 CSP 有两种截然不同的用法：

- **基于来源清单的 CSP**（允许一批域名）在被允许的来源存在用户可控上传、JSONP 或可被当作脚本加载的内容时会变弱；并不是把任意可信 CDN 加入清单就自动安全；
- **严格 CSP（strict CSP）** 基于随机数（nonce）或哈希：服务器每次响应生成一个新的随机值，直接执行的脚本必须带匹配的 nonce（或匹配哈希），而 `strict-dynamic` 还会让受信脚本动态加载的脚本继承信任。

一个最小的严格 CSP（其中 nonce 只是占位符）长这样：

```http
Content-Security-Policy: script-src 'nonce-<每次响应随机生成的值>' 'strict-dynamic'; object-src 'none'; base-uri 'none'
```

```html
<script nonce="<与响应头相同的 nonce>">/* 只有获信任的脚本才会执行 */</script>
```

四点实现要求：

1. nonce 必须每个响应重新生成，并且使用加密安全随机源，否则"随机数"退化成可预测常量；
2. 在支持 nonce 的实现中，同时出现 nonce 和 `unsafe-inline` 时，`unsafe-inline` 对脚本内联执行的放宽会被忽略；兼容旧浏览器时仍应单独检查策略效果；
3. `strict-dynamic` 让被信任脚本动态加载的脚本继承信任，代价是"被信任脚本按不可信数据拼脚本"的写法可能让 CSP 失去实际防护；现代浏览器还会忽略同一 `script-src` 中部分来源清单，旧浏览器则可能按来源清单工作；
4. `object-src 'none'` 与 `base-uri 'none'` 用来堵住插件与 `<base>` 注入这两条旁路。

> **关键认知：** CSP 负责"拦执行"，不负责"防注入"；输出编码负责让数据不再成为代码。两者是纵深关系，不存在谁替代谁。

完整标签与 hash 生成方式的更多细节见 [web.dev 的严格 CSP 指南](https://web.dev/articles/strict-csp)；CSP 的字段语义以 [MDN 的 CSP 文档](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP)为准。

## CSRF：浏览器自动携带的凭证

跨站请求伪造（Cross-Site Request Forgery，CSRF）利用的是浏览器的一条基本行为：**请求是否带上 Cookie，由浏览器依据 Cookie 属性、请求上下文和目标站点规则决定，而不是由攻击者页面决定**。在满足携带条件时，攻击者不需要读响应，也不需要注入脚本，只需要让受害者的浏览器向目标站点发出一个"带凭证的请求"。

一个经典场景：银行用 `GET` 请求处理转账，攻击者页面里放一个指向 `//bank.example/transfer?to=attacker&amount=1000` 的 `<img>` 元素，浏览器加载它时就会自动发出请求。受害者登录过银行、Cookie 尚未过期时，这次请求携带的就是真实会话。攻击者读不到响应，但状态已经被改变。把状态改变限制为 `POST` 能消掉图片这一个向量，但第三方页面同样可以自动提交隐藏表单发出 `POST`：

```html
<!-- 攻击者页面：无需用户点击，脚本直接提交跨站表单 -->
<form id="transfer" method="POST" action="https://bank.example/transfer">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="1000">
</form>
<script>document.getElementById('transfer').submit();</script>
```

两个例子说明：具体载体（图片、表单、导航）可以换，只要"请求会带着凭证自动发出"这一点不变，攻击就成立。

### 三个条件同时成立才有 CSRF

1. 请求使用**浏览器自动携带的凭证**（Cookie、HTTP Basic 等）；
2. 请求**可以被第三方页面构造**出来（表单、图片、导航，或缺少额外条件的跨源请求）；
3. 服务端**只凭凭证有效性判断请求意图**，不区分请求由谁发起。

三个条件缺一不可，这直接给出了防线选择：要么让凭证不再自动携带（例如让浏览器脚本显式附加、跨源页面不能直接设置的 `Authorization` 头），要么让第三方无法构造出有效请求（令牌、来源校验），要么改变凭证的携带规则（`SameSite`）。设计新系统时，最优先考虑的应是“状态改变只发生在带显式令牌的接口上”，并确认令牌没有被放进 URL 或其他会自动携带的位置。

### 令牌、来源校验与 SameSite 如何配合

**同步器令牌（Synchronizer Token）**是 [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) 推荐的主要方案：服务端生成不可预测的随机令牌，绑定到当前会话，随页面发给客户端；客户端在提交时通过表单隐藏字段或自定义请求头回传；服务端比较两者，不匹配就拒绝。关键细节：

- 令牌必须来自加密安全随机源，长度足够；
- 对同步器令牌来说，令牌回传不能只依赖 Cookie（否则攻击者页面也能触发浏览器自动携带）；双提交 Cookie 是另一种需要单独正确实现的方案；
- 令牌不能出现在 URL 里：会进入浏览器历史、`Referer`、代理日志与访问日志；
- 令牌比较应使用框架或密码库提供的常数时间比较，尽量减少通过响应时间差异逐字符猜令牌的机会；不要把手写的高层语言函数当作严格的密码学原语。

会话凭证本身失效前，令牌是"这次请求确实由页面发起"的证据。下面用纯 Dart 实现令牌生成、常数时间比较与最小校验流程。

```dart
// 前置条件：Dart 3.x；纯 Dart；使用 dart:math 的加密安全随机源。
import 'dart:convert';
import 'dart:math';

/// 生成一个 256 位随机的 CSRF 令牌（Base64URL，约 43 个字符）。
String newCsrfToken({int byteLength = 32}) {
  // 1. Random.secure() 读取操作系统提供的加密安全随机源。
  final random = Random.secure();
  final bytes = List<int>.generate(byteLength, (_) => random.nextInt(256));
  // 2. 去掉填充，便于放进表单隐藏字段与自定义请求头。
  return base64UrlEncode(bytes).replaceAll('=', '');
}

/// 教学用的近似常数时间比较；生产代码应优先使用框架或密码库提供的实现。
bool constantTimeEquals(String expected, String actual) {
  final expectedUnits = expected.codeUnits;
  final actualUnits = actual.codeUnits;
  // 1. 长度差异先记入结果，但仍按最长长度完整遍历。
  var difference = expectedUnits.length ^ actualUnits.length;
  final length = expectedUnits.length > actualUnits.length
      ? expectedUnits.length
      : actualUnits.length;
  for (var index = 0; index < length; index++) {
    // 2. 越界位置按 0 参与运算，避免循环次数泄漏长度之外的差异。
    final left = index < expectedUnits.length ? expectedUnits[index] : 0;
    final right = index < actualUnits.length ? actualUnits[index] : 0;
    difference |= left ^ right;
  }
  return difference == 0;
}
```

上面的 `newCsrfToken` 只负责生成值；真实服务还必须把令牌以安全方式绑定到当前会话，并在校验成功或会话轮换时更新/失效，不能把它当作无状态的固定常量。

```dart
/// 一次 CSRF 校验的结论。
enum CsrfCheck { allow, rejectNoToken, rejectTokenMismatch }

/// 有状态会话的最小校验：安全方法只读，状态改变必须携带正确令牌。
CsrfCheck verifyCsrf({
  required String method,
  required String? submittedToken,
  required String? sessionToken,
}) {
  // 1. 业务只允许 GET/HEAD/OPTIONS 读取状态；TRACE 不应作为业务接口开放。
  final normalizedMethod = method.toUpperCase();
  const safeMethods = {'GET', 'HEAD', 'OPTIONS'};
  if (safeMethods.contains(normalizedMethod)) return CsrfCheck.allow;
  // 2. 缺令牌直接拒绝，不做“令牌为空就跳过”的降级。
  final expected = sessionToken;
  final actual = submittedToken;
  if (expected == null || actual == null || actual.isEmpty) {
    return CsrfCheck.rejectNoToken;
  }
  // 3. 用常数时间比较，避免逐字符比较泄漏令牌前缀。
  return constantTimeEquals(expected, actual)
      ? CsrfCheck.allow
      : CsrfCheck.rejectTokenMismatch;
}
```

运行断言后可以观察到预期行为：32 字节令牌是 43 个字符、字符集限定在 Base64URL 字母表；`constantTimeEquals` 在所有样本上与 `==` 结论一致；`GET` 不校验令牌，`POST` 在缺令牌、空令牌、令牌不匹配三种情况下都被拒绝。这里要诚实说明两点：这个教学函数只能缩小**内容前缀**的时间泄漏，长度差异仍然可观察，Dart 运行时也不承诺严格常数时间；它防的是"猜令牌"，不能弥补令牌长度不足或随机源不可靠。

**SameSite** 是改变 Cookie 携带规则的属性。许多现代浏览器会把未声明的会话 Cookie 按 `Lax` 处理，但这是浏览器行为而不是非浏览器客户端的通用保证；在该行为下，跨站顶级导航且使用安全方法时仍可能携带。它的边界必须说清：

- `Lax` 不是“所有跨站请求都拦”：它仍允许部分跨站顶级安全方法导航。任何还在用 `GET` 修改状态的接口，`SameSite=Lax` 拦不住；部分浏览器对新设置的 Cookie 还存在短暂的宽松兼容行为；
- “同站”大致按 schemeful site（协议方案 + 注册域）判断，不是同源：`https://a.example.com` 与 `https://b.example.com` 互为同站，但不同端口仍可能同站；共享父域的不可控子域会绕过这道防线，`http` 与 `https` 之间也不能忽略方案差异；
- 它不保护客户端内发起的请求（恶意输入让自家脚本发出状态改变请求）；
- 因此 OWASP 把它定位为纵深防御层，而不是唯一防线。

`SameSite` 的完整语义、`__Host-` 前缀与当前草案状态见[身份认证一篇](../04-计算机网络/09-身份认证：Cookie、Session与JWT.md#samesite-与名称前缀)。

**来源校验**分两种。`Origin`/`Referer` 校验检查请求头里的来源是否可信：`Origin` 出现在跨源请求与多数跨源 POST 上，比 `Referer` 更不容易被裁剪，但非浏览器客户端与某些请求形态可能不带它，所以实现时必须区分"缺失时拒绝"和"缺失时放行"——后者等于把防线关掉。`Referer` 会被引用策略裁剪、被隐私设置省略，完全依赖它是常见错误。

**Fetch Metadata** 提供了浏览器生成的、页面脚本无法篡改的来源信号：

```http
POST /transfer HTTP/1.1
Host: bank.example
Origin: https://evil.example
Sec-Fetch-Site: cross-site
```

`Sec-Fetch-Site` 的取值是 `same-origin`、`same-site`、`cross-site`、`none`，浏览器在发起请求时自动附加，属于禁止脚本修改的请求头。服务端可以在状态改变接口上拒绝 `cross-site`，但旧浏览器、非浏览器客户端和部分特殊请求可能不发送该头，因此必须设计缺失时的回退策略，并按目标浏览器核对支持情况。

**让请求无法被简单构造**：这是 OWASP 对纯 API 场景的候选方案。第三方页面可以无预检地发出简单请求（`GET`/`HEAD`/`POST` 加安全列表内的请求头），但状态改变接口若严格只接受 `application/json` 或自定义请求头，且服务端确实拒绝不符合 `Content-Type` 的请求，跨源请求就会先触发 CORS 预检；不信任来源的预检被拒绝后，真正的请求不会发出。它依赖浏览器执行，非浏览器客户端不受约束，因此仍要配合令牌或来源校验。

> **关键认知：** CSRF 的防线是让第三方页面**无法构造出有效请求**，不是去识别"谁是好人"。令牌、来源校验、`SameSite`、非简单请求都是这条原则的不同实现；它们都依赖具体浏览器和部署条件，组合使用才能覆盖各自的失败边界。

> **面试高频：** CSRF 令牌、`SameSite`、`Origin` 校验各自解决什么，怎么配合？
> **答题脉络：** 令牌证明请求由页面发起 → `SameSite` 缩小自动携带范围但只挡不安全方法、且按站点而非源 → `Origin`/Fetch Metadata 校验来源但可能缺失 → 主防线选令牌，其余作纵深。
> **追问方向：** 双提交 Cookie 与同步器令牌的差别、SPA 用自定义头为什么能触发预检、`SameSite` 为什么挡不住同站子域。

### XSS 与 CSRF 是两种攻击

| 维度 | XSS | CSRF |
| --- | --- | --- |
| 攻击者控制什么 | 在受害者页面里执行脚本 | 诱导浏览器携带凭证发出请求 |
| 利用的信任 | 站点信任了不可信输入 | 站点信任了带有有效凭证的请求 |
| 是否能读响应 | 若脚本在目标源执行，通常能读同源响应 | 跨源页面通常不能读，也不需要 |
| 成立条件 | 不可信数据到达可执行上下文且缺乏匹配处理 | 凭证自动携带 + 请求可构造 + 只验凭证 |
| 主要防线 | 上下文编码、安全汇点、严格 CSP | 令牌、来源校验、`SameSite` |
| 相互关系 | XSS 可以绕过大多数 CSRF 防线 | 不能读取数据，但能改变状态 |

> **关键认知：** XSS 是"攻击者拿到了页面的执行权"，CSRF 是"攻击者借用了浏览器的凭证携带"；前者先于后者被修复，因为脚本执行能绕过令牌校验在内的多数防线。

## 注入：拼接让数据越过语法边界

注入（Injection）指应用把不可信数据拼接进了有语法的字符串，使数据被解释器当成指令。SQL 注入是数据库解释器上的这类问题，最常见的入口是"用字符串拼接构造查询"。

登录校验本来是查用户名与口令是否匹配。如果代码把输入直接拼进 SQL 文本，攻击者输入 `1' OR '1'='1` 会让条件恒真：

```sql
-- 1. 应用拼接后发出的 SQL
SELECT name FROM users WHERE (name = 'alice') AND (pw = 's3cret');

-- 2. 输入 1' OR '1'='1 之后，实际发出的 SQL
SELECT name FROM users WHERE (name = '1' OR '1'='1') AND (pw = '1' OR '1'='1');
```

第二条查询的 `WHERE` 条件恒真，等价于查全部用户，口令校验被完全绕过。

### SQL 注入如何成立

顺序很关键：数据库收到的是**一段文本**，它先做词法与语法分析，把文本切成关键字、标识符、字符串字面量，再执行。拼接发生在发送之前，因此用户输入和 SQL 代码在同一条文本里竞争解析——输入里的引号提前结束了字面量，后面的内容就成了语法结构的一部分。

> **关键认知：** 注入的本质是"拼接位置具有语法含义"。任何把不可信数据拼接进结构化语法的场景都可能成立同类问题，SQL 只是最常被演示的一种；命令注入（CWE-78）、模板注入、日志注入同属一个家族。

下面把两种写法放进真实的内存 SQLite 数据库中对照。示例依赖 `sqlite3` 包，用真实解析器证明"值是否参与语法"。前两个函数用来建库与对比，运行断言可以观察到：拼接写法在注入输入下返回全部用户，参数化写法返回空集。

```dart
// 前置条件：Dart 3.x；依赖 sqlite3 包（需要真实 SQL 解析器）。
// 这里只演示注入，不是生产登录实现；真实系统应使用口令哈希和安全的认证流程。
// Windows 加载系统 winsqlite3.dll；Linux/macOS 加载系统 libsqlite3。
import 'dart:ffi';
import 'dart:io';

import 'package:sqlite3/open.dart';
import 'package:sqlite3/sqlite3.dart';

/// 打开一个内存数据库，并写入两个已知口令的账号。
Database openDemoDatabase() {
  // 1. Windows 自带 winsqlite3.dll，直接加载即可。
  if (Platform.isWindows) {
    open.overrideFor(OperatingSystem.windows, () {
      return DynamicLibrary.open('winsqlite3.dll');
    });
  }
  final database = sqlite3.openInMemory();
  database.execute('CREATE TABLE users (name TEXT NOT NULL, pw TEXT NOT NULL)');
  database.execute(
    "INSERT INTO users VALUES ('alice', 's3cret'), ('bob', 'hunter2')",
  );
  return database;
}

/// 错误示范：输入被拼进 SQL 文本，成为语法的一部分。
List<String> loginByConcatenation(
  Database database,
  String name,
  String password,
) {
  final sql =
      "SELECT name FROM users WHERE (name = '$name') AND (pw = '$password')";
  return database
      .select(sql)
      .map((row) => row['name'] as String)
      .toList(growable: false);
}

/// 正确做法：SQL 结构固定，输入只作为绑定值参与比较。
List<String> loginByParameter(Database database, String name, String password) {
  final rows = database.select(
    'SELECT name FROM users WHERE (name = ?) AND (pw = ?)',
    [name, password],
  );
  return rows.map((row) => row['name'] as String).toList(growable: false);
}
```

### 参数化查询：结构与值分通道

参数化查询（prepared statement with parameter binding）把 SQL 结构和值放进不同通道：SQL 文本先由驱动或数据库作为固定结构处理，值随后绑定到占位符上。正确实现会让值只作为字面量参与比较，不再被重新解析成 SQL 语法；即使某些驱动内部采用模拟预处理，也必须保持这种结构和值分离的语义。于是 `1' OR '1'='1` 在参数化写法里只是一个"名字恰好长这样的用户"，查不到就返回空集。

> **面试高频：** 参数化查询为什么能防 SQL 注入？
> **答题脉络：** SQL 结构先编译并固定 → 值走绑定通道、不参与语法解析 → 数据库不需要猜哪段是数据 → 输入中的引号与关键字失去结构性作用。
> **追问方向：** 表名/排序列不能绑定时怎么办、ORM 的 raw API、LIKE 中的通配符、二阶注入（存进去再拼出来）。

三个必须记住的边界：

1. **参数化不等于"输入安全"**：绑定的值原样进入数据库，如果它随后被输出到 HTML 页面，XSS 编码仍要做。参数化只解决"值不越界成 SQL 语法"。
2. **参数化不等于 ORM 自动正确**：ORM 的 `raw`/字符串拼接接口不会因为来自 ORM 就变安全；判断标准始终是"值有没有走绑定通道"。
3. **参数化不能用在标识符位置**：占位符只能代表值，不能代表表名、列名或关键字。

### 不能绑定的部分用白名单

表名、列名、`ORDER BY` 的方向这类位置无法用绑定参数表达，因为它们在 SQL 语法里是标识符或关键字，不是值。OWASP 的建议是：需要动态选择时，用**允许清单映射**把用户输入换成代码侧固定的字符串（[SQL 注入预防备忘单](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)）。

```text
用户输入 "name"        -> 命中白名单 -> 使用代码侧固定的列名 name
用户输入 "created_at"  -> 命中白名单 -> 使用代码侧固定的列名 created_at
用户输入 "t; DROP TABLE users" -> 不在白名单 -> 直接拒绝
```

通用验证函数很容易写成"看起来像标识符就放行"，这等于把"是否符合语法"当成了安全标准。安全的做法是让映射表只包含业务真正需要的少数取值，出现白名单之外的值就返回错误。此外，数据库账号应遵循最小权限：登录校验用的账号通常不需要 `DROP`、`ALTER` 或跨库权限，这样即使出现其他漏洞，影响面也被限制。

### 历史机制：转义单引号

> **历史机制（已移除）：** PHP 的 Magic Quotes 会在输入进入应用时自动给引号加反斜杠，PHP 5.3.0 弃用、PHP 5.4.0 移除（[PHP 5.4.0 发布说明](https://www.php.net/releases/5_4_0.php)，[核查日期：2026-09]）。它既覆盖不了非引号上下文，又让转义在数据反复进出数据库的过程中层层叠加。"给输入转义单引号"不应再作为通用防御方案；优先使用参数化查询，只有在确实无法参数化且使用对应数据库官方转义 API、经过测试的遗留边界上，才讨论上下文专用转义。

## 拒绝服务：耗尽有限资源

拒绝服务攻击（Denial of Service，DoS）的目标不是窃取数据，而是让服务对正常用户不可用。它的本质是**消耗某种有限资源**：连接数、内存、CPU、磁盘 I/O、带宽、数据库连接池、下游 API 配额，甚至客服与人工审核能力。

分布式拒绝服务攻击（Distributed Denial of Service，DDoS）由多个分散来源共同制造流量或请求；来源可能是被攻陷的设备，也可能是利用反射/放大服务形成的流量。分布带来的变化有两个：攻击规模可以远超单机带宽，来源高度分散使按 IP 封禁容易误伤且难以追溯。它仍然是资源耗尽问题，但大流量清洗和源头治理通常必须在应用边缘、网络运营商或专业防护服务完成，不能只靠应用层限速。

### DoS 与 DDoS

> **面试高频：** DoS 与 DDoS 的区别是什么，为什么说它们不是两个不同的攻击？
> **答题脉络：** 两者都让资源耗尽、服务不可用 → DDoS 用分布式来源放大规模并掩盖真实来源 → 对策从"拦住某个来源"变为"边缘清洗 + 容量冗余 + 降级"。
> **追问方向：** 应用层攻击为什么不需要带宽优势、限速在僵尸网络面前为什么不够、反射放大与源地址伪造的关系（见[传输层一篇](../04-计算机网络/04-传输层：UDP、TCP与QUIC.md#udp最小传输服务与应用责任)）。

### 三层攻击面与对应防线

OWASP 的 [DoS 备忘单](https://cheatsheetseries.owasp.org/cheatsheets/Denial_of_Service_Cheat_Sheet.html)沿用 CERT-EU 的分类，把攻击面分为网络（饱和带宽）、会话/协议（消耗中间设备与服务器连接资源）、应用层（消耗计算与业务资源）三类。三类不需要同一种应对方式：

| 层面 | 典型手法 | 消耗的资源 | 主要对策 |
| --- | --- | --- | --- |
| 网络/带宽 | 大流量洪水、UDP 反射放大 | 出口带宽 | CDN 与清洗服务、容量冗余 |
| 会话/协议 | 慢速 HTTP：把请求头或正文一点点发送 | 连接池与内存 | 绝对连接超时、最小入站速率、连接数上限 |
| 应用层 | 昂贵查询、大文件上传、输入驱动的对象分配 | CPU、内存、下游配额 | 限速、请求体上限、缓存、异步与降级 |

慢速攻击值得单独理解：它几乎不消耗带宽，靠"把连接占住又迟迟不发完"耗尽服务器的并发连接上限。对它的有效手段是连接超时与最小入站速率，而不是提高限速阈值。反射放大则利用 UDP 无连接、源地址可伪造的特点：攻击者把请求的源地址伪造成受害者，让放大后的应答全部冲向受害者；应用层能做的有限，需要网络侧按来源过滤与运营商配合。

应用层缓解可以先做"便宜的事"：在昂贵的业务校验之前先做请求体大小、内容类型、参数格式的检查；给所有外部依赖设置超时；限制单用户/单接口的并发与速率；对昂贵查询做缓存；给系统设计降级路径，让部分组件失败时核心功能仍可用，而不是整体雪崩。OWASP 清单还提醒：账户锁定策略本身可能被反过来当成攻击手段——持续输错某个可预测账号的密码，就能让合法用户被锁在门外，因此锁定应采用递增延迟等更温和的策略。

### 限速只是其中一层

限速（rate limiting）把一段时间内的请求数量约束在上限内，是应用层最常用的第一道闸。下面用令牌桶（token bucket）实现一个最小限速器：容量决定允许的突发大小，补充速率决定长期平均值，令牌不足时直接拒绝而不是让请求排队。

```dart
// 前置条件：Dart 3.x；纯 Dart；无第三方依赖。
import 'dart:math';

/// 按时间补充令牌的限速器：容量决定突发上限，速率决定长期平均值。
class TokenBucket {
  TokenBucket({required this.capacity, required this.refillPerSecond})
    : assert(capacity > 0),
      assert(refillPerSecond >= 0),
      _tokens = capacity.toDouble(),
      _lastRefill = Duration.zero;

  final int capacity;
  final double refillPerSecond;
  double _tokens;
  Duration _lastRefill;

  /// 尝试消费 [cost] 个令牌；返回 false 表示请求应被拒绝，而不是排队。
  bool tryConsume(Duration now, {int cost = 1}) {
    // 1. 调用方必须传入单调递增的时间，且单次成本必须为正。
    if (cost <= 0 || now < _lastRefill) return false;
    // 2. 按经过时间补充，最多补到容量。
    final elapsed = now - _lastRefill;
    if (elapsed > Duration.zero) {
      final refill =
          elapsed.inMicroseconds /
          Duration.microsecondsPerSecond *
          refillPerSecond;
      _tokens = min(capacity.toDouble(), _tokens + refill);
      _lastRefill = now;
    }
    // 3. 令牌不足就快速失败：排队会把流量压力转成内存与延迟压力。
    if (_tokens < cost) return false;
    _tokens -= cost;
    return true;
  }
}
```

<!-- verify: .work/verify/B19/lib/token_bucket.dart -->

运行断言可以观察到三组边界行为：容量为 3 时前 3 个请求立即通过、第 4 个被拒绝；空闲 2 秒后按速率补回 2 个令牌；空闲 100 秒也只补到容量 3，不会积累成无限令牌。还有三个容易踩的边界：容量必须为正、补充速率不能为负；如果单次请求的 `cost` 大于 `capacity`，这个请求永远不会被放行；如果时钟回拨或成本不为正，示例会拒绝请求。

这个实现只适合说明算法，而且状态只存在单个进程内；生产环境还要决定按什么身份或资源分桶，并使用网关、共享存储或其他具备并发一致性的限速设施。多实例服务若各自维护一份桶，整体额度会随实例数放大，不能把这个类直接当作全局限速器。

限速的失败边界同样要记住：按 IP 限速会误伤 NAT 后面共享出口的正常用户，也会被僵尸网络用分散来源稀释；对慢速攻击无效（请求已经建立、速率也不高）；对"一个请求就非常昂贵"的接口无效（需要按操作成本加权，或改成异步任务）。所以限速是闸门之一，不是整套防护。

> **关键认知：** DoS 防护改变的从来不是攻击者的意愿，而是攻击的成本与影响面：容量冗余、快速失败、降级与限速分别从"抗住""不排队""保核心""限数量"四个角度减少同一种资源被打穿的概率。

## 会话劫持与重放：凭证泄漏之后

前面几类攻击之外，还有一类问题的共同点是"凭证已经泄漏"。XSS、日志、调试代理、共享设备都可能把会话凭证或令牌带出受控范围，此后攻击者不需要再绕过任何校验，直接复用凭证即可。

会话安全可以被三个问题概括：**凭证放在哪里**（Cookie、请求头还是 Web Storage）、**怎么发送**（是否自动携带、是否要求安全通道）、**被复制后还能不能用**（是否有发送者约束）。前两个问题的机制与边界在[身份认证一篇](../04-计算机网络/09-身份认证：Cookie、Session与JWT.md#会话被偷走的几条路)中已经完整展开：

- XSS 能拿到什么、`HttpOnly` 的边界：见[会话被偷走的几条路](../04-计算机网络/09-身份认证：Cookie、Session与JWT.md#会话被偷走的几条路)；
- 重放与发送者约束（DPoP、mTLS）：见[重放与发送者约束](../04-计算机网络/09-身份认证：Cookie、Session与JWT.md#重放与发送者约束)；
- 登录后轮换会话标识、降低会话固定（session fixation）影响：见[轮换、超时与共享存储](../04-计算机网络/09-身份认证：Cookie、Session与JWT.md#轮换超时与共享存储)。

本文只补充一条与攻击面相关的结论：**凭证的生命周期策略就是攻击面的收缩策略**。缩短有效期减少泄漏窗口，轮换让旧凭证尽快失效，发送者约束让"复制即可用"变成"复制也难用"，撤销能力决定泄漏后能否止损。这些都是机制设计问题，而不是靠某一个 header 开关。

## 客户端能做与不能做

把安全职责全部推给客户端，是移动端与 Web 同时使用同一套 API 时最常见的错误。原因很简单：**客户端运行在攻击者可控的设备上**——curl、Postman、改过的 App、浏览器控制台都能直接构造请求，界面上的校验、隐藏字段、灰色按钮不会出现在这些请求里。

| 客户端可以做的事 | 客户端不能承担的事 |
| --- | --- |
| 即时校验与提示，减少误操作 | 安全边界；攻击者可以绕过界面直接请求 |
| 提供 CSP/Trusted Types 的执行环境 | 决定服务端是否信任请求 |
| 按服务端下发的 Cookie 属性工作 | 阻止第三方页面让浏览器自动携带凭证发请求 |
| 减少明文的存储与展示 | 保护"客户端里的秘密"；密钥、算法、规则都可被提取 |

两个容易混淆的机制需要特别说明：

- **CORS 不是服务端授权机制**。它限制的是"浏览器里的脚本能不能读取跨源响应"，curl、移动 App、服务器之间的调用完全不受它约束；接口自身的鉴权与越权校验仍然必须做（详见[HTTP 一篇](../04-计算机网络/07-HTTP语义、缓存与版本演进.md#浏览器边界同源策略与-cors)）。
- **同源策略只存在于浏览器中**。原生桌面与移动客户端没有"同源"这层约束，把浏览器安全模型当作客户端防护是错位。

因此客户端校验的正确位置是体验层：让用户更快得到反馈、减少无效请求。真正的校验、编码、限速、令牌校验必须全部在服务端重新执行，而且要在数据被解释之前的那一侧。

> **关键认知：** 信任边界在服务端。"客户端已经校验过"不构成服务端跳过校验的理由；攻击者手里的客户端没有你的界面代码，只有你的接口协议。

## 安全检查清单

下面的清单按"输入与输出、身份与会话、数据与注入、可用性、工程与运营"组织，适合作为评审或上线前的对照项。它不是合规证明，只保证覆盖了本文讨论的机制。

**输入与输出**

- 所有不可信数据进入页面时按输出上下文处理：HTML 文本、属性、URL、内联脚本各有对应编码；
- 富文本必须走白名单清洗，清洗后的结果不再参与字符串拼接；
- 浏览器端避免 `innerHTML`、`eval`、`document.write` 处理不可信数据，优先用 `textContent` 类安全接口；
- 关键页面部署严格 CSP（nonce 或 hash），并把 `object-src`、`base-uri` 收紧。

**身份与会话**

- 承载会话的 Cookie 通常应具备 `HttpOnly`、`Secure`，并明确设置 `SameSite`；若能满足 `Secure`、`Path=/` 且不设置 `Domain`，可使用 `__Host-` 前缀限制域范围；
- 登录成功后轮换会话标识，设置空闲超时与绝对超时；
- 状态改变接口校验 CSRF 令牌，并可叠加 `Origin`/Fetch Metadata；安全方法保持只读。若依赖来源头，要明确缺失头、旧浏览器和非浏览器客户端的回退策略；
- 自定义令牌不放进 URL、不写进日志与错误上报。

**数据与注入**

- 所有 SQL 使用参数化查询；标识符等无法绑定处使用白名单映射；
- 数据库账号最小权限，错误信息不向用户回显结构细节；
- 记住参数化不等于输出安全：绑定值进入页面时仍要编码。

**可用性**

- 请求体、上传文件、查询参数设置大小与数量上限；
- 关键接口有超时、限速与降级策略；昂贵操作异步化或加缓存；
- 校验来源、`Origin`/Fetch Metadata 时，区分"缺失时拒绝"与"缺失时放行"，前者才是安全默认值。

**工程与运营**

- 依赖与构建产物纳入供应链管理，及时更新并锁定版本；
- 敏感操作记录审计日志，但令牌、口令一类数据不得入日志；
- 上线前用 OWASP Top 10:2025、CWE 与本文清单做一次对照，并记录核查日期与使用的版本。

## 常见误区

- **"XSS 就是过滤 `<` 和 `>`。"** 防护取决于输出上下文，URL、属性、内联脚本的越界方式各不相同；富文本必须白名单清洗。
- **"加了 `HttpOnly` 就没有 XSS 危害了。"** 它阻止脚本读取 Cookie，但脚本仍能以受害者身份操作，也能读走 `Web Storage` 里的令牌。
- **"`SameSite` 加上之后不需要 CSRF 令牌了。"** `Lax` 仍允许部分跨站顶级安全方法导航，且按 schemeful site 而非 origin 判定；OWASP 把它定位为纵深防御层。
- **"参数化查询让数据绝对安全。"** 它只保证值不越界成 SQL 语法；值被绑定后原样落库，输出到页面时 XSS 编码仍不可省。
- **"我们用了 ORM，所以没有 SQL 注入。"** ORM 的字符串拼接/`raw` 接口同样可以注入，判断标准是有没有绑定通道。
- **"Referer 检查可以做 CSRF 的主要防线。"** 它可能缺失或被裁剪，且"缺失时放行"的实现等于没有防线。
- **"DDoS 是运维的事，应用不用管。"** 应用层攻击消耗的是你的 CPU、连接池和下游配额，限速、超时、降级必须在应用里设计。
- **"上了 HTTPS，前面这些就都安全了。"** TLS 保护传输过程，不修复结构注入、输出编码缺失与 CSRF。
