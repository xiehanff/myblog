# 广告变现与聚合 SDK 接入

> 结论：广告接入的难点不在"把广告展示出来"，而在四处：构建期的多联盟依赖治理、审核期的合规形态切换、激励视频"看完发奖"的错误状态机、信息流嵌列表后的加载策略。本篇以国内聚合平台为样本，覆盖从选型决策、宿主工程改造、各广告形态落地到激励链路状态机设计的完整链路；环境与构建管理见第 8 篇，商店审核全流程见第 18、19 篇。核验版本：ToBid（Sigmob/Windmill 系）Flutter 插件 5.5.x，信息截至 2026-08；SDK 行为、错误码与联盟能力以当前官方文档为准。

---

## 一、聚合广告解决什么问题，边界在哪里

单接一家广告联盟的问题不是"接不上"，而是**填充率有天花板**：某家没有库存时请求直接浪费。聚合平台把一次请求同时发给多家联盟（Bidding）或按 eCPM 历史排序依次请求（Waterfall），填充率和综合 eCPM 都显著优于单接。

| 维度 | Waterfall（瀑布流） | Bidding（竞价） |
|---|---|---|
| 原理 | 按 eCPM 历史数据排优先级，依次请求 | 所有联盟同时出价，选最高 |
| 实时性 | 依赖历史数据 | 实时反映当前竞价 |
| 缺点 | 排序靠后的联盟可能永远拿不到请求 | 依赖各联盟竞价能力 |

成熟做法是**两者混用**：支持 Bidding 的联盟走竞价，其余进瀑布兜底。这正是聚合平台的核心价值，也是自研聚合不划算的原因——多联盟的接入、数据与计费口径统一是持续投入，不是一次性开发。

### 选型格局

| 方案 | 定位 | 备注 |
|---|---|---|
| ToBid（Sigmob/Windmill） | 国内聚合 | 本篇样本；Flutter 插件完整，8 家主流 ADN |
| 穿山甲 GroMore | 字节聚合 | 国内主流，Flutter 侧多需自接或桥接 |
| TopOn（国内已拆分 Taku） | 第三方聚合 | 2024-03 拆分：中国区业务由新品牌 Taku 承接，出海仍用 TopOn |
| AdMob | Google 聚合 | 大陆设备基本不可达，仅出海 |
| AppLovin MAX / Unity LevelPlay | 海外主流 | 出海场景 |

一个常见讹传需要澄清：2023 年被 Unity 关停的是**自家的 Unity Mediation**；ironSource 的聚合以 **Unity LevelPlay** 之名继续迭代。网上把"ironSource 关停"当讣告的说法是错的。纯国内产品在 ToBid/GroMore/Taku 里按"插件完整度 + 后台数据 + 服务响应"实测评选择；出海走 MAX/LevelPlay/AdMob。

### 边界：哪些必须自己认领

聚合平台吃掉的是"请求发给谁、联盟怎么结算"；但四件事不能外包给它：**审核形态**（审核期间是否展示广告、采集哪些隐私，是应用自己的合规责任）；**激励发放规则**（今天能看几次、看完发什么，是运营策略，必须服务端可热更）；**错误话术**（联盟错误码对用户不可读，文案要自己翻译并服务端下发）；**SDK 缺陷的兜底**（聚合插件的 bug 不会等你，要有能自己打补丁的集成方式——见第二节）。

## 二、集成方式与宿主工程改造

结论：**集成方式比选型更影响后续效率**——以本地插件目录而非 pub 依赖引入，换来的是"出问题能自己打补丁"的能力；代价是永久的 fork 维护成本，必须用补丁纪律对冲。

### 本地插件引入

案例项目把官方 Flutter 插件以本地目录形式引入（目录名带版本号），`pubspec.yaml` 用 path 依赖：

```yaml
# 插件目录内含：Dart 层 API + 双端原生层 + 各 ADN 的 aar + OAID SDK
# pub get 后经 GeneratedPluginRegistrant 自动注册，宿主无需改 MainActivity
windmill_ad_plugin:
  path: plugins/windmill_5_5_x
```

本地化的两个生产级理由：**补丁能力**——广告 SDK 的 bug 不会等你，走官方 issue 等排期可能要数周，本地插件一行补丁当天解决（第九节的 iOS Modal 问题就是靠这个能力救急的）；**构建链路可控**——ADN 的 aar 版本、依赖冲突都锁在自己仓库里，升级节奏自己定。代价是每次升级要人工同步，必须配升级核对清单；每次改动必须留文档记录（改了什么、为什么、升级时怎么核对），否则半年后没人敢动它。

### 构建期的四个坑

引入聚合插件后，宿主 Android 工程的依赖冲突全部在构建期暴露，报错都在 Gradle/Merger 输出里，集成日预留半天专门处理是合理预期：

**坑 1：AGP 版本链路不匹配**。插件 buildscript classpath 与宿主 AGP 版本不匹配时构建失败，需要对齐版本（案例约束：宿主从 AGP 8.11.1 降到 8.4.0 才能构建，Kotlin 版本不动）。**坑 2：旧版 Support 库与 AndroidX 冲突**。部分 ADN 的 aar 传递依赖旧库，必须开启 Jetifier：

```properties
# android/gradle.properties
android.useAndroidX=true
android.enableJetifier=true
```

**坑 3：androidx 组件版本不一致**。多家 ADN 传递引入不同版本的 androidx，用 `resolutionStrategy` 强制统一；原生信息流模板渲染依赖 CardView，需显式声明：

```kotlin
// android/app/build.gradle.kts
configurations.all {
    resolutionStrategy {
        eachDependency {
            if (requested.group == "androidx.browser" && requested.name == "browser") {
                useVersion("1.8.0")
            }
            if (requested.group == "androidx.core") {
                useVersion("1.15.0")
            }
        }
    }
}
dependencies {
    implementation("androidx.cardview:cardview:1.0.0")
}
```

**坑 4：Manifest 合并冲突**。广告 SDK 声明的 `allowBackup` 等属性与应用取值不同导致 merger 报错，用 `tools:replace` 以应用为准：

```xml
<application
    android:name="${applicationName}"
    android:allowBackup="false"
    android:label="应用名"
    tools:replace="android:allowBackup,android:label">
```

另有硬性门槛：插件通常要求宿主 `minSdkVersion` 达到其最低值（案例为 24）；iOS 侧对应确认 podspec 与权限声明。

## 三、初始化、合规与广告位管理

结论：初始化入口收敛在一个单例里，做三件事——审核形态下收紧隐私采集、失败上报留痕、广告位 ID 集中管理。

### 审核形态是一等公民

商店审核期间"展示广告 + 过度采集个人信息"是高频拒审组合。**审核形态必须做成服务端下发的开关**，不能靠发版切换：审核期间通过 `setCustomDevice` 把应用列表、定位、AndroidId、OAID、IDFA、MAC 地址等采集开关全部关掉；过审后恢复全量采集。

```text
// 示意伪代码：初始化入口
init():
    if (审核形态开关)            // 服务端下发，不是本地常量
        setCustomDevice(全部采集项 = false)
    appId = 按平台取集中配置
    res = await SDK.init(appId)
    if (res.success != true) reportInitError(res)   // 失败上报，不静默
    catch e: reportInitError(e)
```

初始化失败必须上报留痕：广告 SDK 初始化失败往往是静默的——App 其他功能一切正常，没有留痕就永远不知道有一批用户的广告全挂了。上报内容带上错误详情与来源标记，与后端日志对账。

### 广告位 ID 集中管理

所有广告位用 enum 收敛，双平台 ID 成对声明，杜绝散落硬编码（ID 为示意占位，真实广告位 ID 属于商业配置）：

```dart
enum AdPlacement {
  splash(android: '9100000000000001', iOS: '9100000000000011'),
  reward1(android: '9100000000000002', iOS: '9100000000000012'),
  native(android: '9100000000000003', iOS: '9100000000000013'),
  interstitial(android: '9100000000000004', iOS: '9100000000000014'),
  banner(android: '9100000000000005', iOS: '9100000000000015');

  final String android;
  final String iOS;
  String get value => Platform.isIOS ? iOS : android;
}
```

散落硬编码的代价是换广告位要全局搜索替换，双平台各一份还容易只改一半。

## 四、开屏广告：任何回调路径都能在有界时间内到达首页

开屏发生在冷启动的关键路径上，任何一步卡住都直接伤害留存。三条铁律：

```text
// 示意伪代码：开屏骨架
dispatch():
    if (审核形态) 直接进首页          // 铁律 1：审核模式跳过广告
    else loadSplashAd()

loadSplashAd():
    fallbackTimer = 4 秒后强制进首页   // 铁律 2：兜底超时先于加载启动
    ad = SplashAd(
        onLoaded:   try showAd; 失败进首页
        onFailed:   进首页
        onOpened:   取消 fallbackTimer   // 广告真正展示才解除兜底
        onClosed:   进首页
        onSkipped:  进首页
        onShowError: 进首页
        // 铁律 3：宽高用 platformDispatcher 实测逻辑分辨率，不写死
    )
    ad.loadAd()
```

开屏代码的评审标准就一句话：**任何一个回调路径都能在有界时间内到达首页**。加载慢、加载失败、展示失败、用户跳过，全部收敛到"进首页"这同一个出口；兜底 Timer 在加载**之前**启动，`onOpened`（真正展示）才解除——顺序反了就存在"既没展示也进不去"的窗口。尺寸取实测值（`physicalSize / devicePixelRatio`），避免广告尺寸与容器不符导致展示失败。

## 五、激励视频：前置关卡与发奖时序

激励视频（看广告 → 发奖励）是广告变现的主力形态，也是业务复杂度的主体。链路总览：

```text
业务按钮点击
  → 资格校验（服务端）
  → 本地冷却检查
  → 免责弹窗（"观看视频可获得奖励"）
  → 用户确认
  → 多广告位轮换加载
  → SDK 回调
     → 发奖成功: onAdReward → 上报服务端 → 发放奖励
     → 广告关闭: onAdClosed → 业务方刷新页面
     → 加载/展示失败: 查错误文案 → 失败弹窗 → 上报错误日志
```

一个反直觉的设计：**真正触发广告加载的不是业务按钮，而是免责弹窗的确认按钮**。业务按钮只走前置检查；免责弹窗既是合规需要（用户知情），也天然充当广告加载前的确认门。

### 前置三关卡

**关卡 1：资格校验（服务端）**。"今天还能不能看、看了几次"是运营策略，必须可热更，所以资格判断放服务端，按返回码分流：允许观看则缓存结果继续；版本过低则弹升级终止；不满足运营条件（如当日次数用尽）则展示服务端下发的文案终止。业务前置条件（账号状态、版本门槛）都在这一层收敛，广告链路本身不感知业务规则。

**关卡 2：本地冷却**。服务端下发次数上限与冷却秒数，客户端用本地保存的上次成功时间戳算剩余冷却。冷却基准时间戳在**发奖成功时**写入——以真实发奖为准，不以广告关闭为准，用户没看完就关掉不刷新冷却。

**关卡 3：免责弹窗**。见上文。

### 多广告位轮换

案例项目配置 4 个激励广告位，展示时取第一个"未消耗"的实例，全部消耗完则重置再来一轮：

```text
// 示意伪代码：广告位轮换
showNext():
    if (所有实例都已消耗) 重置全部 → 取第一个
    item = 第一个未消耗的实例
    item.loadAdData()

// hasShow 在 onAdOpened（真正展示）时置位——加载失败不算消耗
```

为什么轮换：同一个广告位连续展示会被联盟风控判定异常（填充下降甚至封位）；多广告位让每次请求落在"新鲜"的位上，也天然分摊单联盟无库存的风险。

### 发奖时序：以 onAdReward 为准

```text
onAdReward（SDK 判定完成激励条件）
  → 清空错误态、关闭已弹出的失败弹窗
  → 发奖上报（带签名；请求字段区分触发广告的业务场景）
  → 保存本地成功时间戳（冷却基准）
onAdClosed（广告关闭）
  → 调用业务方挂接的刷新回调
```

两个关键设计：

1. **发奖上报以 `onAdReward` 为准，不以 `onAdClosed` 为准**。前者是 SDK 判定"用户看完了"的唯一信号；后者只说明广告关了（可能没看完）。上报失败时要暴露给用户而不是静默吞掉——拉服务器时间拼接提示，在广告关闭时告知用户，让"发奖失败"有据可查。
2. **页面刷新是出口不是内置**。`onAdClosed` 回调暴露给业务方挂接，广告管理器不内置任何页面刷新——通用能力与具体页面解耦。

## 六、激励视频：错误状态机与对外接口

这一节是激励链路里最有含金量的部分——大部分团队的第一版实现都是"error 就 toast 一句完了"，而线上事故几乎全部出在本节覆盖的场景里。

### 双层错误处理

加载失败（`onAdFailedToLoad`）与展示失败（`onAdShowError`）走同一套处理，但分两层：

```text
recordError(error)
  → 按错误码 + 平台请求文案配置接口（服务端下发，运营可热更话术）
  → 缓存三份信息：
     用户文案        → 给用户看的（接口失败时兜底原始 message）
     最近一次错误     → 给外部调用方复用
     错误详情 JSON    → 给后端日志排障用
showErrorAlert(code)
  → 仅在本轮未成功时才弹（见下文"成功覆盖失败"）
```

**日志上报不在这里发**，而是挂在失败弹窗的 `onDismiss`：用户关掉弹窗时，如果错误详情存在才上报日志接口（带来源场景标记）。收到 error 但没弹窗（比如被成功覆盖）就不打这条日志——用户可见层和日志层是两条独立链路。联盟错误码对用户不可读，文案走服务端配置是刻意设计：运营要能随时调整话术，而不是等发版。

### 成功覆盖失败：最容易写错的状态语义

SDK 回调时序不止"要么成功要么失败"——可能先 error 后 reward（重试成功），也可能先 reward 后 error（关闭时异常）。语义规则：**一旦 `onAdReward` 到达，按成功收口**——立即清空错误态、关闭已弹出的失败弹窗、置位成功标志；失败弹窗只在本轮未成功时才允许弹出。完整行为矩阵（也是错误处理的验收标准）：

| 场景 | 时序 | 错误弹窗 |
|---|---|---|
| 1 | 无广告，error | 弹 |
| 2 | 广告出现，先 error 后 reward | 先弹，reward 到达时主动关闭 |
| 3 | 广告出现，先 reward 后 error | 不弹 |
| 4 | 广告出现，无 reward 无 error，用户关广告 | 不弹 |
| 5 | 广告出现，无 reward，中途 error，用户关广告 | 弹 |

一个如实记录的边界：失败弹窗的日志上报挂在 `onDismiss` 上，如果弹窗已展示、随后被成功回调关闭，`onDismiss` 仍会触发——即场景 2 下失败日志可能照打（用户侧已按成功收口，日志层多一条失败记录）。这是目标语义与实现之间的已知差距，修法是把上报条件改为"本轮未成功"。教训是**"用户可见层"和"日志层"的清理时机必须分开评审**。

### 对外激励接口：Completer 化与三重防挂起

除了内部业务调用，激励能力还应包装成 Future 化接口，供任意业务模块"看广告拿结果"。三个防挂起设计：

```dart
// 示意伪代码：对外激励接口骨架
Future<AdResult> showExternalReward() {
  final completer = Completer<AdResult>();
  final requestId = 下一请求 ID();      // 自增种子 + 时间戳

  scheduleTimeout(requestId, completer); // 1. 超时熔断
  activeRequestId = requestId;           // 2. 回调只认"当前请求"的实例
  // 3. 所有终态（reward/closed/failed/showError/timeout）
  //    统一走 finish，幂等（completer 已完成则跳过）
  return completer.future;
}
```

1. **超时熔断**：广告 SDK 的回调没有可靠性保证——加载卡死、回调丢失都真实发生过，超时器兜底保证调用方的 Future 一定在有限时间内完成。阈值依据线上分位数而非拍脑袋：案例项目从 8 秒调到 15 秒，因为线上发现部分低端机冷启动后首次加载超过 8 秒，被误判为失败。
2. **requestId 防串扰**：多个广告位实例共享状态流，用"当前请求 ID + 广告位 ID"双重匹配，避免把上一个请求的回调错配给当前调用方。
3. **Completer 幂等**：所有终态收敛到一个 finish 函数，已完成直接返回——奖励回调与关闭回调几乎同时到达时不会二次 complete 崩溃。

### 服务端接口清单

激励链路最少依赖 5 个服务端接口（迁移/重构时的核对清单；路径为示意占位）：

| 接口 | 用途 |
|---|---|
| 资格校验 | 前置检查，错误码分流 |
| 发奖上报 | 以 onAdReward 为准，字段区分业务场景 |
| 服务器时间 | 上报失败时拼时间提示 |
| 错误文案配置 | 按错误码 + 平台查用户可见文案 |
| 错误日志留痕 | 初始化失败与激励失败两用 |

## 七、原生信息流：PlatformView 创建时序

原生信息流是 Dart Widget（PlatformView 包装）→ 原生 View（数据绑定渲染）两层，这里藏着 PlatformView 最经典的一类坑。

**原生信息流加载成功但永不渲染**
- 现象：触发加载后状态显示"加载成功，等待渲染"，但广告区域永远空白；Banner 和激励视频都正常，仅原生信息流异常。
- 后果：排查方向被"SDK 加载成功"的日志带偏，容易去查联盟配置与广告位，实际根因在自己这层的时序。
- 成因：PlatformView 在广告数据就绪前创建——原生构造函数立即执行渲染，此时广告数据为 null，原生层空指针被 PlatformView 框架吞掉、返回空容器；之后加载成功，但 `creationParams` 没变，PlatformView **不会重建**，渲染调用不会再执行。
- 对策：只改调用方时序，不动插件——把 PlatformView 包装的 Widget 挂载推迟到 `onLoaded` 回调之后，数据就绪才创建。

```dart
// ❌ 错误：加载前就挂载
final ad = NativeAd(placementId: ...);
setState(() => _adWidget = NativeAdWidget(nativeAd: ad)); // 提前挂载 → 永不渲染
ad.loadAd();

// ✅ 正确：onLoaded 之后再挂载
final ad = NativeAd(
  placementId: ...,
  onLoaded: () {
    if (!mounted) return;
    setState(() => _adWidget = NativeAdWidget(nativeAd: ad)); // 数据就绪才创建
  },
);
ad.loadAd();
```

为什么 Banner 不受影响：Banner 的原生渲染只是放一个空容器视图，不依赖广告数据，SDK 加载完成后自己渲染进去；原生信息流的渲染必须拿到广告数据才能绑定视图——**时序不可逆**。通用教训：任何"依赖异步数据"的 PlatformView，都要保证**首次创建时数据已就绪**——PlatformView 的生命周期由 widget 树驱动，`creationParams` 不变就不会重建，你没有第二次机会。这条教训同样适用于地图、WebView 预注入、原生播放器等一切同构场景。

## 八、信息流进列表：滚动感知与状态缓存

单体信息流跑通只是第一步，嵌进业务列表后还要处理滚动、回收重建和快速划过。下面按案例源码说明滚动监听、索引缓存、占位、挂载时序与可见性检测各自做了什么，以及当前实现的边界。

### 滚动感知：停稳后再检查是否需要加载

`ListView` 把共享的 `ScrollController` 传给每个广告组件。组件在 `initState` 中会立即尝试加载；滚动监听的 300ms 防抖只作用于滚动停止后的再次检查：

```text
// 按案例源码简化的流程
initState():
    添加滚动监听
    检查索引缓存并尝试加载   // 首次挂载不等待滚动停稳
onScroll():
    isScrolling = true
    重置 300ms 定时器
    定时器到期: isScrolling = false; 检查是否需要再次加载
```

因此，已有的首次加载不会因开始滚动而取消，不能把这套实现描述为“滚动中不请求”。防抖能推迟滚动触发的再次检查，但快速划过时首次挂载仍可能发起请求。

### 索引级加载缓存：记录状态，但不保存广告实例

案例组件用静态 `Map<int, bool>` 记录索引是否加载成功。滚动停止后检查时，成功标记可以跳过再次加载；但 item 被回收、组件重新创建后，新的 State 没有广告实例，即使缓存标记为成功，恢复流程仍会重新创建并加载广告。`ValueKey('ad_$index')` 有助于标识同一位置，不能让已销毁的广告实例复活。失败时标记为 false，后续滚动停止检查可以重试；缓存类提供了清空方法。

### 三态占位与"失败即折叠"

| 状态 | 渲染 | 高度 |
|---|---|---|
| 滚动中 / 加载中 / 兜底 | shimmer 占位 | 预留固定高度 |
| 加载成功 | 真实广告 Widget | 展示回调后取真实尺寸，动画过渡 |
| 失败 / 被关闭 | 空 Widget | **折叠为 0** |

"失败即折叠"是容易被忽略的细节：加载失败的广告位如果保留占位高度，用户会看到一条永久的空白缝——组件不仅折叠自身，外边距也只在加载成功时才生效。广告失败率是常态（某联盟无库存很常见），列表的视觉密度不能被它拖垮。

### 挂载时序组件化 + 曝光上报

案例组件收到 `onAdLoaded` 后，还会等待 SDK 的 `isReady()` 返回 true，才将 `isReady` 置位并构建 `NativeAdWidget`。因此它确实避免了加载前挂载，但**仍以 `isReady()` 作为挂载门槛**；若这次检查返回 false，当前分支不会置位，也没有立即安排重试，组件可能继续停留在占位状态。第七节的“数据就绪后挂载”是时序原则，不能据此称案例代码已避开 `isReady()` 的拦截风险。

插件的原生信息流 Widget 使用 `visibility_detector` 检测可见区域；业务侧没有在这个列表组件里另写曝光上报。它不能证明快速划过一定不产生曝光，也不能弥补首次挂载就可能请求广告的情况。

### 列表插入策略

```dart
ListView.builder(
  controller: _scrollController,   // 共享给广告组件做滚动判定
  itemCount: 10,
  itemBuilder: (context, index) {
    if (index == 2 || index == 6) { // 固定间隔插入广告位
      return ListNativeAdWidget(
        key: ValueKey('list_native_ad_$index'), // 稳定 key
        scrollController: _scrollController,
        listIndex: index,           // 对应索引级缓存
        height: 420.px,
      );
    }
    return const NormalListItem(index: index);
  },
);
```

三个要点：**固定间隔**（生产环境间隔通常由运营配置下发而非写死）、**稳定 ValueKey**（重建后缓存能对上号）、**共享 scrollController**（多个广告位共用一份滚动监听，不各自 attach）。

## 九、SDK 缺陷补丁与测试基建

### iOS Modal 场景：一行补丁的复盘

**Modal 页面上激励广告拉不起**
- 现象：普通页面拉激励广告正常；页面上已存在一个由 iOS `present` 弹出的 Modal 控制器时，激励广告无法展示。
- 后果：仅特定交互路径的用户命中，客服反馈零散，难以在测试环境稳定复现。
- 成因：插件把"当前展示的 VC"传给 SDK 用于 present 广告，其查找函数递归算出了正确的控制器（穿透 Navigation/TabBar/Modal 层级），**但最后一行返回了方法入参**——递归白算，SDK 拿到错误的展示控制器。
- 对策：本地插件一行补丁，返回递归结果而非入参。

补丁本身只有一行，**补丁管理的纪律比补丁更重要**：

1. **独立文档记录**：改动文件、改动行、验证状态、回退方式全部落档；
2. **升级核对清单**：SDK 升级时先对比新版该函数实现——上游已修则删补丁，未修且问题仍在则先在独立 demo 复现再与广告商确认，绝不机械套用；
3. **回归范围**：展示控制器的选择影响所有广告形态，补丁后必须覆盖普通页面、Modal、Navigation Push、广告关闭后原页面可操作、连续多次拉起无残留 VC 五个场景，不能只验激励。

### 广告专用测试页

接入广告 SDK 的第一件事不是写业务，是把每种形态的测试页跑通——开屏/激励/信息流/Banner/插屏各有独立的加载、展示、销毁按钮与状态流水。它是后续所有排坑的前置条件：第七节的时序问题、第八节的列表进阶、第九节的 Modal 问题，都是在测试页先稳定复现、再定位到根因的。

测试入口的两个约束：做成**悬浮按钮，release 构建自动隐藏**（`kReleaseMode` 判断）——既保证测试页永远可用，又不泄漏给线上用户；悬浮按钮只放在特定页面而不是全局 Overlay，避免遮挡所有页面。

## 十、常见错误与修正表

| 问题 | 业务后果 | 对策 |
|---|---|---|
| 审核期间展示广告 + 全量隐私采集 | 商店拒审 | 审核形态做成服务端开关，收紧采集项（第三节） |
| 初始化失败静默吞掉 | 一批用户广告全挂且无人知晓 | 失败上报服务端留痕，与日志对账 |
| 广告位 ID 散落硬编码 | 换广告位全局搜索替换，双平台漏改 | enum 集中管理，双平台成对声明（第三节） |
| 开屏兜底超时晚于加载启动 | 存在"既没展示也进不去"的窗口 | Timer 先行，onOpened 才解除，全部回调收敛到单出口（第四节） |
| 发奖以 onAdClosed 为准 | 用户没看完也发奖 | 以 onAdReward 为准，关闭只触发页面刷新（第五节） |
| 冷却基准取广告关闭时间 | 没看完关掉也刷新冷却 | 冷却基准在发奖成功时写入 |
| 同一广告位连续展示 | 联盟风控异常，填充下降甚至封位 | 多广告位轮换，真正展示才算消耗（第五节） |
| 错误处理只做用户提示 | 线上排障无据可查 | 用户文案层与日志层分离，日志带原始错误详情（第六节） |
| "先失败后成功"只清用户层 | 日志层多报失败，口径污染 | 成功收口时两层分别清理，上报条件与弹窗条件一致 |
| 对外激励接口无超时兜底 | 回调丢失时调用方永久挂起 | 超时熔断 + requestId 防串扰 + finish 幂等（第六节） |
| 超时阈值拍脑袋定 | 低端机慢加载被误判失败 | 依据线上分位数调整（案例从 8 秒调到 15 秒） |
| PlatformView 挂载早于数据就绪 | 加载成功但永不渲染，`creationParams` 不变不重建 | onLoaded 之后再挂载（第七节） |
| 列表组件中 `isReady()` 返回 false | 真实广告可能一直未挂载 | 当前源码没有在此分支立即重试，需核查恢复路径（第八节） |
| 列表首次挂载时快速滑动 | 首次请求仍可能在滚动中发出 | 现有 300ms 防抖只推迟滚动停止后的再次检查（第八节） |
| item 回收重建 | 已成功的索引仍可能重新请求 | 索引缓存不保存广告实例，重建会重新加载（第八节） |
| 失败广告位保留占位高度 | 列表出现永久空白缝 | 失败即折叠为 0，外边距仅成功时生效 |
| 本地插件改动不留记录 | 半年后没人敢升级 | 补丁清单文档 + 升级核对清单 + 五场景回归（第九节） |

## 十一、验收清单

| 场景 | 验收标准 |
|---|---|
| 审核形态开启 | 广告入口跳过或收敛，隐私采集项全部关闭；过审后恢复 |
| 初始化失败 | 有服务端留痕，可与后端日志对账 |
| 开屏各失败路径 | 加载慢/失败/展示失败/跳过，全部在有界时间内到达首页 |
| 开屏正常展示 | 兜底 Timer 在展示成功时解除，不误杀 |
| 激励完整观看 | onAdReward 触发发奖上报，冷却时间戳刷新 |
| 激励中途关闭 | 不发奖，不刷新冷却 |
| 无广告库存 | 错误弹窗文案来自服务端配置，日志带错误详情 |
| 先 error 后 reward | 失败弹窗被主动关闭，用户侧按成功收口 |
| 先 reward 后 error | 不弹失败弹窗 |
| 对外激励接口超时 | Future 在阈值时间内完成，不永久挂起 |
| 并发调用对外接口 | 回调不错配，无二次 complete 崩溃 |
| 原生信息流首次渲染 | onLoaded 后挂载，渲染成功 |
| 列表快速滑动 | 记录首次挂载是否发起请求；滚动停止约 300ms 后才进行再次检查 |
| 列表回收重建 | 核查已成功索引重新创建广告实例后的请求与展示，位置对应正确 |
| 信息流加载失败 | 广告位折叠为 0，无空白缝 |
| Modal 页面拉激励 | 各控制器层级下均可展示（补丁回归五场景） |
| release 构建 | 测试入口不可见 |

## 十二、面试问答

### Q1：为什么用聚合 SDK 而不是直接接穿山甲/优量汇？

单联盟填充率有天花板，无库存时请求直接浪费；聚合层做 Bidding（实时竞价）+ Waterfall（瀑布兜底）混调，填充率与综合 eCPM 都更优，还统一了多联盟的接入、数据与计费口径。追问：选型看什么？答：国内联盟覆盖、Flutter 插件完整度、后台数据能力；更深一层的决策是集成方式——本地插件换来补丁能力，代价是 fork 维护成本，要用补丁清单纪律对冲。

### Q2：激励视频的完整链路怎么设计？

前置三关卡（服务端资格校验做错误码分流、本地冷却以发奖成功为基准、免责弹窗做确认门）→ 多广告位轮换（防联盟风控、分摊无库存风险，真正展示才算消耗）→ 发奖以 onAdReward 为准（onAdClosed 可能没看完）→ 上报失败要暴露给用户（拉服务器时间拼提示）→ 页面刷新做成出口暴露给业务方而不是内置。加分项：对外 Future 化接口的超时熔断 + requestId 防串扰 + 幂等收口。

### Q3：广告的错误处理为什么要分两层？

用户可见层（服务端配置文案，运营可热更话术）与日志层（原始错误详情上报后端，排障用）关注点不同、清理时机也不同——"成功覆盖失败"必须两层分别评审，只清用户层会留下日志层的误报。能背出五场景错误弹窗矩阵（无广告弹、先 error 后 reward 主动关、先 reward 后 error 不弹、正常关闭不弹、中途 error 弹）是硬通货。

### Q4：原生信息流"加载成功但不渲染"怎么排查？

先分层（Dart widget / PlatformView / 原生渲染），日志定位到 onLoaded 到了但渲染回调不到；根因是 PlatformView 创建时机早于数据就绪，且 creationParams 不变不重建、原生空指针被框架吞掉。修复是把挂载推迟到 onLoaded。追问：为什么 Banner 不受影响？答：Banner 的原生渲染不依赖广告数据，SDK 加载完自己渲染进空容器；信息流必须拿到数据才能绑定视图，时序不可逆。通用化：依赖异步数据的 PlatformView 都适用"数据就绪再创建"。

### Q5：广告 SDK 出 bug 怎么办？

本地插件化是前提——一行补丁当天解决（iOS Modal 场景 VC 查找返回错值的例子）；配套纪律是独立文档记录改动与回退方式、升级时先对比上游实现（已修删补丁、未修先 demo 复现）、按五场景回归（展示控制器影响所有广告形态）。没有本地插件就只能等官方排期。

### Q6：审核与合规在广告侧怎么做？

审核形态是服务端开关——审核期跳过开屏等广告、通过 setCustomDevice 收紧应用列表/定位/OAID/IDFA 等采集项；初始化失败上报留痕；错误文案走服务端配置。再展开：广告类 App 的合规清单还包括隐私政策披露广告 SDK、个性化推荐关闭开关、未成年人保护，这些与商店审核的高频拒审点直接对应。

### Q7：信息流广告嵌进列表，你会做哪些优化？

按案例实现回答要说明五点及其边界：首次挂载立即尝试加载，300ms 防抖用于滚动停止后的再次检查；索引缓存只记录成功状态，item 回收重建后仍会重新加载；加载中显示占位、失败时折叠、展示后按实际尺寸过渡；`onAdLoaded` 后还要等 `isReady()` 为 true 才挂载，返回 false 时可能停留在占位；插件使用可见性检测，但不能仅据此断言快速划过一定没有曝光。
