# 第三方广告

> 广告是免费 App 最常见的变现方式，但广告接入不是"加个 SDK 就能赚钱"——广告类型选择、聚合策略、加载优化、作弊防控、隐私合规，每一环都影响最终收益。本篇从架构师视角拆解广告变现的工程决策。

---

## 概述：第三方广告解决什么问题？

广告变现的核心问题是：**在用户体验和商业收益之间找到平衡点。** 这不是一个纯技术问题，而是一个产品+技术+合规的综合工程问题。

技术层面的核心挑战：

1. **SDK 碎片化**：国内三大广告联盟（穿山甲、优量汇、快手）各有 SDK，接口不统一
2. **广告类型多**：开屏、激励视频、插屏、Banner、信息流——每种类型的加载策略和缓存机制不同
3. **eCPM 波动大**：同一广告位在不同时段、不同联盟的收益差异可达 3-5 倍
4. **合规风险**：隐私声明、SDK 列表披露、IDFA/GAID 获取权限，违规即下架
5. **作弊与刷量**：激励视频是作弊重灾区，不加防控等于白烧预算

## 核心内容

### 1. 国内主流广告联盟：穿山甲/优量汇/快手

#### 三大联盟对比

| 维度 | 穿山甲（字节跳动） | 优量汇（腾讯） | 快手联盟 |
|------|-----------------|-------------|---------|
| 市场份额 | ~35% | ~30% | ~20% |
| eCPM 水平 | 高（抖音流量池） | 中高（微信/QQ 流量池） | 中（短视频流量池） |
| 填充率 | 高 | 高 | 中 |
| 广告素材质量 | 高（短视频为主） | 中高 | 高（短视频为主） |
| 激励视频支持 | 成熟 | 成熟 | 成熟 |
| SDK 体积 | ~3MB | ~2.5MB | ~2MB |
| 审核门槛 | 需备案 | 需备案 | 需备案 |
| 隐私合规 | 较严格 | 较严格 | 较严格 |

#### 为什么不只接一家？

1. **填充率**：单一联盟的填充率通常 85-95%，多家聚合可达 98%+，剩余流量不浪费
2. **eCPM 竞价**：不同联盟对同一用户的竞价不同，聚合后可以选最高的
3. **风险分散**：单一联盟封号/降权会导致收入归零
4. **素材多样性**：不同联盟的广告素材库不同，避免用户审美疲劳

**不接聚合会怎样？** 单一联盟的 eCPM 通常比聚合低 20-40%，因为无法跨联盟竞价。

### 2. 聚合 SDK 方案：AdMob / TopOn / 穿山甲 GroMore

#### 聚合 SDK 解决什么问题？

聚合 SDK 的核心价值是**统一广告请求接口 + 跨联盟竞价**：

```
┌─────────────────────────────────┐
│        App 广告请求              │
├─────────────────────────────────┤
│        聚合 SDK（TopOn/GroMore） │
│   Waterfall / Bidding 竞价逻辑    │
├──────┬──────┬──────┬─────────────┤
│穿山甲 │优量汇│ 快手 │ AdMob(海外) │
└──────┴──────┴──────┴─────────────┘
```

#### 聚合方案对比

| 方案 | 类型 | 竞价方式 | 国内支持 | 海外支持 | 费用 |
|------|------|---------|---------|---------|------|
| AdMob | Google 自家聚合 | Waterfall + Bidding | 弱（需翻墙） | 强 | 免费（Google 抽成） |
| TopOn | 第三方聚合 | Waterfall + Bidding | 强 | 强 | 免费版/付费版 |
| 穿山甲 GroMore | 字节自研聚合 | Waterfall + Bidding | 强 | 弱 | 免费 |
| Mintegral | 汇量科技 | Waterfall + Bidding | 中 | 强 | 免费 |
| ironSource | Unity 旗下 | Waterfall + Bidding | 弱 | 强 | 免费 |

#### Waterfall vs Bidding

**Waterfall（瀑布流）**：传统方式，按 eCPM 历史数据排优先级，依次请求

```
请求广告 → 穿山甲(eCPM预估 ¥80) → 失败
        → 优量汇(eCPM预估 ¥60) → 成功 → 返回广告
```

- 简单可靠，但依赖历史数据，无法实时反映当前竞价
- 排序靠后的联盟可能永远拿不到请求

**Bidding（竞价）**：实时竞价，所有联盟同时出价，选最高的

```
请求广告 → 穿山甲出价 ¥75
        → 优量汇出价 ¥90
        → 快手出价 ¥65
        → 选优量汇 → 返回广告
```

- eCPM 通常比 Waterfall 高 15-30%
- 但并非所有联盟都支持 Bidding，通常 Waterfall + Bidding 混合使用

#### 选型决策

| 场景 | 推荐方案 | 原因 |
|------|---------|------|
| 纯国内 App | TopOn 或 GroMore | 国内联盟支持好 |
| 国内 + 海外 | TopOn | 同时支持国内外联盟 |
| 纯海外 App | AdMob | Google 生态整合最好 |
| 追求极致 eCPM | TopOn + Bidding | 实时竞价收益最高 |

### 3. 广告类型：开屏/激励视频/插屏/Banner/信息流

#### 类型对比

| 类型 | eCPM | 用户体验影响 | 适用场景 | 加载时机 |
|------|------|------------|---------|---------|
| 开屏 | 高 | 低（等待时间短） | App 启动 | App 启动时预加载 |
| 激励视频 | 最高 | 低（用户主动看） | 获取金币/复活/解锁 | 用户触发前预加载 |
| 插屏 | 中高 | 中（打断流程） | 关卡切换/页面跳转 | 切换前预加载 |
| Banner | 低 | 中（占屏幕空间） | 页面底部/顶部 | 页面加载时 |
| 信息流 | 中 | 低（融入内容） | 列表中穿插 | 滚动到可见前预加载 |

#### 各类型的架构考量

**开屏广告**：
- 必须在 App 启动时立即可见，加载时间直接影响冷启动体验
- 预加载方案：上一次 App 退出时缓存开屏广告素材
- 超时策略：广告加载超过 2 秒直接跳过，不阻塞用户

```dart
class SplashAdManager {
  /// 预缓存开屏广告（App 上次退出时调用）
  Future<void> precacheSplashAd() async {
    await _adService.loadSplashAd(adSlotId: _splashSlotId);
  }

  /// 展示开屏广告（App 启动时调用）
  Future<void> showSplashAd({Duration timeout = const Duration(seconds: 2)}) async {
    final result = await _adService.showSplashAd(
      adSlotId: _splashSlotId,
      timeout: timeout,
    );
    if (!result.shown) {
      // 超时未展示，直接进入首页
      _navigateToHome();
    }
  }
}
```

**激励视频**：
- eCPM 最高，但也是作弊重灾区
- 服务端验证回调是必须的，客户端回调不可信
- 播放过程中不能跳过，需要完整观看才能获得奖励

**插屏广告**：
- 展示频率控制是关键：同一用户 X 分钟内最多展示 Y 次
- 展示场景选择：页面切换时是自然断点，用户体验影响较小

### 4. 广告加载策略与缓存

#### 为什么预加载很重要？

广告加载是网络请求，耗时 200ms-2s 不等。如果等到用户需要看广告时才开始加载，用户会看到白屏/loading，体验极差。

#### 缓存策略

```
┌────────────────────────────────────────┐
│              广告缓存管理器              │
├────────────────────────────────────────┤
│  策略1：提前加载                        │
│  - 激励视频：用户进入相关页面时预加载      │
│  - 插屏广告：页面切换前 1 秒预加载        │
│  - 信息流广告：滚动到可视区域前 2 条预加载 │
│                                        │
│  策略2：缓存池                          │
│  - 维护 N 个已加载的广告对象              │
│  - 展示一个后立即补充加载一个             │
│  - 广告过期时间通常 1-4 小时，过期需重新加载│
│                                        │
│  策略3：降级                            │
│  - 聚合 SDK 加载失败 → fallback 直连联盟  │
│  - 所有广告加载失败 → 展示本地占位图       │
└────────────────────────────────────────┘
```

```dart
/// 广告缓存池
class AdPool<T> {
  final _pool = <T>[];
  final int maxSize;
  final Future<T?> Function() loader;

  AdPool({required this.maxSize, required this.loader});

  /// 获取广告
  T? get() {
    if (_pool.isEmpty) return null;
    final ad = _pool.removeAt(0);
    // 取出一个后立即补充
    _refill();
    return ad;
  }

  /// 预加载填充
  Future<void> preload() async {
    while (_pool.length < maxSize) {
      final ad = await loader();
      if (ad != null) {
        _pool.add(ad);
      } else {
        break; // 加载失败，不再重试
      }
    }
  }

  void _refill() {
    preload(); // 异步补充
  }
}
```

#### 广告过期处理

广告对象有有效期（通常 1-4 小时），过期后展示无效或计费异常。缓存池需要定期清理过期广告：

```dart
Timer? _cleanupTimer;

void startCleanup() {
  _cleanupTimer = Timer.periodic(const Duration(minutes: 30), (_) {
    _pool.removeWhere((ad) => _isExpired(ad));
    preload(); // 清理后补充
  });
}
```

### 5. 广告收益优化（eCPM）

#### 什么是 eCPM？

eCPM（effective Cost Per Mille）= 每千次广告展示的收益。计算公式：

```
eCPM = 总收益 / 展示次数 × 1000
```

eCPM 是衡量广告变现效率的核心指标。

#### 优化手段

**1. Waterfall 排序优化**

传统做法是按历史 eCPM 排序，但历史数据不能反映当前时刻的真实竞价。优化方案：

- 按 COUNTRY × AD_TYPE × HOUR 维度统计 eCPM，分时段调整排序
- 工作日白天 eCPM 高，深夜 eCPM 低——时段排序应该不同
- 新联盟没有历史数据时，先放中间位置试探，再根据实际数据调整

**2. Bidding 比例提升**

逐步提升 Bidding 在 Waterfall 中的占比。Bidding 通常比 Waterfall 的 eCPM 高 15-30%，因为实时竞价反映真实市场价。

**3. 广告场景优化**

| 优化点 | 说明 |
|--------|------|
| 展示时机 | 用户自然停留点展示，不要强制弹出 |
| 展示频率 | 同一用户同一天看太多广告，后续 eCPM 下降 |
| 广告位数量 | 广告位不是越多越好，稀释单广告位的展示量会降低竞价竞争力 |
| 用户分群 | 付费用户少看广告，免费用户适当增加 |

**4. 流量分组**

将用户按价值分组，不同组展示不同策略：

```dart
class AdStrategyManager {
  AdStrategy getStrategy(UserProfile user) {
    if (user.isPayingUser) {
      return AdStrategy.minimal; // 付费用户少打扰
    }
    if (user.dailyAdViews < 10) {
      return AdStrategy.standard;
    }
    return AdStrategy.reduced; // 已看很多广告的用户降频
  }
}
```

### 6. 隐私合规与 SDK 声明

#### 为什么合规这么重要？

2021 年工信部开始专项整治，违规收集个人信息、超范围索取权限的 App 直接下架。广告 SDK 是合规风险的重灾区——它们默认收集设备信息、行为数据用于定向投放。

#### 核心合规要求

**1. 隐私政策**

- App 首次启动必须展示隐私政策，用户同意后才能初始化广告 SDK
- 隐私政策中必须列出所有第三方 SDK 及其收集的信息类型
- 用户可以选择"不同意"并继续使用（非核心功能不可强制同意）

```dart
// 合规的 SDK 初始化顺序
class AppInit {
  Future<void> init() async {
    // 1. 先展示隐私政策
    final agreed = await _showPrivacyPolicy();
    if (!agreed) {
      // 用户拒绝，不初始化广告 SDK，仅保留核心功能
      return;
    }

    // 2. 同意后初始化广告 SDK
    await _initAdSDKs();
  }
}
```

**2. IDFA/GAID 声明**

- [iOS] ATT（App Tracking Transparency）：获取 IDFA 前必须展示 ATT 弹窗，用户拒绝后不能追踪
- [Android] GAID（Google Advertising ID）：需在隐私政策中声明用途
- 国内 Android 的 OAID（移动安全联盟统一标识）同样需要声明

**3. SDK 列表管理**

| 需要声明的信息 | 说明 |
|--------------|------|
| SDK 名称 | 如"穿山甲广告 SDK" |
| SDK 提供者 | 如"北京巨量引擎网络技术有限公司" |
| 收集的信息类型 | 设备信息、位置、应用列表等 |
| 使用目的 | 广告投放、数据分析 |
| 隐私政策链接 | SDK 提供者的隐私政策 URL |

**4. 儿童隐私保护**

如果 App 有未成年人用户（游戏、教育类），需要额外遵守《儿童个人信息网络保护规定》：
- 14 岁以下用户需监护人同意
- 不得向儿童推送定向广告
- 不得收集儿童的精确定位

## 常见坑与踩点

### 坑1：广告 SDK 初始化时机

广告 SDK 必须在用户同意隐私政策后才能初始化。如果在 `Application.onCreate()` 中无条件初始化，会被审核判定为"未获同意即收集信息"。正确做法是先展示隐私弹窗，同意后再初始化。

### 坑2：激励视频作弊

客户端回调 `onRewardVerify()` 可以被 hook，攻击者可以不看广告直接领取奖励。必须做服务端验证回调（S2S Callback），广告平台在用户完整观看后回调你的服务端，服务端验证通过后再发放奖励。

### 坑3：开屏广告影响冷启动

开屏广告加载时间与冷启动时间叠加，用户感知就是"App 启动特别慢"。最佳实践是开屏广告与 App 初始化并行，广告超时（2 秒）则跳过。

### 坑4：多个广告 SDK 冲突

穿山甲、优量汇、快手三家 SDK 可能依赖相同的三方库（如 `okhttp`、`gson`）但版本不同，导致编译冲突。使用聚合 SDK（TopOn/GroMore）可以缓解，但无法完全避免——需要在 `build.gradle` 中强制统一版本。

### 坑5：iOS 审核与广告

[iOS] App Store 对广告有严格要求：
- 不能在 App 启动图位置展示广告（会被拒审）
- 儿童类 App 不得展示广告
- 广告必须有明显的"广告"标识
- 不能在系统通知中展示广告

## 面试追问

###  聚合 SDK 解决什么问题？

聚合 SDK 解决三个核心问题：1) 统一接口——一次集成即可请求多家联盟的广告，不需要逐个对接 SDK；2) 竞价优化——通过 Waterfall/Bidding 机制选择 eCPM 最高的联盟，提升收益；3) 填充率——一家联盟填充失败时自动 fallback 到下一家，减少流量浪费。不接聚合的话，需要自己管理多 SDK 的初始化、缓存、降级逻辑，维护成本极高。

###  激励视频的作弊防控怎么做？

客户端回调不可信，必须做服务端验证。流程是：用户观看激励视频 → 广告平台验证完整观看 → 广告平台回调业务服务端（S2S Callback）→ 服务端验证签名+回调来源 → 发放奖励。客户端的 `onRewardVerify` 只用于 UI 反馈，不能作为发奖依据。还需要做回调去重（同一 callback_id 不重复发奖）和频率限制（同一用户单位时间内最大发奖次数）。

###  Waterfall 和 Bidding 有什么区别？为什么不全部用 Bidding？

Waterfall 按历史 eCPM 排序，依次请求各联盟，实现简单但不够实时；Bidding 让所有联盟实时出价，选最高的，eCPM 更高。不全用 Bidding 的原因：1) 不是所有联盟都支持 Bidding（特别是国内的中小联盟）；2) Bidding 有超时风险，实时竞价如果超时会浪费展示机会；3) Waterfall 对弱网环境更友好。通常的做法是支持 Bidding 的联盟走 Bidding，不支持走 Waterfall，两者混合。

###  广告加载策略怎么设计？如何平衡预加载和内存占用？

核心策略是"提前加载 + 缓存池 + 过期清理"。激励视频等高 eCPM 广告提前预加载 1-2 个存入缓存池，展示一个后立即补充一个。信息流广告在滚动到可视区域前预加载。缓存池需要定期清理过期广告（通常 1-4 小时有效期）。内存方面，图片/视频素材由 SDK 内部管理，开发者主要控制缓存池大小——激励视频缓存不超过 2 个，开屏广告缓存 1 个即可。

###  从零搭建广告变现体系，你会怎么规划？

1. **选型**：根据目标市场选聚合 SDK（国内 TopOn/GroMore，海外 AdMob），接入 2-3 家主力联盟
2. **广告位规划**：根据产品形态决定广告类型和展示场景，优先上激励视频（eCPM 最高）和开屏广告（体验影响最小）
3. **合规先行**：先过隐私合规再上广告——隐私政策、ATT 弹窗、SDK 声明
4. **技术架构**：Flutter 侧统一 `AdService` 抽象层，各广告类型独立管理器（`RewardedAdManager`、`SplashAdManager` 等），缓存池管理预加载和过期清理
5. **收益优化**：先跑 Waterfall 积累数据，再逐步开启 Bidding；按时段/地区调整 Waterfall 排序；流量分组策略区分付费用户和免费用户
6. **防作弊**：激励视频全部走服务端回调验证，客户端回调仅用于 UI；对异常点击/展示频率做风控
