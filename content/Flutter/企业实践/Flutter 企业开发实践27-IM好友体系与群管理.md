# IM 好友体系与群管理

25 篇讲消息怎么接进来、怎么收发，26 篇讲谁在登录、连不稳怎么办，28 篇讲带资金状态的自定义消息怎么做。这篇讲夹在中间、最难对齐的那一层：关系怎么建立、群怎么治理、权限落在哪一层、本地状态过期了怎么办。

加好友是一次请求，建群也是一次请求。真正要设计的是另外三件事：谁有资格做这件事，各端多久才一致，被拒绝时看到什么。

---

## 一、先把关系链和群治理的全景看清楚

结论：好友体系这边业务复杂度低，成熟组件就能覆盖住；群体系那边复杂度高，靠的是权限治理。两块的做法不一样，也就是说，混在一起谈肯定失焦。

先把术语固定下来，全文都按这个含义走：

| 术语 | 含义 | 真值在谁那里 |
|---|---|---|
| 业务用户 ID | 业务系统内的数字身份 | 业务服务端 |
| IM userID | 聊天服务内的身份，决定会话 ID 的拼装 | 业务服务端下发，IM 服务校验 |
| 关系链 | 好友、好友申请、备注、黑名单 | IM 服务 |
| 会话 | 一次对话对应一个会话，单聊与群聊各一个 | IM 服务，客户端只有缓存 |
| 群成员角色 | 群主 / 管理员 / 普通成员，决定能力上限 | IM 服务 |
| 群类型 | 建群时确定，决定加群方式、禁言能力、解散与转让条件 | IM 服务 |

页面和入口长这样：

```text
会话列表
 ├─ 顶部搜索 ──────────→ 统一搜索（会话 / 联系人 / 群组 / 群成员 / 历史消息）
 ├─ 通讯录 ───────────→ 新的朋友 / 我的群聊 / 黑名单 / 好友项 → 用户详情
 └─ 更多 ────────────→ 发起会话 / 扫一扫 / 创建群聊 / 添加好友 / 添加群聊

群聊页
 ├─ 更多 ────────────→ 群资料
 ├─ 群头像 ──────────→ 群成员资料（带"来自群内"标记）
 └─ 入群申请横幅 ────→ 入群申请列表

群资料页
 ├─ 组件能力：群管理（管理员 / 全员禁言 / 成员禁言）、加群与邀请方式、免打扰、置顶、群公告、群昵称、清空 / 退出 / 解散 / 转让
 └─ 业务叠加：群二维码、举报、成员列表、删除成员

用户详情页：组件能力为备注名 / 免打扰 / 置顶 / 加入黑名单，业务叠加为举报 / 发送消息 / 清空聊天记录 / 删除好友
```

按职责切成三层：**关系链层**（好友申请、通讯录、黑名单、备注名）、**群治理层**（建群、进群方式、成员、角色、禁言）、**状态同步层**（未读、成员列表、权限判定，横向穿过所有页面）。

**权限矩阵的每一行都得回答两个问题：入口在哪（客户端），服务端拦不拦得住（IM 服务）。** 案例对"建立新关系"额外加了一道门禁，这属于产品选择；"权限必须有两个落点"才是通用要求。

## 二、入口门禁：建立关系和发起会话，管的不是同一件事

结论：门禁是按"行为风险"分层的，不按页面分层。建立新关系、修改群状态、调用硬件能力，这三件事的性质完全不同。

| 层 | 拦什么 | 案例中的表现 | 性质 |
|---|---|---|---|
| 业务活跃度 | 能不能用 IM 能力 | 未完成当日签到不建立 IM 连接，会话列表被遮罩 | 产品选择 |
| 身份资格 | 能不能建立新关系 | 扫一扫、创建群聊、添加好友、添加群聊要求已实名 | 产品选择，思路可迁移 |
| 设备能力 | 能不能调硬件 | 扫码需要相机与相册权限 | 通用 |

第一层属于连接治理：案例把 IM 登录和每日签到绑在一起，签到状态决定要不要建立连接，实现见 26 篇《IM 登录身份与连接治理》。这里只强调一点：**签到管的是"能不能连上"，实名管的是"能不能建立关系"。** UI 遮罩只认签到状态，别把连接状态做成业务遮罩，不然网络一抖，用户就以为自己被禁用了。

第二层的关键是判定"哪些操作要求实名"：

| 操作 | 要求实名 | 理由 |
|---|---|---|
| 发起会话（已有好友） | 否 | 不产生新的关系链 |
| 添加好友 | 是 | 直接建立新关系 |
| 创建群聊 | 是 | 建立一个新社交实体 |
| 添加群聊 / 扫一扫 | 是 | 可能把陌生人变成关系链 |

反馈顺序固定成先提示、再跳转（"请先进行实名"，确认后才进实名页）。直接静默跳页，用户会反复点同一个入口。

第三层是设备权限：案例把所有权限申请收口到一套封装里，IM 初始化的时候再注入 UI 组件库，这样组件内部申请麦克风、相册也走同一套交互。通用要求是**设备权限只能有一套交互**，不然同一件事在不同页面会长出不同话术。

三层门禁按固定顺序查：签到 → 实名 → 设备权限，任何一层不通过就直接返回。

过了门禁才轮到扫码。扫码的本质是协议分发，案例的二维码装两种内容：业务分享链接（http/https，带邀请码参数），以及群二维码自定义协议 `groupqr;<群ID>;<群主ID>`：

```text
扫码 → 权限校验 → 取内容
  ├─ http(s)://…?info=邀请码 → 查用户 → 是本人？→ 提示"不可以添加本人" / 进入用户详情
  ├─ groupqr;<群ID>;<群主ID> → 校验分段数量 → 进入添加群聊页
  └─ 其他内容 → 提示"请扫描正确的邀请码"
```

协议设计守住三点：**先校验分段数量，再取下标**；用前缀白名单限定能处理的内容，未知内容落到统一提示；扫码拿到的身份先跟本人比对，免得给自己发好友申请。

- **现象**：扫到分段不完整的二维码，客户端直接拿第二段当群 ID，轻则进错页面，重则解析异常。
- **后果**：用户被带到毫不相关的页面，或者干脆看到白屏。这类事故线下必现，线上很难复现。
- **成因**：把自己生成的协议当成"一定合法"，默认每个字段都在。
- **对策**：分发之前先做前缀白名单和分段校验；协议一旦印进二维码就改不动了，要演进只能新增前缀或者加版本段。

## 三、好友申请、通讯录和未读状态

结论：好友申请未读是单独一条数据线。它属于关系链，不属于会话未读，不能并进总未读一起算。

| 层级 | 数据来源 | 展示位置 | 清零时机 |
|---|---|---|---|
| 总未读 | 会话未读数（首次查询 + 增量回调），不含免打扰会话 | 会话入口角标，超过 999 显示 999+ | 阅读会话 |
| 好友申请 | 两种口径：SDK 的申请未读字段，或"入站待处理申请数" | 通讯录入口与"新的朋友"红点 | 显式标记已读，或申请被处理 |
| 底部 Tab 红点 | 布尔值：总未读 > 0 或 好友申请数 > 0 | Tab 上的小红点，只有点没有数字 | 两者都为 0 |

"好友申请未读"是这一节最容易含混的地方，它其实是两个不同的数：

- **未读字段**：SDK 单独给了"标记好友申请已读"的接口，这个字段得靠**显式调用**才清零，它不会"处理完申请自动归零"。
- **待处理申请数**：入站申请列表的长度，收到一条加一，被处理掉一条减一。

两处红点取不同来源，就会出现"已读但还没处理"的窗口里两个红点对不上：业务侧自己读未读字段，UI 组件库里"新的朋友"的红点取的却是入站申请列表长度。所以产品语义得先定：要"处理完才消点"就以待处理数为准，要"看过就消"就用未读字段并显式标记已读。定完了再选数据源，别声称"处理申请会自动清零未读"。

另外两点一样要紧：**首次查询兜底 + 增量事件刷新**（冷启动先查一次当基线，之后靠"收到申请、申请被删除、好友列表新增"这类事件重查）；**只有别人发给我、我还没处理的申请才该计入**，自己发出去的申请不计数。

- **现象**：红点没了，列表里却还有没处理的申请；或者申请都处理完了，红点还挂着，重进页面才更新。
- **后果**：用户以为申请都处理完了，白白错过好友申请；红点长期挂着就成了"红点疲劳"，之后所有红点都被无视。
- **成因**：把"未读字段"和"待处理数"当成同一个数，两处红点各取一个来源；或者客户端自己维护了一份"是不是读过"的状态，跟 IM 服务返回的字段打架。
- **对策**：先定产品语义（看过就消 / 处理完才消），再统一数据源；自己维护的状态一律不写，要清零就显式调标记已读接口，然后重查。

## 四、成熟组件和自研页面怎么共存

结论：选择标准就两条：组件有没有给出扩展点，业务语义有没有超出关系链的通用语义。

| 策略 | 适用场景 | 案例中的页面 | 成本 |
|---|---|---|---|
| 直接复用 | 交互与业务语义完全一致 | 通讯录、添加好友、新的朋友、黑名单 | 接线成本（路由、空态、红点） |
| 能力槽扩展 | 页面通用，但需要插入业务按钮或调整区块顺序 | 用户详情页 | 需要理解组件的插槽模型 |
| 自研页面 | 组件不提供的能力，或排序、权限有差异 | 成员列表、删除成员、创建群设置页 | 全量维护，SDK 升级要回归验证 |

**直接复用**的页面只接三件事：点击之后去哪、空态换成什么、红点绑哪个值。案例里这几个页面几乎没写业务代码，这本身就说明关系链交互已经标准化了。

**能力槽扩展**的典型是用户详情页：备注名、免打扰、置顶、加入黑名单这些通用能力交给组件；举报、发送消息、清空聊天记录、删除好友走自定义插槽插进去，区块顺序由业务说了算。有两个细节值得抄：区块顺序用业务语言来定（先身份卡片，再关系链开关，最后危险操作）；举报用一个接口加对象类型字段来区分对象，进页面之前先比对身份，自己不能举报自己。

**自研页面**接的是组件给不了的能力：成员列表的分组、拼音索引和服务端搜索，删除成员的受限数据源和批量上限，建群设置页的群 ID 和群类型。代价是 SDK 一升级，这些全都得重新验证。

用户详情页里还有两处关系链细节。一是**不可逆操作的确认**：清空聊天记录、删除好友必须二次确认，文案把连带影响写清楚（删除好友会同时清空聊天记录）；失败时回显服务端的错误描述，不要笼统地甩一句"操作失败"。二是**进聊天页之前的导航栈收敛**：

- **现象**：用户从"扫一扫 → 用户详情 → 发送消息"或者"群成员列表 → 用户详情 → 发送消息"进聊天页，返回时一层层退回扫码页、成员列表，连着按返回能退十几层。
- **后果**：返回路径不可控，用户找不到会话列表，深层页面还可能被重复触发请求。
- **成因**：进终态页面时用压栈的方式打开，中间页没有收敛。
- **对策**：进聊天页之前只保留白名单页（Tab 容器、会话列表），其余中间页移除，再用替换的方式打开聊天页。这样不管从哪个入口进来，返回都落在会话列表。

最后是一个产品选择：**群内加好友暂不开放**。群成员之间是弱关系，进一次群就能拿到完整成员名单，"群内一键加好友"等于给批量骚扰开了个入口。能迁移的原则是：**开放批量建立关系的路径之前，先想清楚频控和审核放在哪一层**。事后再补频控，成本比一开始就关掉入口高得多。

## 五、建群、进群和系统提示消息

结论：创建成功的回调只证明"群已经存在"，不证明客户端已经进入可用状态。从创建到能聊天，中间还有三件事要补：会话、提示消息、治理默认值。

另一种做法是让服务端生成群 ID：省掉了唯一性处理，但系统 ID 带固定前缀，展示和传播的体验差。案例选择客户端随机生成 12 位大写字母数字，因为群 ID 要展示在群资料页，还会写进群二维码，可读性直接决定传播成本。这属于产品选择，通用原则是：**会被用户复制、传播的标识，要么短而可读且稳定，要么干脆不在 UI 暴露。** 群 ID 还有长度和字符集约束，超限就直接创建失败，生成规则得按当前官方文档兜住。

**群类型在创建时就锁死了。** 群类型决定加群和邀请方式、成员禁言能力、解散和转让条件，案例在设置页点群类型只回一句"群类型无法修改"。通用原则：类型是治理模型的一部分，创建后不可变；真要变更，那是一次"迁移"，不是改一个字段。

创建群时还得显式映射被邀请成员的角色：角色在接口层是整数常量，到对象层是枚举，两套类型并存，最容易出现强解包取值。**现象**是被邀请成员资料拉取失败、或者角色为空时，创建群流程直接崩，而且崩的位置离数据来源很远；**后果**是用户点了"创建"没反应，群也没建出来；**成因**是双重强解包（先取资料再取角色），又拿服务端整数做枚举数组下标，把"外部数据一定齐全"当成了前提；**对策**是显式映射已知常量，未知值落到"普通成员"的兜底分支，不用数组下标取枚举，也不用强解包。

创建成功后的动作可以画成这样：

```text
用户      → 客户端     : 选好友、填群名、点创建
客户端    → IM 服务    : 创建群（指定群 ID、群类型、成员列表）
IM 服务   → 客户端     : 成功 + 群 ID
客户端    → IM 服务    : 按会话 ID 查询新群会话
IM 服务   → 客户端     : 返回会话对象 / 查不到
客户端                 : 查不到就本地构造最小可用会话（群 ID、类型、展示名）
客户端    → IM 服务    : 发送"创建群组"自定义消息（居中提示）
客户端                 : 移除选好友页 → 以替换方式打开聊天页
客户端    → IM 服务    : 把"邀请进群方式"改为管理员审批
```

这里面会话兜底值得单独展开说：

- **现象**：建群成功后进聊天页，标题是空的、消息列表也是空的，退出去再进才正常。
- **后果**：用户以为建群失败了，反复建同一个群，群里多出一堆同名空群，运营侧还得清理。
- **成因**：本地会话对象是同步事件驱动的，创建回调返回的时候它可能还没到。
- **对策**：创建成功后主动查一次会话，查不到就用已知信息构造一个最小可用会话对象（会话 ID、会话类型、群 ID、展示名）先进入，等同步到了再由组件刷新。其他进群路径（贴群 ID、扫群二维码、从"我加入的群"进入）也一样，都得在进页面之前把会话对象准备好；"我加入的群"还要用过滤器排除讨论组这类不属于"群"定义的会话。

**邀请进群方式默认管理员审批**同样是个产品选择：免得群刚建好就被人随便往里拉人。能迁移的原则是**默认值应该落在安全一侧，放宽权限必须是显式操作**。

最后是提示消息。案例在建群成功后往新群发一条 `group_create` 自定义消息，渲染成居中提示（"某某 创建群组"），操作人昵称取不到时退化成显示 userID。这样新成员（包括后来加进来的）都能在消息流里看到"谁创建了这个群"。但它和红包那类虽然都叫自定义消息，却完全不是一个物种：

| 维度 | 无状态操作提示（这篇） | 有状态业务消息（见 28 篇） |
|---|---|---|
| 事件来源 | 客户端直接构造并发送 | 业务服务端先产生业务实体，再投递卡片 |
| 服务端是不是真值 | 不是，纯展示 | 是，卡片只是快照 |
| 要不要版本与幂等 | 不需要 | 需要 |
| 失败处理 | 失败只影响这条提示 | 失败要补偿与对账 |
| 渲染形态 | 居中提示文案 | 可交互卡片 + 状态角标 |

判断标准就一句话：**这条消息背后有没有一个"多端必须一致"的状态。** 有，就按 28 篇《IM 自定义消息与红包》那套协议设计；没有，就用这篇这种最轻的模式。

## 六、成员列表：角色分组、分页、排序、搜索、删除

结论：成员列表的复杂度来自两类数据形态：角色类数据少而稳定，普通成员多而且一直在变。所以必须分开取、分开分页，再到客户端合并排序。

| 批次 | 过滤条件 | 规模 | 分页 |
|---|---|---|---|
| 群主 | 角色过滤 | 1 个 | 一次 100 条足够 |
| 管理员 | 角色过滤 | 上限 10 | 同上 |
| 普通成员 | 角色过滤 | 可达数百到上千 | 只能游标分页 |

不能图省事一次拉全量普通成员：只拉普通成员，"群主与管理员置顶"就没了数据来源。

游标分页这一块，麻烦的地方就是结束信号，它也是最容易写错的地方。IM 服务约定首次请求传 `"0"`，之后原样回传上一次返回的游标，**直到某次返回 `"0"` 才算拉完**。结束信号是 `"0"`，不是空字符串，也不是空值：

```dart
typedef MemberPage = ({List<String> memberIds, String nextSeq});

/// [fetchPage] 由调用方提供：按游标向 IM 服务要一页成员。
Future<List<String>> loadAllMembers(
  Future<MemberPage> Function(String cursor) fetchPage,
) async {
  final all = <String>[];
  var cursor = '0'; // 首次请求固定用 "0"
  while (true) {
    final page = await fetchPage(cursor);
    all.addAll(page.memberIds);
    cursor = page.nextSeq;
    if (cursor == '0') break; // 结束信号是 "0"，不是空串
  }
  return all;
}
```

- **现象**：千人群滚到底部一直卡在"加载中"，或者成员列表到几十人就断了。
- **后果**：成员搜不到、管理员看不到完整名单、删除成员页漏人，用户看到的就是"群里人数不对"。
- **成因**：把"没有下一页"的判定写成空字符串或者空值比较，或者把非空游标当成了结束。
- **对策**：结束条件只认服务端约定的哨兵值；把请求次数和每页游标记下来，大群场景必须在真机上确认"滚到底部不再发请求"。

排序分三级，目的是让用户三秒内找到人：群主和管理员打 `@` 标签置顶；其余按展示名转拼音，取首字母分组；非字母开头的（中文数字、emoji、空名）打 `#` 垫底。同一标签内部按原始下标保持顺序：这个字段看着多余，可少了它，每次进页面成员顺序都会跳。展示名走四级回退链（好友备注 → 群内昵称 → 昵称 → IM userID），保证非空。

**成员搜索接口搜的是本地已经缓存的成员资料，不是服务端全量**，它是 SDK 的旗舰版能力，语义上等价于"在已经拉到本地的成员数据里做多字段匹配"。放到分页场景下这就是硬伤：只加载了前几页的时候，还没拉到本地的成员搜不到，用户会以为"这个人不在群里"。有两条出路：先把成员数据补齐到本地再搜（大群代价太高），或者改由业务服务端提供成员搜索接口。

案例没走这两条路，只是把四个字段全打开（群内昵称、好友备注、昵称、IM userID）来提高命中率，输入做 1 秒防抖，避开一个字符一个请求，结果按群分组返回，只取当前群那一段。这里得出的结论要记住：**在这种实现下，不应该向产品承诺"任何人搜得到任何成员"**，大群必须真机验证搜索覆盖率。

**删除成员页是成员列表的受限子集**，保护措施全在数据源层：只拉普通成员，群主和管理员根本不会出现在可选列表里，"不存在"和"禁止勾选"是两回事（踢人只对普通成员生效，由 IM 服务裁定）；搜索路径再过滤一次角色；单次批量上限 20 人，超过就给提示、不发请求；成功后带结果返回上一页。

- **现象**：踢人成功返回群资料页，成员数还是旧值，头像墙里被踢掉的人还挂着。
- **后果**：管理员重复操作、误判踢人失败，甚至顺手误踢下一批。
- **成因**：只刷了成员列表没刷群信息，或者刷新请求和组件内部的状态更新撞到了一起。
- **对策**：用"带结果返回"把"已经变更"这个事实传回上一页，上一页收到后同时刷新成员列表和群资料，两次刷新之间留一个很短的延时来补偿组件内部状态。

## 七、权限矩阵，还有禁言的三层联动

结论：权限有两个落点，入口可见性和服务端拦截，缺任何一个都不成立；禁言则是权限在"被治理者"这一侧的镜像。

| 操作 | 群主 | 管理员 | 普通成员 | 边界说明 |
|---|---|---|---|---|
| 解散群 | 可 | 不可 | 不可 | 群主专属 |
| 转让群主 | 可（公开群） | 不可 | 不可 | 仅公开群支持 |
| 设置/取消管理员 | 可（上限 10） | 不可 | 不可 | 管理员数量受上限约束 |
| 踢人 | 可，仅普通成员 | 可，仅普通成员 | 不可 | 不能踢群主或管理员 |
| 设置/解除成员禁言 | 可，仅普通成员 | 可，仅普通成员 | 不可 | 工作群不提供该能力 |
| 全员禁言 | 可 | 可 | 不可 | 只约束普通成员发言 |
| 修改群资料 | 可 | 可 | 不可 | 群名 / 头像 / 公告 |
| 撤回消息 | 可撤他人 | 可撤他人 | 仅自己 | 由组件能力开关控制 |
| 退出群 | 需先转让或解散 | 可 | 可 | 群主退出会被服务端拒绝 |
| 加群/邀请加群方式 | 可 | 可 | 不可 | 决定新成员怎么进来 |
| 我的群昵称 | 可 | 可 | 可 | 仅影响自己 |

三个要点：

1. **客户端显隐不是权限。** **现象**：普通成员绕开 UI，直接拿会话和群 ID 去请求管理接口。**后果**：服务端没拦，群就被越权修改；服务端拦了而客户端没做错误话术，用户看到的就是一个裸露的错误码。**成因**：把"按钮隐藏"当成了权限模型。**对策**：每一行权限都回答三件事：入口在哪、服务端拦不拦、拦截后提示什么。
2. **入口要收敛。** 同一个操作只在一个页面出现，不然两处权限判断迟早漂移：群管理统一走群资料页；成员行上内置的"设为管理员/禁言/踢出"入口应该隐藏，不要和自研的成员管理页同时开放。
3. **"谁是群主"有两种判定，不能混用。** **现象**：转让、解散入口"时有时无"。**成因**：把"拿群主 ID 和本地身份比较"（判断他人）跟"我在群里的角色"（判断自己）混着用了。**对策**：判断他人用群主 ID 比较，判断自己用本地角色。

禁言这边横跨三层：

| 层 | 位置 | 内容 | 由谁负责 |
|---|---|---|---|
| 预防 | 输入区 | 群不存在 / 不是群成员 / 全员禁言中 / 您被禁言，输入框被替换成提示条 | UI 组件库 |
| 兜底 | 发送失败 | 错误码翻译成用户话术 | 客户端统一错误话术 |
| 治理 | 群管理设置页 | 全员禁言开关；成员禁言列表只列"普通成员且未在禁言中"，已禁言的滑动解除 | 群主与管理员 |

兜底层的那张话术表：

| 错误码 | 提示 | 触发场景 |
|---|---|---|
| 20012 / 20049 | 您已被禁言 | 成员禁言后尝试发言 |
| 20050 | 群已被禁言 | 全员禁言开启后普通成员尝试发言 |
| 10017 | 群组禁言 | 群级禁言由服务端拦截 |
| 20041 | 无权限操作 | 普通成员调用管理类接口 |
| 20052 | 群主不能退出群 | 群主未转让就直接退出 |
| 20007 | 被拉黑，无法发送消息 | 黑名单关系下的发送 |

几个容易被问到的细节：**群主和管理员在禁言判定里直接短路**，永远不显示"您被禁言"，全员禁言也拦不住他们发言，"全员禁言只约束普通成员"就是这么落地的；**本地禁言状态可能瞬时不准**，刚被禁言而群信息还没同步时会显示成可以输入，靠错误码兜底，反过来到期时间戳没更新时会短暂显示"您被禁言"，所以提示文案要留出"稍后重试"的解释空间；**判断是不是还在禁言中要用服务端时间**，本地时间不可信，改一下系统时间就能绕过本地判断；禁言接口的第三个参数是**禁言时长（秒）**而不是到期时间戳，**解除禁言传 0**，到期时间由服务端折算下发；**群类型决定能力边界**，案例里工作群不支持成员禁言，UI 直接不渲染入口，而群类型是在创建时锁定的（第五节）。

## 八、统一搜索和关系链状态同步

结论：搜索是入口收敛的问题，状态同步是所有权的问题。谁的状态谁维护，业务要用的状态得自己拿着监听。

搜索的目标是"一个入口覆盖全部查找需求"：会话、联系人、群组、群成员、历史消息这五类内容走同一个搜索页。命中会话之后进聊天页要用"替换"而不是"压栈"，返回应该回到搜索之前的页面。群内历史消息搜索不再单独开入口，重复入口只会带来两套行为和两套权限判断。

关系链的状态同步按"谁需要感知"来分配：

- **好友申请新增/删除、好友列表新增** → 重新查询好友申请未读，刷新红点（第三节）。
- **黑名单变化** → 影响发送能力，20007 就是黑名单关系下的发送失败。
- **群变更（解散、被踢、成员变化）** → 需要业务感知的部分必须自己注册监听。**现象**是群被解散、或者自己被人移出之后，业务侧的会话列表、成员缓存、角标要等用户重新进页面才更新；**后果**是已经解散的群长期挂在列表里，用户点进去才报错；**成因**是群事件监听完全依赖 UI 组件库，而组件库的监听只服务组件内部页面；**对策**是先列出"业务必须自持的状态"（会话存在性、未读、我在群里的角色），这部分自己注册监听，登出时按实例移除，纯展示状态留给组件。

穿过整个关系链，只有一条通用原则：**本地状态随时可能过期。** 展示可以按缓存渲染，判断必须向服务端对齐：权限、角色、禁言到期、分页游标都是同一类问题。

## 九、常见错误和修正表

| 问题 | 业务后果 | 对策 |
|---|---|---|
| 导航栈不清理 | 返回路径不可控，用户退不回会话列表 | 进聊天页之前只保留白名单页，移除中间页再用替换方式打开 |
| 分页游标结束信号判断错 | 大群成员拉不全或无限请求，删人页漏人 | 结束条件只认服务端约定的哨兵值（`"0"`），把请求次数和游标记下来 |
| 角色类型两套并存、强解包崩溃 | 资料拉取失败或角色为空时崩溃，建群也断了 | 显式映射角色常量，空值按普通成员处理，不用强解包 |
| 客户端显隐被当成权限 | 服务端拦了用户只看到错误码，或者存在越权修改的风险 | 每行权限都明确入口、服务端拦截和失败话术，关键操作在数据源层过滤 |
| 踢人后资料不刷新 | 成员数和头像墙还是旧值，管理员重复操作或误判失败 | 带结果返回上一页，同时刷新成员列表和群资料，两次刷新之间留一个短延时 |
| 群主身份两种判定混用 | 转让、解散入口显隐异常，"按钮时有时无" | 判断他人用群主 ID 比较，判断自己用本地角色 |
| 扫码协议不校验分段就取下标 | 扫到不完整或异构内容时进错页面、解析异常 | 前缀白名单加分段数量校验，未知内容统一提示 |
| 用外部整数做枚举下标 | 服务端返回枚举范围外的值时越界崩溃，崩溃点又离数据源很远 | 用显式常量映射，或者带兜底分支的查找，绝不按数组下标取枚举 |
| 群事件监听归属不清 | 群解散、被移出后，业务侧状态长期不更新 | 先明确业务必须自持的状态，自己注册监听，登出时按实例移除 |

## 十、验收清单

| 场景 | 验收标准 |
|---|---|
| 创建群 | 选好友并创建后直接进聊天页；消息流出现居中"某某 创建群组"提示；返回落在会话列表；群资料页"邀请进群方式"为管理员审批 |
| 群类型锁定 | 设置页点群类型只给出"群类型无法修改"，页面不跳转；创建后没有任何修改入口 |
| 群主操作边界 | 能看到群管理、删除成员、转让群主（公开群）、解散群；成员列表里群主和管理员在 `@` 组 |
| 管理员操作边界 | 能看到群管理、删除成员；看不到转让和解散；删除成员页里只有普通成员 |
| 普通成员操作边界 | 看不到群管理和删除成员入口，只能清空消息、退出群；越权请求被服务端拒绝并给出话术 |
| 全员禁言 | 开启后普通成员输入区变成"全员禁言中"，强行发送提示"群已被禁言"；群主和管理员照样能发言 |
| 成员禁言 | 被禁言成员输入区变成"您被禁言"；到期（按服务端时间）后自动恢复；解除禁言后立即恢复 |
| 批量上限 | 勾选到第 21 人时不再被选中，已经勾上的一项保持不变，并给出单次上限提示 |
| 好友申请流 | 申请方发出后好友列表出现对方；接收方红点出现，处理完申请红点就消失，不用重进页面 |
| 实名门禁 | 未实名点扫一扫、创建群聊、添加好友、添加群聊时先提示再跳实名页；点"发起会话"（已有好友）直接放行 |
| 扫码分发 | 扫邀请码进用户详情；扫群二维码带群 ID 进添加群聊页；扫到他人或异常内容给统一提示，不跳错页面 |
| 成员搜索 | 输入群内昵称、好友备注、昵称或 ID 片段都能命中；1 秒防抖后只发一次请求；清空输入回到索引列表 |
| 大群分页 | 滚到底部触发下一页；加载到最后一页后不再发请求，而且 `@` 组始终置顶、`#` 组始终垫底 |

排序分组、展示名回退链、协议分段解析这些纯函数可以抽出来，做小范围的自动化验证，免得后续重构把规则改坏。

## 十一、面试问答

**Q1：群主、管理员、普通成员的权限，靠客户端隐藏按钮够吗？**

不够。客户端显隐只是体验层，真正的边界在 IM 服务：普通成员就算绕开 UI 直接调解散群、踢人这类接口，服务端也会回权限错误码。每一行权限都得回答入口在哪、服务端拦不拦、拦了之后提示什么。删除成员页在数据源层只拉普通成员，算是双保险。

**Q2：成员列表为什么要拆三批拉取，再对普通成员游标分页？**

因为两类数据的形态不同。群主和管理员数量少，还有上限（管理员上限 10），一次拉一百条就够，也不用分页，而且必须出现在置顶的 `@` 组；普通成员能到上千人，只能靠服务端游标分页。三批合并之后，"群主与管理员置顶"才有完整数据。

**Q3：本地 IM 状态随时可能过期，工程上怎么兜底？**

按"展示可以落后、判断必须对齐"分成两类。展示类：建群后会话对象没同步到，就本地构造最小可用会话先进入，展示名走四级回退链。判断类：权限、角色、禁言到期一律以服务端为准；分页结束只认游标哨兵值；踢人这类会改服务端状态的操作，用带结果返回加双刷新，把本地缓存拉回一致。

**Q4：系统提示消息和红包那种业务消息，同样是自定义消息，区别在哪？**

看它背后有没有一个"多端必须一致的状态"。建群提示由客户端构造，纯展示，没有业务实体，渲染成居中提示就够了；红包卡片背后有服务端实体、领取状态、幂等和对账要求，需要版本化协议、服务端真值和失败补偿（见 28 篇）。无状态的用最轻的模式，有状态的必须按业务消息的协议设计。

**Q5：被禁言的用户会看到什么？禁言状态从哪来？**

三层联动。输入区提示由 UI 组件库根据全员禁言开关和自己的到期时间生成，被禁言时输入框被替换成提示条；发送失败时由错误码兜底，把成员被禁言、群被禁言、无权限这些错误翻译成人话；群管理设置页是群主和管理员维护禁言的地方。群主和管理员在判定里直接短路；到期判断用服务端时间；工作群不支持成员禁言，入口直接不渲染。

**Q6：为什么"建立新关系"和"发起会话"要拆成不同权限？**

因为风险不一样。跟已有好友聊天不产生新关系链，放行不会带来骚扰和陌生人风险；添加好友、创建群聊、扫码进群都会产生新的关系，需要额外资格。混在一个权限里，要么把正常聊天限得太死，要么给陌生人骚扰留了口子。能迁移的原则是门禁按行为风险分层，每层只拦自己负责的事，以后新增一层门禁，插一个检查就行。
