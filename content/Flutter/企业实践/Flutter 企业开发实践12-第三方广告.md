# 广告变现与聚合 SDK 接入

> 结论：广告接入难的地方就那么几处：构建期多联盟的依赖治理、审核期合规形态的切换、激励视频"看完发奖"的错误状态机、信息流嵌进列表以后的加载策略。把广告展示出来只是第一步。这篇拿国内聚合平台当样本，从选型决策、宿主工程改造，讲到各广告形态怎么落地、激励链路的状态机怎么设计。环境和构建管理在第 8 篇，商店审核的全流程在第 18、19 篇。核验版本：ToBid（Sigmob/Windmill 系）Flutter 插件 5.5.x，信息截至 2026-08；SDK 行为、错误码和联盟能力以当前官方文档为准。

---

## 一、聚合广告解决什么问题，边界在哪里

只接一家广告联盟，问题出在**填充率有天花板**：这家没库存，请求就直接浪费掉了。聚合平台是把一次请求同时发给好几家联盟（Bidding），或者按 eCPM 历史排好序一个一个请求（Waterfall），填充率和综合 eCPM 都比单接高不少。

| 维度 | Waterfall（瀑布流） | Bidding（竞价） |
|---|---|---|
| 原理 | 按 eCPM 历史数据排优先级，依次请求 | 所有联盟同时出价，选最高 |
| 实时性 | 依赖历史数据 | 实时反映当前竞价 |
| 缺点 | 排序靠后的联盟可能永远拿不到请求 | 依赖各联盟竞价能力 |

成熟的做法是**两种混着用**：能 Bidding 的联盟走竞价，剩下的进瀑布兜底。聚合平台的价值也在这儿：多联盟的接入、数据和计费口径的统一，这是一直要往里投的活，不是做完一次就结束，所以自研聚合不划算。

### 选型格局

| 方案 | 定位 | 备注 |
|---|---|---|
| ToBid（Sigmob/Windmill） | 国内聚合 | 本篇样本；Flutter 插件完整，8 家主流 ADN |
| 穿山甲 GroMore | 字节聚合 | 国内主流，Flutter 侧多需自接或桥接 |
| TopOn（国内已拆分 Taku） | 第三方聚合 | 2024-03 拆分：中国区业务由新品牌 Taku 承接，出海仍用 TopOn |
| AdMob | Google 聚合 | 大陆设备基本不可达，仅出海 |
| AppLovin MAX / Unity LevelPlay | 海外主流 | 出海场景 |

有个常见的讹传得澄清一下：2023 年被 Unity 关停的是**自家的 Unity Mediation**；ironSource 的聚合换了个名字叫 **Unity LevelPlay**，一直在迭代。网上把"ironSource 关停"当讣告写，那是错的。纯国内产品就在 ToBid/GroMore/Taku 里实测三家，按插件完整度、后台数据、服务响应来选；出海走 MAX/LevelPlay/AdMob。

### 边界：哪些必须自己认领

聚合平台管的是"请求发给谁、联盟怎么结算"这摊事；但有四件事不能外包给它：**审核形态**（审核期间展不展示广告、采集哪些隐私，这是应用自己的合规责任）；**激励发放规则**（今天能看几次、看完发什么，这属于运营策略，必须服务端能热更）；**错误话术**（联盟的错误码用户看不懂，文案得自己翻译，再服务端下发）；**SDK 缺陷的兜底**（聚合插件的 bug 不会等你，你得有能自己打补丁的集成方式，见第二节）。

## 二、集成方式与宿主工程改造

结论：**集成方式对后续效率的影响，比选型还大**。用本地插件目录引入，不走 pub 依赖，换来的是"出问题能自己打补丁"；代价是永久背着 fork 的维护成本，得靠补丁纪律对冲。

### 本地插件引入

案例项目把官方 Flutter 插件直接搬到本地目录（目录名带上版本号），`pubspec.yaml` 里用 path 依赖：

```yaml
# 插件目录内含：Dart 层 API + 双端原生层 + 各 ADN 的 aar + OAID SDK
# pub get 后经 GeneratedPluginRegistrant 自动注册，宿主不用改 MainActivity
windmill_ad_plugin:
  path: plugins/windmill_5_5_x
```

把插件本地化，生产上有两个理由。**一是补丁能力**：广告 SDK 的 bug 不会等你，走官方 issue 等排期可能要好几周，本地插件一行补丁当天就解决了（第九节那个 iOS Modal 问题就是靠它救的急）；**二是构建链路可控**：ADN 的 aar 版本、依赖冲突都锁在自己仓库里，什么时候升级自己说了算。代价是每次升级都得人工同步，所以必须配一份升级核对清单；每次改动也都要留文档（改了什么、为什么改、升级时怎么核对），不然半年后没人敢动。

### 构建期的四个坑

引入聚合插件以后，宿主 Android 工程的依赖冲突会在构建期全冒出来，报错都在 Gradle/Merger 的输出里。集成那天预留半天专门处理这些，属于合理预期：

**坑 1：AGP 版本链路不匹配**。插件的 buildscript classpath 和宿主的 AGP 版本对不上，构建就失败，得把版本对齐（案例里的约束：宿主从 AGP 8.11.1 降到 8.4.0 才能构建，Kotlin 版本不动）。**坑 2：旧版 Support 库和 AndroidX 冲突**。有些 ADN 的 aar 传递依赖了旧库，必须把 Jetifier 打开：

```properties
# android/gradle.properties
android.useAndroidX=true
android.enableJetifier=true
```

**坑 3：androidx 组件版本不一致**。好几家 ADN 各传递进来一个版本的 androidx，用 `resolutionStrategy` 强制统一；原生信息流模板渲染要用 CardView，得显式声明：

```kotlin
// android/app/build.gradle.kts
configurations.all {
    resolutionStrategy {
        eachDependency {
            if (requested.group == "androidx.browser" && requested.name == "browser") {
                useVersion("1.8.0")
            }
            if (requested.group == "androidx.core") {
                useVersion("1.15.0")
            }
        }
    }
}
dependencies {
    implementation("androidx.cardview:cardview:1.0.0")
}
```

**坑 4：Manifest 合并冲突**。广告 SDK 声明的 `allowBackup` 这些属性跟应用里的取值不一样，merger 就报错，用 `tools:replace` 以应用为准：

```xml
<application
    android:name="${applicationName}"
    android:allowBackup="false"
    android:label="应用名"
    tools:replace="android:allowBackup,android:label">
```

还有几个硬门槛：插件一般要求宿主的 `minSdkVersion` 达到它的最低值（案例是 24）；iOS 那边要对应确认 podspec 和权限声明。

## 三、初始化、合规与广告位管理

结论：初始化的入口收在一个单例里，就干三件事：审核形态下收紧隐私采集、失败上报留痕、广告位 ID 集中管起来。

### 审核形态是一等公民

商店审核期间，"展示广告 + 过度采集个人信息"是高频的拒审组合。**审核形态必须做成服务端下发的开关**，不能靠发版来切：审核期间用 `setCustomDevice` 把应用列表、定位、AndroidId、OAID、IDFA、MAC 地址这些采集开关全关掉；过审以后再恢复全量采集。

```text
// 示意伪代码：初始化入口
init():
    if (审核形态开关)            // 服务端下发，不是本地常量
        setCustomDevice(全部采集项 = false)
    appId = 按平台取集中配置
    res = await SDK.init(appId)
    if (res.success != true) reportInitError(res)   // 失败上报，不静默
    catch e: reportInitError(e)
```

初始化失败一定要上报留痕：广告 SDK 初始化失败经常是静默的，App 别的功能全都正常，不留痕你就永远不知道有一批用户的广告全挂了。上报内容带上错误详情和来源标记，好跟后端日志对账。

### 广告位 ID 集中管理

所有广告位用 enum 收在一起，双平台的 ID 成对声明，别散着硬编码（这里 ID 是示意占位，真实的广告位 ID 属于商业配置）：

```dart
enum AdPlacement {
  splash(android: '9100000000000001', iOS: '9100000000000011'),
  reward1(android: '9100000000000002', iOS: '9100000000000012'),
  native(android: '9100000000000003', iOS: '9100000000000013'),
  interstitial(android: '9100000000000004', iOS: '9100000000000014'),
  banner(android: '9100000000000005', iOS: '9100000000000015');

  final String android;
  final String iOS;
  String get value => Platform.isIOS ? iOS : android;
}
```

硬编码散着放的代价：换广告位得全局搜索替换，双平台各一份，还很容易只改一半。

## 四、开屏广告：任何回调路径都能在有界时间内到达首页

开屏在冷启动的关键路径上，哪一步卡住都直接伤留存。三条铁律：

```text
// 示意伪代码：开屏骨架
dispatch():
    if (审核形态) 直接进首页          // 铁律 1：审核模式跳过广告
    else loadSplashAd()

loadSplashAd():
    fallbackTimer = 4 秒后强制进首页   // 铁律 2：兜底超时先于加载启动
    ad = SplashAd(
        onLoaded:   try showAd; 失败进首页
        onFailed:   进首页
        onOpened:   取消 fallbackTimer   // 广告真正展示才解除兜底
        onClosed:   进首页
        onSkipped:  进首页
        onShowError: 进首页
        // 铁律 3：宽高用 platformDispatcher 实测逻辑分辨率，不写死
    )
    ad.loadAd()
```

开屏代码的评审标准就一句话：**任何一条回调路径，都要能在有界时间内到达首页**。加载慢、加载失败、展示失败、用户跳过，全都收敛到"进首页"这一个出口；兜底 Timer 要在加载**之前**启动，`onOpened`（真正展示）才解除；顺序反了就会出现"既没展示、也进不去"的窗口。尺寸取实测值（`physicalSize / devicePixelRatio`），免得广告尺寸和容器对不上导致展示失败。

## 五、激励视频：前置关卡与发奖时序

激励视频（看广告 → 发奖励）是广告变现的主力形态，业务复杂度也主要堆在这儿。链路总览：

```text
业务按钮点击
  → 资格校验（服务端）
  → 本地冷却检查
  → 免责弹窗（"观看视频可获得奖励"）
  → 用户确认
  → 多广告位轮换加载
  → SDK 回调
     → 发奖成功: onAdReward → 上报服务端 → 发放奖励
     → 广告关闭: onAdClosed → 业务方刷新页面
     → 加载/展示失败: 查错误文案 → 失败弹窗 → 上报错误日志
```

有个设计挺反直觉：**真正触发广告加载的，是免责弹窗上那个确认按钮**。业务按钮只管前置检查；免责弹窗一方面是合规要求（让用户知情），另一方面刚好就是广告加载前的一道确认门。

### 前置三关卡

**关卡 1：资格校验（服务端）**。"今天还能不能看、已经看了几次"属于运营策略，得能热更，所以资格判断放服务端，按返回码分流：允许观看就把结果缓存下来继续；版本太低就弹升级并终止；不满足运营条件（比如当日次数用尽）就展示服务端下发的文案并终止。业务上的前置条件（账号状态、版本门槛）都在这一层收口，广告链路本身不用知道业务规则。

**关卡 2：本地冷却**。服务端下发次数上限和冷却秒数，客户端拿本地存的上次成功时间戳算还剩多少冷却。冷却基准时间戳是在**发奖成功的时候**写进去的，以真实发奖为准，不看广告关没关，用户没看完就关掉，冷却不刷新。

**关卡 3：免责弹窗**。见上文。

### 多广告位轮换

案例项目配了 4 个激励广告位，展示的时候取第一个"没消耗"的实例，全消耗完了就重置，再来一轮：

```text
// 示意伪代码：广告位轮换
showNext():
    if (所有实例都已消耗) 重置全部 → 取第一个
    item = 第一个未消耗的实例
    item.loadAdData()

// hasShow 在 onAdOpened（真正展示）时置位，加载失败不算消耗
```

为什么要轮换？同一个广告位连着展示，会被联盟风控判成异常（填充下降，严重的直接封位）；多广告位让每次请求都落在"新鲜"的位上，也顺便分摊了单联盟没库存的风险。

### 发奖时序：以 onAdReward 为准

```text
onAdReward（SDK 判定完成激励条件）
  → 清空错误态、关闭已弹出的失败弹窗
  → 发奖上报（带签名；请求字段区分触发广告的业务场景）
  → 保存本地成功时间戳（冷却基准）
onAdClosed（广告关闭）
  → 调用业务方挂接的刷新回调
```

两个关键设计：

1. **发奖上报以 `onAdReward` 为准，不看 `onAdClosed`**。前者是 SDK 判定"用户看完了"的唯一信号；后者只说明广告关掉了（可能根本没看完）。上报失败的时候要暴露给用户，别静默吞掉：拉服务器时间拼个提示，在广告关闭时告诉用户，让"发奖失败"有据可查。
2. **页面刷新做成出口，不做成内置**。`onAdClosed` 回调暴露给业务方去挂，广告管理器里不内置任何页面刷新，通用能力和具体页面解耦。

## 六、激励视频：错误状态机与对外接口

这一节是激励链路里最有含金量的部分：大部分团队第一版实现都是"报 error 就 toast 一句完事"，可线上事故几乎全出在这一节覆盖的场景里。

### 双层错误处理

加载失败（`onAdFailedToLoad`）和展示失败（`onAdShowError`）走同一套处理，但分成两层：

```text
recordError(error)
  → 按错误码 + 平台请求文案配置接口（服务端下发，运营可热更话术）
  → 缓存三份信息：
     用户文案        → 给用户看的（接口失败时兜底原始 message）
     最近一次错误     → 给外部调用方复用
     错误详情 JSON    → 给后端日志排障用
showErrorAlert(code)
  → 仅在本轮未成功时才弹（见下文"成功覆盖失败"）
```

**日志上报不在这儿发**，它挂在失败弹窗的 `onDismiss` 上：用户把弹窗关掉的时候，错误详情还在才上报日志接口（带来源场景标记）。收到 error 但没弹窗（比如被成功覆盖了），这条日志就不打；用户可见层和日志层是两条独立的链路。联盟的错误码用户看不懂，文案走服务端配置是有意为之：运营要能随时改话术，不用等发版。

### 成功覆盖失败：最容易写错的状态语义

SDK 的回调时序不只是"要么成功要么失败"：可能先 error 后 reward（重试成功了），也可能先 reward 后 error（关闭的时候出了异常）。语义规则是：**只要 `onAdReward` 到了，就按成功收口**，立刻清空错误态、关掉已经弹出来的失败弹窗、置位成功标志；失败弹窗只在这一轮没成功的时候才允许弹。完整的行为矩阵（也是错误处理的验收标准）：

| 场景 | 时序 | 错误弹窗 |
|---|---|---|
| 1 | 无广告，error | 弹 |
| 2 | 广告出现，先 error 后 reward | 先弹，reward 到达时主动关闭 |
| 3 | 广告出现，先 reward 后 error | 不弹 |
| 4 | 广告出现，无 reward 无 error，用户关广告 | 不弹 |
| 5 | 广告出现，无 reward，中途 error，用户关广告 | 弹 |

这里如实记一个边界：失败弹窗的日志上报挂在 `onDismiss` 上，弹窗已经展示了、随后又被成功回调关掉，`onDismiss` 照样会触发，也就是说场景 2 下失败日志可能照打（用户侧已经按成功收口，日志层却多一条失败记录）。这是目标语义和实现之间的已知差距，改法是把上报条件换成"本轮未成功"。教训是：**"用户可见层"和"日志层"的清理时机，必须分开评审**。

### 对外激励接口：Completer 化与三重防挂起

除了内部业务调用，激励能力还该包一层 Future 化接口，让任何业务模块都能"看广告拿结果"。三个防挂起的设计：

```dart
// 示意伪代码：对外激励接口骨架
Future<AdResult> showExternalReward() {
  final completer = Completer<AdResult>();
  final requestId = 下一请求 ID();      // 自增种子 + 时间戳

  scheduleTimeout(requestId, completer); // 1. 超时熔断
  activeRequestId = requestId;           // 2. 回调只认"当前请求"的实例
  // 3. 所有终态（reward/closed/failed/showError/timeout）
  //    统一走 finish，幂等（completer 已完成则跳过）
  return completer.future;
}
```

1. **超时熔断**：广告 SDK 的回调没有可靠性保证，加载卡死、回调丢失都真出过，超时器兜底，保证调用方的 Future 一定在有限时间内完成。阈值看线上的分位数，别拍脑袋：案例项目从 8 秒调到 15 秒，因为线上发现有些低端机冷启动后首次加载超过 8 秒，被误判成失败了。
2. **requestId 防串扰**：多个广告位实例共享同一条状态流，用"当前请求 ID + 广告位 ID"双重匹配，免得把上一个请求的回调错配给当前调用方。
3. **Completer 幂等**：所有终态都收敛到一个 finish 函数，已经完成就直接返回，奖励回调和关闭回调几乎同时到达也不会二次 complete 崩溃。

### 服务端接口清单

激励链路最少依赖 5 个服务端接口（迁移或者重构的时候，这就是核对清单；路径是示意占位）：

| 接口 | 用途 |
|---|---|
| 资格校验 | 前置检查，错误码分流 |
| 发奖上报 | 以 onAdReward 为准，字段区分业务场景 |
| 服务器时间 | 上报失败时拼时间提示 |
| 错误文案配置 | 按错误码 + 平台查用户可见文案 |
| 错误日志留痕 | 初始化失败与激励失败两用 |

## 七、原生信息流：PlatformView 创建时序

原生信息流分两层：Dart Widget（包 PlatformView）→ 原生 View（绑数据渲染）。PlatformView 最经典的一类坑就藏在这儿。

**原生信息流加载成功但永不渲染**
- 现象：触发加载后状态显示"加载成功，等待渲染"，广告区域却永远空白；Banner 和激励视频都正常，只有原生信息流不对。
- 后果：排查方向被"SDK 加载成功"的日志带偏，容易一头去查联盟配置和广告位，其实根因在自己这层的时序上。
- 成因：PlatformView 在广告数据就绪之前就创建了，原生构造函数一上来就渲染，这时候广告数据还是 null，原生层的空指针被 PlatformView 框架吞掉、返回个空容器；之后广告加载成功，可 `creationParams` 没变，PlatformView **不会重建**，渲染调用也不会再执行。
- 对策：只改调用方的时序，不动插件，把包 PlatformView 的 Widget 挂载推迟到 `onLoaded` 回调之后，数据就绪了再创建。

```dart
// ❌ 错误：加载前就挂载
final ad = NativeAd(placementId: ...);
setState(() => _adWidget = NativeAdWidget(nativeAd: ad)); // 提前挂载 → 永不渲染
ad.loadAd();

// ✅ 正确：onLoaded 之后再挂载
final ad = NativeAd(
  placementId: ...,
  onLoaded: () {
    if (!mounted) return;
    setState(() => _adWidget = NativeAdWidget(nativeAd: ad)); // 数据就绪才创建
  },
);
ad.loadAd();
```

为什么 Banner 不受影响？Banner 的原生渲染就是放一个空容器视图，不依赖广告数据，SDK 加载完自己渲染进去；原生信息流必须拿到广告数据才能绑视图，**时序不可逆**。通用教训：任何"依赖异步数据"的 PlatformView，都要保证**首次创建的时候数据已经就绪**，PlatformView 的生命周期由 widget 树驱动，`creationParams` 不变就不重建，你没有第二次机会。这条教训在地图、WebView 预注入、原生播放器这些同构场景里一样成立。

## 八、信息流进列表：滚动感知与状态缓存

单体信息流跑通只是第一步，嵌进业务列表以后还得处理滚动、回收重建和快速划过。下面按案例源码说清楚滚动监听、索引缓存、占位、挂载时序和可见性检测各自都做了什么，以及当前实现的边界在哪。

### 滚动感知：停稳了再检查要不要加载

`ListView` 把共享的 `ScrollController` 传给每个广告组件。组件在 `initState` 里就会立刻尝试加载；滚动监听的 300ms 防抖，只管滚动停稳之后的再次检查：

```text
// 按案例源码简化的流程
initState():
    添加滚动监听
    检查索引缓存并尝试加载   // 首次挂载不等待滚动停稳
onScroll():
    isScrolling = true
    重置 300ms 定时器
    定时器到期: isScrolling = false; 检查是否需要再次加载
```

所以已经开始的那次首次加载不会因为滚动而取消，不能把这套实现说成“滚动中不请求”。防抖能把滚动触发的再次检查往后推，但快速划过的时候，首次挂载照样可能发出请求。

### 索引级加载缓存：记录状态，但不保存广告实例

案例组件用一个静态 `Map<int, bool>` 记索引有没有加载成功。滚动停止后检查的时候，成功标记能跳过再次加载；但 item 被回收、组件重新创建以后，新的 State 里没有广告实例，就算缓存标着成功，恢复流程还是会重新创建并加载广告。`ValueKey('ad_$index')` 只是帮着标识同一个位置，没法让已经销毁的广告实例复活。失败的时候标记为 false，后面滚动停止再检查还能重试；缓存类里提供了清空方法。

### 三态占位与"失败即折叠"

| 状态 | 渲染 | 高度 |
|---|---|---|
| 滚动中 / 加载中 / 兜底 | shimmer 占位 | 预留固定高度 |
| 加载成功 | 真实广告 Widget | 展示回调后取真实尺寸，动画过渡 |
| 失败 / 被关闭 | 空 Widget | **折叠为 0** |

"失败即折叠"这个细节容易被忽略：加载失败的广告位要是把占位高度留着，用户就会看到一条永久的空白缝。组件不光要把自己折叠掉，外边距也只在加载成功的时候才生效。广告失败是常态（某家联盟没库存太常见了），列表的视觉密度不能让这个拖垮。

### 挂载时序组件化 + 曝光上报

案例组件收到 `onAdLoaded` 之后，还要等 SDK 的 `isReady()` 返回 true，才把 `isReady` 置位并构建 `NativeAdWidget`。所以它确实避开了加载前挂载，但**挂载门槛仍然是 `isReady()`**；这次检查要是返回 false，当前分支不会置位，也没立刻安排重试，组件可能就一直停在占位状态。第七节讲的“数据就绪后挂载”是时序原则，不能拿它说案例代码已经绕过了 `isReady()` 的拦截风险。

插件的原生信息流 Widget 用 `visibility_detector` 检测可见区域；业务侧没在这个列表组件里另写曝光上报。这不能证明快速划过就一定不产生曝光，也补不了首次挂载就可能请求广告这个情况。

### 列表插入策略

```dart
ListView.builder(
  controller: _scrollController,   // 共享给广告组件做滚动判定
  itemCount: 10,
  itemBuilder: (context, index) {
    if (index == 2 || index == 6) { // 固定间隔插入广告位
      return ListNativeAdWidget(
        key: ValueKey('list_native_ad_$index'), // 稳定 key
        scrollController: _scrollController,
        listIndex: index,           // 对应索引级缓存
        height: 420.px,
      );
    }
    return const NormalListItem(index: index);
  },
);
```

三个要点：**固定间隔**（生产环境的间隔一般由运营配置下发，不写死）、**稳定 ValueKey**（重建之后缓存能对上号）、**共享 scrollController**（多个广告位共用一份滚动监听，别各自 attach）。

## 九、SDK 缺陷补丁与测试基建

### iOS Modal 场景：一行补丁的复盘

**Modal 页面上激励广告拉不起**
- 现象：普通页面拉激励广告正常；页面上已经有一个 iOS `present` 弹出来的 Modal 控制器时，激励广告就展示不了。
- 后果：只有特定交互路径的用户会命中，客服反馈零零散散，测试环境里很难稳定复现。
- 成因：插件要把"当前展示的 VC"传给 SDK 来 present 广告，它的查找函数递归算出来的控制器是对的（穿透 Navigation/TabBar/Modal 层级），**可最后一行返回的是方法入参**：递归白算了，SDK 拿到的是一个错的展示控制器。
- 对策：本地插件打一行补丁，改成返回递归结果。

补丁本身只有一行，**管补丁的纪律比补丁本身更重要**：

1. **独立文档记录**：改了哪个文件、哪一行、验证到什么状态、怎么回退，全部落档；
2. **升级核对清单**：SDK 升级时先拿新版里这个函数的实现对比一下，上游修了就删补丁；没修、问题还在，就先在独立的 demo 里复现，再去跟广告商确认，别机械套用；
3. **回归范围**：展示控制器怎么选，会影响所有广告形态，打完补丁必须把这五个场景都跑一遍：普通页面、Modal、Navigation Push、广告关闭后原页面还能操作、连续多次拉起没有残留 VC。只验激励不够。

### 广告专用测试页

接广告 SDK 的第一件事，是把每种形态的测试页都跑通，别急着写业务：开屏、激励、信息流、Banner、插屏各有独立的加载、展示、销毁按钮和状态流水。后面所有排坑都靠它打底：第七节的时序问题、第八节的列表进阶、第九节的 Modal 问题，都是先在测试页稳定复现，再定位到根因的。

测试入口有两个约束：做成**悬浮按钮，release 构建里自动隐藏**（用 `kReleaseMode` 判断），这样测试页永远可用，又不会泄漏给线上用户；悬浮按钮只放特定页面，别做成全局 Overlay，否则所有页面都被它挡着。

## 十、常见错误与修正表

| 问题 | 业务后果 | 对策 |
|---|---|---|
| 审核期间展示广告 + 全量隐私采集 | 商店拒审 | 审核形态做成服务端开关，收紧采集项（第三节） |
| 初始化失败静默吞掉 | 一批用户广告全挂且无人知晓 | 失败上报服务端留痕，与日志对账 |
| 广告位 ID 散落硬编码 | 换广告位全局搜索替换，双平台漏改 | enum 集中管理，双平台成对声明（第三节） |
| 开屏兜底超时晚于加载启动 | 存在"既没展示也进不去"的窗口 | Timer 先行，onOpened 才解除，全部回调收敛到单出口（第四节） |
| 发奖以 onAdClosed 为准 | 用户没看完也发奖 | 以 onAdReward 为准，关闭只触发页面刷新（第五节） |
| 冷却基准取广告关闭时间 | 没看完关掉也刷新冷却 | 冷却基准在发奖成功时写入 |
| 同一广告位连续展示 | 联盟风控异常，填充下降甚至封位 | 多广告位轮换，真正展示才算消耗（第五节） |
| 错误处理只做用户提示 | 线上排障无据可查 | 用户文案层与日志层分离，日志带原始错误详情（第六节） |
| "先失败后成功"只清用户层 | 日志层多报失败，口径污染 | 成功收口时两层分别清理，上报条件与弹窗条件一致 |
| 对外激励接口无超时兜底 | 回调丢失时调用方永久挂起 | 超时熔断 + requestId 防串扰 + finish 幂等（第六节） |
| 超时阈值拍脑袋定 | 低端机慢加载被误判失败 | 依据线上分位数调整（案例从 8 秒调到 15 秒） |
| PlatformView 挂载早于数据就绪 | 加载成功但永不渲染，`creationParams` 不变不重建 | onLoaded 之后再挂载（第七节） |
| 列表组件中 `isReady()` 返回 false | 真实广告可能一直未挂载 | 当前源码没有在此分支立即重试，需核查恢复路径（第八节） |
| 列表首次挂载时快速滑动 | 首次请求仍可能在滚动中发出 | 现有 300ms 防抖只推迟滚动停止后的再次检查（第八节） |
| item 回收重建 | 已成功的索引仍可能重新请求 | 索引缓存不保存广告实例，重建会重新加载（第八节） |
| 失败广告位保留占位高度 | 列表出现永久空白缝 | 失败即折叠为 0，外边距仅成功时生效 |
| 本地插件改动不留记录 | 半年后没人敢升级 | 补丁清单文档 + 升级核对清单 + 五场景回归（第九节） |

## 十一、验收清单

| 场景 | 验收标准 |
|---|---|
| 审核形态开启 | 广告入口跳过或收敛，隐私采集项全部关闭；过审后恢复 |
| 初始化失败 | 有服务端留痕，可与后端日志对账 |
| 开屏各失败路径 | 加载慢/失败/展示失败/跳过，全部在有界时间内到达首页 |
| 开屏正常展示 | 兜底 Timer 在展示成功时解除，不误杀 |
| 激励完整观看 | onAdReward 触发发奖上报，冷却时间戳刷新 |
| 激励中途关闭 | 不发奖，不刷新冷却 |
| 无广告库存 | 错误弹窗文案来自服务端配置，日志带错误详情 |
| 先 error 后 reward | 失败弹窗被主动关闭，用户侧按成功收口 |
| 先 reward 后 error | 不弹失败弹窗 |
| 对外激励接口超时 | Future 在阈值时间内完成，不永久挂起 |
| 并发调用对外接口 | 回调不错配，无二次 complete 崩溃 |
| 原生信息流首次渲染 | onLoaded 后挂载，渲染成功 |
| 列表快速滑动 | 记录首次挂载要不要发请求；滚动停止约 300ms 后才再次检查 |
| 列表回收重建 | 核查已成功索引重新创建广告实例后的请求与展示，位置对应正确 |
| 信息流加载失败 | 广告位折叠为 0，无空白缝 |
| Modal 页面拉激励 | 各控制器层级下均可展示（补丁回归五场景） |
| release 构建 | 测试入口不可见 |

## 十二、面试问答

### Q1：为什么用聚合 SDK 而不是直接接穿山甲/优量汇？

只接一家联盟，填充率有天花板，没库存的时候请求就白发了；聚合层把 Bidding（实时竞价）和 Waterfall（瀑布兜底）混着调，填充率和综合 eCPM 都更好，还顺手统一了多联盟的接入、数据和计费口径。追问答什么？选型看国内联盟覆盖、Flutter 插件完整度、后台数据能力；再深一层的决策是集成方式，本地插件换来补丁能力，代价是 fork 的维护成本，得用补丁清单的纪律对冲。

### Q2：激励视频的完整链路怎么设计？

前置三关卡（服务端资格校验按错误码分流、本地冷却以发奖成功为基准、免责弹窗当确认门）→ 多广告位轮换（防联盟风控、分摊没库存的风险，真正展示才算消耗）→ 发奖以 onAdReward 为准（onAdClosed 可能根本没看完）→ 上报失败要暴露给用户（拉服务器时间拼个提示）→ 页面刷新做成出口，交给业务方挂。加分项：对外 Future 化接口的超时熔断 + requestId 防串扰 + 幂等收口。

### Q3：广告的错误处理为什么要分两层？

用户可见层（文案走服务端配置，运营能热更话术）和日志层（原始错误详情上报后端，用来排障）关注点不一样，清理时机也不一样："成功覆盖失败"必须两层分别评审，只清用户层，日志层的误报就留下了。能把五场景的错误弹窗矩阵背下来（无广告弹、先 error 后 reward 主动关、先 reward 后 error 不弹、正常关闭不弹、中途 error 弹），这就是硬通货。

### Q4：原生信息流"加载成功但不渲染"怎么排查？

先分层（Dart widget / PlatformView / 原生渲染），看日志定位到 onLoaded 到了，可渲染回调就是不到；根因是 PlatformView 创建得比数据就绪早，而且 creationParams 不变就不重建、原生空指针被框架吞掉。修法就是把挂载推迟到 onLoaded。追问：Banner 为什么不受影响？Banner 的原生渲染不依赖广告数据，SDK 加载完自己渲染进空容器；信息流必须拿到数据才能绑视图，时序不可逆。再泛化一点：依赖异步数据的 PlatformView，都适用"数据就绪再创建"。

### Q5：广告 SDK 出 bug 怎么办？

前提是插件得本地化：一行补丁当天解决（iOS Modal 里 VC 查找返回错值那个例子就是这么修的）；配套纪律是独立文档记录改动和回退方式、升级时先跟上游实现对比（已修就删补丁，没修先 demo 复现）、按五场景回归（展示控制器影响所有广告形态）。没有本地插件，就只能等官方排期。

### Q6：审核与合规在广告侧怎么做？

审核形态做成服务端开关：审核期跳过开屏这些广告，用 setCustomDevice 收紧应用列表、定位、OAID、IDFA 这些采集项；初始化失败要上报留痕；错误文案走服务端配置。再往下展开，广告类 App 的合规清单还包括隐私政策里披露广告 SDK、个性化推荐的关闭开关、未成年人保护，这些跟商店审核的高频拒审点直接对应。

### Q7：信息流广告嵌进列表，你会做哪些优化？

按案例的实现来答，要说清五点和它们的边界：首次挂载立刻尝试加载，300ms 防抖只用在滚动停止后的再次检查；索引缓存只记成功状态，item 回收重建后还是会重新加载；加载中显示占位、失败折叠、展示后按实际尺寸过渡；`onAdLoaded` 之后还得等 `isReady()` 为 true 才挂载，返回 false 就可能一直停在占位；插件用了可见性检测，但不能只凭这一点就说快速划过一定没有曝光。
