# IM 自定义消息与红包

> 普通消息传的是一段文本，红包传的却是一笔带资金状态的交易。两者能共用同一条 IM 通道，但共用不了同一套真值模型：消息是随时可能过期的快照，钱是只能由服务端裁决的事实。这篇是 IM 专题的终篇，讲自定义消息协议怎么演进、红包怎么从"点一下"走到"资金入账"，还有横跨 IM 和业务服务端的一致性靠什么兜住。
>
> 前置三篇：25 篇（IM 接入与消息收发）给了会话、消息收发和自定义消息的投递入口；26 篇（IM 登录、身份与连接治理）管"可发送"的登录前提；27 篇（好友与群管理）提供红包的业务上下文：和谁聊、在哪个群发。

## 一、先定义边界：IM 是通道，不是账本

先给结论：IM 只管把"有一个红包""某人领了红包"这两件事送到会话成员手里；红包存不存在、还剩几份、谁能领、实得多少钱，一律由业务服务端裁决。把自定义消息当成账本，等于把资金安全交给客户端。

| 层次 | 负责什么 | 不负责什么 |
|---|---|---|
| IM 服务与 IM SDK | 消息可达、会话同步、未读、离线与漫游 | 红包是否有效、份数与余额 |
| 业务服务端 | 金额、份数、领取资格、账务流水、补偿与对账 | 消息何时到达、如何渲染 |
| 客户端 | 渲染卡片快照、发起命令、展示结果 | 决定入账金额、判定领取成功 |

三条约束不能越过：

1. 客户端上报的任何"红包状态"都只是一次请求，不是事实；
2. 资金状态只有服务端命令能改，查询和快照都只算交叉验证；
3. IM 投递失败最多让"用户看不见"，回滚不了已经发生的资金事实。

资金类业务比普通消息麻烦的地方有三点：**消息是会话里共享且可写的对象**，谁都能改，所以"改消息"当不了同步手段；**动作必须幂等**，弱网下一次点击会到达多次，服务端得认得出这是同一笔；**结果必须可追溯**，出了问题得能从用户的一次点击追到账务流水，不是靠聊天记录反推。这三点把后面的设计都定死了：协议带事件 ID、写接口带幂等键、领取靠唯一约束兜底。

**产品选择**：红包入口放在聊天页的"更多面板"；会话列表把红包类自定义消息摘要成"红包"，不显示 `[自定义]`；红包卡片禁止转发，免得把一条会过期的业务指令复制到别的会话。
**通用原则**：真值在服务端、IM 只做投递；至少一次投递配幂等消费；唯一约束兜底。这三条跟业务形态无关，任何"有状态业务 + 消息通道"的组合都适用。

## 二、自定义消息协议与演进规则

结论：自定义消息的正文本身就是协议，必须自带类型、版本和事件 ID，不然第一次改字段就得靠客户端猜。

自定义消息的 data 通常是一段 JSON 字符串，建议统一收敛成下面这样的信封（示意结构，字段值都是通用占位）：

```json
{
  "schema": "chat.business_event",
  "version": 2,
  "eventId": "全局唯一事件 ID",
  "type": "redpacket.created",
  "occurredAt": "2026-01-01T10:00:00Z",
  "conversation": { "type": "group", "id": "会话 ID" },
  "actor": { "id": "业务用户 ID", "displayName": "昵称", "avatarUrl": "头像地址" },
  "aggregate": { "type": "redpacket", "id": "业务实体 ID", "revision": 1 },
  "payload": { "remark": "恭喜发财", "cover": "default", "packetType": "random" }
}
```

| 字段 | 语义 | 设计理由 |
|---|---|---|
| schema + version | 协议名与协议版本 | 解析器入口只认这两个字段，未知版本走降级 |
| eventId | 全局唯一事件标识 | 客户端去重、投递重试排查、全链路追踪 |
| type | 过去式事件名 | 表达"服务端已经发生了这件事"，不是"请执行" |
| aggregate.id | 业务实体 ID | 消息可以重发，业务实体不能被重复创建 |
| aggregate.revision | 实体状态版本 | 客户端只接受更新版本，天然抗乱序与重复 |
| payload | 渲染所需快照 | 不放支付密码、账务明细与完整身份信息 |

三条演进规则：

- **业务 ID 和版本是同一个字段的两半**。业务 ID 回答"这是哪笔交易"，版本回答"这是它的第几个状态"。协议里少了版本，多人并发时就判断不出谁新谁旧，只能看到达顺序，可到达顺序在 IM 通道上根本没保证。
- **事件化命名**：`redpacket.created`、`redpacket.claimed`、`redpacket.expired`。命令式命名（比如"领取红包"）会诱导接收方把消息当指令执行，消息一旦被转发或重放，动作就重复了。
- **未知类型必须降级**：解析失败或不认识版本时，渲染成"暂不支持的消息"占位符，原始 JSON 留着排查，绝不让一条脏数据打崩整个消息列表。消息列表里本来就混着不同时期、不同版本、不同客户端写进去的数据，这条是通用要求，不是个别场景的补丁。

还有一条容易漏掉的规则：**类型名用字符串，不用数字枚举**。数字枚举看着紧凑，可它的含义全指望两端对约定版本的理解一致，哪一边把同一个数字理解成别的业务，解析器都不会报错，只会表现为"红包卡片渲染成了别的东西"。字符串类型名至少在日志和排查工具里能自解释，按类型统计解析失败率也方便。

解析结果建议收敛成密封类型，渲染层只做穷举分支，别到处判断字符串：

```dart
sealed class ChatEvent {
  const ChatEvent();
}

final class RedPacketCreated extends ChatEvent {
  const RedPacketCreated({required this.packetId, required this.revision});
  final String packetId;
  final int revision;
}

final class RedPacketClaimed extends ChatEvent {
  const RedPacketClaimed({
    required this.packetId,
    required this.revision,
    required this.receiverId,
  });
  final String packetId;
  final int revision;
  final String receiverId;
}

final class UnsupportedChatEvent extends ChatEvent {
  const UnsupportedChatEvent(this.rawType);
  final String? rawType;
}
```

迁移分四个阶段，不能一次切过去：

1. 客户端先上线双协议解析器，这个阶段只读旧格式；
2. 服务端双写：新信封加上旧客户端的必要字段，新旧客户端都能渲染同一条消息；
3. 看版本活跃率和解析失败率，确认旧客户端占比低于业务阈值；
4. 服务端停止写兼容字段，但客户端**永久保留**旧格式解析能力，历史消息还得能看。

## 三、发红包：配置、支付、创建业务实体、投递卡片

结论：顺序必须是"读配置 → 校验 → 支付 → 服务端创建业务实体 → 投递卡片"，顺序一反，就会冒出一条用户看得见却领不到的幽灵红包。

能发多少、能发几份，来自服务端下发的配置，不是写死在客户端：功能开关、单聊与群聊的可用性、份数范围、单笔固定上限、基于用户可用额度的百分比上限、支付密码与封面约束。最终可发金额取"固定上限"和"额度百分比上限"里小的那个。客户端校验只为即时反馈，全部规则服务端得重跑一遍。

配置和支付这两步的失败要分开跟用户说：额度不足或超出限额算业务拒绝，直接告诉用户现在能发多少，别让他反复试；支付取消是用户自己取消的，不能报成错误，回到输入页把已填内容留着就行；服务端创建失败就一定得明确"红包未发出、资金未冻结"，免得用户以为钱已经扣了。话术不准，交互问题就会升级成资金投诉。

金额一律用"分"做整数运算，不要用浮点数表示钱。拆分算法（二倍均值法）是最常见的答案：

```text
// 示意伪代码：二倍均值法拆分，金额单位为"分"
// 演示用途，未做参数校验
split(totalCents, count):
    remain      = totalCents
    remainCount = count
    result      = []
    for i in 1 .. count-1:
        upper = remain / remainCount * 2          // 均值的两倍为上界
        piece = randomInt(1, upper)
        piece = min(piece, remain - (remainCount - 1))   // 给后面每人留 1 分
        result.append(piece)
        remain      -= piece
        remainCount -= 1
    result.append(remain)                          // 最后一份拿剩余全部
    return result
```

比算法更要紧的是两个决策：

1. **预生成还是领取时计算**。预生成（发红包时一次拆好入库）直观，但过期退款得退回没领的那几份；领取时在事务里实时算，没有预存状态，天然支持动态调整。两者的并发控制和对账口径完全不一样，选型时先把这一条定下来。
2. **拆分必须发生在服务端事务里**。客户端算好金额再上传，等于把分钱权交给攻击者。

发送时序：

```text
用户        客户端            业务服务端                投递器        IM 服务
 │  填金额份数 │                    │                      │              │
 │────────────>│                    │                      │              │
 │  支付密码   │───创建(幂等键)────>│                      │              │
 │             │                    │ 校验限额/额度         │              │
 │             │                    │ 冻结资金+落库实体      │              │
 │             │                    │ 写待投递事件           │              │
 │             │<──实体 ID + 状态───│                      │              │
 │             │                    │───待投递事件─────────>│              │
 │             │                    │                      │──投递事件───>│
 │             │                    │                      │              │──> 会话成员
```

这个顺序不能反。先发卡片再创建实体，会话里就多出一条永远领不到的消息：用户点不开、退不了款、客服也解释不清。"第 4 步成功、第 5 步失败"一样危险：资金冻住了，会话里却没有卡片，用户连入口都找不到。这类缺口不是客户端 try-catch 能补的，服务端至少得提供一种能力：带幂等键的重发、短时间内能撤销未领取的红包，或用待投递事件表交给可重试任务投递（第七节）。

## 四、领红包：快照检查、服务端原子领取、定向回执

结论：可用性检查只是为了让用户少白点一次，真正建立资金事实的是服务端那条原子命令。

```text
用户        客户端                  业务服务端            IM 服务
 │ 点击卡片    │                        │                    │
 │────────────>│ 读本地快照(已领完/过期→详情)               │
 │             │──可用性检查(我是否已领/可否领)─>│            │
 │             │<────────可领取───────────│            │
 │             │ 播放开红包动画            │            │
 │             │──领取(幂等键+命令 ID)────>│            │
 │             │                        │ 事务内校验并原子入账 │
 │             │<──本次金额+最新状态───────│            │
 │             │ 用返回值更新卡片投影       │            │
 │             │──领取回执(定向)───────────────────────>│
 │  进入详情页  │                        │                    │
```

检查和执行之间有个并发窗口：两个用户可以同时通过可用性检查。所以领取事务里服务端必须重新校验状态、份数和过期时间，再用条件更新、行锁或唯一约束保证不超发。提前检查图的是交互体验，不是安全边界。

开红包动画这里还有一个容易做错的细节：动画只是等待期的过渡，不能当成功信号。领取请求返回之前，界面保持"处理中"并禁用重复点击；返回之后，看服务端结果决定是展示金额还是解释失败原因。如果动画播完就算成功，弱网下会出现"看到金额但服务端并未入账"的错觉，这种错觉在资金场景里代价极高。

回执得按会话类型分流：

| 场景 | 回执目标 | 原因 |
|---|---|---|
| 单聊红包 | 红包发送者 | 单聊只有两个人，直接发给对方 |
| 群红包 | 仅红包发送者 | 每次领取都广播会在群里刷屏 |
| 只有本机可见的状态提示 | 本地插入消息（只写本地、不投递），或只在本机渲染 | 不能用"发送后再删除"：删除是本地语义，对方在投递成功时已经可见，批量删除也不支持多端同步 |

群定向消息的语义、可用性和套餐能力由 IM 服务商定义，不是所有会话类型都支持；在单聊里创建定向消息是接口语义错误，正确做法是群聊走定向、单聊直发。

最容易被写错的一处是失败归因：**服务端领取已经成功、后续 IM 操作失败时，不能对用户说"领取失败"**。资金事实已经建立，回执和卡片更新只是通知同步。正确做法是记可观测日志、照常进入详情页，让用户看到服务端最终状态。把通知失败伪装成资金失败，会诱发重复请求、重复客服沟通，用户还可能认定"钱被吞了"。

| 操作 | 性质 | 失败后 |
|---|---|---|
| 可用性检查 | 只读查询 | 提示稍后重试，不改变任何状态 |
| 服务端领取 | 资金主交易 | 按错误码向用户说明，不确定就查详情 |
| 更新本地卡片投影 | UI 同步 | 记日志，由详情页或快照接口纠正 |
| 发送领取回执 | 通知同步 | 可重试、最终一致，不回滚资金事实 |

## 五、三层一致性模型：卡片快照、服务端查询、服务端命令

结论：客户端手里同时握着三份状态，谁排前面，看谁有权改变资金事实。

```text
第三层  服务端原子命令   创建 / 领取      唯一能改变资金状态，最终真值
              ↑ 校验
第二层  服务端查询       可用性 / 快照    交叉验证，结果随时可能被并发改变
              ↑ 兜底
第一层  卡片快照         消息体里的状态   立即可渲染，随时可能过期
```

| 层次 | 维护者 | 允许用来做什么 | 绝不允许用来做什么 |
|---|---|---|---|
| 卡片快照 | 消息体，投递时写入 | 列表渲染、状态角标、快速拦截明显失效 | 判定能否领取、判定已领金额 |
| 服务端查询 | 业务服务端 | 弹窗前的可用性确认、详情页真相、重连纠正 | 替代领取事务 |
| 服务端命令 | 业务服务端 | 建立资金事实、返回最终结果 | —— |

所以落到实处就两条规则：

- 列表页可以只依赖快照，图个流畅，但用户一点击、一看详情、一涉及金额，就必须回到服务端；
- 事件乱序时用版本号做单调合并：只接受 revision 更大的事件，发现版本跳号就拉一次快照纠正，别等下一个事件。

## 六、为什么不能让客户端改消息来维护领取名单

结论：一旦把"谁领过"写进消息体、交给客户端维护，领取名单就变成了一个没有事务、没有唯一约束、没有权限控制的共享变量。

### 6.1 用字符串子串判重

- **可观察现象**：有些用户点开自己从没领过的红包，界面却提示"你已领取"，然后就拦住了，没法继续。
- **业务后果**：用户觉得钱被吞了，客服工单跟着涨，同时"已领名单"和资金明细对不上，对账口径被污染。
- **通用成因**：领取人列表拿逗号分隔的字符串存，判重用的是子串包含。用户 ID 互为子串时（短 ID 是长 ID 的一部分）就会命中假阳性。
- **可迁移对策**：先解析成精确集合再判断；更彻底的做法是把名单移出消息体，改由服务端查询。

```dart
Set<String> parseUserIds(String? raw) => (raw ?? '')
    .split(',')
    .map((id) => id.trim())
    .where((id) => id.isNotEmpty)
    .toSet();

bool hasPicked(String? raw, String userId) =>
    userId.isNotEmpty && parseUserIds(raw).contains(userId);
```

精确匹配只是兼容存量协议的兜底修正，更根本的问题它没解决：名单为什么会在客户端。

### 6.2 多人并发改同一条消息

- **可观察现象**：群红包被多人同时领取之后，卡片上的已领人数偶尔比实际少，或者刚显示 5 人又退回 3 人；不同成员手机上的份数长期对不上。
- **业务后果**：用户对"还剩几份"判断错了，出现"看着有、点进去没了"的体验崩塌；服务端明细和消息体永久分叉，排查什么都得从日志重新拼事实。
- **通用成因**：客户端"读消息 → 改消息 → 上传"是典型的读-改-写循环，中间没有任何版本检测。N 个客户端并发操作同一条消息时，最后一次写入覆盖其余所有人；而消息在 IM 服务上是个全局共享对象，会话里每个成员都能改它。
- **可迁移对策**：客户端改消息只能用于本地渲染的即时反馈，不承担真值；跨端同步改用带版本的投影事件；用户进详情、重连或发现版本跳号时，用快照接口纠正本地投影。

版本化投影的最小形态是这样的：

```dart
enum RedPacketStatus { preparing, active, exhausted, expired, cancelled }

final class RedPacketProjection {
  const RedPacketProjection({
    required this.packetId,
    required this.status,
    required this.claimedCount,
    required this.totalCount,
    required this.revision,
    required this.claimedByMe,
  });

  final String packetId;
  final RedPacketStatus status;
  final int claimedCount;
  final int totalCount;
  final int revision;
  final bool claimedByMe;

  /// 只接受更新的版本，重复与乱序事件都会被自然丢弃。
  RedPacketProjection merge(RedPacketProjection incoming) =>
      incoming.revision > revision ? incoming : this;
}
```

投影只保留粗粒度状态：状态、已领份数、总份数、版本、我是不是已经领过。它不保存领取人全量列表，也不参与任何资金校验。如果确实想让原消息卡片在别的端更快看到"已领完"，可以评估 IM 服务商提供的消息扩展能力，只写有上限的粗粒度字段；上线前必须按实际 SDK 版本和套餐验证支持范围，扩展值终究还是 UI 快照，不是账本。

判断一个字段能不能放进消息体，只要问一句：**如果它在所有客户端上的值都不一致，会不会影响到钱**。会，它就只能待在服务端，消息里最多放一个用于渲染的近似值；不会（比如备注、封面、昵称快照），放在消息里就是合理优化，省掉一次网络请求，还天然随会话分发。

## 七、可靠性架构：Outbox、幂等与并发领取

结论：跨系统的一致性靠四件事凑齐：事务内写业务实体与待投递事件、幂等键、唯一约束兜底、至少一次投递配幂等消费。单看某一次请求的成败，说明不了一致性。

### 7.1 Outbox：资金已动，卡片未到

- **可观察现象**：偶尔出现"钱被冻了但聊天里没有红包"，用户反复下拉会话列表也等不到卡片，重进页面还是没有。
- **业务后果**：资金冻住了却找不到入口，只能人工退款；用户不知道发生了什么，客服也拿不出可查的证据链。
- **通用成因**：创建红包和"通知 IM"是两次独立的外部调用，中间哪一次崩溃、断网或进程被杀都会留下不一致。说白了，分布式环境里"两次远程写都成功"本来就保证不了。
- **可迁移对策**：Transactional Outbox。创建业务实体和写待投递事件放进同一个数据库事务，事务只做本地写入，**绝不在事务内调用外部 IM 接口**，投递交给独立任务重试。

```sql
-- 示意 DDL：红包实体与待投递事件
CREATE TABLE redpacket (
  id              VARCHAR(64) PRIMARY KEY,
  sender_id       VARCHAR(64) NOT NULL,
  conversation_id VARCHAR(128) NOT NULL,
  status          VARCHAR(32) NOT NULL,
  total_cents     BIGINT NOT NULL,
  claimed_cents   BIGINT NOT NULL DEFAULT 0,
  total_count     INT NOT NULL,
  claimed_count   INT NOT NULL DEFAULT 0,
  revision        BIGINT NOT NULL DEFAULT 1,
  expires_at      TIMESTAMP NOT NULL,
  idempotency_key VARCHAR(64) NOT NULL,
  UNIQUE (sender_id, idempotency_key)
);

CREATE TABLE outbox_event (
  event_id      VARCHAR(64) PRIMARY KEY,
  aggregate_id  VARCHAR(64) NOT NULL,
  event_type    VARCHAR(64) NOT NULL,
  payload       JSON NOT NULL,
  status        VARCHAR(16) NOT NULL,
  retry_count   INT NOT NULL DEFAULT 0,
  next_retry_at TIMESTAMP NULL,
  created_at    TIMESTAMP NOT NULL,
  delivered_at  TIMESTAMP NULL,
  im_message_id VARCHAR(128) NULL
);
```

```text
-- 示意伪代码：创建红包的本地事务
BEGIN
  校验幂等键 —— 命中则直接返回首次结果
  校验发送人资格、限额、份数、可用额度
  冻结资金并写冻结流水
  INSERT redpacket   (status = PENDING_DISPATCH)
  INSERT outbox_event(status = PENDING, type = redpacket.created)
COMMIT
```

投递器用行锁或等价的队列抢占方式取任务，状态机很窄：

```text
PENDING ──抢占（带租约）──→ SENDING
SENDING ──IM 投递成功──→ DELIVERED（红包转 ACTIVE）
SENDING ──可重试失败──→ PENDING（指数退避，retry_count + 1）
SENDING ──超过最大次数──→ DEAD（进入补偿队列）
SENDING ──租约超时未被回收──→ PENDING（崩溃恢复出口）
```

`SENDING` 必须有一个崩溃恢复出口，不然它自己就成了新的"中间态陷阱"：投递器抢占之后进程崩了或被重启，任务就永久卡在这个状态，既不重试也不进死信，红包一直停在"准备中"，资金冻结到天荒地老。做法是抢占时写入带过期时间的租约（`lease_until`），由看门狗把"租约已过期但仍在 `SENDING`"的任务回收成 `PENDING`（或超过重试上限直接判 `DEAD`）。

三个细节不能省：租约要由投递方在投递期间**续期**，不然长耗时投递会被误判成崩溃，引发重复投递；回收动作必须**幂等**，免得看门狗和正常投递同时改同一条任务；租约回收和重试上限要共用同一个计数器，不然每次回收都把计数清零，死信永远进不去。这也解释了为什么这类系统必须有基于时间的兜底：跨系统投递没有事务可用，任何中间状态都得靠时间捞回来。

红包在 `PENDING_DISPATCH` 期间只冻结资金，不允许领取。如果卡片先到、状态还没切过来，可用性检查返回"准备中"，客户端显示"红包准备中"并做短轮询，别直接报错。

死信补偿只有三种处置：还没投递且没有任何领取记录，取消红包、解冻全部金额；有投递证据但状态回写失败，修正成 ACTIVE，不退款；判定不了的进人工对账队列，**绝不让客户端决定资金结果**。

### 7.2 IM 已投递但业务状态未回写

- **可观察现象**：红包卡片在会话里显示正常，主表状态却还是待投递；用户点进去一会儿能领、一会儿报"红包不存在"，换了入口表现又不一样。
- **业务后果**：同一笔红包在不同入口给出矛盾答案，用户反复重试；要是投递任务再把状态回滚，还会出现"已领过的红包被重新放回可领"这种更严重的问题。
- **通用成因**：投递器在"IM 已成功、本地还没标记成功"的窗口里崩溃或超时，重启后分不清"没发出去"和"发出去了但没记住"。这是跨系统的典型歧义，不是偶发 bug。
- **可迁移对策**：把事件 ID 当幂等标识，投递结果允许重复到达；接收端按事件 ID 去重，重复事件只刷新投影，不重复计数、不重复渲染；投递器重发同一事件必须带相同的事件 ID 和版本，而且永远不做"状态回退"的写入。

### 7.3 领取请求超时后的重复领取风险

- **可观察现象**：弱网下用户点了一次领取，界面转圈之后报超时；用户再点一次，出来两条领取记录，或者提示"你已领取"，金额却跟第一次不一样。
- **业务后果**：同一个人拿到两笔钱，红包份额被提前消耗，其余成员少领；对账时主表已领金额和明细合计对不上，只能人工冲正。
- **通用成因**：网络超时不代表服务端执行失败。用户重复点击、客户端自动重试、App 重启后恢复请求，都会重发同一个动作，服务端就把它当成了新请求。
- **可迁移对策**：所有写接口都接受客户端生成的幂等键，服务端保存"用户 + 操作 + 幂等键"和首次响应。同键同参数重复请求直接返回首次结果；同键不同参数返回冲突错误，免得一个键被用到两笔不同交易上。接口路径是通用示意：

```text
POST /api/red-packets
Idempotency-Key: <客户端生成，全局唯一>

POST /api/red-packets/{packetId}/claims
Idempotency-Key: <客户端生成，全局唯一>
```

### 7.4 唯一约束是最后一道保护

```sql
-- 示意 DDL：领取明细与两条唯一约束
CREATE TABLE redpacket_claim (
  id              VARCHAR(64) PRIMARY KEY,
  packet_id       VARCHAR(64) NOT NULL,
  receiver_id     VARCHAR(64) NOT NULL,
  amount_cents    BIGINT NOT NULL,
  idempotency_key VARCHAR(64) NOT NULL,
  created_at      TIMESTAMP NOT NULL,
  UNIQUE (packet_id, receiver_id),
  UNIQUE (receiver_id, idempotency_key)
);
```

```text
-- 示意伪代码：领取红包的原子事务
BEGIN
  1. 查幂等记录，已有结果直接返回
  2. 锁定红包行，校验 ACTIVE、未过期、剩余份数 > 0
  3. 事务内计算本次金额（按"分"做整数运算）
  4. INSERT 领取明细 —— 由唯一约束挡住同一人重复领取
  5. 累加已领份数与已领金额，revision + 1
  6. 最后一份被领走时状态改为 EXHAUSTED
  7. 写账务流水与 redpacket.claimed 待投递事件
COMMIT
```

行锁、条件更新、乐观版本号都能用，但唯一约束必须存在：它是"并发"和"重试"两种风险同时出现时唯一不会失效的那一层。只靠缓存里的分布式锁，锁一过期或者缓存一抖，超发就会直接从数据库层落下来。

### 7.5 至少一次投递 + 幂等消费

投递器可能在"IM 已成功、本地未标记成功"时崩溃，重启后重发同一个事件 ID。跨系统要严格 exactly-once 很难，务实的目标是把投递语义收敛成"至少一次投递 + 幂等消费"：客户端按事件 ID 去重，服务端按事件 ID 记账。这条原则也解释了为什么事件 ID 必须出现在协议信封里：它是重试和去重的唯一依据。

## 八、SDK 隔离、可观测性与对账

结论：页面别直接跟 IM SDK 说话，也别自己判断资金结果；可观测性和对账是把"猜"变成"查"的基础设施。

把边界收敛成两个接口：一个管收发自定义消息，一个管资金相关的 HTTP 命令和快照。

```dart
abstract interface class ChatGateway {
  Stream<ChatEvent> get events;

  Future<void> sendBusinessEvent({
    required ChatEvent event,
    Set<String> visibleTo = const {},
  });
}

abstract interface class RedPacketRepository {
  Future<void> create({required int totalCents, required int count});

  Future<void> claim({
    required String packetId,
    required String idempotencyKey,
  });

  Future<RedPacketProjection> getSnapshot(String packetId);
}
```

- 消息适配层吸收单聊和群聊的投递差异、定向消息的可用性差异，还有"创建消息"这类两步返回（错误码和数据都要判空，不能强制解包）；
- 仓储层吸收 HTTP 错误码和幂等响应；用例层只管组织业务流程，返回值由服务端结果决定，IM 回执成不成功都不影响它；
- 收益是可测性：超时、重试、事件重复、事件乱序都能用假实现覆盖，不用真的登录 IM 才能验证。

这种划分还有个附带收益：IM SDK 升级只影响消息适配层的一个实现。页面直接调 SDK 的写法，一次升级得在多个页面分别回归；收敛成接口之后，"哪些行为依赖 SDK 的返回结构"就变成一份能枚举的清单，升级前按清单做定向验证就行。

```text
红包主表冻结/已领金额
        ↕
领取明细金额合计
        ↕
账务流水的冻结、入账、退回
        ↕
待投递事件的投递与死信状态
```

对账规则至少覆盖这几条：已领金额等于领取明细合计；发送者冻结金额等于已领 + 待领 + 已退；`EXHAUSTED` 的已领份数等于总份数；`EXPIRED`/`CANCELLED` 红包的未领部分已经生成退回流水；`ACTIVE` 红包必须有一条成功投递的创建事件；已投递事件保留 IM 消息 ID，方便排查。发现差异时先冻结异常实体的后续操作，再执行可重复的补偿命令；补偿命令一样要带幂等键，不然任务重启会重复退款。

可观测性：命令 ID、事件 ID、红包 ID、IM 消息 ID 要贯穿客户端日志、HTTP 请求、数据库记录和投递日志。不记录支付密码、登录凭证、完整身份信息和不必要的金额明细。脱敏要落到具体字段上，实现上建议把"可记录字段"做成白名单，别逐处判断"这个字段敏感吗"。逐处判断在字段增删时必漏。

| 指标 | 用途 |
|---|---|
| 创建量 | 业务基线与异常波动 |
| 领取冲突数 | 最后一份竞争与重复领取情况 |
| 投递延迟 | 创建成功到卡片可见的时间 |
| 投递重试数 | 对 IM 依赖的短期稳定性 |
| 死信数 | 需要补偿或人工介入的事件量 |
| 事件解析失败数 | 协议兼容与脏数据问题 |
| 投影版本跳号数 | 事件丢失、乱序与快照纠正频率 |

## 九、常见错误与修正表

结论：下面这些问题，在"有状态的业务 + 消息通道"的系统里会反复冒出来，先看业务后果，再决定对策的轻重。

| 问题 | 业务后果 | 对策 |
|---|---|---|
| 用字符串子串判断"我是否已领" | 用户被误判为已领，无法领取 | 解析为精确集合作判重；名单移出消息体 |
| 客户端读-改-写消息维护领取名单 | 并发覆盖，多端状态分叉 | 真值放服务端；客户端只维护版本化投影 |
| 先投递卡片再创建业务实体 | 会话里出现永远领不到的幽灵红包 | 顺序固定为"创建实体 → 投递卡片" |
| 领取请求超时后无幂等键直接重试 | 同一人重复领取，份额被提前消耗 | 写接口强制幂等键 + 唯一约束 |
| 领取事务只靠分布式锁，无唯一约束 | 锁失效时超发，主表与明细不一致 | 唯一约束作为最后一道保护 |
| 服务端领取成功、IM 回执失败时提示"领取失败" | 用户重复请求，认为钱被吞 | 回执失败只记日志，继续展示服务端事实 |
| 在单聊里创建定向群消息 | 回执发送失败，语义错误 | 群聊定向、单聊直发，按会话类型分流 |
| 自定义消息不带版本与事件 ID | 字段一改旧客户端解析崩溃、无法去重 | 版本化信封 + 事件 ID + 未知类型降级 |
| 未知类型消息直接抛异常 | 单条脏数据打崩整个消息列表 | 降级为"暂不支持的消息"占位 |
| 金额使用浮点数计算 | 拆分与合计出现分位误差 | 一律用"分"的整数运算 |
| 过期红包不退款、死信不补偿 | 资金被长期冻结，无法回收 | 到期退款与死信补偿形成闭环 |
| 创建消息结果强制解包 | 创建失败时崩溃 | 错误码与数据两层都判空 |
| 投递中间态没有超时回收 | 任务永久停在投递中，红包长期"准备中"、资金一直冻结 | 抢占时写租约，看门狗回收过期任务，且回收幂等 |

## 十、验收清单

结论：验收得按失败路径来设计，主流程点通不算完。

| 场景 | 验收标准 |
|---|---|
| 发红包 | 资金冻结、实体落库、卡片投递三者最终一致；金额与份数由服务端校验 |
| 重复点击发送 | 同一幂等键多次请求只产生一个红包与一笔冻结流水 |
| 并发领取最后一份 | 只有一个请求成功，主表、明细与账务金额完全一致 |
| 同一用户重复领取 | 被唯一约束拒绝，返回首次结果而非第二笔金额 |
| 领取请求超时重试 | 重试返回首次结果，不新增明细、不重复入账 |
| IM 投递失败 | 待投递事件可重试；恢复后卡片最终可见，且不重复渲染同一事件 |
| 投递达到死信阈值 | 未投递且无领取记录的红包被取消并解冻，不留不可访问的活跃资金 |
| 投递器抢占后进程崩溃 | 租约到期后任务被回收重投，不会永久停在"投递中"，红包也不会长期停在"准备中" |
| 跨版本消息解析 | 新旧协议都能渲染同一条消息；未知类型降级为占位，列表不崩 |
| 旧客户端兼容 | 迁移期内旧客户端仍可显示与领取；历史消息始终可读 |
| 红包过期与退款 | 到期后未领部分生成退回流水，卡片显示为已过期且不可再领 |
| 事件乱序与重复 | 版本更小的事件被丢弃；版本跳号触发一次快照纠正 |
| 对账 | 任意异常交易可通过红包 ID 追溯到命令 ID、事件 ID、账务流水与 IM 消息 ID |

## 十一、面试问答

结论：这些问题最终都指向同一条边界，谁有权改变事实。

**Q1：为什么红包不能只用 IM 自定义消息实现？**
因为 IM 解决的是投递，不是交易。自定义消息的正文由客户端构造、由客户端修改、在会话内共享可写，天然没有原子性、没有唯一约束、没有权限边界。资金要求"唯一、原子、可追溯"，这三条只能在服务端事务里满足。所以也能推出客户端改消息的唯一合法用途：本机渲染的即时反馈。判据是"改了之后错了会不会影响钱"，不是"能不能改"。

**Q2：既然有可用性检查，为什么还要服务端重新校验？**
检查和执行之间有时间窗口，两个用户可以同时通过检查。可用性检查的作用是让用户在明显不可领的时候少点一次，省掉无谓的开红包动画；真正的约束得在领取事务里重新施加，不然并发场景下份数必然超发。

**Q3：IM 回执失败，能不能告诉用户"领取失败"？**
不能。服务端领取返回成功的那一刻，资金事实就建立了，回执只是通知同步。把通知失败当成资金失败，用户会重复领取、重复找客服，还会怀疑资金安全。正确做法是记可观测日志，继续展示服务端最终状态。

**Q4：为什么群领取回执要做成定向消息？**
回执的受众只有红包发送者。每次领取都往全群投递一条消息的话，一个 200 人的群红包会产生 200 条噪声消息，正常聊天直接被淹没。定向消息既能保证发送者收到，也不打扰其他人；同时要注意定向能力受会话类型和套餐约束，单聊场景应该直发。

**Q5：自定义消息协议为什么必须带版本和事件 ID？**
版本解决"怎么变"：没有版本就只能靠字段在不在做兼容判断，第一次改名就会让旧客户端解析失败。事件 ID 解决"是不是处理过"：网络重试、投递重试、用户重复点击都会让同一条事件到达多次，没有事件 ID 就没法去重，排查时也没法把客户端日志、服务端事件和 IM 消息串成一条链路。

**Q6：为什么说"至少一次投递 + 幂等消费"比追求 exactly-once 更现实？**
因为投递器可能在"IM 已成功、本地未标记成功"的窗口里崩溃，跨系统没法原子地同时提交两边的状态。与其引入代价高昂的分布式事务，不如承认重复是常态：投递端允许重发同一事件 ID，接收端按事件 ID 去重，业务结果依然唯一。
