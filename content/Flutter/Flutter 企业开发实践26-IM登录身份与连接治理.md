# IM 登录、身份与连接治理

> 结论：登录类线上事故几乎跟"SDK 调用写错了"没关系，根源是身份、凭证、连接这三件事被压成了一个布尔值。压扁之后，重试会被自己拦死，遮罩会盖错地方，用户被踢了还能接着用。这篇只回答一件事：谁在登录、什么时候登录、失败了怎么自愈、连接状态归谁管。消息收发看第 25 篇，好友与群管理看第 27 篇，自定义消息和红包看第 28 篇。核验版本：腾讯云 Chat Flutter SDK 8.6.x / TUIKit 4.0.x，截至 2026-08。

---

## 一、身份、凭证与连接是三件事

结论：IM 登录的问题，几乎都来自把这三件事合成一个"是否已登录"的判断。

| 术语 | 含义 | 谁负责 |
|---|---|---|
| 业务用户 ID | 业务服务端的账号主键 | 业务服务端 |
| IM userID | IM 服务内唯一标识账号的字符串，是消息、会话、漫游数据的主键 | 服务端决定 |
| 凭证（UserSig） | 服务端用密钥签发、代表某个 IM userID 的短期登录票据 | 服务端签发，客户端持有 |
| 连接状态 | 与 IM 服务之间长连接的存活情况 | SDK 维护，业务只读 |
| 门禁状态 | 业务判断"用户此刻有没有资格使用 IM"，如签到、实名 | 服务端下发 |

三层出问题时，表现、归属和处置完全不一样：

| 出问题的层 | 典型表现 | 正确处置 |
|---|---|---|
| 身份映射 | 登录成功但历史消息对不上、换设备看不到自己的会话 | 冻结映射规则、修数据 |
| 凭证 | 登录被拒，错误码指向凭证过期或与 userID 不匹配 | 清缓存、重拉凭证、重登，**不重试** |
| 连接 | 登录超时、切前后台后消息延迟、断网恢复慢 | 交给 SDK 重连，客户端只做恢复后对齐 |

这三者变化的频率也不一样：凭证几小时一变，连接一分钟能抖好几次，门禁一天一变。用一个状态值来表达它们，就会出现"网络不好却被要求签到"这种错位提示。

## 二、业务账号到 IM userID 的映射

结论：这个映射一旦跟着历史数据落库，它就升级成账号主键了，不再只是"一个字段"。

**稳定**：消息、会话、漫游记录、离线推送的定向标识，主键都是 IM userID。换掉它就等于把账号切成两半：老会话找不回来，未读从零开始。**唯一**：可回收的值（离职工号、临时编号）会让两个真实用户共用一个身份。**不可变**：手机号会换绑，昵称会改，设备标识重装就变，这几个只能当登录凭据。

| 候选映射键 | 稳定 | 唯一 | 用户可读 | 主要风险 |
|---|---|---|---|---|
| 业务数字主键 | 高 | 高 | 差 | 多环境易串号，用户无法口头传播 |
| 公开邀请码 / 展示 ID | 取决于能否重生成 | 高 | 好 | 允许重生成则身份漂移，历史断裂 |
| 手机号 | 低（换绑） | 中（有重复期） | 中 | 归属错乱，且把隐私字段暴露给 IM |
| 昵称 | 低 | 低 | 好 | 可重复可修改，绝不可做主键 |

**案例约束（产品选择，不是通用推荐）**：案例直接把业务侧对用户公开、唯一、稳定的"邀请码"拿来当 IM userID，省掉一层映射表，而且邀请码能分享、能扫码、能搜索。代价是公开标识把"可定位"放大成了"可发消息"。前提是邀请码**不可变**，而且由服务端用唯一约束生成；哪天允许用户自己重新生成，方案就退化成上表第二行的风险。

**可迁移原则**：选服务端生成、有唯一约束、永不重用的字段。映射由服务端下发，客户端不要在本地拼。它一旦成了历史主键就冻结。另外留一份显式映射记录，给风控和对账用。

## 三、UserSig 的生命周期

结论：UserSig 是短期凭证，不是账号属性。要管好四件事：谁签发、存在哪、什么时候重拉、怎么让它不进日志。

### 3.1 服务端签发

SDKAppID 只标识应用，不是密钥，明文放客户端没关系；签发用的密钥必须只放在业务服务端。客户端只向业务接口要凭证，拿到 `{ IM userID, UserSig }` 再交给 IM SDK。

凭证跟 userID 是**绑定**的，不能随便拿个 userID 去套一张凭证，所以缓存必须按身份隔离，"凭证与 userID 不匹配"要单独处理。签发接口由业务登录态保护，"IM 登录跟着业务登录走"就落在这里。同一个账号，在任何设备上都是同一个 IM userID。

### 3.2 缓存按身份隔离

缓存有两个用处：少发几次签发请求，接口临时不可用时还能兜底。但键里必须带上身份。

```dart
/// 缓存键必须携带身份，否则换账号后会读到上一个账号的凭证
String userSigCacheKey(String userId) => 'im_user_sig::$userId';

Future<void> cacheUserSig(String userId, String userSig) async {
  await _storage.write(userSigCacheKey(userId), userSig);
}

Future<String?> readCachedUserSig(String userId) async {
  return _storage.read<String>(userSigCacheKey(userId));
}
```

键里只有凭证、没有身份，是换账号场景最经典的事故：A 退出、B 登录，结果读到 A 的凭证，轻则登录被拒，重则把 B 的会话挂到 A 的身份上。所以登出和切号都得清缓存。也别假设有效期，能活多久由签发方和套餐决定。

### 3.3 服务端不可用时怎么降级

降级是一条有顺序的链：接口成功，就用新凭证登录并写进缓存；接口失败但缓存里有这个身份的凭证，就用缓存的登录；两个都不可用，就进"失败"终态，**不要无限循环请求**。降级不是长期方案，缓存的凭证迟早会失效。用户在线的时候，也别因为一次签发失败就把他踢下线。

### 3.4 过期与签名类错误码

6206、70013、70014、70016、70017 这几个码，实践中都指向"凭证过期或非法"。这是经验归纳，不是官方约定，最终以官方文档为准。原则只有一条：**签名类错误不重试**。重试一万次结果都一样，只会刷屏，让用户更久停在失败态。

```text
签名类错误码 → 清凭证缓存 → 状态复位为空闲 → 按实例移除本端监听器 → 重拉凭证 → 走同一个登录状态机（不是另一条路径）
```

这里麻烦的地方在于，还得跟被踢下线区分开：被踢是账号级事件，另一端正在用同一个账号，本端不该自动恢复；凭证过期重拉一下就自愈了。两者要是共用一条路径，就会出现"被踢后自动重登、把另一端踢回去"的互踢死循环。

### 3.5 凭证别进日志

- 现象：登录日志把完整凭证打了出来，而这份日志同时流向本地调试输出、错误上报和用户反馈附件。
- 后果：凭证就等于"以这个用户身份登录"的能力。拿到它，在有效期内就能冒充这个用户读消息、发消息，改密码也不会让它提前失效。
- 成因：把登录参数当成普通调试信息，跟 userID、错误码一起被日志辅助函数拼进了输出。
- 对策：只记 IM userID、错误码、尝试次数。错误上报不带请求体。日志进工单系统之前先过一遍脱敏规则。

```dart
// 反例
log('login userId=$userId userSig=$userSig');

// 正例
log('login userId=$userId userSigLength=${userSig.length} attempt=$attempt');
```

## 四、初始化与登录状态机

结论：登录是一个状态机，不是布尔值。它最容易死在"用自己写的守卫拦住自己写的重试"上。

### 4.1 初始化成功了才置位

案例选了**懒初始化**：初始化不放在冷启动，放在首次需要登录的时候触发。可迁移的原则是，初始化触发点要跟"首次使用"同源。

**初始化失败了，却仍被标记成已初始化**
- 现象：某次启动初始化失败，之后每次启动都跳过初始化直接登录，报错却指向 SDK 内部状态。
- 后果：用户永远登不上，提示跟真实原因（初始化从没成功过）没关系。
- 成因：幂等标志只记了"调用过"，没记"成功过"。
- 对策：只在明确成功之后置位。失败了就保持未初始化，好让下次还能重试。依赖它的配置和能力注入，放进成功分支里。

```dart
bool _sdkReady = false;

/// 返回 false 表示本次未就绪，调用方不要继续登录
Future<bool> ensureSdkReady() async {
  if (_sdkReady) return true;

  final bool? ok = await _core.init();   // 失败或抛异常都不置位
  if (ok != true) return false;

  _applyTheme();                          // 这两步依赖初始化成功
  _injectPermissionBridge();
  _sdkReady = true;
  return true;
}
```

### 4.2 四态状态机与并发守卫

| 当前状态 | 事件 | 下一状态 |
|---|---|---|
| loggingIn | 再次收到登录请求 | loggingIn（守卫丢弃） |
| loggingIn | 登录成功 | online，注册监听器 |
| loggingIn | 凭证类错误 | idle（清缓存后重拉凭证） |
| loggingIn | 可重试错误且次数未用尽 | loggingIn（循环内继续） |
| loggingIn | 次数用尽，或不可重试错误 | failed |
| online | 登出 / 被踢 / 业务登出 / 凭证过期 | idle |
| failed | 门禁 / 用户重试 / 生命周期事件 | loggingIn |

守卫的语义得写清楚：**并发指的是"同一时刻只允许一次登录在飞"**。它是入口闸门，不是重试开关，也不是"用户是不是已经登录了"；把它当成后者的，就会出 4.4 那个故障。

### 4.3 重试要有上限

重试得满足四点：次数有上限、间隔有节奏、每条失败路径都有显式终态、**异常路径也必须落到终态**。抛异常直接跳出函数，跟递归被守卫拦住是同一个后果：状态停在中间态。

```dart
enum LoginStatus { idle, loggingIn, online, failed }

/// 凭证过期或非法的错误码（实践归纳，最终以官方文档为准）
const Set<int> sigInvalidCodes = {6206, 70013, 70014, 70016, 70017};

abstract class ImGateway {
  /// 返回 SDK 错误码，0 表示成功
  Future<int> login({required String userId, required String userSig});
}

class LoginCoordinator {
  LoginCoordinator(this._gateway);

  final ImGateway _gateway;
  final ValueNotifier<LoginStatus> _status = ValueNotifier(LoginStatus.idle);

  ValueListenable<LoginStatus> get status => _status;

  bool get canLogin =>
      _status.value == LoginStatus.idle || _status.value == LoginStatus.failed;

  static const int _maxAttempts = 3;
  static const Duration _retryDelay = Duration(seconds: 5);

  Future<void> login({required String userId, required String userSig}) async {
    if (userId.isEmpty || userSig.isEmpty) return;
    if (!canLogin) return;                          // 并发守卫：入口只放行一次
    _status.value = LoginStatus.loggingIn;          // 状态只置位一次

    try {
      for (int attempt = 0; attempt < _maxAttempts; attempt++) {
        final int code = await _gateway.login(userId: userId, userSig: userSig);

        if (code == 0) {
          _status.value = LoginStatus.online;
          return;
        }
        if (sigInvalidCodes.contains(code)) {
          _status.value = LoginStatus.idle;         // 凭证问题不重试
          return;
        }
        if (attempt < _maxAttempts - 1) {
          await Future<void>.delayed(_retryDelay);
        }
      }
      _status.value = LoginStatus.failed;           // 重试用尽
    } catch (_) {
      // 网关抛异常（网络层异常、解析失败）同样要落到终态，
      // 否则状态停在"登录中"，之后所有登录入口都被并发守卫挡住
      _status.value = LoginStatus.failed;
    } finally {
      // 不变量：函数返回时状态一定不是"登录中"
      assert(_status.value != LoginStatus.loggingIn, '登录结束却停在中间态');
      if (_status.value == LoginStatus.loggingIn) {
        _status.value = LoginStatus.failed;
      }
    }
  }
}
```

### 4.4 最要命的一处：递归重试被"登录中"守卫拦死

- 现象：网络一抖，界面就长期停在"正在连接"，日志里只有一条开始登录的记录。
- 后果：用户在没法自愈的状态里丢掉了 IM 能力。业务侧的"重新登录触发条件"通常写的是"状态空闲或失败"，而状态卡在"登录中"，所有自愈入口就一起失效了。
- 成因：一个状态机同时扛了并发守卫和重试入口两件事。失败分支递归调用登录函数，登录函数第一步却是"状态已是登录中就直接返回"，递归进来的那一层被自己拦住了；失败分支又没复位状态。
- 对策：重试收敛为同一函数内的有界循环；状态在入口只置位一次；每条失败路径显式写终态，并用断言把"停在中间态"当成不变量被违反。

```text
错误写法：递归重试 + 入口守卫
点登录 → 守卫通过 → 置为"登录中" → 失败 → 递归调用自己 → 命中"已是登录中" → 直接返回
（重试次数永远是 0，状态永久停在"登录中"）

正确写法：同一函数内的有界循环
点登录 → 守卫通过 → 置为"登录中" → 循环内重试（间隔 5 秒，上限 3 次）→ 用尽后置"失败"
```

它难被发现，是因为界面提示一直没消失，看着像"网络很慢"，不像"重试根本没发生"。

### 4.5 失败路径的状态复位

| 出口 | 终态 | 说明 |
|---|---|---|
| 参数为空 / 业务未登录 | 不进入状态机 | 保持 idle，不消耗尝试次数 |
| 凭证类错误 | idle | 清缓存后重拉凭证 |
| 可重试错误且次数用尽 | failed | 允许门禁或生命周期事件再次触发 |
| 不可重试错误（如账号被封禁） | failed | 必须给用户明确提示，不能静默 |
| 网络异常 / 未知异常 | failed | catch 里也要复位 |

复位写在每条 `return` 前面很容易漏，用 `try / finally` 包住。

## 五、连接恢复、生命周期与多端互踢

结论：连接状态只能有一个地方写，五种外部事件（前后台、断网、主动登出、凭证过期、被踢）全得收敛到同一处。

### 5.1 前后台切换

长连接由 SDK 维护。回到前台时**不要重新登录一次**，那会打断会话同步，可能又注册一组监听器，还会以"同端重复登录"的形式触发互踢。正确做法是读一次连接状态，断开就走同一个"恢复"入口，同样受状态机守卫约束。从深链或者通知进来的时候，先把身份和连接等到就绪，再渲染目标页。

### 5.2 断网重连

断网期间 SDK 自己重连，客户端不用插手。说白了，客户端要管的是**恢复之后的对齐**，把错过的增量状态补齐，未读展示见第 25 篇。这里有个硬约束：幂等。重复触发不能重复注册监听器，不能重复拉历史，也不能重复累加未读。

### 5.3 主动登出

登出是一条有序的链，顺序原则是：先断"下游消费者"，再断"上游事件源"，最后才改状态。

```dart
Future<void> logout() async {
  _subscriptions.disposeAll();       // 1. 先断 UI 订阅，避免回调写回
  await _gateway.logout();           // 2. 通知 IM 服务断开
  await _removeListeners();          // 3. 按实例移除自己注册的监听器
  await _clearCachedUserSig();       // 4. 清凭证缓存
  _status.value = LoginStatus.idle;  // 5. 最后复位状态，作为唯一出口
}
```

**异步清理函数被写成同步签名**
- 现象：点了退出立刻回到登录页，但 IM 那边还是登录态。
- 后果：用户以为"已经退出"，账号却还在线。切账号的时候更严重，上一个账号的监听器还在回调。
- 成因：清理链路内部有好几个异步步骤，函数签名却是同步的，调用方拿不到"已完成"的信号。
- 对策：清理函数返回可等待的结果，内部步骤串行执行，不要并发。

### 5.4 凭证过期

复用 3.3 和 3.4 的链路：清缓存 → 复位状态 → 移除监听 → 重拉凭证 → 走**同一个**登录状态机。两条路径要是并存，一条走 idle → loggingIn，另一条直接调登录接口，同时发生就会出两组监听器。

### 5.5 多端互踢

被踢下线是账号级安全事件：同一个账号在另一端登录了，本端被 IM 服务断开并收到回调。这时候只提示一句不够，只清 IM 侧也不够，否则用户会卡在"半退出"状态：IM 掉线了，业务 token 还在。

| 断线原因 | 用户可见行为 | 必须清理的范围 |
|---|---|---|
| 主动登出 | 无提示，回登录页 | IM 状态 + 凭证缓存 + 监听器 |
| 凭证过期 | 通常无感 | 凭证缓存 + 状态复位 |
| 被踢下线 | 阻断式弹窗 | 全局登出（业务态 + 本地数据 + IM 状态） |

```text
另一端登录 → 断开本端 → 收到"被踢"回调 → 阻断式提示 → 广播"账号级登出" → 回到登录页
```

被踢意味着账号可能被人盗用，提示不能一闪而过。**被踢后不要自动重新登录**，否则会跟另一端互踢成死循环，这个决定权得交回用户。

### 5.6 后台与离线：长连接不等于通知

- 现象：App 在前台，消息和音效都正常；退到后台几分钟，或者进程被回收之后，IM 消息就没任何系统通知了。
- 后果：IM 偏偏在"App 不在前台"这个最需要它的场景里失效，用户回到 App 才发现消息积压。
- 成因：把业务推送通道当成了 IM 的离线触达通道。业务通知走厂商通道是正常的，但 IM 消息的离线通知得在 IM 服务商那边单独配一次，才能复用同一批厂商通道。
- 对策：在线消息和离线通知是两条链路，验收的时候分开测。想要"App 被杀也能收到通知"，就必须把离线推送配置做完。

## 六、监听器与状态同步

结论：监听器是有主的东西。谁注册谁持有，谁持有谁移除，而且移除必须精确到实例。

### 6.1 保存实例并按实例移除

会话、好友、消息这三类事件各有一对注册/移除方法，移除方法的参数是**可空**的。参数为空，语义就是"清空这一类全部监听器"，所以业务得自己做所有权管理：

```dart
/// 登录后注册、登出前移除，注册与移除严格配对
class ImListenerOwner {
  ImListenerOwner({required this.add, required this.remove});

  final Future<void> Function(Object listener) add;
  final Future<void> Function(Object listener) remove;

  final List<Object> _owned = <Object>[];

  Future<void> attach(List<Object> listeners) async {
    await detach();                     // 先移除，让注册是替换语义，不是叠加语义
    for (final Object listener in listeners) {
      await add(listener);
      _owned.add(listener);
    }
  }

  Future<void> detach() async {
    for (final Object listener in _owned) {
      await remove(listener);           // 按实例移除，不影响其它所有者
    }
    _owned.clear();
  }
}
```

把注册与移除收口到同一对方法（`attach` / `detach`），登出、凭证过期、重登前、账号切换都只调这一个入口。

### 6.2 无参移除会清空组件库自己注册的监听

- 现象：登出再登进来，会话列表就不自动刷新了，未读数和音效重启之前一直不对。
- 后果：用户看到的是"消息刷新不出来"，而且它只在特定操作序列后才出现（先登出，再登录，再收消息）。
- 成因：把"移除监听"当成了无状态清理。UI 组件库初始化的时候，也向同类事件注册了监听器来刷新列表。业务的本意是清掉自己那份，实际执行的却是"清空该类全部监听器"，而组件库不会因为登出就重新初始化。
- 对策：按实例移除；注册与移除收口到同一对生命周期方法。

### 6.3 重登后监听叠加，回调重复

- 现象：同一条消息音效播两遍、未读数一次加 2、好友申请红点闪烁。
- 后果：用户的感受是"消息重复"，未读被加倍之后得点好几下才能清零，他慢慢就不信这个未读数了。
- 成因：登出的时候旧实例没被真正移除，重登又注册一批新的，N 个实例就有 N 次副作用。
- 对策：注册之前先移除，让注册具备替换语义；回调副作用尽量做成幂等；把"一次登录后监听器实例恰好一组"当成可观测指标盯着。

### 6.4 外部整数怎么安全映射成枚举

- 现象：好友申请列表偶尔整体不刷新，异常是范围越界。触发条件通常是外部返回了客户端不认识的类型值。
- 后果：一条脏数据打崩整个回调，用户看不到新的好友申请。
- 成因：把外部返回的整数直接当成本地枚举数组的下标。本地枚举长度是编译期常量，外部取值范围却是运行期的变量。
- 对策：用枚举的 `index` 做等值比较，未知取值走明确降级分支（忽略 / 默认 / 上报）。

```dart
// 反例：外部整数做数组下标，越界就抛
final type = FriendApplicationTypeEnum.values[rawType];

// 正例：直接比较 index，未知取值安全跳过
// 这里必须用 final：枚举取值的 index 是属性访问，不能出现在 const 表达式里，
// 写成 const int 会直接报 const_eval_property_access，编译不过
final int incomingIndex =
    FriendApplicationTypeEnum.V2TIM_FRIEND_APPLICATION_COME_IN.index;

final incoming =
    applications.where((a) => a.type == incomingIndex).toList();
```

### 6.5 哪些事件由业务自持，哪些交给 UI 组件库

判断标准只有一条：**这份状态会不会被"组件之外的页面"消费**。会被消费的，业务必须自己拿着；只在组件内消化的，别抢，抢了就是两份状态。

| 事件 | 归属 |
|---|---|
| 未读总数增量、好友申请未读、音效回调 | 业务自持：这些数据的消费端在组件之外 |
| 凭证过期、被踢下线 | 业务自持：影响整个账号态，组件库无权处理 |
| 会话列表渲染与排序、聊天页消息状态与已读回执 | UI 组件库：只有组件知道自己的 UI 结构与时序 |
| 群变更事件（成员、禁言、解散） | UI 组件库：群界面由组件承担 |

推论：**没注册群事件监听，不等于不需要感知群变更**。如果业务要在群解散、被移出群的时候清理数据或者埋点，那部分状态就得自己注册。红点和未读的业务模型见第 25 篇，好友申请的细节见第 27 篇。

## 七、业务门禁与跨端协作

结论：门禁状态（业务允不允许）和连接状态（技术连不连得上）得分开，UI 只能由门禁驱动。两者混在一起，肯定会出现"网络不好却被要求签到"。

### 7.1 产品案例：签到驱动登录

这是**产品选择**，其实不是行业默认做法。案例的规则是：进聊天入口的时候才检查今天的签到状态。已签到就触发 IM 登录；没签到，如果已经登录了就强制登出，再给会话列表盖一层遮罩。

```text
进入聊天 Tab → 节流刷新 → 查今日签到
   ├── 已签到 → 状态空闲/失败？是则请求凭证并登录，否则跳过
   └── 未签到 → 已在线则强制登出（会话与未读同步停止），否则只展示门禁遮罩
```

好处是门禁做在了"数据层可达性"上：绕过 UI 直接跳聊天页也没用，因为连接压根不存在。代价是签到之后必须重走一遍登录链路，业务活跃度和 IM 可用性被彻底绑在一起。

**可迁移原则**：门禁要拦在能力入口，不是拦在渲染层。不过"用签到换 IM 可用性"是产品决策，别当通用方案推荐，大多数产品更适合按能力分级（没登录也能看会话列表，只是不能发消息）。案例试过按**连接状态**盖"连接中"遮罩，最后去掉了：用户对连接状态的心智是"等一下会好"，不是"我没有权限"。

### 7.2 门禁分层

| 层级 | 拦截对象 | 判断依据 |
|---|---|---|
| 签到 | 使用聊天能力的资格 | 今日是否已签到 |
| 实名 | 创建新关系链（扫码、建群、加好友、加群） | 实名认证状态 |
| 设备权限 | 硬件能力（相机、相册） | 系统权限状态 |

实名这一层拦的是"建立新关系"的动作，**放行"与已有好友发起会话"**，因为后者不产生新的关系链。可迁移的原则是把"新增关系"和"使用关系"分开授权。

### 7.3 门禁状态和连接状态得分开

| 门禁状态 | 连接状态 | 正确的 UI | 常见错误 |
|---|---|---|---|
| 通过 | 在线 | 正常使用 | — |
| 通过 | 未在线 / 连接中 | 连接中提示 + 重试入口，列表照常可见 | 弹"请先签到"（用户无从下手） |
| 未通过 | 在线（正在被强制登出） | 门禁遮罩，阻断一切操作 | 让用户继续操作 |
| 未通过 | 未在线 | 门禁遮罩，不额外提示连接 | 同时弹门禁与网络两个弹窗 |

**任何提示文案都得能回答"用户现在该做什么"**。"请先签到"能回答；"连接中"得配上重试入口或者自动恢复才有意义。

### 7.4 跨端协作：宿主与 Flutter 的边界

边界先写清楚：原生宿主负责进程、权限、厂商通道和冷启动深链；Flutter 侧负责 IM 业务本身（身份、登录、监听器、未读），两套状态各归其主。

**跨端信号没有接收方**：宿主在会话失效的时候通知"回登录页"，但 Flutter 侧从来没注册过这个方法的处理器，未知方法被静默丢掉了。两端对失效的判定码也不一致（宿主 1001、Flutter 402）。对策：跨端契约要有单一的权威定义，未知方法打日志告警。

**跨端通道只绑定一次**：通道存在静态字段里，而且只在为空的时候绑定，多引擎或者引擎重建之后，事件就发往已销毁的引擎了。对策：绑定跟着引擎生命周期走，重建就重绑。

**冷启动暂存数据不清空**：通知数据存在一个从不清理的结构里，Flutter 侧能重复读到旧数据，于是重复跳到上次的落地页。对策：读取即消费，并且带唯一 ID 去重。

**宿主权限回调需要手工转发**：漏转发一次，聊天页里发图、拍照的权限申请就一直挂起。对策：统一通道 + requestId + 超时兜底。

这四条说的是同一件事：**跨端调用缺少所有权与契约的生命周期**。组合起来，就是"某些设备偶尔没反应"这种最难查的问题。

## 八、常见错误与修正表

| 问题 | 业务后果 | 对策 |
|---|---|---|
| 初始化失败仍置位"已初始化" | 登录在未初始化状态下运行，报错指向别处 | 只在明确成功后置位，失败保持可重试 |
| 登录失败后递归重试，入口又有"登录中"守卫 | 重试一次都不发生，状态永久卡住 | 改为有上限循环，每条路径写终态 |
| 凭证进日志 | 凭证随日志进入上报、厂商日志、客服工单 | 只记 userID、错误码、次数、凭证长度 |
| 移除监听不传参数、不保存实例 | 组件库监听被清空致界面静默失效；重登后未读翻倍、音效重复 | 按实例移除，注册与移除配对收口 |
| 用外部整数做枚举数组下标 | 一条脏数据打断整个回调 | 比较枚举 index，未知值走降级分支 |
| 异步清理函数写成同步签名 | 登出与状态清理时序竞争，"已退出但还在收消息" | 清理链路返回可等待结果，串行执行 |
| 页面订阅未在销毁时释放 | 脏更新与内存泄漏，反复进出后卡顿 | 订阅持有为字段，销毁时统一释放 |
| 缓存键只含凭证不含身份 | 换账号读到上一账号凭证，登录被拒或会话错乱 | 缓存键按身份隔离，切号时清缓存 |
| 被踢只提示、只清 IM 状态 | 半退出状态：业务登录态仍有效 | 当作账号级事件广播全局登出，不自动重登 |
| 业务推送被当成 IM 离线通道 | App 在后台或被杀后收不到 IM 消息 | 单独接 IM 离线推送，复用厂商通道 |
| 跨端信号没有接收方 | 失效联动链路静默失效，用户不被引导回登录页 | 跨端方法成对注册，未知方法记日志 |

## 九、验收清单

| 场景 | 验收标准 |
|---|---|
| 首次初始化失败 | 不置位"已初始化"，下次进入能重新初始化并登录 |
| 登录成功 | 状态依次为 空闲 → 登录中 → 在线，监听器恰好一组 |
| 连续三次网络失败 | 按固定间隔重试三次后进入"失败"终态，日志可见三次尝试 |
| 弱网抖动 | 状态不停在"登录中"，要么在线，要么失败且可再次触发 |
| 凭证过期 | 自动清缓存、重拉凭证并重登成功；日志无凭证原文 |
| 签发接口临时不可用 | 缓存可用时降级登录成功；无缓存时进入失败终态，不无限重试 |
| 换账号登录 | 不读到上一账号凭证，未读、音效、状态归属新账号 |
| 登出再登录 | 一条消息只响一次音效，未读只加一次 |
| 登出之后 | 会话列表与聊天功能仍正常（组件库监听器未被清空） |
| 另一设备登录同一账号 | 阻断式提示；确认后业务态、本地数据、IM 状态全部清理并回登录页 |
| 未签到进入聊天 | 遮罩只由门禁驱动，已在线时强制登出，不弹连接类提示 |
| 已签到但连接未就绪 | 展示连接中提示与重试入口，不出现签到类文案 |
| 退到后台或进程被杀 | 能收到 IM 消息通知；未接离线推送必须记为缺口而非"未测" |
| 跨端失效信号触发 | 接收方存在且有处理器，用户被引导回登录页；未知方法有日志告警 |

## 十、面试问答

### Q1：线上反馈"登录一直卡在连接中"，日志里只有一条开始登录的记录，怎么定位？

先看状态机里有没有"停在中间态"的路径：日志只有一次尝试、状态不变、用户怎么操作都自愈不了，这三点同时出现，基本就能断定重试没执行。重试是从入口递归进去的，入口又有"已是登录中则返回"的守卫，失败分支又没复位状态。追问：为什么难发现？因为它伪装成了网络慢。修复是把重试改成同一个函数里的有上限循环，再加一条断言："登录调用返回后状态必须不是 loggingIn"。

### Q2：登出再登录后，音效播两遍、未读数翻倍，原因是什么？

监听器叠加了：登出的时候旧实例没被真正移除，重登又注册一批，N 个实例就有 N 次副作用。追问：为什么"移除"会失败？因为移除接口的参数可空，为空时语义是清空该类全部监听器。要么把组件库的监听清掉了，要么因为没保存实例，没能精确移除自己那份。再追问：为什么清掉组件库的更可怕？因为它不报错，表现只是"列表偶发不刷新"，重启就恢复。

### Q3：冷启动后未读数显示 0，划掉一条消息才变成正确值，是哪一层的问题？

这是"把请求成功当成了值为 0"：首次查询成功之后直接写 0，没写返回值，历史未读就被清零了，得等下一次未读变化事件才修正。追问：为什么要"首次查询 + 增量回调"两条数据源？因为增量回调只在登录后生效，冷启动之前的未读变化不会补发。再追问边界：这篇只谈这两条数据源由谁持有，未读数的业务模型和展示属于第 25 篇。

### Q4：用户反馈"被踢下线了，但还是能继续用 App"，问题出在哪？

只清了 IM 侧的状态，没联动业务登录态：IM 断开了，业务 token 还有效，用户点别的页面照常工作，只有 IM 功能是哑的。追问：正确做法是什么？把被踢当成账号级安全事件广播给业务登出链路，业务登录态、本地缓存、IM 状态和监听器一起清理，唯一出口是登录页。再追问：为什么不能自动重新登录？因为会跟另一端互踢成循环，这个决定权得交给用户。

### Q5：宿主侧明明已经通知"回登录页"，用户却没有被引导，怎么排查？

先确认接收方在不在：跨端调用最常见的失效方式，是发送方正常发出了，接收方却从来没注册处理器，未知方法被静默丢掉，整条链路在没有任何报错的情况下变成死路。追问：为什么两端会不一致？因为对"会话失效"各写了一套码（宿主 1001、Flutter 402），改一处就整体失效；对策是契约有单一权威定义，未知方法必须告警。再追问一层：通道只绑定一次、冷启动暂存数据不清空、权限回调漏转发，都是同一类问题，都指向跨端调用缺少所有权与契约的生命周期。
