# IM 接入与消息收发

> 结论：IM 接入的难点不在"把消息发出去"，而在接入分层、入口收敛、未读数的唯一数据源、离线是否真的可达。本篇覆盖从会话入口到消息到达的完整链路，**假设读者已经取得可用身份（IM userID 与凭证）并处于可发送状态**；身份映射、凭证生命周期、登录状态机、重试、互踢与监听器注册治理见第 26 篇，好友与群管理见第 27 篇，自定义消息与红包见第 28 篇。核验版本：腾讯云 Chat Flutter SDK 8.6.x / TUIKit 4.0.x，信息截至 2026-08；SDK 行为、错误码与套餐能力以当前官方文档为准。

---

## 一、IM 解决什么问题，边界在哪里

IM 要交付的是"消息在正确的时间到达正确的人，各端看到同一份状态"，而不是"能发消息"。这条链路上至少有六件事：连接保活与重连、断连期间的补拉、消息顺序与去重、离线存储与历史漫游、未读与已读的状态同步、多端在线与互踢。任何一项自建，成本都不止于写代码——弱网下的保活策略、网络切换、群消息扩散是最难测对的部分，所以社交核心链路应当使用成熟的 IM 服务，把协议栈交出去。

但有三件事必须自己认领：**IM 是通道不是账本**，订单、金额、领取记录这类业务真值放业务服务端，消息只承载可被纠正的投影（第 28 篇）；**谁在登录、凭证何时过期**是另一条与消息链路正交的生命线（第 26 篇）；**关系链与群权限**是业务治理问题，不是消息问题（第 27 篇）。

术语统一：业务用户 ID（业务系统内标识）、IM userID（IM 侧身份）、凭证（服务端签发的登录票据）、会话（消息容器）、业务服务端（签发凭证、提供业务真值）、IM 服务（连接与消息的平台能力）。

## 二、接入方案：纯 SDK、UI 组件库与业务适配层

接入分三层：SDK 打底，UI 组件库吃掉界面与协议细节，业务适配层（下称消息网关）只守身份、门禁与自定义消息。

### 依赖与版本选择

不带界面的 IM SDK 负责连接、消息、会话与关系链；官方 UI 组件库提供会话列表、聊天页等成品界面。

```yaml
dependencies:
  tencent_cloud_chat_sdk: ^8.6.7019+5
  tencent_cloud_chat_uikit: ^4.0.8
```

选择原则：SDK 跟随官方升级；组件库只有确实要改内部行为时才 fork，且必须锁版本、维护补丁清单。接入时三件事容易忽略：**懒初始化**，把初始化放在首次登录之前而不是冷启动，既省启动耗时，也不让未登录用户长期占着连接；**权限注入**，组件库内部申请的相机、相册、麦克风应委托给应用统一的权限封装，否则同一个 App 会出现两套权限弹窗；**错误统一出口**，组件库的错误回调集中过滤与翻译，页面不各自弹窗。另外，幂等标志只应代表"成功过"，而不是"调用过"。

**初始化失败仍被标记为已初始化**
- 现象：初始化失败后，后续登录跳过初始化直接进入登录流程，报错指向登录失败或超时，真实原因是 SDK 未就绪。
- 后果：用户反复重试都连不上，且复现不稳定（下次冷启动可能又走一遍未初始化路径），定位成本极高。
- 成因：幂等标志的置位写在异常捕获之后，且不检查初始化返回值，"调用过"被当成"成功过"。
- 对策：只在初始化明确成功后置位，失败时保持未初始化以便下次重试，主题设置与权限注入等副作用放进成功分支。

### UI fork 的收益与升级成本

收益很实在：会话列表的消息摘要遇到业务自定义消息时能显示业务文案，而不是统一的"[自定义]"；聊天页更多面板里能插入业务入口；个别内部交互可以贴合业务习惯。成本同样清楚：每次升级都要重新对齐上游改动，补丁越多冲突面越大；上游一次重构就可能让补丁静默失效——编译通过、行为不再生效；没有补丁清单时回归范围不可控。

对策是分层：**能用扩展点就不改内部**。组件库通常已暴露自定义消息渲染、面板回调、消息生命周期钩子，够用就不 fork；确实要改的收敛成"补丁清单 + 每处用途 + 验证方式"，升级后逐项验证。

### 页面、消息网关、SDK 三层边界

```text
页面层（会话列表 / 聊天页 / Tab 容器）：读业务状态、调网关方法
   │
消息网关：初始化、登录前置、监听器、未读数、音效、错误出口
   │
SDK 与 UI 组件库：连接、消息、会话、关系链 + 成品界面
业务服务端：签发凭证、门禁状态、业务真值
```

页面层不持有 SDK 实例、不解析错误码；网关不承载页面逻辑、不直接驱动某个页面刷新；组件库不读取业务登录态。这样换 SDK 时页面层不动，页面重构时网关不动。

## 三、从会话入口进入聊天页

会话列表复用它，聊天页配置化，路由只传必要参数。

### 会话列表与路由最小参数

列表结构是顶部业务卡片（消息中心、公告）+ 搜索入口 + 组件库会话列表；空态自己渲染，避免"没有会话"看起来像加载失败。

进入聊天页的路由参数有取舍：传整个会话对象，还是只传会话 ID。案例约束是传整个会话对象——聊天页需要的会话 ID、类型、免打扰状态直接取到，省一次查询，也没有"查询未返回时页面已渲染"的竞态；代价是对象会过期，标题、免打扰、最后一条消息在进入后仍可能变化。可迁移原则是：**会话 ID 必须传，展示性字段可以带但不能当权威**，聊天页以"会话更新事件 + 网关状态"为最终真值，路由参数只用于首屏。

会话 ID 的生成规则要与 SDK 一致：案例项目按 `c2c_`、`group_` 前缀拼接对端标识或群标识，接收新消息时同样按此规则反推会话 ID，才能查出该会话的免打扰设置。不要在业务里另造一套。

导航一致性单独处理：从用户详情页点"发送消息"进入聊天页前，先清掉中间页面栈，只保留 Tab 容器与会话列表，再用替换方式打开聊天页，保证从聊天页返回永远落在会话列表。

案例约束：聊天入口还受业务门禁控制（例如要求当天签到才可用）。要守住一条——**门禁状态与连接状态是两件事**，不要用连接状态做业务遮罩，也不要让门禁失败被当成连接故障（第 26 篇）。

### 聊天能力开关与产品约束

| 能力项 | 取值 | 约束来源 |
|---|---|---|
| 语音消息 | 开 | 需要语音沟通 |
| 表情面板 / 更多面板 | 开 | 表情与业务扩展入口 |
| 群主与管理员撤回他人消息 | 开 | 群治理需要 |
| 已读回执 | 仅单聊开启 | 按产品需要与套餐能力决定 |
| C2C 编辑状态 / 回复时 @ / Markdown 渲染 | 关 | 场景不需要、避免未知渲染 |
| 群聊顶部安全提示条 | 注入 | 群防诈骗提示 |
| 自定义消息渲染 | 业务接管 | 卡片类消息（第 28 篇） |

两条约束写进文档：**开关只控制入口可见性，服务端权限才是边界**；**已读回执按产品与套餐能力开通**，不要预设某类会话"没有意义"。

## 四、普通消息收发与自定义扩展点

普通消息完全不碰协议；自定义消息只做"创建 + 投递"，业务状态放业务服务端。

### 普通消息交给组件库

文本、图片、语音、表情的输入组装、发送、失败重试与气泡渲染都由组件库负责。业务只需三个介入点：**发送成功钩子**（用于发送音效，比业务自己监听发送结果更可靠，不依赖回调时序）、**自定义消息渲染**（只有业务消息走业务分支）、**更多面板与菜单入口**。不要为普通消息再包一层，多一层封装只会多一处与组件库行为不一致的地方。

### 自定义消息只讲创建、投递与失败边界

链路固定三步：定协议、创建、投递。协议最小字段是业务标识（区分消息种类，只新增不改语义）、协议版本（新增字段时递增，旧端忽略未知字段）、业务主键（与业务服务端一致，用于对账）和展示快照（备注、封面、状态，只作展示不作真值）。

```dart
import 'dart:convert';

/// 把业务卡片编码成自定义消息的数据体。
String encodeCardPayload({
  required String businessId,
  required int version,
  required String bizId,
  required String title,
}) => jsonEncode({
      'businessID': businessId,
      'version': version,
      'bizId': bizId,
      'title': title,
    });
```

```text
// 示意伪代码
created = createCustomMessage(data: encodeCardPayload(...))
if (created.code != 0 || created.data == null) {
    提示("发送失败，请稍后重试")
    return                  // 创建失败不投递，也不自动重试
}
sent = sendMessage(
    id: created.data.id,    // 参数是创建返回的消息 id
    receiver: 单聊的对端标识,
    groupID: 群会话的群标识,
)
if (sent.code != 0) return  // 进入失败态，由组件库重发入口重试
```

三个必须守住的边界：**错误码非 0 时数据为空，必须先判空再取消息 id**，不能强解包；**投递失败不无限自动重发**，否则业务动作会被重复触发，宁可让用户手动重发；**回执类消息用定向投递**，只发给指定成员而不在群里刷屏。

这里还要纠正一个常见误解：**不要用"先发送再删除"实现"只有本机可见"**。删除在本产品里是本地删除语义——清的只是自己这份副本，官方也明确说明它不支持多端同步；而消息在投递成功的那一刻对方就已经收到、可能已经展示。也就是说"先发送再删除"得到的是"对方可见、自己不可见"，与目标正好相反。真正只在本机可见的状态提示，应当用 SDK 的本地插入消息能力（只写本地、不投递），或干脆只在本机渲染一条提示。

### 错误码到用户话术

| 错误类别 | 话术 | 处理方式 |
|---|---|---|
| 凭证/签名类（6206、70013、70014、70016、70017） | 登录状态已失效，正在重新连接 | 不重试，重新获取凭证后重登（第 26 篇） |
| 网络与超时 | 网络不稳定，请稍后重试 | 交给组件库失败态与手动重发 |
| 被拉黑（20007） | 对方拒收消息 | 提示一次，不重试 |
| 无权限（20041） | 无权限操作 | 提示并刷新页面状态 |
| 群禁言类（20012、20049、20050、10017） | 按官方文案翻译 | 输入区直接拦截（第 27 篇） |
| 已知噪声（解散群等残留请求） | 不展示 | 在统一出口过滤 |
| 未知错误 | 操作失败，请稍后重试 | 记录错误码与场景，不把原始码给用户 |

原则两条：**未知错误必须兜底**，否则用户会看到"错误码 70001"这类无法理解的提示；**过滤名单要写来源注释**，否则后来者会把噪声过滤当成漏报。

## 五、未读数与 UI 状态一致性

未读数是"权威值 + 增量事件"两路合流的问题，不是一次查询。

### 首次查询 + 增量回调

```text
冷启动
  客户端 ──首次查询未读总数──> IM 服务 / 本地会话缓存
  客户端 <────── 未读总数 N ──┘
  客户端：把 N 写入响应式状态          ← 不是写 0
在线运行
  IM 服务 ──未读总数变化事件────> 客户端
  客户端：用事件值覆盖状态 → debounce 1 秒 → 刷新标题与角标
```

分工必须说清楚：**增量回调只在登录后的连接上生效**，冷启动期间产生的未读变化不会补发；**首次查询**拿到的是当前权威值，用于兜底。两条都保留，才能既不丢历史也不漏增量。

**首次未读查询成功后把状态硬写成 0**
- 现象：冷启动进入会话列表，标题与角标都是 0，直到下一条新消息到来才显示正确未读数。
- 后果：用户看不到历史未读，以为消息丢失，重装或换设备后尤其明显。
- 成因：把"请求成功"当成"值为 0"，而成功只说明拿到了权威值，权威值本身可能非 0。
- 对策：直接写入查询返回值并做空值兜底；失败时保留本地已知值，不用 0 掩盖失败。

### 总未读、好友申请、Tab 红点三层模型

| 层 | 数据源 | 展示 | 失效时的表现 |
|---|---|---|---|
| 总未读 | 首次查询 + 未读总数变化事件 | 会话列表标题"聊天(N)"，超过 999 显示 999+ | 冷启动为 0，或需新消息才修正 |
| 好友申请 | 好友申请列表返回的未读数（申请新增/删除事件触发重查）；它与"待处理申请数"不是同一个数，取舍见第 27 篇 | 通讯录入口与"新的朋友"红点 | 事件漏刷，红点不消失 |
| Tab 红点 | 前两层任一大于 0 | 只显示小红点，不显示数字 | 任一层算错，红点常亮 |

前两层到 Tab 红点是**或**不是**与**：`总未读 > 0 || 好友申请数 > 0`。写成与就会漏——只看聊天未读时，"有人申请加好友"这种最需要即时响应的信号不亮红点；反过来只看好友申请时，普通消息也会被忽略。案例约束是 Tab 只显示小红点、不显示数字；可迁移原则是数字角标要求精确聚合与多端一致，出错面大，点只需一个布尔判断，产品没有强需求时先上点。

**用服务端返回的整数直接做枚举数组下标**
- 现象：偶发回调异常，或好友申请红点不更新，堆栈指向与网络无关的位置。
- 后果：一条脏数据就能打断整个申请事件的处理，红点与实际申请不一致。
- 成因：信任外部整数与本地枚举一一对应，而本地枚举常带占位项，下标与业务值存在偏移。
- 对策：用枚举 index 做等值比较，未知取值走默认分支并记日志，解析层再做一次白名单校验。

### debounce 与页面订阅释放

未读数一秒内可能变化多次，UI 不必每次都刷，用 debounce 合并到 1 秒一次：

```dart
// 依赖 get 包（状态与 debounce）
class UnreadBadgeController extends GetxController {
  final unread = 0.obs;
  Worker? _worker;

  void bind(RxInt source) {
    _worker?.dispose();
    _worker = debounce(source, (int value) => unread.value = value,
        time: const Duration(seconds: 1));
  }

  @override
  void onClose() {
    _worker?.dispose();
    super.onClose();
  }
}
```

刷新频率要按**成本来源**定，不要统一成一个常量：未读角标的成本在渲染，用短 debounce；顶部业务数据的成本在网络请求，用 10 秒节流。

**页面级订阅没有跟随生命周期释放**
- 现象：页面已退出，状态变化仍在触发回调；反复进出同一会话，内存与回调次数逐步增长。
- 后果：脏更新叠加持续泄漏，只在重度用户身上复现，容易被归因为"设备问题"。
- 成因：订阅被创建为局部变量，页面关闭时没有释放点，每次进入页面又新建一份。
- 对策：订阅持有为控制器字段，在销毁回调统一释放，创建时先释放旧的再建新的。

**未读重复累加与音效重复播放，根源是监听器没有按实例移除**
- 现象：登出再登录后，一条新消息让未读数加两次、音效播两遍；更隐蔽的是组件库的会话列表在登出后不再刷新。
- 后果：角标翻倍让用户怀疑消息丢失；组件库界面静默失效时，排查方向容易误判成组件库自身的问题。
- 成因：移除监听不传参数的语义是"清空该类全部监听器"，会把组件库自己注册的一起清掉；业务侧又没有保存实例，重登后旧实例仍可能存活，新实例再注册一次，同一事件被回调多份。
- 对策：注册时保存实例、移除时按实例移除，把注册与移除配对收口在网关的生命周期方法里（第 26 篇）。

## 六、免打扰与消息音效

音效不是"收到就播"，而是"先判断该不该播，再判断能不能播"，并且要防并发、防标志不复位。

免打扰的数据源是会话对象的接收选项，取值为 2 表示该会话免打扰（以所用 SDK 的枚举定义为准）；它是**会话级设置**而不是全局静音，用户可以对某个群免打扰，同时希望其他会话照常提醒。

| 判断 | 数据来源 | 不满足时 |
|---|---|---|
| 会话是否免打扰 | 会话接收选项（用消息的会话 ID 匹配本地会话列表） | 不播 |
| 系统是否有其他音频在播 | 平台音频会话状态 | 不播，延迟 2 秒复位标志 |
| 是否已有播放任务 | 锁 + 布尔标志双检 | 直接返回 |

四个细节决定这套逻辑是否可靠：会话不在本地列表时按不播处理（保守策略，代价是刚到的新会话第一条消息可能没有提示音，取舍要让产品明确接受）；播放 2 秒后停止并释放播放器实例，不要长期持有一个播放器给多路消息复用；异常路径必须在 finally 里复位播放标志，否则一次异常就永久静默；发送音效触发于消息发送成功钩子，因此不查免打扰。

一个必须澄清的误解：**免打扰只影响提示音**。它实际作用在三个地方，外加一个不受影响的地方：

| 影响面 | 免打扰的实际行为 |
|---|---|
| 本机提示音 | 不播（业务按接收选项自行判断） |
| SDK 的总未读数 | **会被减去**：官方明确"未读总数会减去设置为免打扰的会话的未读数"，含"不接收消息"与"接收但不通知"两种接收选项 |
| 离线推送 | 接收选项为"在线接收、离线不通知"时，离线不推送 |
| 该会话自身的未读数 | 照常累加，不受免打扰影响 |

所以"SDK 的总未读"和"把会话列表的未读数相加"是两个不同的数。角标取哪一个要在需求阶段定死：要求包含免打扰会话就自己求和（或用按过滤条件取未读的接口），不要混用两个来源，也不要拿其中一个去校验另一个。

## 七、离线触达与混合栈职责

在线消息与离线通知是两条链路，任何一条没接，用户感受都是"有时收不到"。

```text
在线（前台、长连接存活）
  对端发送 ──> IM 服务 ──长连接推送──> 客户端 ──> 渲染消息 + 提示音
离线（退到后台 / 进程被杀）
  对端发送 ──> IM 服务 ──离线推送（厂商通道）──> 系统通知栏 ──点击──> 冷启动 ──> 深链到会话
```

| 角色 | 负责 | 不负责 |
|---|---|---|
| 原生宿主 | 进程与生命周期、通知权限声明、厂商通道依赖与配置、冷启动暂存通知参数并交给 Flutter、权限回调转发 | 消息与会话逻辑 |
| Flutter 模块 | IM 初始化与登录、会话与消息、业务推送解析、角标清零、深链跳转 | 厂商通道配置 |
| IM 服务 | 连接与投递、离线消息存储与漫游（时长按套餐）、触发离线推送 | 业务真值 |

**业务推送已接，IM 离线推送未接**
- 现象：App 在前台一切正常，退到后台或进程被杀后不再收到任何 IM 消息通知，重新打开 App 才一次性刷出新消息。
- 后果：用户以为消息没发出去，错过沟通时机；产品承诺的"实时"只在 App 打开时成立。
- 成因：业务推送通道已经打通，于是被当成 IM 的离线触达通道，而 IM 消息的离线推送要在 IM 服务商侧单独配置并复用同一批厂商通道资源，两者互不替代。
- 对策：把"在线可达"与"离线可达"写成两个独立验收项；离线推送与厂商通道配置一起在原生宿主侧落地（包名、签名、证书都属于宿主职责）；通知点击后的会话深链要有唯一入口。

混合栈还有三条通用教训：**跨端信号没有接收方**会让链路静默失效，宿主发了"凭证失效"通知而 Flutter 侧未注册处理方法，消息被直接丢弃，两端对失效码的判定还不一致，对策是方法与接收方成对注册并留自检日志；**冷启动暂存参数不清空**会让用户每次启动都被跳到上一次的通知落地页，对策是读取即消费；**权限回调未转发**会让聊天页的拍照、发图权限申请停在等待状态，对策是把它纳入跨端契约与验收清单。

离线消息的保存与历史漫游时长由套餐与官方文档决定，产品承诺"消息保留多久"之前先确认套餐能力。

## 八、常见错误与修正表

| 问题 | 业务后果 | 对策 |
|---|---|---|
| 初始化失败仍置位"已初始化" | 后续登录在未初始化状态下运行，报错指向错误位置 | 只在明确成功后置位，失败保持可重试 |
| 首次未读查询成功后硬写 0 | 冷启动历史未读被清零，用户以为消息丢失 | 写入查询返回值，失败时保留本地已知值 |
| 移除监听不传参数、不保存实例 | 清掉组件库监听致界面静默失效；重登后未读重复累加、音效重复播放 | 按实例移除，注册与移除配对收口（第 26 篇） |
| 用外部整数做枚举数组下标 | 一条脏数据打断整个事件回调 | 比较枚举 index，未知值走默认分支 |
| 页面订阅未在销毁时释放 | 脏更新与内存泄漏，反复进出后卡顿 | 订阅持有为字段，销毁回调统一释放 |
| 音效播放标志异常路径未复位 | 一次异常后永久静默，用户收不到提醒 | finally 复位标志，播放后释放实例 |
| 以为免打扰只作用于提示音 | 总未读与列表求和口径不一致，角标对不上，离线推送该不该来也会判断错 | 明确免打扰影响提示音、SDK 总未读与离线推送，角标口径在需求阶段定死 |
| 自定义消息创建结果未判空 | 直接取消息 id 抛异常，消息发不出去 | 错误码非 0 或数据为空即终止投递 |
| 业务推送被当成 IM 离线通道 | App 在后台或被杀后收不到 IM 消息 | 单独接入 IM 离线推送并复用厂商通道 |
| 冷启动暂存参数不清空 | 重复跳到上一处通知落地页 | 读取即消费，区分冷启动与运行时参数 |
| 跨端信号没有接收方 | 凭证失效等联动链路静默失效 | 跨端方法成对注册并自检 |
| 异步清理函数写成同步签名 | 登出与状态清理存在时序竞争 | 清理链路返回可等待的结果 |

## 九、验收清单

| 场景 | 验收标准 |
|---|---|
| 冷启动进入会话列表 | 未读数与另一端口径一致且不为 0，标题与 Tab 角标同步 |
| 收发普通消息 | 文本、图片、语音正常，发送与接收音效各播一次 |
| 发送自定义卡片消息 | 卡片正常渲染；创建失败时不产生半成品消息 |
| 自定义消息投递失败 | 消息进入失败态，可手动重发，业务动作不被重复触发 |
| 群免打扰会话收到消息 | 无提示音；该会话自身未读数 +1，而 SDK 总未读不含它（要包含就自行求和）；离线按接收选项不推送 |
| 系统正在播放音乐时收到消息 | 不打断音乐，也不叠加播放 |
| 未读清零 | 读完全部会话后角标归零，与另一端口径一致 |
| 反复进出聊天页 | 会话实例不累积，无重复回调与重复音效 |
| 断网重连 | 监听器不叠加，重连后消息不重复计未读 |
| 退到后台或进程被杀 | 能收到 IM 消息通知，点击后进入正确会话（离线推送接入后） |
| 凭证过期 | 自动重新获取凭证并恢复连接，用户无感知（第 26 篇） |
| 业务门禁 | 门禁只控制入口可用性，连接状态不暴露为业务遮罩（第 26 篇） |

## 十、面试问答

### Q1：为什么用成熟 IM 服务加现成 UI 组件库，而不是自研？

自建要维护长连接保活、重连、补拉、顺序去重与群扩散，这些是最难写对也最难测对的部分；纯 SDK 加自研界面的问题不在界面，而在"隐含协议"——已读、撤回、输入状态、多端同步都要自己实现一遍。组件库的代价是外观与交互约束，以及 fork 后的升级成本，所以要确认它是否暴露了自定义消息渲染、面板回调、消息生命周期这些扩展点，再决定要不要 fork。追问：fork 之后怎么控升级成本？答：把改动收敛成补丁清单，逐处写明用途与验证方式，能用扩展点就绝不改内部。

### Q2：未读数为什么必须"首次查询 + 增量回调"两条数据源？

增量回调只在连接可用时推送，冷启动期间发生的变化不会补发，只剩增量会出现"角标要等下一条消息才正确"；只剩首次查询则在线期间不更新。追问：查询成功但未读为 0，与查询失败，怎么区分？答：两者都不能按 0 处理，成功要写入返回值，失败要保留本地已知值并等待事件修正。

### Q3：免打扰会影响哪些东西？为什么角标口径必须在需求阶段定死？

三处：本机提示音（业务按接收选项判断）；SDK 的总未读数（官方明确会减去免打扰与"不接收消息"会话的未读，而该会话自身的未读数照常累加）；离线推送（接收选项为"在线接收、离线不通知"时离线不推）。追问：那"总未读"和"把列表未读相加"是同一个数吗？答：不是，前者排除了免打扰会话。再追问：产品要求总未读包含免打扰会话怎么办？自己遍历会话累加，或改用按过滤条件取未读的接口，绝不能混用两个来源做展示与校验。

### Q4：在线消息与离线通知为什么不能共用一条链路？

在线依赖长连接存活，离线依赖厂商通道与 IM 服务商侧的离线推送配置，二者的失败原因与排查手段完全不同。只接业务推送的表现是前台一切正常、退后台或被杀后完全静默。追问：那离线推送该谁做？答：原生宿主负责进程、权限、厂商通道与通知权限声明，Flutter 侧负责 IM 登录与会话消息，IM 服务商侧要单独开启离线推送并复用同一批厂商通道。

### Q5：自定义消息里能不能放业务真值，比如领取记录？

不能。消息是通道不是账本：它可被客户端修改、可被重放、顺序不保证。把真值放进消息，并发时会互相覆盖，"是否已领取"这类判断还会因为用字符串匹配而误判。正确做法是真值放业务服务端并加唯一约束，消息只承载带版本的投影快照，详情页或重连时用服务端接口纠正（第 28 篇）。追问：那消息发送失败怎么办？答：业务结果以服务端记录为准，消息可重发，但重发不能重复产生业务结果，靠业务幂等键保证。
