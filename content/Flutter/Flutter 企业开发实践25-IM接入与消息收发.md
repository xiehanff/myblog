# IM 接入与消息收发

> 先说结论：IM 接入真正麻烦的地方，不在"把消息发出去"。难的是接入怎么分层、入口怎么收敛、未读数认哪一份数据源、离线到底可不可达。这篇把完整链路捋一遍，从会话入口一直到消息到达。**这里假设你已经拿到可用身份（IM userID 与凭证），处于可发送状态**；身份映射、凭证生命周期、登录状态机、重试、互踢、监听器注册治理这些见第 26 篇，好友与群管理见第 27 篇，自定义消息与红包见第 28 篇。核验版本：腾讯云 Chat Flutter SDK 8.6.x / TUIKit 4.0.x，信息截至 2026-08；SDK 行为、错误码与套餐能力以当前官方文档为准。

---

## 一、IM 到底解决什么问题，边界在哪

IM 要交付的东西，是"消息在正确的时间到达正确的人，各端看到同一份状态"。光能发消息不算交付。这条链路上至少有六件事：连接保活与重连、断连期间的补拉、消息顺序与去重、离线存储与历史漫游、未读与已读的状态同步、多端在线与互踢。这六件里任何一件自己写，成本都不止写代码这么点：弱网下的保活策略、网络切换、群消息扩散，是最难测对的部分。所以社交核心链路该用成熟的 IM 服务，把协议栈交出去。

但有三件事得自己认领：**IM 是通道不是账本**，订单、金额、领取记录这类业务真值放业务服务端，消息只承载可被纠正的投影（第 28 篇）；**谁在登录、凭证什么时候过期**，是另一条跟消息链路正交的生命线（第 26 篇）；**关系链与群权限**是业务治理的事，不是消息的事（第 27 篇）。

术语先统一一下：业务用户 ID（业务系统内标识）、IM userID（IM 侧身份）、凭证（服务端签发的登录票据）、会话（消息容器）、业务服务端（签发凭证、提供业务真值）、IM 服务（连接与消息的平台能力）。

## 二、接入方案：纯 SDK、UI 组件库，加一层业务适配

接入就分三层：SDK 打底，UI 组件库把界面和协议细节吃掉，业务适配层（下面叫消息网关）只守身份、门禁、自定义消息这三样。

### 依赖与版本选择

不带界面的 IM SDK 管连接、消息、会话和关系链；官方 UI 组件库给你会话列表、聊天页这些做好的界面。

```yaml
dependencies:
  tencent_cloud_chat_sdk: ^8.6.7019+5
  tencent_cloud_chat_uikit: ^4.0.8
```

选择原则是这样：SDK 跟着官方升级走；组件库只有确实要改内部行为才 fork，而且必须锁版本、维护一份补丁清单。接入的时候有三件事容易被忽略：**懒初始化**，把初始化放在首次登录之前，别放在冷启动，既省启动耗时，也不让未登录用户长期占着连接；**权限注入**，组件库内部申请的相机、相册、麦克风，要委托给应用统一的权限封装，不然同一个 App 里会出现两套权限弹窗；**错误统一出口**，组件库的错误回调集中过滤、集中翻译，页面不各自弹窗。另外，幂等标志只该代表"成功过"，不代表"调用过"。

**初始化失败仍被标记为已初始化**
- 现象：初始化失败以后，后面的登录会跳过初始化直接往下走，报错指向登录失败或者超时，真实原因其实是 SDK 还没就绪。
- 后果：用户反复重试都连不上，而且不好复现（下次冷启动可能又走一遍未初始化的路径），定位起来很贵。
- 成因：幂等标志是在异常捕获之后置位的，也没检查初始化返回值，把"调用过"当成了"成功过"。
- 对策：只在初始化明确成功之后置位；失败就保持未初始化，留给下次重试。主题设置、权限注入这些副作用放进成功分支。

### UI fork 的收益与升级成本

收益挺实在：会话列表的消息摘要碰到业务自定义消息，能显示业务自己的文案，不是统一的一串"[自定义]"；聊天页的更多面板里能插业务入口；个别内部交互也能贴着业务习惯来。成本也很清楚：每次升级都得重新对齐上游改动，补丁越多，冲突面越大；上游来一次重构，补丁可能就静默失效了，编译能过，行为不生效；没有补丁清单的话，回归范围根本控不住。

对策还是分层：**能用扩展点就不动内部**。组件库一般已经暴露了自定义消息渲染、面板回调、消息生命周期钩子，够用就别 fork；确实要改的，收敛成"补丁清单 + 每处用途 + 验证方式"，升级之后逐项验证。

### 页面、消息网关、SDK 三层边界

```text
页面层（会话列表 / 聊天页 / Tab 容器）：读业务状态、调网关方法
   │
消息网关：初始化、登录前置、监听器、未读数、音效、错误出口
   │
SDK 与 UI 组件库：连接、消息、会话、关系链 + 成品界面
业务服务端：签发凭证、门禁状态、业务真值
```

页面层不持有 SDK 实例，也不解析错误码；网关不承载页面逻辑，也不直接驱动某个页面刷新；组件库不读业务登录态。这么分下来，换 SDK 的时候页面层不动，页面重构的时候网关不动。

## 三、从会话入口进入聊天页

会话列表直接复用现成的，聊天页做成配置化的，路由只传必要参数。

### 会话列表与路由最小参数

列表的结构是上面一张业务卡片（消息中心、公告），中间一个搜索入口，下面挂组件库的会话列表；空态自己渲染，免得"没有会话"看起来像加载失败。

进入聊天页的路由参数有个取舍：传整个会话对象，还是只传一个会话 ID。案例里的约束是传整个会话对象：聊天页需要的会话 ID、类型、免打扰状态直接就取到了，省一次查询，也不会出现"查询还没返回、页面已经渲染"的竞态；代价是这个对象会过期，标题、免打扰、最后一条消息在进入之后仍然可能变。可迁移的原则是：**会话 ID 必须传，展示性字段可以带，但不能当权威**，聊天页以"会话更新事件 + 网关状态"为最终真值，路由参数只用于首屏。

会话 ID 的生成规则得跟 SDK 对齐：案例项目按 `c2c_`、`group_` 前缀去拼对端标识或群标识，收到新消息时也按同一套规则反推会话 ID，这样才能查出这个会话的免打扰设置。别在业务里另造一套。

导航一致性单独处理：从用户详情页点"发送消息"进聊天页之前，先把中间的页面栈清掉，只留 Tab 容器和会话列表，再用替换的方式打开聊天页。这样从聊天页返回，永远落在会话列表上。

案例里的约束：聊天入口还受业务门禁控制（比如要求当天签到才可用）。这里有一条要守住：**门禁状态和连接状态是两件事**，别拿连接状态去做业务遮罩，也别让门禁失败被当成连接故障（第 26 篇）。

### 聊天能力开关与产品约束

| 能力项 | 取值 | 约束来源 |
|---|---|---|
| 语音消息 | 开 | 需要语音沟通 |
| 表情面板 / 更多面板 | 开 | 表情与业务扩展入口 |
| 群主与管理员撤回他人消息 | 开 | 群治理需要 |
| 已读回执 | 仅单聊开启 | 按产品需要与套餐能力决定 |
| C2C 编辑状态 / 回复时 @ / Markdown 渲染 | 关 | 场景不需要、避免未知渲染 |
| 群聊顶部安全提示条 | 注入 | 群防诈骗提示 |
| 自定义消息渲染 | 业务接管 | 卡片类消息（第 28 篇） |

有两条约束要写进文档：**开关只管入口可不可见，服务端权限才是边界**；**已读回执按产品和套餐能力开通**，别预设某类会话"没有意义"。

## 四、普通消息收发与自定义扩展点

普通消息完全不用碰协议；自定义消息只做创建和投递，业务状态放业务服务端。

### 普通消息交给组件库

文本、图片、语音、表情的输入组装、发送、失败重试和气泡渲染，都交给组件库。业务这边只要三个介入点：**发送成功钩子**（用来放发送音效，比业务自己去监听发送结果更可靠，不用管回调时序）、**自定义消息渲染**（只有业务消息走业务分支）、**更多面板与菜单入口**。别为普通消息再包一层，多包一层就多一处跟组件库行为对不上的地方。

### 自定义消息只讲创建、投递和失败边界

链路就固定三步：定协议、创建、投递。协议里最小的字段是业务标识（区分消息种类，只新增不改语义）、协议版本（新增字段时递增，旧端忽略未知字段）、业务主键（与业务服务端一致，用于对账）和展示快照（备注、封面、状态，只作展示不作真值）。

```dart
import 'dart:convert';

/// 把业务卡片编码成自定义消息的数据体。
String encodeCardPayload({
  required String businessId,
  required int version,
  required String bizId,
  required String title,
}) => jsonEncode({
      'businessID': businessId,
      'version': version,
      'bizId': bizId,
      'title': title,
    });
```

```text
// 示意伪代码
created = createCustomMessage(data: encodeCardPayload(...))
if (created.code != 0 || created.data == null) {
    提示("发送失败，请稍后重试")
    return                  // 创建失败不投递，也不自动重试
}
sent = sendMessage(
    id: created.data.id,    // 参数是创建返回的消息 id
    receiver: 单聊的对端标识,
    groupID: 群会话的群标识,
)
if (sent.code != 0) return  // 进入失败态，由组件库重发入口重试
```

有三个边界必须守住：**错误码非 0 的时候数据是空的，得先判空再取消息 id**，不能强解包；**投递失败别无限自动重发**，否则业务动作会被重复触发，宁可让用户自己手动重发；**回执类消息用定向投递**，只发给指定成员，别在群里刷屏。

这里还有个常见误解得纠正：**别用"先发送再删除"去做"只有本机可见"**。删除在这个产品里是本地删除语义：清掉的只是自己那份副本，官方也明确说了它不支持多端同步；而消息在投递成功那一刻，对方就已经收到，可能也已经展示了。"先发送再删除"得到的是"对方可见、自己不可见"，跟目标正好相反。真要只在本机可见的状态提示，用 SDK 的本地插入消息能力（只写本地、不投递），或者干脆只在本机渲染一条提示。

### 错误码到用户话术

| 错误类别 | 话术 | 处理方式 |
|---|---|---|
| 凭证/签名类（6206、70013、70014、70016、70017） | 登录状态已失效，正在重新连接 | 不重试，重新获取凭证后重登（第 26 篇） |
| 网络与超时 | 网络不稳定，请稍后重试 | 交给组件库失败态与手动重发 |
| 被拉黑（20007） | 对方拒收消息 | 提示一次，不重试 |
| 无权限（20041） | 无权限操作 | 提示并刷新页面状态 |
| 群禁言类（20012、20049、20050、10017） | 按官方文案翻译 | 输入区直接拦截（第 27 篇） |
| 已知噪声（解散群等残留请求） | 不展示 | 在统一出口过滤 |
| 未知错误 | 操作失败，请稍后重试 | 记录错误码与场景，不把原始码给用户 |

两条原则：**未知错误必须兜底**，不然用户会看到"错误码 70001"这种看不懂的提示；**过滤名单要写上来源注释**，不然后来的人会把噪声过滤当成漏报。

## 五、未读数与 UI 状态一致性

未读数是个"权威值 + 增量事件"两路合流的事，不是查一次就能拿到。

### 首次查询 + 增量回调

```text
冷启动
  客户端 ──首次查询未读总数──> IM 服务 / 本地会话缓存
  客户端 <────── 未读总数 N ──┘
  客户端：把 N 写入响应式状态          ← 不是写 0
在线运行
  IM 服务 ──未读总数变化事件────> 客户端
  客户端：用事件值覆盖状态 → debounce 1 秒 → 刷新标题与角标
```

分工要说清楚：**增量回调只在登录之后的连接上生效**，冷启动期间产生的未读变化不会补发；**首次查询**拿到的是当前权威值，用来兜底。两条都留着，才能既不丢历史，也不漏增量。

**首次未读查询成功后把状态硬写成 0**
- 现象：冷启动进会话列表，标题和角标都是 0，要等下一条新消息来了才显示正确的未读数。
- 后果：用户看不到历史未读，以为消息丢了，重装或者换设备之后尤其明显。
- 成因：把"请求成功"当成了"值为 0"。成功只说明拿到了权威值，权威值本身可能不是 0。
- 对策：把查询返回值直接写进去，再做一层空值兜底；失败时保留本地已知值，别拿 0 掩盖失败。

### 总未读、好友申请、Tab 红点三层模型

| 层 | 数据源 | 展示 | 失效时的表现 |
|---|---|---|---|
| 总未读 | 首次查询 + 未读总数变化事件 | 会话列表标题"聊天(N)"，超过 999 显示 999+ | 冷启动为 0，或需新消息才修正 |
| 好友申请 | 好友申请列表返回的未读数（申请新增/删除事件触发重查）；它与"待处理申请数"不是同一个数，取舍见第 27 篇 | 通讯录入口与"新的朋友"红点 | 事件漏刷，红点不消失 |
| Tab 红点 | 前两层任一大于 0 | 只显示小红点，不显示数字 | 任一层算错，红点常亮 |

前两层到 Tab 红点，取的是**或**，不是**与**：`总未读 > 0 || 好友申请数 > 0`。写成与就会漏。只看聊天未读的时候，"有人申请加好友"这种最需要即时响应的信号不亮红点；反过来只看好友申请的时候，普通消息也会被忽略。案例约束是 Tab 只显示小红点、不显示数字；可迁移原则是数字角标要求精确聚合和多端一致，出错面大，点只要一个布尔判断就够，产品没有强需求时先上点。

**用服务端返回的整数直接做枚举数组下标**
- 现象：偶尔回调异常，或者好友申请的红点不更新，堆栈指向的位置跟网络没关系。
- 后果：一条脏数据就能打断整个申请事件的处理，红点跟实际申请对不上。
- 成因：默认外部整数跟本地枚举是一一对应的。本地枚举往往带占位项，下标跟业务值之间有偏移。
- 对策：用枚举 index 做等值比较，未知取值走默认分支并记日志，解析层再补一次白名单校验。

### debounce 与页面订阅释放

未读数一秒内可能变好几次，UI 用不着每次都刷，用 debounce 合并成 1 秒一次：

```dart
// 依赖 get 包（状态与 debounce）
class UnreadBadgeController extends GetxController {
  final unread = 0.obs;
  Worker? _worker;

  void bind(RxInt source) {
    _worker?.dispose();
    _worker = debounce(source, (int value) => unread.value = value,
        time: const Duration(seconds: 1));
  }

  @override
  void onClose() {
    _worker?.dispose();
    super.onClose();
  }
}
```

刷新频率要按**成本来源**定，别统一成一个常量：未读角标的成本在渲染，用短 debounce；顶部业务数据的成本在网络请求，用 10 秒节流。

**页面级订阅没有跟随生命周期释放**
- 现象：页面已经退出了，状态变化还在触发回调；反复进出同一个会话，内存和回调次数一点点往上涨。
- 后果：脏更新叠加持续泄漏，只在重度用户身上冒出来，很容易被归到"设备问题"上。
- 成因：订阅是用局部变量创建的，页面关闭时没有释放点，每次进页面又重新建一份。
- 对策：订阅用控制器字段持有，在销毁回调里统一释放，创建的时候先释放旧的再建新的。

**未读重复累加与音效重复播放，根源是监听器没有按实例移除**
- 现象：登出再登录之后，一条新消息会让未读数加两次、音效播两遍；更隐蔽的是组件库的会话列表在登出后不再刷新。
- 后果：角标翻倍，用户会怀疑消息丢了；组件库界面静默失效的时候，排查方向很容易误判成组件库自己的问题。
- 成因：移除监听不传参数，语义是"清空这一类全部监听器"，会把组件库自己注册的那些一起清掉；业务侧又没保存实例，重登之后旧实例还可能活着，新实例再注册一次，同一个事件就被回调好几份。
- 对策：注册时保存实例，移除时按实例移除，把注册和移除配对收口到网关的生命周期方法里（第 26 篇）。

## 六、免打扰与消息音效

音效这块，先判断该不该播，再判断能不能播，另外还得防并发、防标志没复位。

免打扰的数据源是会话对象的接收选项，取值 2 表示这个会话免打扰（具体以所用 SDK 的枚举定义为准）；它是**会话级设置**，不是全局静音。用户可以对着某个群免打扰，同时希望其他会话照常提醒。

| 判断 | 数据来源 | 不满足时 |
|---|---|---|
| 会话是否免打扰 | 会话接收选项（用消息的会话 ID 匹配本地会话列表） | 不播 |
| 系统是否有其他音频在播 | 平台音频会话状态 | 不播，延迟 2 秒复位标志 |
| 是否已有播放任务 | 锁 + 布尔标志双检 | 直接返回 |

这套逻辑靠不靠得住，看四个细节：会话不在本地列表时按不播处理（保守策略，代价是刚到的新会话第一条消息可能没提示音，这个取舍要让产品明确接受）；播 2 秒后停下来并释放播放器实例，别长期撺着一个播放器给多路消息复用；异常路径一定要在 finally 里复位播放标志，不然一次异常就永久静默了；发送音效是在消息发送成功钩子上触发的，所以不查免打扰。

还有个误解得澄清：**免打扰只影响提示音**。它实际作用在三个地方，另外有一个地方不受影响：

| 影响面 | 免打扰的实际行为 |
|---|---|
| 本机提示音 | 不播（业务按接收选项自行判断） |
| SDK 的总未读数 | **会被减去**：官方明确"未读总数会减去设置为免打扰的会话的未读数"，含"不接收消息"与"接收但不通知"两种接收选项 |
| 离线推送 | 接收选项为"在线接收、离线不通知"时，离线不推送 |
| 该会话自身的未读数 | 照常累加，不受免打扰影响 |

所以"SDK 的总未读"和"把会话列表的未读数相加"，说白了是两个不同的数。角标取哪一个，要在需求阶段定死：要求包含免打扰会话，就自己求和（或者用按过滤条件取未读的接口），别混用两个来源，也别拿其中一个去校验另一个。

## 七、离线触达与混合栈职责

在线消息和离线通知是两条链路，哪一条没接上，用户的感受都是"有时收不到"。

```text
在线（前台、长连接存活）
  对端发送 ──> IM 服务 ──长连接推送──> 客户端 ──> 渲染消息 + 提示音
离线（退到后台 / 进程被杀）
  对端发送 ──> IM 服务 ──离线推送（厂商通道）──> 系统通知栏 ──点击──> 冷启动 ──> 深链到会话
```

| 角色 | 负责 | 不负责 |
|---|---|---|
| 原生宿主 | 进程与生命周期、通知权限声明、厂商通道依赖与配置、冷启动暂存通知参数并交给 Flutter、权限回调转发 | 消息与会话逻辑 |
| Flutter 模块 | IM 初始化与登录、会话与消息、业务推送解析、角标清零、深链跳转 | 厂商通道配置 |
| IM 服务 | 连接与投递、离线消息存储与漫游（时长按套餐）、触发离线推送 | 业务真值 |

**业务推送已接，IM 离线推送未接**
- 现象：App 在前台一切正常，退到后台或者进程被杀之后就再也收不到 IM 消息通知了，重新打开 App 才一次性刷出新消息。
- 后果：用户以为消息没发出去，错过了沟通时机；产品承诺的"实时"，只在 App 打开的时候成立。
- 成因：业务推送通道已经打通了，就被当成 IM 的离线触达通道。IM 消息的离线推送要在 IM 服务商侧单独配置，同时复用同一批厂商通道资源，两者谁也替代不了谁。
- 对策：把"在线可达"和"离线可达"拆成两个独立验收项；离线推送和厂商通道配置一起在原生宿主侧落地（包名、签名、证书都算宿主职责）；通知点击之后的会话深链要有唯一入口。

混合栈还有三条通用教训：**跨端信号没有接收方**会让链路静默失效，宿主发了"凭证失效"通知，Flutter 侧却没注册处理方法，消息直接被丢掉，两端对失效码的判定还不一致，对策是方法和接收方成对注册，并留自检日志；**冷启动暂存参数不清空**，用户每次启动都会被跳到上一次的通知落地页，对策是读取即消费；**权限回调没转发**，聊天页的拍照、发图权限申请会停在等待状态，对策是把它纳入跨端契约和验收清单。

离线消息的保存和历史漫游时长由套餐和官方文档决定，产品要承诺"消息保留多久"，先确认套餐能力。

## 八、常见错误与修正表

| 问题 | 业务后果 | 对策 |
|---|---|---|
| 初始化失败还置位"已初始化" | 后续登录在未初始化状态下跑，报错指向别处 | 只在明确成功之后置位，失败就保持可重试 |
| 首次未读查询成功后硬写 0 | 冷启动把历史未读清零，用户以为消息丢了 | 写入查询返回值，失败时保留本地已知值 |
| 移除监听不传参数、不保存实例 | 清掉组件库监听导致界面静默失效；重登后未读重复累加、音效重复播放 | 按实例移除，注册与移除配对收口（第 26 篇） |
| 用外部整数做枚举数组下标 | 一条脏数据打断整个事件回调 | 比较枚举 index，未知值走默认分支 |
| 页面订阅没在销毁时释放 | 脏更新加内存泄漏，反复进出之后卡顿 | 订阅用字段持有，销毁回调统一释放 |
| 音效播放标志在异常路径没复位 | 一次异常之后永久静默，用户收不到提醒 | finally 里复位标志，播放后释放实例 |
| 以为免打扰只作用于提示音 | 总未读与列表求和口径不一致，角标对不上，离线推送该不该来也会判断错 | 明确免打扰影响提示音、SDK 总未读与离线推送，角标口径在需求阶段定死 |
| 自定义消息创建结果没判空 | 直接取消息 id 抛异常，消息发不出去 | 错误码非 0 或数据为空就终止投递 |
| 业务推送被当成 IM 离线通道 | App 在后台或被杀之后收不到 IM 消息 | 单独接入 IM 离线推送，复用厂商通道 |
| 冷启动暂存参数不清空 | 重复跳到上一处通知落地页 | 读取即消费，区分冷启动与运行时参数 |
| 跨端信号没有接收方 | 凭证失效等联动链路静默失效 | 跨端方法成对注册并自检 |
| 异步清理函数写成同步签名 | 登出与状态清理之间存在时序竞争 | 清理链路返回可等待的结果 |

## 九、验收清单

| 场景 | 验收标准 |
|---|---|
| 冷启动进入会话列表 | 未读数与另一端口径一致且不为 0，标题与 Tab 角标同步 |
| 收发普通消息 | 文本、图片、语音正常，发送与接收音效各播一次 |
| 发送自定义卡片消息 | 卡片正常渲染；创建失败时不产生半成品消息 |
| 自定义消息投递失败 | 消息进入失败态，可手动重发，业务动作不被重复触发 |
| 群免打扰会话收到消息 | 无提示音；该会话自身未读数 +1，而 SDK 总未读不含它（要包含就自行求和）；离线按接收选项不推送 |
| 系统正在播放音乐时收到消息 | 不打断音乐，也不叠加播放 |
| 未读清零 | 读完全部会话后角标归零，与另一端口径一致 |
| 反复进出聊天页 | 会话实例不累积，无重复回调与重复音效 |
| 断网重连 | 监听器不叠加，重连后消息不重复计未读 |
| 退到后台或进程被杀 | 能收到 IM 消息通知，点击后进入正确会话（离线推送接入后） |
| 凭证过期 | 自动重新获取凭证并恢复连接，用户无感知（第 26 篇） |
| 业务门禁 | 门禁只控制入口可用性，连接状态不暴露为业务遮罩（第 26 篇） |

## 十、面试问答

### Q1：为什么选成熟 IM 服务加现成 UI 组件库，不自己写？

自建就得维护长连接保活、重连、补拉、顺序去重和群扩散，这些是最难写对、也最难测对的部分；纯 SDK 加自研界面，卡点不在界面。真正的成本在"隐含协议"上：已读、撤回、输入状态、多端同步，都得自己实现一遍。组件库的代价是外观和交互受约束，还有 fork 之后的升级成本，所以要确认它有没有暴露自定义消息渲染、面板回调、消息生命周期这些扩展点，再决定要不要 fork。追问：fork 之后怎么控升级成本？答：把改动收敛成补丁清单，逐处写明用途和验证方式，能用扩展点就绝不改内部。

### Q2：未读数为什么要有"首次查询 + 增量回调"两条数据源？

增量回调只在连接可用的时候推送，冷启动期间发生的变化不会补发，只留增量的话，会出现"角标要等下一条消息才正确"；只留首次查询，在线期间又不更新。追问：查询成功但未读为 0，和查询失败，怎么区分？答：这两种都不能按 0 处理。成功就把返回值写进去，失败就保留本地已知值，等事件来修正。

### Q3：免打扰会影响哪些东西？为什么角标口径得在需求阶段定死？

三处：本机提示音（业务按接收选项判断）；SDK 的总未读数（官方明确会减去免打扰和"不接收消息"会话的未读，而这个会话自身的未读数照常累加）；离线推送（接收选项是"在线接收、离线不通知"的时候，离线不推）。追问：那"总未读"和"把列表未读相加"是同一个数吗？答：不是，前者把免打扰会话排除掉了。再追问：产品要求总未读包含免打扰会话怎么办？自己遍历会话累加，或者改用按过滤条件取未读的接口，绝不能混用两个来源来做展示和校验。

### Q4：在线消息与离线通知为什么不能共用一条链路？

在线靠长连接活着，离线靠厂商通道和 IM 服务商侧的离线推送配置，两者的失败原因和排查手段完全不一样。只接业务推送的表现就是：前台一切正常，退后台或者被杀之后完全静默。追问：那离线推送该谁做？答：原生宿主管进程、权限、厂商通道和通知权限声明，Flutter 侧管 IM 登录和会话消息，IM 服务商侧要单独开启离线推送，并复用同一批厂商通道。

### Q5：自定义消息里能不能放业务真值，比如领取记录？

不能。消息是通道，不是账本：它可以被客户端改、可以被重放、顺序也不保证。把真值塞进消息，并发的时候会互相覆盖，"是不是已经领取了"这类判断还会因为用字符串匹配而判断错。正确做法是把真值放业务服务端并加唯一约束，消息只承载带版本的投影快照，详情页或者重连的时候用服务端接口纠正（第 28 篇）。追问：那消息发送失败怎么办？答：业务结果以服务端记录为准，消息可以重发，但重发不能重复产生业务结果，靠业务幂等键保证。
